# Exploration: Versioned Approval Invalidation

Generated: 2026-09-20

## Problem statement

The investigation began while designing schema-driven skippable workflow phases. That work exposed a more fundamental problem: approval invalidation is currently too aggressive and too tightly coupled to lifecycle transitions.

Today one generic `invalidated` event simultaneously:

- makes both spec approval and sign-off inactive;
- rolls the change back to `designing`;
- reopens artifact files according to `invalidationPolicy`;
- records the audit event.

This makes it difficult to determine the correct next workflow state. A backward transition or a localized artifact drift can globally invalidate the change even when the approved subject did not materially change. The user decided to solve invalidation semantics first and defer schema-driven workflow skipping to a later change.

## Confirmed scope

This change will:

1. Introduce explicit manifest format versioning.
2. Temporarily support both legacy and new manifests.
3. Materialize current approval state in dedicated manifest fields instead of deriving normal validity by scanning history.
4. Keep history append-only and preserve every approval and invalidation decision for audit.
5. Separate artifact-review scope from workflow consequences.
6. Give spec approval and sign-off distinct fingerprints.
7. Add an implementation-file fingerprint to sign-off.
8. Preserve approval records when they become stale rather than making them disappear.
9. Make approval gates constrain lifecycle rollback rather than treating every backward transition as a global invalidation.

Schema-driven skipping of `implementing` and `verifying` is explicitly out of scope and must be handled by a later change after these invalidation semantics are stable.

## Manifest versioning

The current root `schema.version` identifies the workflow/schema version and must not be overloaded for storage format versioning.

The agreed root field is:

```yaml
manifestVersion: 2
```

Compatibility rules:

- A missing `manifestVersion` means legacy manifest v1.
- `manifestVersion: 2` uses the new structure.
- Unknown/future versions must fail with a typed unsupported-version error; no best-effort parsing.
- New changes are written as v2.
- Reading a v1 manifest adapts it in memory.
- A normal read must not rewrite a manifest merely to upgrade it.
- The next real persisted mutation may atomically write the adapted active manifest as v2.
- Archived manifests must not be rewritten merely because they are inspected.

Suggested internal structure:

```typescript
type ChangeManifest = LegacyChangeManifestV1 | ChangeManifestV2
```

The loader should branch explicitly on `raw.manifestVersion ?? 1`.

## Invalidation configuration

The existing `invalidationPolicy` name is misleading because it controls only artifact/file reopening. The user preferred a nested structure with two independent dimensions:

```yaml
invalidation:
  artifacts: downstream
  workflow: preserve
```

`artifacts` retains the existing values and meanings:

- `none`: reopen no artifact files.
- `surgical`: reopen only directly selected files.
- `downstream`: reopen selected files plus schema-DAG descendants.
- `global`: reopen all artifact files.

Initial `workflow` values discussed:

- `preserve`: retain the current lifecycle state unless an invalidated gate imposes an earlier checkpoint.
- `redesign`: roll back to `designing`.

Legacy v1 `invalidationPolicy: downstream` must adapt to:

```yaml
invalidation:
  artifacts: downstream
  workflow: redesign
```

This preserves existing behavior during migration rather than silently applying a new default.

Gate constraints are core invariants, not another configurable policy value. The workflow policy proposes the desired lifecycle consequence; invalidated approval gates may constrain the effective state.

Examples discussed:

- With no affected gates and `workflow: preserve`, artifact drift keeps the current state but unresolved review must block relevant forward/archive operations.
- A stale spec approval forces the change back before the spec gate. Because drifted artifacts are incomplete, the effective working state is normally `designing`.
- A stale sign-off alone limits the change to `done`.
- Gate _configuration_ alone is not enough to force rollback. The deciding fact is whether an actual approval covering the changed subject became stale.

## Approval state in manifest v2

History remains append-only audit data. Current approval state becomes an explicit manifest projection and is the normal source of truth:

```yaml
approvals:
  spec:
    status: valid
    decision:
      at: 2026-09-20T10:00:00Z
      by: {}
      reason: Approved
    fingerprint: {}
  signoff:
    status: valid
    decision:
      at: 2026-09-20T12:00:00Z
      by: {}
      reason: Ready to ship
    fingerprint: {}
```

Initial explicit statuses:

- `valid`
- `stale`
- `revoked`

Absence represents an approval that was never granted. `inactive` was considered but should not be used because it mixes approval validity with lifecycle position.

When an approval becomes stale, retain its original decision and fingerprint and add stale metadata such as timestamp, actor, cause, and changed inputs. Re-approval replaces the current projection while prior decisions remain in history.

The legacy loader is the only place that should reconstruct approvals by scanning events. New v2 runtime behavior must not rely on the current `activeSpecApproval` / `activeSignoff` history scan as the normal validity model.

## Approval coverage

### Spec approval

Spec approval already records per-artifact hashes in its `spec-approved` history event. These are keyed as `artifactId:fileKey` after schema `preHashCleanup`.

For v2, materialize that data as the spec approval fingerprint. A map is preferred to only an aggregate digest because it can identify precisely which artifact invalidated approval.

Spec approval conceptually covers scope, specs, design artifacts, and task definitions. Changes to implementation alone must not invalidate it.

### Sign-off

Current sign-off records only the same artifact hashes as spec approval. It does not fingerprint code, implementation links, or verification evidence. This is both over-aggressive in lifecycle handling and under-specified in what sign-off actually covers.

The v2 sign-off fingerprint must include:

- artifact hashes;
- implementation file hashes derived from confirmed implementation links.

The first version deliberately does not resolve or fingerprint individual symbols.

## Implementation fingerprint v1

The user explicitly chose a conservative, simple file-level implementation fingerprint because changes are normally applied individually within one branch. A change to a linked file probably belongs to the change.

Algorithm:

1. Refresh implementation tracking.
2. Require the existing `impl.filesResolved` check to pass.
3. Require the existing `impl.linksInScope` check to pass.
4. Collect project-relative file paths from confirmed `Change.implementationLinks`.
5. Normalize and deduplicate paths; multiple spec links to the same file produce one entry.
6. Read each complete file and hash normalized content.
7. Persist the deterministically ordered map of path to hash.

Proposed shape:

```yaml
fingerprint:
  version: 1
  artifacts:
    proposal:proposal: sha256:...
  implementation:
    normalization: text-v1
    files:
      packages/core/src/domain/entities/change.ts: sha256:...
```

Rules:

- Symbol refinements on links are ignored for fingerprinting in v1; the full file is hashed.
- A file referenced by several links appears once.
- Key-set differences (added, removed, moved, or renamed linked files) make sign-off stale.
- Hash differences make sign-off stale.
- A missing linked file makes sign-off stale/fails fingerprint evaluation.
- A valid implementation-empty sign-off stores `files: {}`.
- `implementation: null` is reserved for legacy sign-offs that never had an implementation fingerprint.
- A changed `specId -> file` relationship with the same final file set is not detected by this v1 fingerprint. This was accepted as a first-version limitation; link-consistency checks remain responsible for link validity.

## Implementation content normalization

The user wants formatting-only changes not to invalidate sign-off, especially incidental formatter activity. A parser-aware or symbol-aware normalizer was rejected as too complex for the first version.

The agreed initial normalizer is conservative and purely textual:

```text
text-v1
```

It should at least:

- normalize CRLF/LF;
- remove a UTF-8 BOM;
- strip trailing spaces/tabs;
- normalize blank-line whitespace;
- normalize final newline handling.

It must not delete all whitespace: doing so could hide real changes inside strings or indentation-sensitive formats. Consequently, v1 may still require a new sign-off for some broad Prettier reformatting. This false positive is preferable to a false negative that preserves sign-off after a semantic change.

The normalization identifier/version must be stored with the fingerprint so future algorithms do not reinterpret old hashes.

## Current codebase observations

Relevant anchors observed during discovery:

- `packages/core/src/domain/entities/change.ts`
  - `Change.invalidate()` appends `invalidated`, rolls back to `designing`, and reopens artifacts according to policy.
  - `activeSpecApproval` scans history and clears on every `invalidated` event.
  - `activeSignoff` scans history and clears on `invalidated` or `signoff-invalidated`.
  - `invalidateSignoff()` is a narrower existing precedent that preserves spec approval and artifact state.
  - `updateSpecIds()` always calls `invalidate('spec-change', ...)`.
- `packages/core/src/application/use-cases/transition-change.ts`
  - Any later-state transition to `designing` calls `Change.invalidate('artifact-review-required', ...)` before any artifact is necessarily modified.
  - Skill-aligned hops from `done`, `signed-off`, or `archivable` to `implementing`/`verifying` call only `invalidateSignoff()`.
- `packages/core/src/application/use-cases/invalidate-change.ts`
  - Manual invalidation requires `force` when either approval is active.
  - Even policy `none` returns the change to `designing` and clears approvals.
- `packages/core/src/application/use-cases/validate-artifacts.ts`
  - Compares artifact content against approval/sign-off `artifactHashes` and emits one focused `artifact-drift` invalidation.
- `packages/core/src/infrastructure/fs/change-repository.ts`
  - Detects validated artifact drift during active change load and persists an automatic invalidation.
  - `changeToManifest()` currently writes no root manifest version or materialized approvals.
- `packages/core/src/infrastructure/fs/manifest.ts`
  - Current manifest schema includes `invalidationPolicy`, implementation tracking, artifacts, and history.
  - `RawSpecApprovedEvent` and `RawSignedOffEvent` both contain only `artifactHashes`.
- `packages/core/src/application/use-cases/archive-change.ts`
  - Archiving with allowed spec overlap automatically invalidates overlapping active changes.
- `packages/core/src/domain/checks/impl-files-resolved.ts`
  - Existing check passes only when no tracked implementation file remains `open`.
- `packages/core/src/domain/checks/impl-links-in-scope.ts`
  - Existing check enforces implementation-link scope unless explicitly skipped.

Current invalidation causes all sharing the global entity behavior:

- `spec-change`
- `artifact-drift`
- `artifact-review-required`
- `spec-overlap-conflict`

`signoff-invalidated` is the only current approval-specific invalidation event.

## Deferred workflow-skipping design

The original discussion concerned schema-driven optional workflow phases. Preserve this context for the later change:

- `ready`, `done`, and `archivable` should be mandatory semantic checkpoints.
- `implementing` and `verifying` are candidate optional activities.
- `done` should mean all schema-required delivery phases are satisfied or legitimately omitted, not necessarily that verification ran.
- Candidate forward routes included `ready -> verifying`, `ready -> done`, and `implementing -> done` when omitted phases permit them.
- Skip conditions should use registered workflow checks, not a second condition system.
- Proposed condition composition used `all` and `any`; no `not` was preferred for monotonic safety.
- Omitted `when` would mean unconditional skip.
- `workflow.taskCompletion` should determine whether implementation work remains; total task count being zero is not the criterion by itself.
- `GetStatus`, `TransitionChange`, CLI status/transition, and skills must share the same next-step resolver.
- Backward transitions should not be schema-configurable, but their effective destinations must account for absent/skipped phases and approval gates.
- This design was intentionally paused because reliable routing depends on correct approval validity and invalidation behavior.

## Rejected alternatives

- Implement workflow skips before fixing invalidations: rejected because next-step routing would be based on unreliable approval validity.
- Treat every backward transition as approval invalidation: rejected because state direction does not prove approved content changed.
- Keep one generic invalidation policy: rejected because artifact scope and lifecycle rollback are separate concerns.
- Use `gate-aware` as a configurable workflow policy: rejected because gate enforcement is a core invariant, not optional configuration.
- Remove or rewrite approval history: rejected; history must stay append-only.
- Continue deriving active approvals exclusively by scanning history: rejected for v2; explicit manifest projections are required.
- Retroactively invent an implementation fingerprint for legacy sign-offs: rejected because it would falsely claim the approver reviewed current code.
- Fingerprint individual implementation symbols in v1: rejected as excessive complexity for the branch/change model.
- Strip all whitespace from code before hashing: rejected because whitespace can be semantically significant.
- Implement parser-aware whitespace normalization in v1: rejected as too complex.

## Open questions for design

- Exact v2 manifest field names and Zod schema organization.
- Whether v1-to-v2 upgrade happens on every real active mutation or through a narrower migration boundary.
- Transitional gate behavior for a legacy sign-off with artifact hashes but no implementation fingerprint. It must be represented honestly (`implementation: null`); decide whether it remains temporarily accepted with a warning or requires renewal at the next gate crossing.
- Exact stale-event shape and whether spec/sign-off use one generic scoped event or distinct event types.
- Exact workflow-policy default for newly created v2 changes and where project/schema defaults are declared.
- Which unresolved review checks must block forward/archive operations when `workflow: preserve` retains a late lifecycle state.
- Whether exact content hashes should also be stored for diagnostics in addition to normalized hashes; not required for v1.
- How implementation fingerprint calculation is exposed through Core without violating package dependency direction or allowing unsafe paths.
- Whether changes to tracked-file disposition after sign-off should directly mark sign-off stale or simply be caught by existing implementation checks before archive.

## Conversation evolution

1. The discussion began with new schema-driven `implementing` and `verifying` skips.
2. The user clarified that implementation is skipped when no work remains, not merely when no tasks exist.
3. Skip conditions were aligned with the current workflow check registry and composable `all`/`any` expressions.
4. Backward transitions raised questions about destinations when implementation/verification phases are absent.
5. Reconsidering state meanings showed that approval-gate invalidation could dominate any route calculation.
6. The user identified current invalidation as too aggressive, so workflow skipping was deferred.
7. Investigation confirmed that `invalidated` globally couples approvals, artifact reopening, lifecycle rollback, and audit.
8. The user selected nested `invalidation.artifacts` and `invalidation.workflow` policies.
9. The user required explicit current approval fields in the manifest while preserving append-only history.
10. Manifest v2 and temporary v1 compatibility were added to scope.
11. Sign-off was extended with a deliberately simple linked-file fingerprint.
12. Parser/symbol-aware fingerprinting and aggressive whitespace removal were rejected; conservative `text-v1` normalization was selected.
