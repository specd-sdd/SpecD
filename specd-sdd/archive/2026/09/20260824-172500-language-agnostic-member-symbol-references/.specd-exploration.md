# Exploration Context

Generated: 2026-08-24

## Problem statement

GitHub issue `specd-sdd/SpecD#58`, "feat(code-graph): enrich member symbol identities for implementation links", requests stable and expressive identities for class/interface members. Stored implementation symbols such as `VcsAdapter.rootDir`, `ArchiveChange.execute`, and `CodeGraphProvider.analyzeSpecImpact` can be reported stale even when the member exists because the current graph exposes a simple member name, an owner separately, or only the parent.

The implementation must be a native `@specd/code-graph` capability, not an implementation-tracking-specific patch. Existing Code Graph methods and commands must continue to work. CLI, SDK, future APIs, and MCP must delegate to Code Graph and must not duplicate symbol syntax parsing or resolution policy.

## Confirmed scope and constraints

- Support owner-qualified member references across language adapters while keeping the Code Graph domain language-neutral.
- Centralize exact symbol selection behind `CodeGraphProvider`; CLI, SDK, APIs, and MCP remain thin consumers.
- Preserve all existing Code Graph command and provider behavior additively, including legacy occurrence IDs, logical IDs, simple-name selectors, public bindings, graph search, graph impact, and implementation review.
- Keep human-readable references such as `ArchiveChange.execute` while retaining an opaque, deterministic, structured canonical identity.
- Language-specific syntax belongs to language adapters; the indexer must not gain language-specific parsing or resolution logic.
- Exact selection must remain conservative: no fuzzy matching, edit-distance selection, best guesses, or runtime inference.
- Full-text query expansion is discovery-only and must never prove semantic identity.
- All artifacts, code, comments, tests, and documentation must be written in English.

## Current behavior and codebase observations

### Existing semantic foundations

- `packages/code-graph/src/domain/value-objects/symbol-reference.ts`
  - `LogicalSymbol` already contains `id`, `workspace`, `surface`, simple `name`, `space`, optional `ownerId`, and optional `memberForm`.
  - `MemberForm` currently contains `instance`, `static`, `constructor`, `getter`, `setter`, and `signature`.
  - `createLogicalSymbol` builds a delimiter-safe deterministic identity from workspace, surface, name, space, owner ID, and member form.
  - `DeclarationOccurrence.kind` preserves the legacy graph symbol kind separately from logical identity.
- `packages/code-graph/src/application/use-cases/resolve-symbol-reference.ts`
  - Resolution can query by structured `ownerId` and `memberForm` and supports hierarchy traversal.
  - `normalizeRequest` only parses the opaque logical ID format. It does not parse human owner-qualified text such as `Owner.member`.
- `packages/code-graph/src/infrastructure/tree-sitter/typescript-language-adapter.ts`
  - The current member classification maps every `SymbolKind.Method` to `MemberForm.Instance` and does not yet prove static/property/getter/setter/interface distinctions comprehensively.
- All current tree-sitter adapters emit additive `ReferenceFacts`: TypeScript, Python, Go, and PHP.
- The existing `code-graph:resolve-symbol-reference` spec already requires structured identity to be authoritative, canonical rendered references to round-trip with escaping, and language syntax analysis to live in adapters.

### Current implementation-review gap

- `packages/sdk/src/orchestration/build-implementation-review.ts`
  - `buildResolutionRequests` explicitly projects stored symbol strings into Code Graph requests without parsing symbol syntax.
  - A stored `Owner.member` reaches Code Graph as `requested: "Owner.member"` plus its file path.
  - Because the current resolver treats that entire string as a simple name, it cannot reliably reach owner then member.
- SDK tests verify forwarding `Owner.member`, but do not prove end-to-end owner/member resolution.

### Search splitter and FTS behavior

- `packages/code-graph/src/domain/services/expand-search-query.ts`
  - Preserves the normalized original token.
  - Splits whitespace, separators `:`, `/`, `_`, `.`, `-`, and CamelCase/PascalCase boundaries.
  - `ArchiveChange.execute` therefore expands to the full `archivechange.execute` token plus components including `archive`, `change`, and `execute`.
- `packages/code-graph/src/infrastructure/sqlite/sqlite-graph-database.ts`
  - `prepareExpandedSearchQuery` sends expanded tokens to `sanitizeFtsQuery`.
  - `sanitizeFtsQuery` joins tokens with FTS `OR` expressions.
  - This is useful for discovery recall but broadens results. The observed current search for `ArchiveChange.execute` returned textual results such as `archivedChange` and the owner `ArchiveChange`, rather than resolving and ranking its `execute` child as an exact qualified member.
- `code-graph:graph-store` already allows backend-native FTS results to be supplemented by identity-derived candidates, requires identity-aware ranking, and requires structured logical fields to be indexed. It explicitly prohibits parsing or substring-searching serialized canonical IDs for selector resolution.

### Risk and overlap

- Graph impact for `code-graph:src/domain/value-objects/symbol-reference.ts` is CRITICAL: 61 direct dependents, 147 indirect dependents, and 81 affected files were reported during discovery.
- Active change `code-graph-symbol-semantic-context` is in `designing` and targets `code-graph:symbol-model`, `code-graph:language-adapter`, and `code-graph:indexer`.
- `changes create` confirmed overlap on those three specs. Design must coordinate, merge compatible scope, or establish a clear sequencing boundary before implementation.

## Proposed architecture

### Code Graph owns one exact-resolution pipeline

Expose a single public provider path for canonical, structured, legacy, and textual references. Conceptual input:

```ts
interface ResolveCodeGraphSymbolInput {
  readonly workspace: string
  readonly reference: SymbolReferenceInput
  readonly filePath?: string
  readonly publicSurface?: string
  readonly language?: string
  readonly scopeId?: string
  readonly buildContext?: Readonly<Record<string, string>>
}

type SymbolReferenceInput =
  | { readonly kind: 'text'; readonly value: string }
  | { readonly kind: 'canonical'; readonly value: string }
  | { readonly kind: 'structured'; readonly selector: StructuredSymbolSelector }
```

`CodeGraphProvider.resolveSymbol` and batched `resolveSymbols` should own adapter selection, health/freshness, structured lookups, evidence, ordering, and outcomes. `graph impact`, implementation review, SDK, CLI, API, and MCP call this shared path rather than reimplementing selection.

Existing resolution surfaces such as `ResolveSymbolReference` and `resolveGraphSelector` should converge on the common policy. Search may retain broad textual retrieval but must use the same exact resolver for selector-like inputs.

### Separate canonical identity, structured path, and presentation

- Keep an opaque, deterministic, versionable canonical logical reference as the authoritative identity.
- Represent qualification structurally as ordered owner/member segments rather than making `.` part of identity.
- Expose a generic display reference such as `ArchiveChange.execute`.
- Allow adapters to render a native reference when syntax differs, for example PHP `ArchiveChange::execute`.
- Never use ad hoc delimiter splitting for canonical references.

Conceptual additions:

```ts
interface SymbolPathSegment {
  readonly name: string
  readonly role?: 'namespace' | 'type' | 'value' | 'member'
}

interface StructuredSymbolSelector {
  readonly path: readonly SymbolPathSegment[]
  readonly space?: SymbolSpace
  readonly member?: Partial<MemberSemantics>
}
```

### Normalize member semantics along independent axes

The current `MemberForm` combines declaration kind, dispatch, and accessor semantics. Prefer or add a normalized structure such as:

```ts
interface MemberSemantics {
  readonly kind: MemberKind
  readonly dispatch?: 'instance' | 'static'
  readonly accessor?: 'get' | 'set' | 'read-write'
  readonly nativeKind?: string
}
```

Cross-language `MemberKind` should cover at least method, property, field, constructor, signature, indexer, operator, event, and an extensible/other form. `nativeKind` preserves language-specific information without pushing language-specific enums into the domain.

Examples:

- static method: `{ kind: 'method', dispatch: 'static' }`
- instance getter: `{ kind: 'property', dispatch: 'instance', accessor: 'get' }`
- interface member: `{ kind: 'signature', dispatch: 'instance' }`
- unsupported language-native form: `{ kind: 'other', nativeKind: '...' }`

### Adapter responsibilities

Each language adapter should:

1. Emit normalized owner and member semantics during indexing.
2. Parse exact human references in its language syntax into structured selectors.
3. Optionally render a native reference for presentation.

Conceptual adapter methods:

```ts
parseSymbolReference(
  input: AdapterSymbolReferenceInput,
): readonly StructuredSymbolSelector[]

renderSymbolReference?(
  input: AdapterSymbolReferenceRenderInput,
): string
```

Parsing remains synchronous, deterministic, stateless, and proof-based. If syntax cannot be interpreted safely, return no selector or multiple explicit candidates; do not guess.

Expected adapter coverage:

- TypeScript/JavaScript: classes, interfaces, methods, fields, properties, getter/setter, constructor, static and instance forms.
- Python: classes, instance methods, statically proven `staticmethod`, `classmethod`, `property`, and setter forms.
- Go: named/pointer receiver methods, interface signatures, and struct fields where supported.
- PHP: class/interface/trait methods, properties, constructor, static and instance forms; preserve native syntax such as `::`.
- Future adapters emit only facts they can prove.

### Owner-first exact resolution

For a text reference like `ArchiveChange.execute`:

1. Select the adapter from anchored file language, indexed file metadata, explicit language, or another proven source.
2. Parse to structured segments.
3. Resolve the owner in the addressed file/surface/scope.
4. Use the resulting owner ID to query the child simple name and semantic constraints.
5. Repeat for nested owners.
6. Return the existing conservative `resolved`, `ambiguous`, `unresolved`, or `missing` outcome with evidence.

Do not search globally for only the last segment and infer its owner. If no language can be selected safely, return ambiguity/unresolved rather than selecting a default adapter arbitrarily. Canonical and structured inputs do not require adapter parsing.

### Store and indexing

Backends need bounded structured lookup and indexes over combinations including:

- workspace, surface, simple name
- workspace, surface, owner ID, simple name
- workspace, owner ID, simple name, member kind, dispatch/accessor

Potential persisted fields include member kind, dispatch, accessor, native kind, and a searchable qualified-name projection. The store remains backend-neutral; SQLite defines its physical representation. A storage-generation bump and derived-cache rebuild are preferable to source-data migration.

A reference-alias projection/table may be considered for canonical, generic display, and native spellings, but aliases are retrieval/presentation aids; structured facts remain authoritative.

### Search and FTS separation

Keep the current lexical splitter because it improves discovery and supports adding related words. Its output must not participate in exact identity proof.

`graph search` should run two independent lanes:

1. Exact selector lane: adapter parsing and owner/member structured resolution.
2. Lexical discovery lane: current normalized/raw/expanded token plan and FTS/BM25.

Merge and deduplicate results, ranking exact structured matches before public/logical component and textual matches. Search should continue returning broader related results after the exact target.

Exact operations such as `resolveSymbol`, `graph impact --symbol`, implementation tracking, and symbol coverage must not fall back to FTS.

The qualified display/native reference may be indexed for candidate retrieval and exact identity ranking, but FTS tokenization must never be trusted to preserve `.`, `::`, or future language separators. A separate equality/indexed lookup is required.

Proposed spec rule:

> Query expansion is discovery-only. Expanded lexical tokens MUST NOT participate in exact symbol identity resolution, implementation-link review, coverage materialization, or impact target selection.

And:

> Symbol search MUST run structured exact-reference resolution independently from full-text retrieval. Successfully resolved structured targets MUST rank ahead of lexical matches, while full-text discovery remains available.

### Compatibility and public consumers

Maintain the existing selector precedence additively:

1. Exact canonical logical identity.
2. Legacy occurrence ID.
3. Exact public binding.
4. Structured owner/member reference.
5. Existing simple-name behavior.
6. Textual ranking only in discovery operations.

Public output should add fields rather than remove existing ones, potentially including canonical reference, display reference, native reference, qualified path, and normalized member semantics.

CLI remains formatting/bootstrap only. SDK implementation review forwards to provider-owned resolution. Future APIs and MCP expose provider inputs/results, including structured references for capable clients and text references for humans.

Proposed architecture rule:

> All exact symbol selection, including human-readable, canonical, legacy, structured, search-derived, implementation-link, impact, API, and MCP requests, MUST be resolved by the Code Graph provider through one backend-neutral resolution pipeline. Consumers MUST NOT parse language syntax or reproduce symbol-selection policy.

## Verification expectations

### Shared contracts

- Adapter contract tests validate stable simple name, owner identity, member semantics, parsing, and native rendering for every built-in adapter.
- GraphStore contract tests cover persistence, indexed structured queries, deterministic ordering, and backend equivalence.
- Resolver tests cover canonical round-trip, owner-first nested paths, public/local bindings, hierarchy, ambiguity, overloads/merged declarations, getters/setters, static/instance distinction, stale/partial health, and unknown languages.

### End-to-end examples

- `VcsAdapter.rootDir`
- `ArchiveChange.execute`
- `CodeGraphProvider.analyzeSpecImpact`

For each:

- implementation review resolves the expected logical member;
- graph search returns it first as an exact structured match while retaining lexical discovery results;
- graph impact selects only the exact member or reports ambiguity;
- provider/SDK/CLI results agree;
- future API/MCP consumers can obtain the same result without parsing output strings.

### Search-specific tests

- `expandSearchQuery` preserves the complete normalized `ArchiveChange.execute` token and adds `archive`, `change`, and `execute`.
- FTS may retrieve related results, but cannot prove an exact owner/member match.
- `ArchiveChange.missing` cannot resolve merely because the owner or unrelated `missing` symbols are searchable.
- Exact matches outrank `ArchivedChange`, `createArchiveChange`, comment-only matches, and unrelated `execute` members.
- PHP `ArchiveChange::execute` and generic display `ArchiveChange.execute` can reach the same logical target where the adapter proves equivalence.
- SQLite and future backends expose identical semantic outcomes and deterministic ordering.

## Rejected alternatives

- Splitting all qualified references on `.` in the core: rejected because it is language-specific, ambiguous, and incompatible with PHP, Go, escaping, nested syntax, and future adapters.
- Making `Owner.member` itself the sole canonical identity: rejected because it can be ambiguous across files/modules/forms and depends on presentation delimiters.
- Removing the lexical word splitter: rejected because its expanded tokens are useful for discovery and adding related results.
- Using FTS/BM25 ranking to resolve implementation links or impact selectors: rejected because textual relevance cannot prove semantic ownership or identity.
- Parsing qualified symbol strings in SDK, CLI, API, or MCP: rejected because behavior would diverge across consumers; Code Graph must own it directly.
- Runtime reflection or fuzzy inference for dynamic members: rejected by existing conservative resolution constraints.

## Open questions for design

- Whether to evolve `MemberForm` compatibly or introduce `MemberSemantics` alongside it before deprecation.
- Exact versioned canonical-reference encoding and escaping rules.
- Whether qualified paths are persisted, reconstructed through owners, or both persisted as a searchable projection and reconstructed authoritatively.
- Whether reference aliases deserve a separate backend-neutral concept/table.
- Precise adapter-selection behavior when a text reference lacks an anchored file, explicit language, or uniquely typed surface.
- Whether `graph search` always attempts exact parsing or only does so for recognizably structured/canonical input; in either case search must preserve lexical results.
- Which extra specs, especially `cli:change-implementation`, must be added once artifact-level behavior is detailed.
- How to sequence or consolidate with active change `code-graph-symbol-semantic-context` to avoid conflicting deltas and implementation edits.
