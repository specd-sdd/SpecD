# Exploration: include-overlaps-in-project-summary

Branch at discovery: `main`. User said the session is on main. Do not touch API, SDK, client, or UI. Those are a follow-up on branch `feat/user-interface` after merge.

## Problem statement

Hosts need project spec-validation health and active-change overlaps from one aggregate. `GetProjectSummary` already returns counts, `specsByWorkspace`, optional `includeChanges` (active/drafts with name, state, tasks) and optional `includeSpecsHealth` (`GetSpecsHealth.execute({})` for the whole project). The per-spec validation cache lives in `ValidateSpecs`. Overlaps are the missing enrichment.

Why: `project status` and other hosts currently assemble this from several calls. The user wants one core aggregate, then the CLI `project status` command to surface overlaps from it.

## Approach / solution outline

Extend `GetProjectSummary`. Do not create a second use case such as "shell status".

- Additive flag `includeOverlaps` (default false).
- When true: orchestrate `DetectOverlap` over active changes, with no name filter, and return the `OverlapReport`.
- When false or omitted: do not call `DetectOverlap` and do not include the key.
- Counts without flags stay the same.
- Do not add another cache. Spec validation cache stays in `ValidateSpecs`.

CLI `project status` (`cli:project-status`) is in this change so the command can show that overlap report. SDK stays out of scope.

## Design decisions

User closed the intent. Do not reopen.

Bell semantics (`specsHealth`):

- The bell is project spec validation (`specsHealth`).
- A spec that sits inside a change still counts.
- Do not introduce `failedClosedSpecs`.
- Do not filter by `activeSpecIds`.
- Do not use "only specs outside changes" semantics.
- Overlaps are a separate signal. They are not part of the meaning of `specsHealth`.

Overlap enrichment:

- `includeOverlaps` default false, additive.
- True: `DetectOverlap` on active changes, no name filter, return `OverlapReport`.
- False or omitted: do not call `DetectOverlap`, omit the key (same absent-key style as `active` / `drafts` / `specsHealth`, not null).
- Unflagged counts unchanged.

Cache:

- Do not add a cache on `GetProjectSummary`. Cache stays in `ValidateSpecs`.

Tests required in verify of `core:get-project-summary`:

- With overlap, `overlaps` present.
- Without overlap, `overlaps` empty or absent according to the flag.
- `specsHealth` does not drop a spec because it is in `specIds` of an active change.
- Without flags, result has no `active`, `drafts`, `specsHealth`, or `overlaps`.
