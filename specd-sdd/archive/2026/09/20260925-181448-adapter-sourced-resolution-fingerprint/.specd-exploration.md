# Exploration: adapter-sourced-resolution-fingerprint

Generated: 2026-09-25

Source: GitHub issue https://github.com/specd-sdd/SpecD/issues/64

## Problem statement

The graph fingerprint hashes package/build manifests from a **hardcoded** list in `discoverResolutionInputs` (`packages/code-graph/src/application/use-cases/_shared/compute-graph-fingerprint.ts`). That list is **not** derived from language adapters.

Current hardcoded set (from the issue):

```ts
const RESOLUTION_MANIFESTS = new Set([
  'package.json',
  'pyproject.toml',
  'setup.cfg',
  'setup.py',
  'go.mod',
  'go.work',
  'composer.json',
])
// plus /^(?:tsconfig|jsconfig)(?:\.[^.]+)?\.json$/
```

Problems:

1. **Drift risk** — Adding a language means updating a second, separate list. Fingerprint and adapter can diverge.
2. **False staleness from CRLF** — Indexer hashes raw file bytes (`readFileSync` with no encoding). Adapters read manifests as UTF-8 text via `findManifestField`. A CRLF checkout of `package.json` / `composer.json` / `go.mod` / `pyproject.toml` does not change what adapters parse, but changes the fingerprint → graph reported stale.
3. **`.gitattributes` does not help** — SpecD does not apply this repo's gitattributes to projects it indexes. Indexed **source** hashes already go through `NodeContentHasher` (newline-normalized). Manifest hashes in the fingerprint do **not**.

## Expected outcome (from issue)

1. The set of files that can change import/package resolution MUST come from the **language adapter that uses them**, not a hardcoded set in the fingerprint module.
2. The fingerprint MUST hash the **same files the adapters read**, as **text with newline normalization**, so CRLF and LF of an unchanged manifest produce the same digest.

## Approach / solution outline

Agreed direction (user confirmed create with this scope):

- Extend `LanguageAdapter` (or related adapter surface) so each adapter **declares** which resolution-manifest filenames / patterns it reads for package identity / import resolution.
- `discoverResolutionInputs` / `computeGraphFingerprint` should collect those declarations from the registered adapters instead of `RESOLUTION_MANIFESTS`.
- Hash discovered manifests via the same newline-normalized text path used for source content (`NodeContentHasher` / equivalent), not raw bytes.
- Drop (or stop fingerprinting) files that no adapter actually reads: `tsconfig*.json`, `jsconfig*.json`, `setup.cfg`, `setup.py`, `go.work` — unless design discovers they _are_ needed for resolution and an adapter should own them.

Adapter → manifest mapping already known from adapters / issue:

| Adapter    | Manifest         | Extracted                |
| ---------- | ---------------- | ------------------------ |
| TypeScript | `package.json`   | `name`                   |
| PHP        | `composer.json`  | package name + PSR-4 map |
| Go         | `go.mod`         | module path              |
| Python     | `pyproject.toml` | project name             |

Shared helper: `findManifestField` at `code-graph:src/infrastructure/tree-sitter/find-manifest-field.ts` (walks up from `codeRoot` bounded by `repoRoot`, UTF-8 text).

## Design decisions / agreements

- User pointed at issue #64 and asked to create a change to fix it; confirmed name/description/specs as proposed.
- Fix is spec-driven (no code-only path): update staleness/indexer/adapter specs, then implement.
- Fingerprint manifests must be **adapter-sourced**.
- Manifest content hashing must use **newline-normalized text**, matching source hashing behavior.
- Files in the hardcoded list that **no adapter reads** should leave the fingerprint (unless design finds a real resolution use and assigns ownership to an adapter).

## Rejected / deferred alternatives

- Not relying on `.gitattributes` / CRLF normalization at the host checkout — issue explicitly says SpecD does not apply this repo's attributes to indexed projects.
- Not keeping a parallel hardcoded list “for convenience” — that is the bug (drift).
- Whether `tsconfig`/`jsconfig`/`setup.cfg`/`setup.py`/`go.work` belong in any adapter is **open for design** — default expectation from issue is they should not be fingerprinted if adapters do not read them.

## Open questions for `/specd-design`

1. Exact adapter API shape: e.g. `resolutionManifestNames(): readonly string[]` vs patterns vs richer descriptors (path relative to codeRoot vs upward search like `findManifestField`)?
2. Discovery roots: issue says indexer looks at project root and each workspace `codeRoot` — keep that discovery topology when sourcing names from adapters?
3. Confirm removal of non-adapter-read files from fingerprint (`tsconfig*`, `jsconfig*`, `setup.cfg`, `setup.py`, `go.work`).
4. Does fingerprint formula in `code-graph:staleness-detection` / `code-graph:indexer` already document resolution-input hashes, or only version + workspace hash? Optimized contexts still emphasize version + workspace layout — design may need to **extend** the normative fingerprint inputs to include adapter-declared resolution manifests (code already hashes them; specs may lag).
5. How to minimize conflict with overlapping changes on `indexer` / `language-adapter`.
6. Migration: existing graphs fingerprint-mismatch after this change (expected) → full rebuild via `graph index`; document as intentional derivation change?

## Key codebase observations

- `findManifestField` reads manifests as text and extracts fields; shared by adapters.
- Source file incremental hashing already normalizes newlines via `NodeContentHasher`; resolution manifests currently do not.
- Specs `code-graph:staleness-detection` and `code-graph:indexer` describe derivation fingerprint primarily as package version + canonical workspace hash / effective discovery config; resolution-manifest hashing appears to be an implementation detail that specs should make normative as part of this change.
- Graph was `CONTENT_KNOWN_STALE` during exploration; investigation proceeded with warnings. Indexer LLM-optimized context was stale and was refreshed via `specd-spec-context-optimizer` before create.
