# Exploration Context: fix-config-spec-drift

Generated: 2026-09-29

## Problem Statement

Issue #57 (https://github.com/specd-sdd/SpecD/issues/57) identifies three pre-existing discrepancies where the specifications do not match the actual codebase implementation. These discrepancies originated during previous refactorings (specifically the `config-cascade-variants` audit `20260520-095622`). All three issues represent spec drift: the code is correct, functional, and covered by tests, whereas the specs need updating to match reality.

The three discrepancies are:

1. `ConfigWriter.initProject` method signature in `core:config` specifies two parameters `(configPath: string, options: InitProjectOptions)`, but the implementation and port accept a single parameter `(options: InitProjectOptions)` where `projectRoot` is inside `options`.
2. `ConfigWriter.listPlugins` in `core:config` specifies `type: string` as required, but the implementation and port declare `type?: string` (optional). When omitted, all plugins across types are returned.
3. Hook type mapping responsibility in `core:config-loader`: `specs/core/config-loader/verify.md` still contains orphaned verification scenarios claiming `load()` transforms `{ run: 'make test' }` to `{ type: 'run', command: 'make test' }` and `{ instruction }` to `{ type: 'instruction', text }`, and `specs/core/config-loader/spec.md` retains an outdated heading `### Requirement: Workflow and context entry mapping`. In reality, `ConfigLoader` preserves raw `schemaOverrides`, while hook mapping is handled by schema resolution (`specs/core/resolve-schema/spec.md` line 31 and `schema-yaml-parser.ts`).

## Approach / Solution Outline

Align the specs with the current codebase implementation:

1. In `specs/core/config/spec.md` (and `verify.md`), update the `ConfigWriter.initProject` method signature requirement and scenario to take a single parameter `(options: InitProjectOptions)`.
2. In `specs/core/config/spec.md` and `specs/core/config/verify.md`, update `ConfigWriter.listPlugins` to specify `type?: string` as optional.
3. In `specs/core/config-writer-port/spec.md`, clarify that `listPlugins(configPath: string, type?: string)` allows `type` to be optional.
4. In `specs/core/config-loader/verify.md`, remove the two obsolete hook mapping scenarios (`Scenario: Run hook mapped to typed form` and `Scenario: Instruction hook mapped to typed form`).
5. In `specs/core/config-loader/spec.md`, adjust the requirement heading `### Requirement: Workflow and context entry mapping` to reflect its actual current content (`### Requirement: Schema plugins, schema overrides, and context entry mapping`).

## Design Decisions

- **Spec drift fix only**: No code changes are necessary because the TypeScript port definitions, runtime implementations, and unit tests already have the desired behavior.
- **Single-param initProject**: `options: InitProjectOptions` encapsulates `projectRoot`, `schemaRef`, `workspaceId`, `specsPath`, and `force`. `configPath` is derived as `path.join(options.projectRoot, 'specd.yaml')`.
- **Optional `type` in `listPlugins`**: `listPlugins(configPath: string, type?: string)` provides flexibility to inspect either a specific plugin category or all configured plugins.
- **Hook normalization location**: `resolve-schema` remains the authoritative place for hook transformation. `config-loader` only handles loading and cascade merging of configuration files, storing `schemaOverrides` in raw operation format.
