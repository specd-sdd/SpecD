# Problem statement

The change now targets conservative symbol-reference resolution across every built-in
language, both for implementation review and impact analysis. TypeScript re-exports
are the clearest motivating case, but the contract must also preserve the distinct
semantics of Python package exports, Go package visibility/embedding, PHP aliases and
traits, and inheritance/type hierarchy in general.

Current behavior in changes implementation review produces frequent false-positive stale diagnostics even when the graph is fresh and the code is still plausibly linked. The reported failure modes are:

- Ports/interfaces: the stored link points to a member signature, but the graph can index the interface or port container without indexing each declared member. Current evidence: `ImplementationDetector` is indexed at `core:src/application/ports/implementation-detector.ts`, but its `detectModifiedFiles` signature is not; only the concrete `VcsImplementationDetector.detectModifiedFiles` method is resolvable.
- Rename mismatch: a real rename or typo should remain stale rather than being accepted merely because a vaguely similar symbol exists. The original `toProjectStatusDto` / `toProjectStatusDtoFromSnapshot` example is historical and neither name is present in the current graph.
- Barrels and re-exports: a link may point to `index.ts`, while the symbol is actually defined in a file like `host-context.ts` and only re-exported through the barrel.
- Simple symbol names: current fallback only helps for composed member notation such as `Change.transition`, `Foo#bar`, or `X::Y`; simple names do not get a second chance and are marked stale immediately.

The user explicitly framed the goal as reducing false-positive stale links without losing the signal for real stale links.

# Approach / solution outline

The brief proposes distinguishing among:

- `stale`: real breakage, symbol no longer exists or the file/target is wrong
- `unresolved`: the link is imprecise, but the implementation is still plausible
- optionally `ambiguous`: multiple plausible candidates exist and the CLI should not guess

The original brief proposed several design options. The ownership of Option A was revised
after checking the current package boundaries.

## Option A: SDK-orchestrated resolution

The current CLI helper `enrichImplementationTracking` performs the whole orchestration:
it loads graph statistics, resolves the VCS ref, canonicalizes paths, queries symbols,
classifies stale links, and returns a rendering projection. This is current behavior,
not the desired ownership boundary.

The revised direction is:

- `@specd/core` continues to expose the persisted, delivery-agnostic implementation
  review through `GetImplementationReview`.
- `@specd/sdk` orchestrates Core, VCS/config state, and an opened
  `CodeGraphProvider`, following the established `SDK -> Core + Code Graph` dependency
  direction.
- `@specd/code-graph` owns generic graph lookup or resolution primitives if the
  existing provider queries are insufficient. SDK must not parse TypeScript ASTs
  itself.
- `@specd/cli` invokes the SDK orchestration and renders the resulting
  delivery-neutral resolution projection. It must not own the matching policy.

When exact same-file matching fails, the SDK-owned workflow should be able to:

- retry composed identifiers against the rightmost member in the same file
- search the same symbol name within the spec workspace, not across unrelated workspaces
- distinguish one plausible candidate from multiple candidates
- use graph export/re-export information when the stored file is a barrel
- represent interface-member imprecision without declaring a real, uniquely supported
  link stale
- preserve real stale results for deleted, renamed, mistyped, or wrong-target links

## Option B: richer code-graph indexing

- index interface members as resolvable symbols such as `PortChangesMutate.validateChangeAll`
- index re-export aliases so a barrel symbol can resolve back to its real definition

## Option C: richer link semantics

- add link kinds such as `interface-member`, `re-export`, or `definition`
- make review logic branch by link kind

## Option D: hygiene and UX only

- keep the algorithm conservative, but surface `resolved`, `unresolved`, `ambiguous`,
  and `stale` as point-in-time review outcomes
- improve `implementation add` UX by suggesting graph symbols and encouraging definition-file links instead of barrel files

The final recommendation is `A + B + the diagnostic portion of D`:

- `@specd/code-graph` owns canonical reference resolution, enriched member identity,
  alias/export provenance, hierarchy-aware traversal, and the distinction between
  public-export impact and canonical-symbol impact.
- `@specd/sdk` owns the cross-subsystem implementation-review orchestration.
- `@specd/cli` only supplies input and renders structured outcomes.
- `resolved`, `unresolved`, `ambiguous`, and `stale` remain explicit, non-blocking
  diagnostics.
- interactive suggestions for `implementation add` remain outside this change.

# Design decisions

Decisions made so far:

- Open a new change named `implementation-review-symbol-resolution`.
- The original `cli:change-implementation`-only scope was discovery scaffolding and is
  superseded by the registered multicomponent scope above.
- The initial CLI-only ownership assumption is superseded: the CLI currently
  orchestrates resolution, but the new matching policy must not remain there.
- Put cross-subsystem orchestration in `@specd/sdk`, which already owns host-facing
  composition over Core and Code Graph.
- Keep `@specd/core` delivery-agnostic and keep generic graph mechanics in
  `@specd/code-graph`.
- Existing provider queries and raw `EXPORTS` relations are insufficient: Code Graph
  needs a generic resolver and richer first-class identity/provenance.

Design assumptions captured from the brief:

- Real typos or renamed symbols should still be reported as stale.
- A barrel/re-export mismatch should not be treated as stale when resolution is unambiguous and the workspace graph is fresh.
- Interface-member links should not become stale merely because graph indexing is coarser than the stored symbol string.
- Ambiguity should be surfaced, not silently treated as healthy.
- Workspace-wide fallback must be conservative: a unique candidate can support a
  resolved or explicitly imprecise result, while multiple candidates must remain
  ambiguous and a merely similar name must not suppress stale.
- Resolution outcomes are point-in-time diagnostics and must not rewrite persisted
  implementation links or archived sidecars.
