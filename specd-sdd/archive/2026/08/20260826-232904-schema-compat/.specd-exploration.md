## Motivation & Problem

Schemas currently dictate both change workflow ceremony and canonical spec identity in `spec-lock.json`. When a change is executed under a lightweight or custom change workflow schema (e.g. hotfix), its schema name gets written directly into `spec-lock.json` upon archive, causing schema identity divergence across specs that share the exact same canonical spec format. We want a declarative `compat` field on schemas so they can state compatibility with a canonical spec schema (e.g. `@specd/schema-std@1`), ensuring durable spec uniformity across the repository.

## Approaches Explored & Agreed Strategy

- Added optional `compat` field (string `ref@version` or object `{ name, version }`) to `schema.yaml` schema definition and domain `Schema` value object.
- Implemented a 3-level resolution hierarchy in `Schema.canonicalSpecSchema()`:
  1. `this._compat` (if explicitly declared on schema)
  2. `this._extends` (if schema extends another schema, parsed to parent identity)
  3. `this._name` & `this._version` (fallback to self identity)
- Updated Zod parsing in `SchemaYamlZodSchema` and `parseSchemaCompat` utility.
- Updated schema layers merge engine (`mergeSchemaLayers`, `SetTargets`, `RemoveTargets`) and extends chain cascade (`overlayData`) to handle `compat`.
- Updated archive and spec persistence flows (`archive-change`, `initialize-persisted-spec-state`, `generate-spec-metadata`) to use `canonicalSpecSchema()` when recording `spec-lock.json` identity.

## Consolidation & Audit Summary

### 1. Root Cause & Solution Summary

When archiving specs or persisting state, SpecD was using the change's active schema identity (`schema.name()`, `schema.version()`) directly. By introducing `compat` and `canonicalSpecSchema()` (with 3-tier fallback `compat` -> `extends` -> `name`), specs produced under ceremony variants or inherited schemas stamp the canonical spec schema identity in `spec-lock.json`.
