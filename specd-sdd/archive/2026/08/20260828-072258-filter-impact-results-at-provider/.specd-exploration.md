# Exploration: Provider-side impact result filters

Generated: 2026-08-28

## Problem statement

`specd graph impact` needs result filters that are executed by Code Graph and
SQLite before results reach the CLI. The user wants to filter impact results by
result type (`docs`, `symbols`, `files`, `specs`, and any supported categories),
and to filter symbol results by symbol kind. The CLI must remain a delivery
adapter that calls Code Graph as it does today; it must not post-filter results.

## Agreed command contract

- `--type` selects impact-result categories.
- `--kind` limits symbol results by symbol kind.
- `--workspace` uses the same repeatable inclusion semantics as `graph search`.
- `--exclude-workspace` uses the same exclusion semantics as `graph search`.
- Provider results must already satisfy all filters.
- The SQLite-backed provider must express the filtering in its own queries rather
  than loading broad result sets and filtering after query execution.

## Affected areas

- CLI command: `cli:src/commands/graph/impact.ts`.
- Code Graph impact/traversal services and value objects, including
  `code-graph:src/domain/services/analyze-impact.ts` and
  `code-graph:src/domain/services/analyze-file-impact.ts`.
- `CodeGraphProvider` contract and facade composition.
- SQLite graph store/database/worker RPC query path, notably
  `code-graph:src/infrastructure/sqlite/sqlite-graph-store.ts` and
  `code-graph:src/infrastructure/sqlite/sqlite-graph-database.ts`.
- Unit and integration tests in the CLI and Code Graph packages.

## Relevant specifications

- `cli:graph-impact` currently specifies `graph impact` selectors, presentation,
  and provider-owned traversal.
- `code-graph:traversal` specifies provider-side impact traversal and impact
  result semantics.
- `code-graph:graph-store` owns backend-neutral persistence/query contracts.
- `code-graph:composition` owns the lifecycle-managed `CodeGraphProvider` facade.

## Key observations

- The graph was current at discovery: 1,116 indexed files, 38,835 symbols,
  276 specs, with no stale or fingerprint warning.
- Graph search found CLI-local symbols `ImpactResultType`, `ImpactResultFilters`,
  `parseImpactFilters`, and `projectImpactResult` in
  `cli:src/commands/graph/impact.ts`. Their comments identify these as
  presentation-only filters and projection, which is the behavior this change
  must relocate.
- `cli:graph-impact` states that the CLI does not compute traversal, risk, or
  aggregate impact, delegating those responsibilities to Code Graph. This change
  extends that boundary to final result filtering.
- `code-graph:composition` already requires delivery adapters not to recreate
  provider-owned unified search behavior; the proposed impact contract should
  follow the same ownership principle.

## Coordination and constraints

- The change targets `cli:graph-impact`, `code-graph:traversal`,
  `code-graph:graph-store`, and `code-graph:composition`.
- SpecD reported overlap on all four specs with the active designing change
  `language-agnostic-member-symbol-references`. Coordinate during design and do
  not overwrite or revert that change's work.
- Existing unrelated worktree modifications, including managed spec-lock files
  and two untracked change directories, belong to the user and must be preserved.
- Repository directives require TypeScript, ESM, hexagonal boundaries, graph-first
  research, English artifacts, and no direct edits to `specs/`.

## Decisions and rejected alternatives

- Chosen: parse flags in CLI and delegate a typed request to Code Graph; have the
  provider and SQLite produce pre-filtered results.
- Rejected: CLI-side projection/filtering after analysis, because the user
  explicitly requires provider-owned filtering and SQLite query-time execution.
- No decision has yet been made about exact result-value spellings beyond the user
  examples (`docs`, `symbols`, `files`, `specs`); design should align them with
  the existing search vocabulary and current CLI compatibility needs.
