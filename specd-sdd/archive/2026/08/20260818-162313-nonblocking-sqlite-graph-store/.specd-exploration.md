# Exploration Context: nonblocking-sqlite-graph-store

Generated: 2026-08-18

## Problem Statement & Motivation

`SQLiteGraphStore` exposes the asynchronous `GraphStore` contract, but its current SQLite implementation is backed by `better-sqlite3`, whose database operations execute synchronously on the Node.js thread that owns the store.

As a result, methods such as graph searches, lookups, mutations, bulk commits, FTS rebuilds, schema initialization, and maintenance operations may block the host event loop even though callers interact with them through Promise-returning APIs.

This is increasingly problematic as SpecD evolves beyond short-lived CLI execution and is consumed by long-lived or concurrent hosts such as:

- Future HTTP API
- MCP servers
- SDK consumers
- Electron
- Studio/server integrations

A long-running SQLite operation must not prevent the host from accepting unrelated requests, processing timers, serving other non-database work, or progressing unrelated asynchronous operations.

The existing `GraphStore` asynchronous contract already provides the correct abstraction boundary. The problem is therefore not the public graph-store API, but the execution context in which synchronous SQLite work runs.

The built-in SQLite backend should remain based on `better-sqlite3`, while its synchronous database work is moved away from the host event-loop thread.

## Goals

This change SHALL:

- Prevent synchronous SQLite operations from blocking the host event loop.
- Retain `better-sqlite3` as the built-in SQLite driver.
- Preserve the existing asynchronous `GraphStore` contract.
- Preserve existing SQLite persistence and query semantics.
- Preserve bulk-index transaction atomicity.
- Preserve explicit `open()` / `close()` lifecycle semantics.
- Support concurrent callers without requiring concurrent SQLite execution.
- Provide bounded backpressure for long-lived hosts.
- Preserve runtime-specific SQLite bindings.
- Provide a clean future merge path for the Electron SQLite integration currently developed on `feat/user-interface`.

## Non-goals

This change SHALL NOT attempt to:

- Make SQLite itself fully concurrent.
- Execute multiple writes against the same database in parallel.
- Introduce a SQLite worker pool.
- Create one worker per request.
- Replace SQLite with another database.
- Replace `better-sqlite3` solely to obtain an asynchronous API.
- Introduce PostgreSQL or another external database dependency.
- Change the `GraphStore` public abstraction.
- Expose worker concepts through application APIs.
- Change HTTP, MCP, CLI, SDK, or Studio APIs.
- Change graph query semantics.
- Change FTS ranking semantics.
- Change persisted graph identities or relations.
- Change the SQLite schema solely because of this execution change.
- Implement Electron-specific code that does not exist on `main`.

## Proposed Architecture

The SQLite implementation SHALL execute its synchronous database work inside one persistent Node.js Worker Thread (`node:worker_threads`) owned by each open `SQLiteGraphStore`.

```
                         HOST THREAD
                    CodeGraphProvider
                           |
                           v
                       GraphStore
                           |
                           v
                    SQLiteGraphStore
                           |
                           | async request / response
                           v
                  SQLiteWorkerClient
                           |
                    worker_threads
                           |
================ execution boundary ================
                           |
                           v
                      sqlite-worker
                           |
                           v
                  SQLiteGraphDatabase
                           |
                           v
                    better-sqlite3
                           |
                           v
                  code-graph.sqlite
```

### Component Responsibilities

1. **`SQLiteGraphStore` (Host):**
   - Implements `GraphStore`
   - Public store lifecycle
   - Translates `GraphStore` operations into worker requests
   - Correlates requests and responses
   - Translates worker errors
   - Forwards progress events
   - Enforces pending-operation limits
   - Handles worker failure

2. **`SQLiteWorkerClient` (Host):**
   - Worker Thread lifecycle
   - Request correlation
   - Pending Promise tracking
   - FIFO dispatch semantics
   - Progress messages
   - Errors
   - Shutdown
   - Worker termination detection

3. **`sqlite-worker` (Worker):**
   - Loads configured SQLite runtime
   - Owns `better-sqlite3` connection
   - Owns prepared statements
   - Executes SQL
   - Executes complete transactions
   - SQLite-specific filesystem lifecycle where appropriate
   - Schema initialization
   - FTS maintenance
   - Returns serializable results

4. **`SQLiteGraphDatabase` (Worker):**
   - Encapsulates SQL-heavy database behavior separated from host-facing adapter
   - Executes entirely synchronous SQL queries/mutations inside worker

## Worker Lifecycle

- **One persistent worker per open store** (not created per operation).
- **`open()` flow:**
  1. Create worker
  2. Establish communication
  3. Provide serializable SQLite runtime configuration
  4. Load SQLite runtime inside worker
  5. Create required storage directories
  6. Open database
  7. Configure SQLite (pragmas, etc.)
  8. Initialize or validate schema
  9. Prepare backend state
  10. Report readiness to host
  11. Resolve `open()`
- **`close()` flow:**
  1. Stop accepting new operations
  2. Deterministically settle or reject queued operations
  3. Request worker-side DB closure
  4. Close SQLite connection
  5. Clear prepared statements and worker-owned state
  6. Terminate worker
  7. Reject any unresolved requests if termination occurs unexpectedly
  8. Clear host-side request tracking
  - `close()` remains idempotent.
- **Worker termination:**
  - Unexpected worker death fails the store and outstanding operations. No silent auto-restart.

## SQLite Runtime Binding & Electron Compatibility

- Worker loads `better-sqlite3` inside worker execution context.
- Runtime binding mechanism evolves from function-based loader to serializable descriptor:
  ```ts
  export interface SqliteRuntimeDescriptor {
    readonly modulePath?: string
  }
  ```
- **Default Node runtime:** `createSqliteGraphStoreFactory()` -> worker loads normal `better-sqlite3` dependency.
- **Runtime-specific module:** `createSqliteGraphStoreFactory({ runtime: { modulePath: ... } })`.
- **Target `main` only:** Files on `feat/user-interface` (`packages/code-graph-sqlite-electron`) will cleanly adapt to pass `modulePath` once merged, without duplicating worker or protocol.
- `packages/code-graph-electron` is legacy and not a compatibility target.

## Worker Protocol & Serialization Boundary

- Request/Response protocol over `node:worker_threads` `postMessage`:
  - `SQLiteWorkerRequest`: `{ id: number, operation: string, payload: unknown }`
  - `SQLiteWorkerResponse`: `{ id: number, type: 'result', result: unknown }`
  - `SQLiteWorkerFailure`: `{ id: number, type: 'error', error: SerializedError }`
  - `SQLiteWorkerProgress`: `{ id: number, type: 'progress', stage: string }`
- Prefer discriminated unions and plain serializable DTOs (primitives, plain objects, arrays).
- No transfer of prototypes, functions, DB connections, or prepared statements.

## Execution Ordering & Backpressure

- FIFO serial execution in worker.
- Finite pending-operation limit (initial default: 256 pending operations).
- Overload error thrown when limit exceeded (infrastructure error, not HTTP 503).

## Transaction Semantics & Bulk Indexing

- Complete transactions execute worker-side inside `db.transaction(...)`. Host does NOT send individual RPCs for `BEGIN`/`COMMIT`.
- Bulk index session continues staging on host memory; complete payload sent to worker in single atomic `commitBulkIndex(payload)` operation.
- Worker emits serializable progress events (`cleanup`, `files`, `documents`, `symbols`, `specs`, `reference-facts`, `observations`, `relations`, `search-indexes`), host invokes `metadata.onProgress(...)`.

## Error Handling

- Errors serialized across worker boundary preserving category/type, message, SQLite error code, operation context.
- Worker startup failure, crash, queue overflow, or malformed responses reject all outstanding Promises.

## Filesystem Operations

- Backend-owned SQLite filesystem work executes in worker where practical (DB creation, recreation, SQLite artifacts, WAL/SHM lifecycle, backend cleanup).
- Host-side filesystem operations must remain non-blocking.

## Worker Packaging & Built Package Layout

- Deterministic build artifact: `src/infrastructure/sqlite/sqlite-worker.ts` -> `dist/sqlite-worker.js`.
- Worker resolved relative to installed/built module (`import.meta.url`), not `process.cwd()`.
- Integration tests must verify the actual built package layout.

## Host Responsiveness Test

- Acceptance test proving that while an expensive SQLite operation is running in worker, host timer / event-loop tasks can execute and complete before SQLite finishes.

## Specs Affected

- `code-graph:sqlite-graph-store`
- `code-graph:composition`

## Locked Decisions Summary

1. Keep `better-sqlite3`
2. Use Node.js `worker_threads`
3. 1 persistent worker per open store
4. 1 SQLite connection per worker (serial execution)
5. FIFO operation ordering
6. Bounded queue (default: 256)
7. Complete transactions execute worker-side
8. Bulk staging remains host-side initially
9. Runtime binding is serializable (`SqliteRuntimeDescriptor`)
10. Preserve future Electron merge compatibility via `modulePath`
11. `packages/code-graph-electron` is legacy
12. No Electron `utilityProcess` in this change
13. Worker is an explicit package artifact (`dist/sqlite-worker.js`)
14. No silent worker recovery
15. No host-side synchronous persistence work
