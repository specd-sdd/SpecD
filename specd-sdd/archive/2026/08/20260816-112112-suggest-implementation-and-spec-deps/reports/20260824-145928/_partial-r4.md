## Subtle-issue analysis (generation-token logic)

**(a) ensureLoaded promise-first guard interplay — SOUND.** `ensureLoaded()` checks `_loadPromise` before the `_data !== null` guard (impl :91-103, deps :74-86); the JSDoc (:84-90 / :66-72) explains why: `loadFromDisk` synchronously initializes `_data = new Map()` before its first `await`, so a caller arriving mid-load would otherwise see an empty map. Because callers share the same promise via `.finally(() => { this._loadPromise = null })`, late joiners resume only after the load fully settles. Verified consequence used by the race tests: a `get()` that triggered the cold load resumes after invalidation+discard, reads the invalidated empty `_data`, and correctly yields `null`. `set()` mid-load (test :102-120/:173-191) awaits the same promise and writes into the settled map — no lost update. No deadlock/stuck-promise path: every failure inside `loadFromDisk` is swallowed by its own try/catch (missing/corrupt file ⇒ fresh start), so the `finally` always runs.

**(b) Observer consistency between invalidate() and load completion — CONSISTENT.** Sequence analysis: L1's synchronous prologue (capture generation, `_data=new Map()`, `_header=null`, `_isDirty=false`) executes at L1 _start_, i.e., strictly before any subsequent `invalidate()` can run (single-threaded event loop — `invalidate()` cannot interleave into the prologue). `invalidate()` then synchronously installs a coherent empty state (all four fields reset, gen bumped). Therefore any caller observing the instance between `invalidate()` and L1's completion sees a valid empty cache, never a half-state. When L1 later completes, its guarded early-return leaves that empty state untouched. One deliberate nuance worth recording: after `invalidate()` the in-memory `_data` stays a non-null empty map, so `ensureLoaded` will never reload from disk for this instance (the file was unlinked anyway) — the generation token therefore guards exactly the one in-flight load, which is the only case where stale repopulation was possible. Also checked `flush()`: it cannot resurrect discarded data because any `set/setMany` preceding it shares L1's promise and mutates only the post-discard state, and `flush()` bails unless `_isDirty`.

**(c) Path where an old-generation load could still commit — NONE.** In both adapters the discard check (:120-122 / :102-104) sits immediately before the commit block, and the entire commit (`_header = parsed.header` + per-entry `_data.set` loop, impl :129-134 / deps :111-116) is **synchronous**. On the JS event loop no `invalidate()` can interleave between a passing check and the completed commit. Exhaustive interleavings: invalidate before L1 starts ⇒ captured gen already stale ⇒ discard; invalidate during `readFile`/`JSON.parse` ⇒ discard; invalidate after commit ⇒ invalidate's own reset clears whatever committed. There is no await point inside the guarded section, hence no TOCTOU window.
