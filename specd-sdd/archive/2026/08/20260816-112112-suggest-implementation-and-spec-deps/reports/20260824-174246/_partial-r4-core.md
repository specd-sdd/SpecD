## Spec coherence findings

Merged previews are coherent on all four contract axes:

1. **Optional on `SpecArtifactEntry`** — `core:spec-repository-port` merged spec ("Requirement: get returns a Spec or null") now reads: "`size` — artifact file size in bytes observed from the same stat as `lastModified`. Optional on the wire for adapter families without cheap file metadata; when present it MUST reflect the byte length…". Correctly optional, matching `size?: number` in code.
2. **Required on `ArtifactMeta`** — same port spec, item 6 under "Aggregate persisted state, Meta observations, and specFingerprint": "`ArtifactMeta` MUST include `lastModified` and `size` … MAY include `hash` only when `options.includeHash === true`." Matches required `size: number`.
3. **No content reads for stamps** — both deltas preserve it explicitly: FS spec says "`get` MUST NOT read file contents to build these stamps"; port spec keeps "Artifact **content** MUST NOT be loaded by `get`" and "get MUST NOT return content hashes, `persistedStateHash`, or `specFingerprint`" (retained verbatim — `size` is not a content hash, so no conflict).
4. **Hash gating unchanged** — both specs restate `hash` only when `includeHash === true`; `persistedStateMeta` / `generatedMetadataMeta` rules untouched.

Verify deltas add exactly **4 scenarios**, all present in merged previews:

- `core:spec-repository-port` verify: "SpecArtifactEntry carries byte-size from the adapter stat" (under _get returns a Spec or null_), "artifactMeta exposes size without hashing" (under _Aggregate persisted state…_).
- `core:fs-spec-repository` verify: "get stamps include byte-size from the same stat" (under _Spec stamp population on get_), "artifactMeta exposes size from stat without hashing" (under _Metadata snapshot persistence_).

- **Docs drift:** `docs/core/ports.md:131` ("Every Meta type exposes `lastModified`; content `hash` is opt-in") predates the delta and does not mention `ArtifactMeta.size`; the change ships no docs delta. Non-contradictory, just incomplete.
- Note: on-disk `specs/core/fs-spec-repository/spec.md:76` still shows pre-delta wording ("`filename` and `lastModified` from `stat`"). Expected mid-change state — `spec-preview` is the authoritative merged view and applies cleanly.

## Consistency vs \_global/architecture + sibling specs

- `_global/architecture` contains no hash/stamp/port-shape constraints — no conflict introduced by adding `size`.
- **"get MUST NOT return content hashes" honored**: `Spec` carries `filename`/`lastModified`/`size` only; size is cheap physical metadata, not a content digest; fingerprint rules untouched.
- **List projection asymmetry is intentional and consistent**: `SpecListArtifactMeta` stays `{filename, lastModified}` (port spec: list Meta "MUST NOT include `hash`", projected "from existing index `sourceFiles`" — the index stores mtimes, not sizes, and the adapter "MUST NOT enrich the index wire format solely for Meta"); `projectListMetaFromSourceFiles` (project-list-meta.ts:20-45) conforms exactly.
- **`PersistedStateMeta` / `GeneratedMetadataMeta` without `size`**: coherent asymmetry — those observations feed lock/metadata hard-gates whose consumers compare mtime/hash, never byte-length, and no cache in this change size-prefilters sidecars. Documented at change level in design.md:558-569 ("Cache stamp identity pre-filter (size+mtime)": zero-extra-I/O rationale, three-stage freshness check, legacy fallback), though neither delta text nor design explicitly states why the sibling Meta types stay size-less — a sentence-level justification would make the asymmetry self-evident to future auditors (minor, non-blocking).
- `core:validation-result-cache-port` ("stamps derived from `Spec` via `get()` — `SpecArtifactEntry.lastModified`") is unaffected: its comparisons use lastModified/filename only (fs-validation-result-cache.ts:403-419).
