# Exploration context — context-extracted-first

Generated: 2026-08-24

## Problem statement

Loading change context (`specd changes context <name> <step>`, implemented by
`CompileContext` in `packages/core/src/application/use-cases/compile-context.ts`)
produces spurious warnings and serves stale/inconsistent data for specs involved in
the active change. The user (repo owner) observed this while loading context of
changes that create/modify specs. Verified empirically and by code reading during
this conversation.

## Root causes verified (with anchors)

### 1. Spurious metadata warnings for NEW specs

- `MaterializeSpecMetadata._resolveSpec`
  (packages/core/src/application/use-cases/materialize-spec-metadata.ts:90-103)
  resolves specs ONLY from the persisted workspace repo → new specs (only inside the
  change) throw `SpecNotFoundError`.
- compile-context.ts catches it (:566-571) leaving `metadata = null`, then warns:
  - summary mode: `"No metadata for 'X' — summary may lack description"`
    (compile-context.ts:605-611) — ALWAYS for new specs.
  - full-mode fallback: `"No metadata for 'X' — falling back to extracted sections"`
    (:677-682).
  - Note: in full mode with successful preview there is NO warning (merged files
    render fine, :650-662). The warnings hit summary mode + fallback paths.

Entry paths for a new spec WITHOUT `--include-change-specs`:

- **Path A (no flag needed)**: manifest `specDependsOn` VALUES are seeded raw,
  no existence check (compile-context.ts:351-358). If any in-scope spec declares
  dependsOn the new spec (common when creating related specs), the new spec enters
  collection. Proven real: draft `graph-change-context` declares
  `"cli:graph-change-context": [..., "code-graph:change-context"]` where the dep is
  a non-persisted spec.
- **Path B (`--follow-deps`)**: outer loop over change.specIds skips non-persisted
  specs early (compile-context.ts:435 `if (!spec) continue`) BUT
  `traverseDependsOn` registers deps BEFORE any persistence check
  (packages/core/src/application/use-cases/\_shared/depends-on-traversal.ts:76-78)
  and then emits its own `missing-metadata` warning (:108-112) + attempts fallback
  extraction against nonexistent files. Result: DOUBLE warning for the same new
  spec. Guard inconsistency between :435 and :76-78.
- Include patterns never match new specs (resolve against disk).

### 2. Asymmetric sources: canonical metadata vs merged content ("bicéfala" context)

For an EXISTING spec modified in the change (has deltas, in specIds):
| Piece | Source | Version |
|---|---|---|
| Catalogue title/description (summary row) | persisted metadata cache (.specd/metadata/), regenerated only from PERSISTED artifacts | pre-change |
| Full-mode body (rules/constraints/scenarios) | PreviewSpec merge of persisted+deltas, extracted live (compile-context.ts:619-631, :654-662, :956-967) | post-delta |
| Description INSIDE the rendered content block | extracted from merged files (:967 → :759-763) | post-delta |
| optimizedContext | only via lock; merged extraction has no lock access | n/a |

Consequences: in full mode the catalogue shows OLD description while the content
block shows NEW description (both in one response). In summary mode (the DEFAULT
contextMode) the preview never runs (only in full mode, :619) so the agent designs
against pre-change state with zero indication.

Key fact: mid-change deltas do NOT touch persisted state (metadata.json, locks);
they apply only at archive. So loading context mid-change does not corrupt caches —
but also means cached metadata describes pre-delta reality for scoped specs.

### 3. stale-optimization warnings for scoped specs

compile-context.ts:573-582 emits `stale-optimization` whenever
`llmOptimizedContext && metadata && !metadata.optimizedContext` — regardless of why
it's missing or whether the spec is being modified by the change.

Mechanism verified for code-graph:composition/graph-store/traversal (observed 3
warnings on `changes context deprecate-ladybug-store designing`): their lock
optimizations were persisted 2026-08-20 with artifact baselines that no longer match
current artifacts (changed 2026-08-22T10:50, post-archive drift, re-optimization
never ran). `buildFreshOptimizationProjections`
(packages/core/src/application/use-cases/generate-spec-metadata.ts:255-291) excludes
non-fresh optimizations from regenerated metadata → optimizedContext empty → warning.
So the warning fires due to REAL historical drift — but for specs IN the current
change's scope, lock optimizations describe pre-change content and are useless/misleading
by definition.

Project-level already solves its analogous case silently: overlap check disables the
optimized project blob when projectMeta inputs ∩ change.specIds ≠ ∅
(compile-context.ts:303-313). Spec-level has no such exemption.
BUT note: `get-project-context.ts` / `project status --context`
(packages/core/src/application/use-cases/get-project-context.ts) is entirely
change-agnostic — same per-spec stale-optimization warnings (:290-299), freshness is
purely hash-based (\_shared/project-metadata-freshness.ts). User accepted this as
correct-by-design (canonical truth = persisted state) as long as scope is narrow
(include patterns only → default:\* globals here).

### 4. "was regenerated" cache-miss noise

\_shared/materialize-context-spec-metadata.ts:35-41 relays `result.regenerated` as a
`stale-metadata` warning `"Metadata for 'X' was regenerated (generated)."`. Metadata
is a self-healing cache: regeneration succeeded AND persisted; next load hits cache;
nothing actionable. Same type (`stale-metadata`) as genuine "No metadata" — pollutes
semantics. The sibling diagnostic `metadata-cache-write-failed` (:43-50) IS
actionable and stays. No test asserts the regenerated warning (residual, not designed
contract). The provenance info already exists as structured fields
(`source`, `regenerated`) on GetSpecMetadata result / `specs metadata` output.

### 5. stale-optimization OUTSIDE scope is LEGITIMATE (keep)

User explicitly confirmed: for non-scoped specs (deps/globals) whose optimizations
drifted, the warning is legitimate information (their dense view lags canonical rules
that bind your work). System degrades gracefully (\_renderFromMetadata :769-789 falls
back to raw extracted sections). Only defects to fix there:

- Message conflates never-optimized ("missing") vs drifted ("stale") — same text/type today.
- Emission repeats identically every load until re-optimization (policy concern lives
  in .specd/config/skills/shared/shared.md — NOT addressed in this change unless
  user says otherwise).

## Agreed solution (user-confirmed rule)

```
Spec EN specIds (change scope):
  1º PreviewSpec (persisted + deltas + new-spec files) → extraction
  2º fallback: canonical metadata (if preview fails or yields nothing)
  3º lock optimizations: NEVER applied to scoped specs (describe pre-change content)
  → preview runs in SUMMARY mode too (today it only runs in full mode)
Spec FUERA del scope (deps, globals):
  unchanged: canonical metadata cache primary; stale-optimization warning kept,
  now distinguishing missing vs stale in message/type
Warnings:
  - new-spec "No metadata ... summary may lack description" / "...falling back..."
    → disappear by construction (extraction from merge works without persistence)
  - scoped specs → no lock consultation → no stale-optimization
  - "was regenerated" removed from context-warning channel (provenance stays as
    structured fields on results / specs metadata diagnostics)
  - traversal: align guards so non-persisted deps don't double-warn; missing-metadata
    suppressed when the dep is a change-scoped (new) spec whose merged content exists
```

Design notes agreed:

- Perf acceptable: extraction cost paid per load only for the few scoped specs
  (full mode already pays it today).
- Fingerprint must reflect MERGED content so delta edits invalidate --fingerprint
  caching (verify existing fingerprint covers rendered output — likely free, confirm).
- Fallback ladder when preview fails: merged → canonical metadata → base-file
  extraction (:684-694 already exists) + legit `preview` warning.
- Side effect noted (accepted, out of scope): freshness checks materialize metadata
  with if-needed policy → reads can write caches.
- Out of scope: shared.md agent policy aggressiveness ("MUST optimize before
  proceeding"); project-status design (deemed correct); auto re-optimization after
  archive (future idea, not committed).

## Open questions for /specd-design

1. Should summary-mode scoped entries render a light extraction (title+description
   only) or reuse full section extraction? Cost vs consistency.
2. Exact warning taxonomy after fix: keep type names? New type for
   optimization-stale vs optimization-missing?
3. Whether get-spec-context/get-project-context should ALSO skip lock consultation
   for specs overlapped by an active change (project-level has overlap data absent —
   they are change-agnostic; probably leave them untouched except sink/message fixes).
4. Fingerprint verification: does compileContextFingerprint already hash merged
   rendered content such that delta edits change it? Confirm before relying.
5. Traversal: suppress missing-metadata when dep ∈ change.specIds, or reorder guards
   (existence check before registration)? Prefer minimal consistent behavior.
