# Exploration: repair Code Graph coverage indexing

Generated: 2026-08-26

## Problem statement

`specd graph stats` reports both `COVERS_FILE` and `COVERS_SYMBOL` as zero even though canonical persisted spec state contains extensive implementation traceability. A forced index makes the inconsistency worse: the SQLite physical code graph is emptied while retained coverage hashes cause every discovered file to be skipped, leaving later incremental runs unable to recover.

This change must make forced and incremental indexing rebuild and preserve file and logical-symbol coverage, and must prevent graph health from reporting a graph as current/complete when its physical nodes are missing.

## Reproduction and repository evidence

Observed graph state before the change:

- Physical graph: `files=0`, `documents=0`, `symbols=0`.
- Specs: 274 canonical specs.
- Relations: 1,086 `DEPENDS_ON`, zero `COVERS_FILE`, zero `COVERS_SYMBOL`.
- Index coverage: 1,378 records: 1,106 indexed and 272 unsupported/no-language-adapter.
- Observations: 548, all spec observations.
- Health was nevertheless presented as current/complete.
- A forced run discovered 1,378 files, indexed zero, and skipped all 1,378.
- A subsequent ordinary run also skipped them all.

Canonical implementation-state counts were obtained through the repository/SDK boundary rather than raw filesystem counting:

- 274 canonical specs.
- 163 specs with implementation links.
- 199 file links.
- 224 symbol-link records containing 437 symbol names.
- All 199 file-link targets exist.
- 436 of 437 symbol-name target files exist.

Two now-deleted orphan sidecars explained the larger raw counts reported by another audit. They are not canonical specs and must not be included in Code Graph expectations.

## Root cause: forced rebuild retains the skip authority

Relevant anchors:

- `packages/code-graph/src/composition/code-graph-provider.ts`, around line 280: `CodeGraphProvider.index` invokes `store.clear()` for `force`.
- `packages/code-graph/src/infrastructure/sqlite-graph-database.ts`, around line 366: SQLite `clear()` deletes relations, physical files/documents/symbols, specs, observations, latches, metadata and FTS state, but does not clear `index_coverage` or the logical-symbol/binding/resolution tables.
- The in-memory store clears those retained structures, so backend behavior is asymmetric.
- `packages/code-graph/src/application/index-code-graph.ts`, around lines 714-731: the indexer reloads `index_coverage` hashes into `existingArtifactHashes` after the physical graph was cleared.

Failure sequence:

1. `--force` clears physical nodes and relations in SQLite.
2. `index_coverage` survives and says the discovered artifacts already have their current hashes.
3. The indexer classifies every discovered file as skipped rather than as needing analysis.
4. `semanticRefreshRequired` remains false and the in-memory indexing session stays empty.
5. The replacement/persistence stage has no analyzed files or symbols to insert.
6. Coverage relations cannot be persisted because their target endpoints are absent.
7. Later normal runs remain trapped because the same surviving hashes keep authorizing the skip.

The design must define one coherent force-rebuild contract. Likely choices include clearing every table that participates in skip/semantic authority, or making force ignore retained hashes and rebuild all discovered artifacts. Backend parity between SQLite and in-memory stores is required.

## Independent root cause: logical-symbol coverage is rejected by SQLite

Relevant anchors:

- `packages/code-graph/src/application/index-code-graph.ts`, around lines 1580-1603: implementation links resolve symbol names and target the logical symbol identifier, matching the logical-symbol contract.
- `packages/code-graph/src/infrastructure/sqlite-graph-database.ts`, around line 4155: relation endpoint validation checks physical `ids.symbols` but not `logical_symbols`.

Therefore a valid logical target for `COVERS_SYMBOL` is dropped at the persistence boundary. Existing tests commonly construct coverage relations with physical `SymbolNode` IDs and do not exercise the production logical-ID path.

The change should make the endpoint contract explicit and consistent across domain types, stores, persistence, querying and tests. It should not silently coerce logical coverage back to obsolete physical IDs.

## Incremental indexing gaps

### Session hydration when only persisted spec state changes

`implementation` is not ignored by the spec metadata fingerprint: production metadata generation includes implementation data, and fingerprinting strips provenance only. The earlier theory that implementation changes are always skipped is therefore rejected.

However, when persisted implementation state changes while code files remain clean, the spec may be reprocessed while `semanticRefreshRequired` is false. The symbol resolution path then queries an unhydrated in-memory session and cannot find persisted symbols. Relevant area: `index-code-graph.ts`, roughly lines 888-973 and 1580-1606.

The design must hydrate enough persisted semantic state to resolve implementation links whenever specs with symbol links need projection, independently of whether code changed in the current run.

### Coverage loss while replacing changed files

File-local deletion removes relations whose target is the file or one of its symbols. The incremental preservation path around `index-code-graph.ts` lines 915-918 retrieves covering specs for files but has no equivalent logical-symbol reconstruction/preservation path. Legacy physical `COVERS_SYMBOL` relations may therefore be destroyed after a code edit.

The preferred direction is deterministic re-projection of coverage from canonical persisted implementation state against the refreshed logical-symbol graph. Blindly preserving stale physical-symbol edges risks retaining invalid identities.

## Unresolved-symbol behavior

Current implementation treats file-only and symbol-qualified links as mutually exclusive. If a link contains symbols and they do not resolve uniquely, it emits neither `COVERS_SYMBOL` nor `COVERS_FILE`.

Another audit proposed automatic fallback to `COVERS_FILE`. That is not yet an accepted requirement: it may overstate coverage and conflict with the existing rule against guessing ambiguous symbols. Design must decide explicitly among:

- fail/diagnose unresolved symbol coverage;
- retain a separately modelled unresolved state;
- emit file coverage as a documented conservative fallback.

Silent loss is not acceptable, but fallback semantics require a spec decision.

## Health integrity gap

`packages/code-graph/src/application/get-graph-health.ts`, around lines 235-256, determines coverage completeness mainly from coverage statuses such as parse-failed/partial. It does not reconcile coverage records against the existence of physical files, documents and symbols.

Consequently 1,378 retained coverage records can make an empty graph appear current/complete. Health should detect impossible combinations, at least retained indexed coverage with missing corresponding physical nodes, and surface a stale/incomplete/corrupt condition with an actionable remedy.

## Spec and test drift

- The `code-graph:indexer` spec refers to `repo.readPersistedImplementation()`, while production uses `readPersistedState()`.
- Test repository mocks return `readPersistedState: async () => null`, so they cannot validate real sidecar-to-relation projection.
- All 708 Code Graph tests passed while the production SQLite database exhibited the failure.
- Force-index coverage is predominantly tested with the in-memory backend.
- SQLite clear-contract tests assert only a subset of physical counts.
- Repeated CLI force tests validate command output/locking rather than retained graph contents.

Required regression coverage should include:

1. A real persisted `spec-lock.json` implementation link projected to SQLite.
2. Both file-only and logical-symbol coverage relations.
3. Force indexing after an already-populated index, verifying physical nodes, logical semantic state, coverage hashes and coverage relations.
4. A second ordinary incremental run after force.
5. Implementation-only sidecar changes with unchanged code.
6. A code edit that replaces symbols and then reconstructs valid coverage.
7. Rejection/diagnostics for unresolved and ambiguous symbol links.
8. Backend parity for `clear()` and force-rebuild behavior.
9. Graph-health detection of retained coverage over missing physical nodes.

## Rejected or corrected claims from the external audit

- Rejected: the spec skip fingerprint excludes `implementation`. Production metadata projection includes it.
- Correct but incomplete: an empty session breaks symbol coverage when no semantic refresh occurs.
- Unconfirmed policy: always falling back to `COVERS_FILE`; this needs an explicit coverage-semantics decision.
- Correct direction but unsafe remedy: preserving old `COVERS_SYMBOL` blindly. Logical coverage should be recalculated from canonical state.
- Correct: production/spec naming and mocks have drifted, leaving the real integration path untested.

## Conversation flow

The user noticed impossible zero coverage counters and requested a complete new audit without changes. A separate agent's audit was supplied only as a hypothesis to challenge. The investigation reproduced the force-index failure, inspected SQLite state, distinguished canonical repository counts from raw filesystem counts, corrected inaccurate fingerprint claims, and identified independent force-clear, logical-endpoint, hydration, incremental replacement and health-integrity issues. Two raw-count discrepancies were traced to orphan sidecars. The user then requested two changes, but chose to proceed only with the Code Graph repair and park orphan-sidecar prevention as a root exploration. The user explicitly confirmed continuation after specd reported overlaps.

## Open design questions

- Is force authoritative by clearing all incremental/semantic tables, by ignoring them during rebuild, or both defensively?
- Which logical node kinds are valid endpoints for each relation type, and where is that invariant enforced?
- What exact diagnostic/fallback contract applies to unresolved or ambiguous persisted symbol links?
- Should health report corruption separately from stale/incomplete?
- Can coverage projection be made a deterministic phase from canonical persisted spec state after semantic indexing?
- Which overlapping active-change deltas should this change depend on or incorporate rather than duplicate?
