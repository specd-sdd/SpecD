# Exploration: align-spec-optimization-cli-and-agents

## Problem statement

The repository's optimizer agents and workflow skills do not agree with the effective CLI
and project-status contracts:

- The spec-context optimizer uses `specs metadata` to gate work on
  `llmOptimizedContext`, but spec metadata output does not expose effective project
  configuration.
- The spec-context optimizer documents direct `--optimized-description` and
  `--optimized-context` flags for `specs optimizations set`, while the implemented CLI
  and current `cli:spec-optimizations` spec require `--input <json-file|->`.
- The archive skill checks `approvals.llmOptimized`, but `project status` exposes the
  effective setting as top-level `llmOptimizedContext`.
- The project-context optimizer requires a configuration gate without naming the
  authoritative command or output field.
- Template tests only assert broad keyword presence, so invalid commands and field paths
  pass.

The user explicitly requested a new change and asked that the CLI itself be corrected,
not only the consuming templates.

## Confirmed scope

- Add ergonomic direct optimization flags to the CLI contract:
  - `--optimized-description <text>`
  - `--optimized-context <text>`
- Preserve `--input <json-file|->` compatibility and its suitability for complex or
  multiline JSON input.
- Reject ambiguous mixed use of direct set flags and `--input`.
- Align `clear` with direct field flags while considering `--field` compatibility during
  design.
- Gate optimizer work through `specd project status --format toon` and read the top-level
  `llmOptimizedContext` field.
- Keep `specs metadata` for materialization diagnostics (`source`, `regenerated`,
  warnings, normalized metadata), not effective project configuration.
- Correct the archive skill, both optimizer agents, generated/installed copies, and
  command documentation.
- Strengthen tests to assert executable commands and exact output field paths.

## Relevant specs and contracts

### Specs in change

- `cli:spec-optimizations`
  - Current spec defines:
    `specs optimizations set <spec-id> --input <json-file|->`.
  - Input JSON keys are restricted to `optimizedDescription` and `optimizedContext`.
  - Current clear signature uses repeated
    `--field optimizedDescription|optimizedContext`.
  - CLI handlers must delegate mutation/freshness logic to the Kernel.
- `skills:agents`
  - Optimizers must inspect effective project configuration before writing.
  - Optimization must be skipped unless `llmOptimizedContext` is exactly `true`.
  - Optimized fields must be persisted through `specs optimizations set`.
  - Agents must not regenerate metadata after persisting.
- `skills:skill-templates-source`
  - Canonical templates live under `packages/skills/templates/`.
  - Installed runtime files are rendered from these templates.
  - Optimizer templates must declare the `llmOptimizedContext` gate and use lock-owned
    optimization commands.

### Context/dependency specs

- `cli:project-status`
  - Guarantees top-level `llmOptimizedContext` in every status output.
- `cli:spec-metadata`
  - Returns materialized spec metadata plus `source`, `regenerated`, warnings, and
    fingerprint diagnostics.
  - Does not promise effective project configuration.
- `core:get-persisted-spec-optimizations`
  - `get` freshness is derived from persisted optimization baselines, current artifacts,

- `core:update-persisted-spec-optimizations`

- `cli:entrypoint`
  - CLI leaf commands must reject excess arguments and support standard output/error
    conventions.
- `skills:workflow-automation`
  - Agent commands should use canonical plural resource groups and deterministic
    freshness/source mappings.

## Reproduction during exploration

The mandatory context-optimization policy launched specialized optimizers for:

- `core:get-persisted-spec-optimizations`
- `core:update-persisted-spec-optimizations`

Both agents reproduced the same failure:

1. Attempting `specs optimizations set` with the documented direct flags exited with:
   `required option '--input <path>' not specified`.
2. Both successfully persisted through `specs optimizations set <spec-id> --input -`.
3. Final `specs optimizations get` reported both fields fresh with no staleness reasons.

This optimized lock-owned state is a context-maintenance side effect required by the
active skill, not an implementation of this change. No metadata cache files were edited
or explicitly regenerated; subsequent context loading self-healed metadata projections.

## Design considerations

- Direct flags are ergonomic and match existing public documentation and agent
  expectations.
- `--input` remains valuable for multiline Markdown, quotes, and programmatic callers;
  removing it would create needless compatibility and shell-escaping risk.
- The CLI should map every accepted surface to exactly one
  `Kernel.specs.updatePersistedOptimizations` call and must not duplicate Core validation,
  hashing, or persistence.
- Mixing `--input` with direct set flags should fail at the CLI boundary with a typed,
  actionable error.
- Design must decide whether clear's old `--field` form remains as a compatibility alias
  or is deprecated. The user approved considering compatibility rather than requiring
  immediate removal.
- Canonical templates are the source of truth; installed copies should be regenerated by
  the repository's supported sync/install workflow rather than independently edited.

## Testing expectations

- Set one direct field and both direct fields.
- Preserve and test JSON file/stdin input.
- Reject no set value.
- Reject mixing `--input` and direct set flags.
- Clear one and both fields through direct flags.
- If retained, verify `--field` compatibility and reject ambiguous mixed clear syntax.
- Assert exactly one Kernel mutation call with the expected `set` or `clear` payload.
- Template tests should assert:
  - `project status --format toon`
  - top-level `llmOptimizedContext`
  - no config gate through `specs metadata`
  - valid direct optimization flags
  - no `approvals.llmOptimized`
- Update `docs/cli/spec-optimizations.md` in the same change if the final designed
  compatibility/error behavior differs from its current concise usage.

## Rejected or superseded alternatives

- Fixing only the agent gate was rejected by the user; the CLI must also be corrected.
- Treating `specs metadata` as a configuration source is invalid because its contract is
  spec materialization, not project configuration.
- Removing `--input` outright is not the current proposal because it would break the
  implemented structured-input path and make multiline optimized context harder to pass
  safely.
- Running `specs generate-metadata` after optimization is explicitly forbidden; normal
  reads self-heal.

## Open questions for design

- Should `--field` on `clear` remain indefinitely as a supported alias, or be documented
  as transitional compatibility?
- Should direct set flags be considered the primary human/agent interface while
  `--input` is documented as the structured/bulk interface?
- What exact typed CLI error code/message should represent mixed input mechanisms?
- Which repository sync command is authoritative for refreshing every generated agent
  and skill copy after canonical templates change?
