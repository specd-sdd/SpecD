# Exploration Context

## Problem statement

While working on an unrelated change (`persist-spec-context-optimizations`), we tried
to force artifact invalidation by editing a change artifact so the open change would
return to `designing` without a manual lifecycle transition.

Expected:

- content differs from `validatedHash`
- next `changes status` / `get()` detects **artifact-drift**
- auto-invalidate → `drifted-pending-review` / `[!]` and lifecycle back to `designing`

Observed (for the artifact that was saved through the repository API, not a raw disk
edit):

- no `[!]` drift display
- no `artifact-drift` invalidation event for that edit
- artifact ended up as `in-progress` with `validatedHash: null` (no baseline)

This exploration captures that investigation so it can be resumed as its own change.
It is **orthogonal** to `persist-spec-context-optimizations` (SpecListEntry `*Meta`,
`includeMeta`, remove `persistedStateHash`, validate without N×`get()`).

## Naming note

There is **no** use case class named `SaveChangeArtifact` in the current codebase.
The persistence primitive is:

- `ChangeRepository.saveArtifact(change, artifact, options?)`
- FS adapter: `FsChangeRepository.saveArtifact`

If a caller/wrapper was invoked as `SaveChangeArtifact.execute()`, it almost certainly
delegates to `saveArtifact`.

## Confirmed `saveArtifact` behavior

From `specs/core/change-repository-port` and `FsChangeRepository.saveArtifact`:

1. Writes the artifact **file content to disk** (with optional optimistic concurrency via
   `originalHash`, unless `force: true`).
2. Updates the **in-memory** tracked file/artifact status to `in-progress`
   (`setFileStatus` → `ArtifactFile.markInProgress()`).
3. Does **not** write `manifest.json`. The caller MUST call `save(change)` to persist
   the status change.

Important: `markInProgress()` does **not** clear `validatedHash`.

Port wording (paraphrased): after a successful write, reset corresponding status to
`in-progress`; caller persists via `save(change)`.

## Drift detection path (for contrast)

On load (`_manifestToChange` when artifact types are resolved):

- Auto-invalidate only considers files that still have a `validatedHash` (skips
  `undefined` / skipped sentinel).
- For `complete` files, re-hashes disk content (with `preHashCleanup`) and compares to
  `validatedHash`.
- Mismatch → `change.invalidate('artifact-drift', ...)` → typically
  `drifted-pending-review` + sticky `[drift]` + transition toward `designing`.

Verified during this session: editing a still-`complete` specs delta on disk and running
`changes status` **did** fire `ARTIFACT_DRIFT` and transitioned the open change to
`designing`.

## Why some edits do not look like drift

| Edit kind                                                 | Result                                                                                           |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Raw disk edit of a `complete` file with `validatedHash`   | Should auto-invalidate as `artifact-drift`                                                       |
| Checkbox-only edits on `tasks.md`                         | Intentional no-op: schema `preHashCleanup` normalizes `[x]` → `[ ]` before hash                  |
| Artifact already `in-progress` with `validatedHash: null` | No baseline → drift detector skips the file                                                      |
| `saveArtifact` then `save(change)` while complete         | Reopens to `in-progress` **without** an `artifact-drift` history event (manual reopen semantics) |

Also: DAG `effective: in-progress` on a still-`complete` downstream artifact (e.g. tasks)
is **not** content drift — it is upstream incompleteness.

## Suspected bug / design gap (to confirm in this change)

Possible problematic sequences:

### A. `saveArtifact` only (no `save`)

- Disk has new content
- Manifest still says `complete` + old hash
- Next `get()` / `changes status` **should** detect drift

If that sequence was used and drift still did not fire, that is a real detector bug.

### B. `saveArtifact` + `save(change)`

- Disk has new content
- Manifest becomes `in-progress` (hash should remain unless something else clears it)
- No `artifact-drift` event — looks like “reopen”, not drift
- User expectation of `[!]` / invalidate may be unmet even though behavior matches the
  written port contract

### C. `validatedHash: null` after API save

- `saveArtifact` alone should not clear hash
- Seeing `null` implies another path: file never had a hash, reconstruction without hash,
  or a later save that dropped it
- Needs reproduction with a known-complete artifact through the exact caller wrapper
