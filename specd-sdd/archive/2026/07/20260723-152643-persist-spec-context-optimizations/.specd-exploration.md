# Exploration: Persist Spec Context Optimizations

Generated: 2026-07-23

## Problem statement

LLM context optimizations (`optimizedDescription` and `optimizedContext`) are currently stored only in generated `metadata.json`. This makes generated metadata a de-facto source of truth for authored/curated optimization data, which is incorrect: metadata is a generated normalized consumer projection and can be regenerated or become stale independently.

The durable source of optimization state should be the persisted semantic sidecar, `spec-lock.json`. Metadata generation must project that state into `metadata.json` for existing consumers. Staleness must account for both authored spec artifacts and lock state. Spec validation must report stale optimization/metadata deterministically. CLI commands are needed to mutate durable optimization state and persisted dependencies without treating schema artifacts as the only dependency source.

## User intent and preferences

- Explore the whole impact before creating implementation artifacts.
- Move context optimizations out of generated metadata and into spec lock.
- Store hashes and mtimes of spec artifacts in the lock to detect stale optimizations.
- Metadata generation must obtain optimizations from the lock.
- Spec validation must use the lock data to determine staleness.
- Metadata must include a lock-state hash in addition to artifact hashes; the intended repository function was confirmed as `SpecRepository.persistedStateHash(spec)`.
- Consumers may continue reading optimization from metadata, but must treat it as stale when the lock changes.
- Add CLI commands under `specs` to modify lock-owned data, including optimized context and `dependsOn` for schemas that do not declare dependencies in artifacts.
- Archived implementation links already live in spec lock and are not to be reimplemented; they are a precedent for this design.
- After creation, the proposal must be closed carefully; this is explicitly a required next design step.

## Current architecture observations

### Existing spec lock

- `packages/core/src/domain/services/parse-spec-lock.ts`
  - `SpecLockData` currently contains required `schema`, `dependsOn`, and `implementation` fields plus an in-memory `originalHash`.
  - Runtime validation is `specLockSchema`; lock content is JSON.
- `packages/core/src/application/ports/spec-repository.ts`
  - exposes semantic operations: `readPersistedSchema`, `readPersistedDependsOn`, `readPersistedImplementation`, `updatePersistedSchema`, `updatePersistedDependsOn`, `updatePersistedImplementation`, `persistedStateHash`, and `specFingerprint`.
  - generic `artifact()` and `save()` must never access `spec-lock.json`.
- `packages/core/src/infrastructure/fs/spec-repository.ts`
  - reads/writes the sidecar privately and applies optimistic conflict detection with `originalHash`.
  - `persistedStateHash(spec)` is SHA-256 of raw lock bytes or `null` when absent.
  - `specFingerprint(spec)` already incorporates authored artifact content hashes and `persistedStateHash` (or an absent sentinel), excluding generated metadata.

### Existing metadata behavior

- `packages/core/src/domain/services/parse-metadata.ts`
  - `SpecMetadata` currently includes `optimizedDescription` and `optimizedContext` directly.
  - strict, lenient, and permissive schemas all define these fields, but no persisted lock hash field exists.
- `packages/core/src/application/use-cases/generate-spec-metadata.ts`
  - deterministic generator reads persisted dependencies and implementation through repository semantic methods.
  - persisted dependencies win over extraction and are projected into metadata; disagreement is an error.
  - implementation links are projected into metadata.
  - it currently emits artifact `contentHashes` and `generatedBy: 'core'`, but no persisted-state hash or optimization projection.
- `packages/core/src/application/use-cases/update-spec-metadata.ts`
  - current LLM update path does a fresh deterministic metadata generation then merges agent-provided optimized fields and persists the result as `generatedBy: 'agent'`.
  - this is the behavior to replace/redirect: it must update lock-owned optimization state, then metadata must be regenerated as a projection.
- `packages/core/src/application/use-cases/_shared/metadata-freshness.ts`
  - checks only recorded artifact content hashes.
- `packages/core/src/infrastructure/fs/spec-repository.ts:_classifyMetadataFreshness`
  - currently requires all recorded artifact hashes to match and, when available, `metadata.dependsOn` to equal persisted dependencies.
  - it does not yet compare metadata with `persistedStateHash`.
- `packages/core/src/application/use-cases/validate-specs.ts`
  - already fails validation when `metadata.freshness === 'stale'`.
  - already validates metadata `dependsOn` against persisted dependencies and checks artifact-extracted dependencies when the schema declares extraction.

### Existing context consumers

- `packages/core/src/application/use-cases/compile-context.ts`
  - reads metadata via repository; in full mode it only renders from metadata when `freshness === 'fresh'`, otherwise falls back to extraction and emits `stale-metadata`.
  - when optimized context is enabled, it renders `metadata.optimizedContext` only as part of the fresh metadata path.
  - it emits `stale-optimization` only when the optimized field is missing, not when it is lock-stale independently.
- `packages/core/src/application/use-cases/get-spec-context.ts`
  - same consumer shape: it uses optimized metadata only for fresh metadata and produces a minimal stale entry otherwise.
  - it emits missing-optimization warnings but current freshness has no lock check.

### CLI surface today

- `specs update-metadata <specPath>` (`packages/cli/src/commands/spec/update-metadata.ts`) accepts JSON/YAML with optimized fields and delegates to `UpdateSpecMetadata`.
- `specs generate-metadata [specPath] --write [--all --status ...]` performs deterministic extraction and writes metadata.
- `specs metadata <specPath>` displays artifact-hash freshness but does not display/combine lock freshness.
- `specs write-metadata` persists an entire metadata document and should remain constrained to generated/projection workflows or be reviewed for compatibility.
- No `specs` command currently mutates persisted dependencies independently of a change manifest, and no command mutates persisted optimization state.

## Recommended design direction

1. Extend lock semantics, not generic artifacts. Add an optional durable optimization block to `SpecLockData`, with `optimizedDescription` and/or `optimizedContext` plus an artifact baseline. The exact JSON shape and versioning/migration policy must be decided in the proposal.
2. Store an artifact baseline per relevant schema artifact: authoritative SHA-256 content hash and diagnostic `mtime`/last-modified stamp. Hash is the semantic freshness criterion; mtime is a fast diagnostic/cache hint and must not be the sole freshness proof.
3. Add semantic repository APIs for lock-owned optimization state and a single atomic persisted-state patch/update operation if needed. Do not expose raw sidecar shapes to application use cases.
4. Make `GenerateSpecMetadata` project lock optimizations and record the exact `persistedStateHash` used for the projection. Preserve existing projection of `dependsOn` and implementation links.
5. Add `persistedStateHash` to strict/lenient/permissive metadata types. Metadata freshness requires artifact hashes, persisted `dependsOn` projection, and equality between recorded and current persisted-state hash. Define legacy behavior: absent lock hash makes metadata stale for specs with a lock, while legacy lock-less specs can retain existing migration/backfill behavior.
6. Validate optimization baseline in `ValidateSpecs`: report stale optimization when recorded artifact baseline does not match current required spec artifacts. The current metadata stale failure should surface stale lock projections as well.
7. Keep `CompileContext` and `GetSpecContext` consuming metadata only. Once repository freshness incorporates the lock hash, they automatically reject stale optimized content. Improve warnings so a stale/missing lock optimization is distinguishable from missing optimization.
8. Preserve the existing rule that schemas without `metadataExtraction.dependsOn` still get canonical dependencies from persisted lock state and metadata projection. Do not require artifacts to store `dependsOn`.

## Candidate CLI contract (needs proposal decision)

- `specs update-optimization <specPath>`: accepts only `optimizedDescription` / `optimizedContext`; captures current required artifact hashes and mtimes; atomically updates lock state with conflict detection. It may optionally regenerate metadata, but that side effect must be explicit in the final contract.
- `specs optimization <specPath>`: read-only inspection of persisted optimization, artifact-baseline comparisons, and stale reasons.
- `specs deps <specPath> --set <ids> | --add <id>... | --remove <id>...`: updates persisted `dependsOn` in the lock. This is useful especially when schema artifacts do not declare dependency extraction.
- Rework `specs update-metadata <specPath>`: preferred migration is deprecate it in favor of `update-optimization`, or keep it as a compatibility alias with a clearly documented lock-write + metadata-generation sequence. It must not preserve metadata as the authoritative optimization store.
- Enhance `specs metadata <specPath>` to display lock projection freshness and stale reason(s), including current/recorded persisted-state hash.
- Keep `specs generate-metadata` as deterministic metadata projection/rebuild. It must never mutate optimization state in the lock.

## Impact and risk

- `GenerateSpecMetadata` is CRITICAL in the code graph: direct/indirect impact includes `ArchiveChange`, kernel composition, update-metadata composition, and extensive archive/generator tests.
- `UpdateSpecMetadata` has MEDIUM impact, confined to kernel composition and its tests, but its behavior changes materially.
- `ValidateSpecs`, metadata freshness, and context compilation cross package boundaries and cache fingerprints. The validation cache already includes `specFingerprint`, which includes persisted lock state; behavior/specs must ensure cache engine/version treatment remains correct after new semantic checks.
- Archive publication already stages canonical artifacts and spec-lock before generating metadata. The proposal must specify ordering so lock state is finalized before metadata snapshots its `persistedStateHash`.

## Decisions made

- Durable truth for optimization: spec lock, not metadata.
- Metadata remains the canonical normalized consumer projection; consumers should not read lock directly.
- Lock hash must participate in metadata staleness.
- Hash is authoritative; mtime is retained only as an auxiliary signal.
- Existing implementation-link lock behavior is out of scope except as a compatible precedent.

## Open questions for proposal

1. Exact lock JSON: a single `optimization` block vs independently versioned `optimization` object; optionality and legacy/migration behavior.
2. Whether metadata contains `persistedStateHash` at top level or a namespaced projection field, and whether it records optimization artifact baseline separately for diagnostic output.
3. Artifact baseline scope: all present spec artifacts vs only schema-required artifacts vs only artifacts read by optimization. Existing metadata freshness uses recorded files and needs tightening to ensure required resolved outputs are covered.
4. Atomicity: whether `update-optimization` must regenerate metadata in the same command/transaction or deliberately leave metadata stale until `generate-metadata` runs. Strong preference: make the state transition explicit and never serve stale optimization; atomic regeneration is preferable if repository boundaries permit it.
5. Conflict protocol for lock updates: use persisted lock `originalHash` / `persistedStateHash` and support `--force` only when explicitly desired.
6. `specs deps` lifecycle boundaries: direct persisted-state mutation vs change-scoped `changes deps`; document that the latter controls a work-in-progress manifest while the former owns canonical archived state.
7. Backward compatibility of `specs update-metadata` and `specs write-metadata`, including whether write-metadata may accept optimized fields after this change.
8. Need for a distinct optimization freshness status/reason model instead of folding every case into generic metadata `stale`.

## Conversation flow

1. User identified the architectural problem: optimizations are currently stored in generated metadata and should live in spec lock.
2. User requested stale detection from artifact hashes/mtimes, lock-aware metadata generation and validation, continued metadata-based consumers with lock-aware stale handling, and CLI commands for lock mutation and schema-independent dependencies.
3. Exploration verified that `spec-lock.json`, semantic repository APIs, persisted implementation links, persisted dependency projection, artifact metadata freshness, validation failures, and context-consumer freshness gates already exist.
4. Proposal direction settled on extending those existing semantic boundaries rather than exposing sidecars as artifacts or rewriting consumers to read locks directly.
5. User approved creation of this change and emphasized that the subsequent proposal must be fully closed.
