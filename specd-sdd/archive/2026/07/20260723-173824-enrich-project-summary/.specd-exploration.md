# Exploration: enrich-project-summary

Generated: 2026-07-23

## Problem statement

`project status` (via `GetProjectSummary` → `buildProjectStatusSnapshot` → CLI) today returns only change-bucket **counts** and per-workspace spec counts. The entry skill and tooling still need a second round of `changes list` / `drafts list` (and later task counts / specs health) to present useful welcome state.

User wants `GetProjectSummary` extended so that, when explicitly requested, it can also return:

1. Listings of **active** and **draft** changes (not discarded/archived), each with **name**, **state**, and **pending/total tasks**
2. **Specs health** (from existing `GetSpecsHealth`)

Without the new flags, behaviour must remain exactly as today (count-only).

## Approach / solution outline

- Evolve **`GetProjectSummary`** (user initially said "GetProjectStatus" by mistake; corrected to `GetProjectSummary`).
- Add optional input flags (names tentative):
  - `includeChanges?: boolean` — populate `active[]` and `drafts[]` with name, state, tasks `{ incomplete, total }`
  - `includeSpecsHealth?: boolean` — populate `specsHealth` from `GetSpecsHealth`
- Default / no flags → same `GetProjectSummaryResult` fields as today; no list materialization, no health validation.
- Propagate flags through:
  - `sdk:build-project-status-snapshot` (`BuildProjectStatusSnapshotOptions` + result shape)
  - `cli:project-status` (CLI flags such as `--changes`, `--specs-health` — exact names TBD in design)
- Tasks sourced from **`CountTasks`** (`kernel.changes.countTasks`) aggregate `total.incomplete` / `total.total` (not full `byArtifact` map in the summary listing).
- Discarded and archived remain **counts only** (no listings).

## Design decisions (confirmed)

1. **Target use case:** `GetProjectSummary` (not inventing `GetProjectStatus`).
2. **Opt-in via flags:** both change listings and specs health behind flags; without flags, act as today.
3. **Listings:** active + drafts only; no discarded/archived item lists.
4. **Per-change fields:** name, state, tasks `{ incomplete, total }` (pending = incomplete from `CountTasks.total`).
5. **Wait for CountTasks:** user deferred creation until `refactor-task-completion` finished; confirmed landed before create (2026-07-23 evening).
6. **Spec overlap accepted:** `sdk:build-project-status-snapshot` also targeted by `deprecate-ladybug-store` (designing). User chose to proceed with overlap (option 1). Archive may be blocked until resolved.

## Agreements reached

- Enrich summary rather than only SDK/CLI glue — core owns the richer optional contract.
- Preserve count-only default path (performance / existing callers).
- Tasks shape default: `{ incomplete, total }` not full `TaskCompletionStatus` with `complete` unless design revisits.
- Flag names for use-case input and CLI not finalized — propose in design (`includeChanges` / `includeSpecsHealth` and `--changes` / `--specs-health` as working names).

## Key codebase observations

### Current `GetProjectSummaryResult` (count-only)

```
activeCount, draftCount, discardedCount, archivedCount, specsByWorkspace, workspaceCount
```

Uses `ChangeRepository.count()` / `countDrafts()` / `countDiscarded()`, `ArchiveRepository.count()`, per-workspace `SpecRepository.count()`. Explicitly MUST NOT call list use cases solely to measure `.length`.

### Current snapshot

`BuildProjectStatusSnapshotResult`: `{ summary, graphHealth, approvals, llmOptimizedContext, hotspots? }`

### `GetSpecsHealthResult`

Aggregates `totalSpecs`, `passed`, `failed`, `warned` + `issues[]` (only failing/warned specs). Invokes `ValidateSpecs` internally — justify flag.

### `CountTasks`

Accepts a `Change`; returns `byArtifact` + `total: { complete, incomplete, total }`. Schema must materialize `taskCompletionCheck`; use case does not invent fallback patterns. Exposed as `kernel.changes.countTasks`.
