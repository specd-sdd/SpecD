# Exploration: verify-scenario-gwt-list-validation

Generated: 2026-11-10

## Problem statement

Agents sometimes author `verify.md` scenarios without Gherkin list items (`- GIVEN` / `- WHEN` / `- THEN`). Structural validation still passes because it only requires `#### Scenario:` headings under `### Requirement:` blocks. Metadata extraction (`metadataExtraction.scenarios`) looks for `list-item` nodes matching `^GIVEN\b` / `^WHEN\b` / `^THEN\b`, so malformed scenarios produce objects with empty `given` / `when` / `then` arrays — silently. The user wants schema-level detection so invalid format fails validation instead of yielding empty extracted scenarios.

## Approach / solution outline

Harden `@specd/schema-std` `verify` artifact validations with nested `children` under each `Scenario:` section:

- Require at least one `list-item` matching WHEN
- Require at least one `list-item` matching THEN
- GIVEN remains optional (`required: false`) per current contract
- Optionally reinforce `deltaValidations` so added/modified verify deltas that introduce scenarios also carry WHEN/THEN list content (today only asserts `#### Scenario:` presence for requirement deltas)
- Clarify authoring `instruction` text that currently says "Never three, never bullets" — ambiguous; agents may interpret as "do not use bullet lists for GWT clauses", which breaks extraction. Clarify that "never bullets" refers to scenario _headings_ (must be `####`, not bullet titles), while scenario _body_ MUST use list items for GWT.

No new Core validation engine feature is required: AST `validations` with `type: list-item` + `required`/`count` already support this (documented in `specd guide selectors` — Validation rules / nested structure / cardinality).

There is no "extracted field must be non-empty" post-extraction check today; structural AST validation is the correct lever.

## Design decisions (confirmed / agreed)

1. **Detect via schema validations, not post-extraction metadata checks.** Nested list-item rules under Scenario.
2. **WHEN and THEN required; GIVEN optional** — matches current prose contract and template comments.
3. **Bold markers:** Official verify content uses `- **GIVEN** …`. Extraction already succeeds (metadata for `schema-std:standard-schema` has populated given/when/then). Matcher `^GIVEN\b` works because list-item labels strip emphasis — confirm during design when writing matchers; if needed use a regex that tolerates optional `**` around keywords for defensive matching.
4. **Include both schema-std specs** in the change: standard-schema for the rule; templates as companion (expected no-op or minor guidance tweak).
5. **Change name:** `verify-scenario-gwt-list-validation`
6. **Description:** Fail verify validation when scenarios lack GIVEN/WHEN/THEN list items so empty extracted scenarios are blocked

## Rejected / deferred alternatives

- **Post-extraction emptiness validation on metadata fields** — not supported by schema format today; would be a Core feature. Deferred; structural validation is enough.
- **`contentMatches` only on Scenario body** (e.g. `(?s)WHEN[\s\S]*THEN`) — weaker; does not force list-item nodes that the extractor requires. Prefer list-item children; contentMatches only as optional supplement for deltas.
- **Making GIVEN required** — rejected for now; contract and template mark GIVEN optional when precondition is obvious.

## Open questions for /specd-design

1. Exact `matches` regex for list items — `^WHEN\b` vs `^(?:\*\*)?WHEN(?:\*\*)?\b` vs relying on AST plain label (preferred if parser strips bold).
2. Should `deltaValidations` require WHEN/THEN list lines inside scenario content for added/modified verify deltas, or is full-file `validations` after merge/preview enough?
3. Version bump of `schema.yaml` `version` integer — confirm project convention when tightening validations (breaking for existing malformed verify files in the wild / this repo).
4. Repo-wide impact: after tightening, do any existing `specs/**/verify.md` fail validation? Design/implement should sample or run validation; may need a remediation pass outside this change or a soft warning first (`required: false`) — user asked for detection; default intent is hard fail (`required: true` for WHEN/THEN). Confirm hard vs warning.
5. Clarify instruction wording around "never bullets" — agreed as needed; exact copy TBD in design.
