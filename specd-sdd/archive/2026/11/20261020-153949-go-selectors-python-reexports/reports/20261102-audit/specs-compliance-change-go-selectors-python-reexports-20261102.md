## Verdict summary

Core happy paths (call/construct/type facts, resolveImports qualifiedTargets, buildRelations, no name search, unexported stays unresolved, no step without local binding, cross-workspace) are IMPLEMENTED and TESTED. Real defects found:

1. (code vs spec, MEDIUM) Shadowing detection is incomplete and position-insensitive (A:121-208, 1319-1368). Probed:
   - Emits a fact (so can create a FALSE edge if `auth` is an imported namespace) when the qualifier is shadowed by: named result `func f() (auth int)`; grouped local `var ( auth int )` (tree-sitter var*spec_list not walked, A:159-167); `for *, auth := range`; `if auth := g(); ...`; `switch auth := v.(type)`.
   - Suppresses a legitimate fact (FALSE negative) when the shadowing declaration comes AFTER the use in the same block (`auth.A(); auth := 1`), because block bound-names are collected for the whole block, and for a parameter named like the package used in a parameter TYPE (`func f(auth int, x auth.User)`, Go scopes params to the body).
   - Local type declarations (`type auth struct{}`) are not treated as bindings.
     Spec text (go "Package identity..." and verify "Shadowing applies to every fact kind") lists "parameter, result, receiver, local variable, or local declaration". Code covers parameter, receiver, `:=`, plain `var`/`const` only. Fix is in code (spec is right).
2. (spec/code gap, MEDIUM) Resolution step is lost whenever the namespace name differs from the import's local binding name. goNamespaceBindings looks up the file-scope Namespace local binding by the NAMESPACE name (A:1251-1256) but the binding is created under `imp.localName` = last path segment or alias (A:958-969, 1708-1713). Probe: `import "github.com/acme/go-auth"` (package auth) and `.../auth/v2` resolve the target (qualifiedTargets=1, fileImports=1) but produce 0 steps and the local binding `go-auth` / `v2` keeps targetId undefined; plain `.../auth` gives 1 step. This is spec-literal ("namespace without such a binding contributes no step") but defeats the purpose for exactly the declared-name/versioned cases. Either the spec should say the step is anchored on the import's own local binding (code should look up by `imp.localName`/specifier), or accept. No test asserts steps for these cases.
3. (spec wording) language-adapter "Qualified reference resolution" says missing `sourceSymbolId` blocks only `call`/`construct`; code (A:1199) blocks all three kinds (a USES_TYPE relation cannot exist without a source anyway). Spec should say "any kind". Test only covers call/construct.
4. (undocumented behaviour) Two resolved imports yielding the same namespace name are both dropped (A:1246-1249). Not in spec (Go compile error anyway); harmless but unspecified/untested.

### R1. Requirement: Imports and package resolution (modified paragraph set)

1. Re-export route names resolve for `from pkg import X` through entry-file route. OK.
   - IMPL 1477-1493 -> context.resolvePackageExport; RESOLVER 80-136 reads public bindings of entry surface (which include linked route bindings added by INDEXER via session.addReferenceFacts).
   - Scenario "Re-exported name resolves through the entry file": T (IT: binding.targetId contains 'auth' and import:package step; UC 84-116: User and `User as ViaInit` via `__init__` resolve to the same target as `acme_auth.models.User`, IMPORTS relation, step). UT 1953-1976 unit-level (Tw: only `importMap.has('User')`, does not assert target is models.User).
2. `import:package` step. OK. RESOLVER 135 builds step; IMPL 1491 pushes it.
   - Discrepancy (minor, code vs spec): step is pushed only `if (localBinding !== undefined)` where localBinding must be scopeId==='module' (IMPL 1478-1491). A resolved import whose local binding is not module-scope (e.g. an import inside a function, if extracted as an import) gets importMap entry but NO step, with `localBindingId ''`. Spec says "Resolved package imports SHALL return an import:package step". Either relax the spec ("module-scope imports") or push a step regardless. Low severity.
   - Test: T for module-level (IT, UC 107, UT 1975).
3. Submodule fallback (`not-exported` or `no-entry-surface` -> file dependency, no binding; several indexed files -> `ambiguous` diagnostic). OK. IMPL 1494-1519.
   - T: UC 118-144 (models submodule becomes IMPORTS, `Helper` stays unresolved and util.py not imported). Case "pkg has no **init** at all" and "more than one under different roots" (ambiguous diagnostic): Tx (no test found).
   - Note (spec wrong vs code wrong): spec limits ambiguity to "different roots"; code also reports ambiguous when `X.py` and `X/__init__.py` both exist under the SAME root (entrySurface returns both). Python itself prefers the package. Spec is silent, so spec incomplete; low severity.
4. Scenario "Plain import in an entry file is not a route". OK by construction: extractReExports only looks at `import_from_statement` children of the module (IMPL 978-980); `import acme_auth.models` produces nothing; `from acme_auth import models` gets no public binding -> `not-exported` -> submodule file dependency (IMPL 1494-1503).
   - Tx: no test has `import acme_auth.models` in an `__init__.py` followed by `from acme_auth import models`. UT 1881-1893 includes `import models` in a combined test, but only asserts nothing is published by linking (and nothing would be published anyway: `import_statement` is never read), not the resolution outcome. UC 118 has an empty `__init__.py`, so it is not the scenario.
5. Absolute same-package/other package, tie to `packageResolution` (matchSpecifier, entrySurface, pyproject, src layout, stub/source precedence, ambiguity of normalized identities). OK (IMPL 577-606, 2494-2506). Not audited in detail here (pre-existing, outside this delta); entrySurface candidate order and `.pyi` filtering at 597-599 match the spec text. `pythonModuleCandidates` (IMPL 427-437): module path "" -> `__init__.py`,`__init__.pyi`; otherwise `.py`,`.pyi`,`/__init__.py`,`/__init__.pyi` - matches spec (module file, stub, package + stub). Tx for direct unit test of pythonModuleCandidates (private function), indirectly covered by src-layout tests (UT 1840, 1978) and UC.
6. Spec statement "The adapter MUST NOT search symbols by name in the target workspace": linkReExports looks up only public bindings by surface+name (IMPL 1142-1150, 1172) = declared surface, not name search. OK. BUT relative `from .x import y` resolution in resolveImports (IMPL 1432-1444) uses `session.findSymbolsByFile(candidate).find(name)`: a lookup by name within one resolved file, not in workspace; not a violation. Consequence: a RELATIVE import of a re-exported name (`from . import User` / `from .. import User` where target `__init__` re-exports it) does not follow routes (falls to submodule path and stays unresolved). Spec only requires absolute imports to follow routes ("A non-relative absolute import SHALL resolve through the shared package import helpers"), so compliant, but note as a functional gap if relative-import-of-barrel is intended.

### R3. Static `__all__` classification details (spec: "`=` or `+=` of a list or tuple literal whose elements are all string literals, or `+` concatenation")

- Annotated assignment `__all__: list[str] = [...]` : treated as static (tree-sitter `assignment` node; IMPL doc 1018). Spec does not mention annotated assignment explicitly; behaviour is reasonable and consistent with "assignment ... `=`". Test: UT 2016 T. Spec gap: add annotated form to spec text (spec silent; code not wrong).
- Tuple literal: T (UT 2000, parenthesized with trailing comma).
- Edge discrepancies (verified with ast-grep parse):
  1. Unparenthesized tuple `__all__ = "A", "B"` parses as `expression_list`, not `tuple`, so it is classified DYNAMIC (no routes published). Spec says "tuple literal"; strictly an unparenthesized tuple is a tuple literal. Code too conservative (or spec should say "parenthesized"). Tx.
  2. Bytes literal `__all__ = [b"A"]` is accepted as a name (plainPythonString only checks kind `string`, 1112-1117). Harmless but not "string literal" in the spec sense. Tx.
  3. `other.__all__` / `mod.__all__ = ...` (attribute) make the file dynamic because any identifier named `__all__` counts (1027). Spec: "Any other reference to `__all__` in the file"; consistent, though arguably over-broad. Tx.
  4. `__all__` assigned inside `if`/`try` at module level is dynamic (parent not module, 1057-1060); spec says "every assignment ... in the module body" - consistent. Tx.
  5. Empty `__all__ = []` is static with zero names, so all routes are suppressed (1158-1162). Consistent with spec. Tx.
- Duplicated `__all__` assignments accumulate (`names.push` + dedupe, 1032, 1039-1046): matches "every assignment".

### R4. Other conditions from the spec

- "Route whose reached module resolves to more than one file MUST NOT produce a binding": OK, `kept.length === 1` (IMPL 1257) after dropping `.pyi` shadowed by a source (1254-1256). Tx (no test where `models.py` and `models/__init__.py` both exist, or `.py` + `.pyi`).
- "Route whose reached module does not publish name": OK (targets.size !== 1 -> continue, 1176). Tx for dedicated test (UT 1953 `Hidden` is not an import in the entry at all).
- "Routes reached through another entry's routes followed": OK via `lookup` that includes `created` (1142-1150). T (UT 1864, weak).
- Both symbol spaces (value and type) handled, 1171. Spec silent; fine. Class routes are `type`; no test for function (value) route.
- Both `__init__.py` and `__init__.pyi` present: both files are processed as entries (files list, 1127-1137) and share one surface; the spec's "only the source file is an entry" is applied in entrySurface but linkReExports does not exclude the `.pyi` twin; conflicting `__all__` in the two files would mix. Tx; low severity (edge).
- Name collision: if an entry both declares and route-imports the same name (different targets), both bindings exist; only same-target dedupe at 1179-1182, so import resolution later reports `ambiguous`. Spec silent.
- Absolute route resolution requires an entry in `packageToWorkspace` (a pyproject name matching the first segment, after normalization). A package whose pyproject name differs from the directory name never gets absolute routes. Consistent with the spec ("through the packageResolution facet") but worth knowing. Relative routes work without packageToWorkspace (UT passes an empty map).
