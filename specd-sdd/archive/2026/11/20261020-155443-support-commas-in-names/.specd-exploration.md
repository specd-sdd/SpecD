# Exploration: support-commas-in-names

> Created as `support-commas-in-names` on 2026-10-20. It replaces the draft `reject-commas-in-paths-and-spec-ids`, whose direction (reject) was reversed to support every case.

## Problem

Several CLI options take comma-separated lists. Their values are split on `,` before they reach the use cases, so a name that contains a comma becomes two names that do not exist.

Observed (2026-10-20): `specd changes implementation ignore|resolve <change> --file <list>` could not handle the tracked file `SpecD — Análisis de identidad LogicalSymbol, dependencias y casos de uso.md`. The CLI split it into `SpecD — Análisis de identidad LogicalSymbol` and `dependencias y casos de uso.md` and failed with `Implementation file "dependencias y casos de uso.md" does not exist`. The file had to be marked `ignored` by editing the change `manifest.json` by hand.

## Where the defect is, and where it is not

- **Not in detection.** The VCS detector reads git with `-z` (`git diff -z`, `git ls-files -z --others`) and splits on `\0` (`packages/core/src/infrastructure/git/vcs-adapter.ts`). A name with a comma arrives intact and is stored as one item. Git allows commas in file names. Detection must keep working this way.
- **In how names come back in.** The input path turns a string into names by splitting on commas: `packages/cli/src/commands/change/implementation.ts` (`f.split(',')` over `--file`), plus the other comma-list options listed below. A user (or a skill) has no way to pass one name that contains a comma.
- **The asymmetry.** The system can record a file the user cannot then ignore, resolve, or link. Every case below must work.

## Known comma-splitting sites (confirm and extend during design)

- `packages/cli/src/commands/change/implementation.ts`: `--file` of `add`, `ignore`, `resolve`.
- `changes edit --add-spec | --remove-spec`, `changes create --spec`, `changes deps --add | --remove | --set`: check whether they split, and what they do with a value that has a comma.
- `packages/cli/src/helpers/parse-comma-values.ts` (`parseCommaSeparatedValues`) and its callers.
- Closed-vocabulary options where a comma cannot occur in a valid value (`graph impact --type`, file categories in `graph index`): only the error message may need care.
- Search for more: anything that accepts a comma list of paths, spec ids, symbols, workspaces, or change names.

## Cases to support

1. **Intact names through the CLI.** One path or spec id that contains a comma must be passable. Candidate mechanisms (combine as needed; decide in design):
   - Repeatable options: `--file a --file "b, c"`: each occurrence is one whole name, never split. Define whether the comma-list form stays for compatibility.
   - Exact match first: for `ignore`, `resolve`, and `remove`, a value that equals a known name exactly (tracked file, existing spec id) is taken whole before any splitting. This alone fixes the observed failure without changing syntax. Risk: a value like `a,b` is ambiguous when both `a`, `b`, and `a,b` exist; define the precedence and report the ambiguity.
   - An escape (`\,`) in the comma-list form.
   - A list from stdin or a file, delimited by NUL or newline (`--files-from -`), for scripts and skills that already hold a list.
2. **Hosts other than the CLI.** MCP tools, the SDK, and any JSON/TOON input must pass arrays of names, never a joined string. The use cases take `string[]` and never split. The split belongs to one shared, tested CLI helper.
3. **Output that lists names.** Text output prints `open: a, b, c`: ambiguous when a name has a comma. Decide the rule (one per line, quoting, or a count plus a list), and keep JSON/TOON as arrays.
4. **Spec ids and spec paths.** Check `core:spec-id-format`: does it accept a comma today? Decide whether a comma is valid in a capability path. If valid, every spec-id option must support it (cases 1-3). If invalid, creation must say so clearly, and the error for a split value must explain that the value was split. Do not leave both behaviours.
5. **Other awkward characters.** A name can also contain a leading or trailing space (the current code trims), a quote, a backslash, a newline, non-ASCII text (as above), or Windows separators. List the ones that must be preserved and test them. Trimming must not alter a name that the system recorded.
6. **Error messages.** A failure on a split value must show the original value and say that it was split on commas, so the cause is visible (today the message names only a fragment).
7. **Stored data.** `manifest.json`, history, and implementation links hold names as JSON strings: check that nothing joins or re-splits them elsewhere (for example when printing, hashing, or comparing).

## Test matrix (to refine in design)

For each option that takes names: one name; several names; a name with a comma; a name with a comma next to another name; a name with a leading and a trailing space; a non-ASCII name; the same through each mechanism chosen in case 1; and the equivalent array input through the SDK.

## Questions to settle in design

- Which mechanisms from case 1 do we ship? Proposal: use-case-level `string[]` everywhere; repeatable options that never split; exact-match-first for `ignore`/`resolve`/`remove`; keep the comma-list form for compatibility with the existing skills and scripts; and a stdin list for bulk use.
- Should the comma-list form be deprecated once repeatable options exist?
- Do the skills (`specd-implement`, `specd-design`) that generate `--file a,b,c` need to change to repeatable options?

`core:update-implementation-tracking`, `cli:change-implementation`, `core:edit-change`, `cli:change-edit`, `core:spec-id-format`. Probably also the `changes deps` command spec and the MCP and SDK specs for any list input. No overlap warning at creation.

## Scope extension (2026-11-03): dependency commands, spec ID validation and lock repair

Added after a real incident while using `specd changes deps` in the change `global-cross-platform-convention` (archived 2026-11-03). The user decided to fold it into this change rather than open separate ones, because this change already has to decide what a valid spec ID is (case 4 above) and already lists `changes deps --add | --remove | --set` as a site to review. The change name no longer covers everything; the CLI cannot rename a change, keep the name and rely on the description.

### The incident

- Needed to remove the dependencies of a spec in a change. `changes deps` has `--add`, `--remove`, `--set` but no `--clear`, and `--set` needs a value, so the call used `--set ""`.
- That stored an empty spec ID: `changes deps <name> default:_global/cross-platform --set ""` printed `dependsOn: ` and succeeded.
- At archive the empty ID was copied into `specs/_global/cross-platform/spec-lock.json` as `"dependsOn": [""]`.
- Every read of that lock then failed with a raw `ZodError` ("must be a valid spec ID (capabilityPath or workspace:capabilityPath)", path `dependsOn.0`), printed as a pino `fatal` dump with a stack trace. `specd specs metadata` and `specd specs deps clear` both failed on it. The fix was a hand edit of `spec-lock.json` to `"dependsOn": []`, done outside the workflow with explicit user consent.

### Defects (verified in code, 2026-11-03)

1. **ID validation is a no-op on write.** `packages/core/src/application/use-cases/update-spec-deps.ts`: `validateDepIds` calls `parseSpecId(id)` ("Throws on invalid format — actually parseSpecId doesn't throw, it's lenient" says the code comment). `packages/core/src/domain/services/parse-spec-id.ts` only splits on the first `:`. So `""`, whitespace, `:` and `ws:` are accepted by `add` and `set` and stored in the change. The persisted lock schema (Zod, `parseSpecLock`) is strict, so the invalid value is only noticed on read, after it was persisted. Check the same gap in `core:update-persisted-spec-deps` (`update-persisted-spec-deps.ts`), `edit-change.ts` (`--add-spec`, `--remove-spec`) and `changes create --spec`.
2. **`changes deps` cannot clear.** `packages/cli/src/commands/change/deps.ts` exposes `--add`, `--remove`, `--set` only. `specd specs deps` has `clear`, and the shared helper `_shared/apply-depends-on-mutation.ts` already supports `clear: true`, but `UpdateSpecDeps` and the CLI command do not expose it. There is no way to say "no dependencies" for a spec in a change.
3. **An invalid lock cannot be repaired by the CLI.** `FsSpecRepository._readSpecLock` -> `parseSpecLock` throws a raw `ZodError`, not a `SpecdError`, so the user sees a stack dump, and the repair commands (`specs deps clear`, `specs deps set`) read the same lock first and fail. `_global/error-handling-conventions` requires a typed `SpecdError` with an actionable message for expected failures.

### Direction (to settle in design)

- One shared validator for spec IDs in core, used by every use case that accepts IDs: reject empty or blank, a missing workspace or capability path, and anything `core:spec-id-format` rejects. Decide in the same place whether a comma is valid in a capability path (case 4). Validation happens in the use case, not only in the CLI, so MCP and SDK get it too.
- Add `--clear` to `changes deps` (mutually exclusive with `--add`, `--remove`, `--set`) and a `clear` input to `UpdateSpecDeps`, reusing `applyDependsOnMutation`.
- Reading a spec lock: a validation failure becomes a typed `SpecdError` (code UPPER_SNAKE, names the spec and the field path, says how to repair). Decide whether the repair commands (`specs deps clear|set`, `specs init`) read the lock leniently so they can fix an invalid `dependsOn`, or whether a dedicated repair path is needed. Do not silently drop invalid entries.
- Decide what happens to existing locks that already hold invalid IDs: detect on read and report, never rewrite silently.

### Decisions agreed in design conversation (2026-11-03)

- **Canonical spec ID format (cross-platform), to be written into `core:spec-id-format`:** workspace `^[a-z][a-z0-9-]+$` (2+ chars, so `c:` is never read as a Windows drive); capability-path segment `^[a-z0-9_][a-z0-9_-]*$`, never a Windows device name; no `.`, spaces, commas or uppercase. Commas are NOT valid in spec IDs; the comma defect only concerns file paths (`--file`). Today there are 5 divergent rules: core `parseSpecId` (none), CLI `parseSpecId` (workspace exists only), Zod in `parse-spec-lock.ts` and `parse-metadata.ts` (strict, duplicated), `SpecPath.parse` (permissive).
- **One shared validator in core** (domain, no I/O): `validateSpecId(id, { workspaces?, defaultWorkspace? })` returns `{ workspace, capPath, specId }` fully qualified. Without `workspaces`: syntax only (Zod lock/metadata). With `workspaces`: also checks the workspace exists (`WorkspaceNotFoundError`, lists known ones; bare IDs check the default workspace). Typed `InvalidSpecIdError` (`INVALID_SPEC_ID`). Everything delegates to it: `SpecPath`, both Zod schemas, `UpdateSpecDeps`, `UpdatePersistedSpecDeps`, `EditChange`, `CreateChange`, CLI `parseSpecId`, and `ConfigLoader` workspace-name check. `remove` does NOT validate syntax, so an invalid stored ID can still be removed.
- **Existence rules:** `changes deps` (change level): target may be a spec that does not exist yet (it can be created by the change); validate syntax + workspace only, no error when the spec is missing. `specs deps` / `UpdatePersistedSpecDeps` (persisted level): always acts on existing specs and cannot point to future or missing ones; dependency targets MUST exist (a future dependency belongs in the change, not in the lock).
- **`--clear`:** added to `changes deps` and also `specs deps clear` gets the same behavior. Confirmation follows `project init`: interactive confirm on TTY, `--force` skips it, no TTY and no `--force` fails with a clear error. No `--yes` (not used anywhere in the CLI). Confirmation lives in the CLI, the use case only receives `clear: true`.

- **Comma handling for names, cut at the root (no compatibility):** no CLI option that takes names splits on commas, and there is no smart or quote-aware splitter, no escape, no CSV. Each value is one whole name; `--file a --file b` and `--file a b` are the canonical forms. Sites to change: `change/implementation.ts:290` (`--file` of add/ignore/resolve) and `graph/index-graph.ts:75` (`--exclude-path`, globs can contain commas). No exact-match-first fallback, no deprecation warning. A value that fails shows the original value. Closed-vocabulary options (`graph impact --type`, file categories, `--status` via `parseCommaSeparatedValues`) keep their comma lists because a comma is never valid in their values. Use cases take `string[]` and never split. Text output lists names one per line; JSON/TOON stay arrays. Names are never trimmed once recorded. Skills that emit `--file <p1>,<p2>` must change to repeated `--file` (known: `specd-archive` L112/L117, `specd-implement` L185; sweep `packages/skills/templates` in design); treated as an implementation task, no new skills spec unless the sweep says otherwise. Optional stdin list (`--files-from -`) is out of scope.

### Test ideas

`changes deps --set ""` and `--add " "` are rejected with a clear error and store nothing; `--clear` empties the list; an invalid `dependsOn` in a lock gives a typed error naming the spec, and a documented command repairs it; `specs deps clear` works on an invalid lock; the same inputs through the SDK; and valid IDs (including a comma, if allowed) keep working.
