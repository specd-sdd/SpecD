# Exploration Context: delta-merge-effective-change-checks

## Problem Statement

1. **Silent no-op delta merges across multiple parsers:**
   - During `decouple-core-cli-workflow-guidance`, `op: modified` entries targeting `type: paragraph` with `value` or `rename` passed `specd changes validate` with no errors or blockings, yet produced no changes in `specd changes spec-preview` / merged output (the old text remained verbatim).
   - Cross-parser audit revealed the same class of bug across `MarkdownParser`, `YamlParser`, and `PlaintextParser`.
2. **No validation check ensuring each non-`no-op` operation produces an effective change:**
   - `applyDelta` and `ValidateArtifacts` do not verify that `op: modified` (with or without `content`/`value`/`rename`) or any non-`no-op` op actually alters the serialized output compared to the previous state.

## Key Codebase Observations & Root Causes

### 1. `MarkdownParser` (`packages/core/src/infrastructure/artifact-parser/markdown-parser.ts`)

- **`paragraph` + `value`:**
  - `convertBlockNode` (`markdown-parser.ts:223-227`) stores both `value: text` and `_inlines: inlines` (and `_blockquoteChildren` for blockquotes at `markdown-parser.ts:266-270`).
  - `applyDelta` (`packages/core/src/infrastructure/artifact-parser/_shared/apply-delta.ts:537-547`) clones all properties except `value` and `children`, **preserving `_inlines`** (and `_blockquoteChildren`) while updating `clone['value']`.
  - `nodeToMdastNodes` (`markdown-parser.ts:506-528`) prioritizes `node._blockquoteChildren` and `node._inlines` over `node.value` (`children: inlines ?? [{ type: 'text', value: ... }]`), so `serialize()` emits the stale old text.
- **`list-item` + `rename`:**
  - `convertListItem` (`markdown-parser.ts:308-317`) stores `_inlines` on `list-item` nodes.
  - `applyDelta` (`apply-delta.ts:497-504`) updates `clone['label'] = entry.rename` while preserving `_inlines`.
  - `nodeToMdastNodes` (`markdown-parser.ts:545-552`) prioritizes `item._inlines` over `item.label`, so `rename` on `list-item` silently emits the old item text.
- **`paragraph` + `rename`:**
  - `MarkdownParser.nodeTypes()` (`markdown-parser.ts:607-615`) sets `identifiedBy: ['contains']` and `isLeaf: true` on `paragraph`.
  - `validateRename` (`packages/core/src/application/ports/artifact-parser.ts:151-182`) checks `descriptor.identifiedBy.length > 0`, treating `contains`-identified nodes as having a `label`. It accepts `rename` on `paragraph` with only a warning (`consider using value`), while `validateValue` warns `consider using rename`.
  - `nodeToMdastNodes` never reads `label` on `paragraph`, so `rename` is silently ignored.
- **Blast radius:** `specd graph impact` on `markdown-parser.ts` reports `riskLevel: CRITICAL` (13 affected files in `core`, including `registry.ts` and `composition/*`).

### 2. `YamlParser` (`packages/core/src/infrastructure/artifact-parser/yaml-parser.ts`) — Critical

- `documentToArtifactAST` (`yaml-parser.ts:180`) stores `_yaml: originalContent` on `ast.root`.
- `applyDelta` updates the tree via `setChildren(root, ...)` (`apply-delta.ts:265`), which copies `_yaml` from the original `root` onto the new `root` (`apply-delta.ts:222-229`).
- `YamlParser.serialize()` (`yaml-parser.ts:362-369`) returns `ast.root._yaml` directly whenever it is a string, causing **any** delta (`added`, `modified`, `removed`) on YAML files to serialize back to the unmodified `originalContent`.

### 3. `PlaintextParser` (`packages/core/src/infrastructure/artifact-parser/plaintext-parser.ts`)

- `PlaintextParser.nodeTypes()` (`plaintext-parser.ts:113-131`) defines `paragraph` with `identifiedBy: ['contains'], isContainer: false, isLeaf: false, isCollection: true` and `line` with `identifiedBy: ['contains'], isLeaf: true`.
- Attempting `paragraph` + `value` throws `DeltaApplicationError: \`value\` is not valid on node type "paragraph" — use \`rename\``, while `rename`sets`label`which`\_serializeParagraph` (`plaintext-parser.ts:257`) never reads.

### 4. `JsonParser` (`packages/core/src/infrastructure/artifact-parser/json-parser.ts`)

- Verified `property` + `value` works properly (`"name": "new-name"`), as it stores no cached raw node metadata.

### 5. Ambiguous Selectors & Duplicate Ops

- Verified in `applyDelta` (`apply-delta.ts:364-373`, `435-445`): `modified` and `removed` reject ambiguous (`>1` match) or zero-match selectors and duplicate targets with `DeltaApplicationError`.
- Note: `added` with `position.parent` only checks `paths.length === 0` (`apply-delta.ts:424-431`) and picks `paths[0]!` (`apply-delta.ts:623`).

### 6. Validation Pipeline (`packages/core/src/application/use-cases/validate-artifacts.ts`)

- `ValidateArtifacts` (`validate-artifacts.ts:502-510`) collects `mergedResult.warnings` (which do not fail validation) and only fails on `DeltaApplicationError` or post-merge `artifactType.validations` failures.
- Because `baseArtifact.content` and `parser.serialize(mergedAST)` are already computed in memory, per-op and/or overall effective-change checks can be performed in memory without disk writes.

## Approach / Solution Outline

1. **Fix parser metadata invalidation & serialization:**
   - Ensure `applyDelta` / format parsers invalidate cached parser metadata (`_inlines`, `_blockquoteChildren`, `_yaml`, etc.) on modified nodes and mutated ancestor/root nodes so `serialize()` reflects applied changes while preserving untouched siblings' formatting (as required by `core:delta-format`).
   - Fix `PlaintextParser` `paragraph`/`line` descriptors/value handling so `paragraph` and `line` can actually be modified and serialized.
2. **Fix `validateRename` semantics (`packages/core/src/application/ports/artifact-parser.ts`):**
   - Restrict `rename` to nodes whose identifying property is a name/label (`identifiedBy.includes('matches')`), rejecting `rename` on `contains`-only nodes like `paragraph` and `line`.
3. **Add effective-change validation check (in memory):**
   - Require `modified` entries to specify at least one of `content`, `value`, or `rename`.
   - During validation (in memory), verify that each non-`no-op` operation in a delta produces an actual change relative to the previous serialized state (op-by-op sequential serialization/comparison or subtree/document serialized diff check), failing validation if an operation leaves the output unchanged.
