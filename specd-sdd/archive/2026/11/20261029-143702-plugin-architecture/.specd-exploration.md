# Exploration: plugin-architecture

Generated: 2026-10-29

Branch: `feat/lifecycle-transitions-ux` (nothing from this branch has been released; breaking changes are acceptable, per the user).

Origin: split out of `check-plugins-runtime` during its design. That change was narrowed to what is specific to checks and builds on this one. `check-plugins-example` also depends on it. Decisions below were agreed with the user one by one; items marked OPEN are not decided.

## Why

The plugin system (`@specd/plugin-manager`, `specd-plugin.json`, `plugins:` in `specd.yaml`) only knows plugin type `agent`, one type per plugin, and nobody calls `init`/`destroy`. We want plugins for anything with a registry in the kernel (checks, external hook runners, parsers, extractor transforms, storage factories, VCS/actor providers), for other subsystems (code-graph language adapters and graph stores), for agent assets (skills, template injections), and for hosts (CLI commands, MCP tools). What is decided now fixes how every future plugin works.

## Verified codebase facts (anchors; re-verify before trusting)

- `PLUGIN_TYPES = ['agent']` (`packages/plugin-manager/src/domain/types/specd-plugin.ts`), manifest `pluginType: z.enum(['agent'])` (`infrastructure/loader/plugin-loader.ts`), `ConfigSchemaEntry.type` is flat `'string'|'boolean'|'number'`, `PluginContext` only has `config: SpecdConfig`.
- `init`/`destroy` are on `SpecdPlugin` but nothing calls them (grep of plugin-manager src and `cli/src/commands/plugins`). The 5 `plugin-agent-*` declare an empty `configSchema`.
- `LoadPlugin` only calls `loader.load`. `InstallPlugin` throws `PluginValidationError` if the plugin is not `isAgentPlugin`. `cli plugins install` is partly type-aware (`toPluginBucket(type)`, `ConfigWriter.addPlugin(configPath, type, name, config?)`), but "already installed" uses `getDeclaredPlugins(config, 'agents')` and `uninstall.ts` hardcodes `agents`.
- Manifest fields today: `schemaVersion`, `name`, `version`, `description`, `pluginType`, `minCoreVersion`. `name`/`version` come from the manifest and MUST NOT be hardcoded in plugin code (`plugin-manager:specd-plugin-type`).
- `PluginEntryZodSchema` = `{ name, config?: z.record(z.unknown()) }`, `PluginsZodSchema` = `{ agents?: [...] }` strict (`core/src/application/ports/config-schema.ts`). Config cascade in `config-cascade.ts`.
- Kernel registries (`KernelBuilder.register*`): spec/schema/change/archive storage, change/archive repository, spec/schema repositories, parser, extractor transform, VCS provider, actor provider, external hook runner, check, disposer. Code-graph has its own: `adapters` (LanguageAdapter[]) and `graphStoreFactories` in `createCodeGraphProvider`. An independent plugin `specd-plugin-graphstore-ladybug` is mentioned in specs.
- `host-lifecycle-dispose` landed: `registerDisposer`, `Kernel.dispose()`, `SdkHostContext.dispose()`.
- Skills: templates `.md.tpl` under `packages/skills/templates/{skills,agents,shared,prompt}`, each skill with `skill.meta.json` (capabilities, required shared templates). Only injection point today: `extraInstructions` in `agent-instruction.md.tpl`, fed by `renderBaseAgentInstruction`. `AgentInstallOptions` = `skills?`, `agents?`, `variables?`, `capabilities?`. `SkillRepository`/`createSkillRepository`, `ResolveBundle`.
- Dependency graph (AGENTS.md): `plugin-* -> skills -> core`; `cli -> core, code-graph, skills, plugin-*, schema-std`; `sdk` depends on `core` and `code-graph`. No cycles allowed.
- `check-registry.ts`: `PLUGIN_NAME_REGEX = /^[a-zA-Z0-9_-]+$/`, canonical check id `@${pluginName}.${check.id}`, JSDoc says `^[a-z][a-z0-9-]*$` (inconsistent). Plugin checks are discriminated from built-ins by `id.startsWith('@')` (`composition/use-cases/workflow-check-registry.ts`).

## Agreed model

1. **Plugin = a feature**: one scoped package owning identity, namespace, config, lifecycle and ONE code entry. Reason: a CLI command that writes a namespaced section into a change manifest and a check that validates it must share namespace, config and state; one plugin per kind would force dependency resolution between plugins. Precedent: VS Code `contributes`, Eclipse extension points.
2. **Contributions** are declared statically in `specd-plugin.json` under `contributes`, a map keyed by kind (`checks`, `agents`, `cliCommands`, ...). Each entry has a local id (no `.`), unique across the whole plugin. Address of any contribution: `@scope/name.id`. `pluginType` disappears.
3. **Kinds are extension points** owned by the subsystem that consumes them, supplied as handlers to an OPEN registry in plugin-manager (not a closed enum). A handler defines the manifest block schema of its kind, the code contract and how it registers. plugin-manager is the generic engine: discovery, manifest, config validation, lifecycle, addressing, uniqueness.
4. **Naming**: the plugin name is its npm `name`, MUST be scoped (`@scope/name`, the leading `@` is mandatory, never added). Validated in the base (manifest schema, loader, `isSpecdPlugin`, `cli plugins install`), plus defensively in the check registry. `.` is the reserved separator. Fix the JSDoc/regex mismatch in `check-registry.ts`. No separate `namespace` field. Existing agent names (`@specd/...`) already comply.
5. **Config**: one config per plugin (shared by its contributions), declared with a bounded JSON Schema subset (not Zod; `type`, `properties`, `required`, `items`, `enum`, `default`, `additionalProperties`; unsupported keywords rejected with a typed error). Applies to ALL plugins; empty schema = no config. A plugin with no schema cannot have config (typed startup error if `config` is present). plugin-manager converts the schema to Zod internally; zod is `^3.25.76` which has no JSON Schema converter and `ajv` is only transitive, so plugin-manager writes its own converter for the subset. Manifest gains optional plugin-level `defaultConfig`, written to `specd.yaml` on install only when the entry has no config, validated against the schema. `configSchema` stays in plugin code (reversible).
6. **`specd.yaml`**: flat list.
   ```yaml
   plugins:
     - name: '@<scope>/<plugin>'
       config: { ... } # optional
       contributions: ['<id>'] # optional allowlist; absent = all
   ```
   Allowlist only (no `exclude`/`disable`): a plugin update never activates a new contribution by surprise. `exclude` can be added later (additive). Selection lives in YAML because uninstall/update/list need to know what was installed. Unknown id in `contributions` = typed error at load. `PluginsZodSchema` becomes an array; `ConfigWriter.addPlugin/removePlugin` lose the `type` param and gain selection; migrate this repo's `specd.yaml`, cascade, `project init`, `cli plugins *`.
7. **Lifecycles** (explicit methods, not a phase switch):
   - Runtime: `init`/`destroy`, once per process in which the host loads plugins, called for EVERY configured plugin of any kind, config only (no services, no phase). Order: `init` all (list order) -> kind handlers register kernel-attached contributions on the builder -> `build()` -> host calls its own `host:<name>` entry for host contributions -> `destroy` in reverse order through ONE named disposer registered by plugin-manager (error isolation; if a later `init` fails, destroy the already-initialized ones).
   - Install: `install`/`uninstall` receive the selected contribution ids; does not call `init`.
   - Contributions have no lifecycle of their own; a kind handler activates them, passing the kind's context (e.g. `CheckServices` for checks).
   - Failure policy: a plugin is a plugin; any load/validation/`init` failure fails startup with a typed error naming the plugin. Known consequence: a broken plugin blocks every host-based command.
8. **SDK**: single entry `registerPlugins(builder, config)` called by `createSdkContext` (NOT `openSpecdHost`) before `build()`; `createSdkContext` moves from `createKernel` to `createKernelBuilder` + `registerPlugins` + `build()`. `sdk` depends on `@specd/plugin-manager`. Option `plugins: false` (boolean, default `true`) skips everything (no load, no `init`, no disposer); used by the graph-index worker and by `cli plugins *` so a broken plugin can still be repaired. Targets beyond `KernelBuilder` (code-graph adapters/stores) need handlers supplied by their owners.
9. **Skills and agents**: two contributions owned by `@specd/skills`: `skills` (full skill: template + meta) and `skillInjections` (fragment aimed at a NAMED SLOT of a skill/shared file). Named slots become public contract of `@specd/skills` (`extraInstructions` becomes one of them; the real slot list must be derived by reading the templates, not yet done). Agent plugins do not change: the install use case composes an extended `SkillRepository` plus injections map and passes them to the agent `install`. New edge `plugin-manager -> skills` (acyclic).
10. **Out of scope here, reserved in specs**: host contributions (`host:cli`, `host:mcp`; `@specd/mcp` is a 14-byte stub), data extensions (plugin-namespaced section in the change manifest), per-contribution config/`init`/entry (bundles), `exclude`/`enabled`.

## Rejected

- One plugin per kind (breaks the shared namespace/config/state use case).
- Separate `namespace` field in the manifest; deriving a namespace from the npm name; `<npm-name>:<id>` id format.
- Closed `PLUGIN_TYPES` enum; per-kind `specd.yaml` buckets; `exclude`/`disable` in v1.
- Zod or a flat custom type as the config schema format.
- Slots inside templates replaced by schema plugins: `schemaPlugins` are workflow-schema layers and unrelated to skills (user correction).

## OPEN

- 5b: staleness. When a plugin contributing skills/injections is installed, updated or uninstalled, already-installed agent files are stale: auto-reinstall declared agents, or warn "run `plugins update`"?
- Who owns which handler and where it lives (check handler: plugin-manager vs core-adjacent; storage/VCS/actor/parser/transform handlers; code-graph handlers). Dependency edges must stay acyclic.
- Scope of implementation in this change: agent migration and the registry for sure; which other kinds are implemented vs only specified as reserved extension points (recommendation: implement `agent` only here; `check` comes with `check-plugins-runtime`).
- Whether `configSchema` should move to the manifest.
- Exact manifest per-kind block shapes beyond `checks` (see `check-plugins-runtime`).
- Extending `init` ordering across plugins with dependencies on each other (not needed yet).
