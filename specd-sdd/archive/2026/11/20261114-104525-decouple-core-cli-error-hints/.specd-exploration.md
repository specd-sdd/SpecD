# Exploration Context: decouple-core-cli-error-hints

## Problem Statement

During `specd specs validate --all` (after merging `main` into `feat/lifecycle-transitions-ux`), `DependsOnOverwriteError` surfaced with:
`dependsOn would change (...). Use --force to overwrite curated dependencies.`

Two issues were identified:

1. **Layer coupling:** `@specd/core` domain/application errors and use cases hardcode CLI flags (`--force`, `--next`, `--allow-out-of-scope`, `--target`, `--set`, `--add`, `--remove`, `--clear`) and CLI commands (`specd specs show ...`) in error messages. Non-CLI consumers (`@specd/sdk`, `@specd/mcp`, programmatic callers) do not have CLI flags.
2. **Misleading command hints:** Because `DependsOnOverwriteError` is thrown by `MaterializeSpecMetadata` / `GenerateSpecMetadata` / `UpdatePersistedSpecSchema` and propagated into `specs validate --all`, suggesting `Use --force` inside `specs validate` is misleading because `specs validate` has no `--force` flag (the flag lives on `specs generate-metadata --force`, and `specs deps add/set` is an alternative).

## Architectural Decision & Boundaries

Checked against `default:_global/architecture` and `default:_global/error-handling-conventions`:

- Rendering command-specific CLI hints in `@specd/cli` does **not** violate the "Adapter packages contain no business logic" rule. `default:_global/architecture` explicitly defines delivery packages' role as: _"They translate between their delivery mechanism and use cases."_
- **Core (`@specd/core`):** detects the domain/application invariant violation, throws a typed `SpecdError` subclass with stable `UPPER_SNAKE_CASE` `code`, structured metadata fields (e.g., `existingDeps`, `incomingDeps`, `specId`, `gates`), and a delivery-agnostic message.
- **CLI (`@specd/cli`):** inspects the typed error (`code` / `instanceof`) and the active command context to render command-appropriate hints (e.g., `--force` for `specs generate-metadata`, vs `specs deps add` / `specs generate-metadata --force` for `specs validate`).
