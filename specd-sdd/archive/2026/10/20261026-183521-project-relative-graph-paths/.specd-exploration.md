# Exploration: project-relative-graph-paths

Working memory for `/specd-design`. Everything below was discussed in the session that created this change; anchors (file paths, line numbers, spec ids) are given so the reader can check freshness. Line numbers are approximate and may have moved.

## Problem statement

Every path or pattern written in `specd.yaml` should be interpreted **relative to the project root** (the directory that contains `specd.yaml`), with no exceptions per key and no exceptions per level (global or workspace). Today the interpretation depends on the key and on where the list is evaluated, so a user cannot tell from the YAML alone which file a pattern refers to. The user's reasoning: "what is configured in specd.yaml must always be project-relative, otherwise it is chaos to guess the path of a file."

Triggering evidence came from reindexing `../iccms` (a legacy CakePHP 1.x repository with nested workspaces `default` `./`, `backend` `app`, `backoffice` `app/webroot`, `cake` `cake`). Its global `graph.excludePaths` contains rooted patterns and negations written project-relative (`/app/vendors/*`, `!/app/vendors/iccms`, `!app/vendors/iccms/**`, `app/tmp/`, `dev/storage/`) which did not behave as written inside the `backend` workspace:

- `backend:vendors/iccms/utils.php` was not indexed (0 files under `backend:vendors/`), producing a `FILE_NOT_INDEXED` coverage diagnostic for a spec-lock link.
- `app/tmp/` did not apply in `backend`: 4 compiled Smarty templates under `backend:tmp/smarty/compile/` were indexed.
- The author had written both `/vendors/*` and `/app/vendors/*` because they could not know which one would apply; the re-inclusions (`!`) only existed in project-relative form and were inert in `backend`.
- A test with the `ignore` library confirmed it: against `app/vendors/iccms/utils.php` (project-relative) the rules give `ignored: false` (intended), against `vendors/iccms/utils.php` (codeRoot-relative, what `backend` evaluates) they give `ignored: true`.
- It was worked around in `../iccms/specd.yaml` by duplicating the rules in codeRoot-relative form (`!/vendors/iccms`, `!/vendors/iccms/**`, `!/vendors/full-text-rss`, `!/vendors/full-text-rss/**`, `/tmp/`). After the workaround `backend:vendors/` has 63 files and `backend:tmp/` has 0. That workaround is the behaviour this change makes unnecessary.

## Decisions (confirmed by the user)

1. **Principle**: every path or pattern in `specd.yaml` is relative to the project root, for every graph key (`excludePaths`, `testPaths`, `ignorePaths`, `allowedPaths`, `largeFilePaths`, and `includePaths` which already is), at both global and workspace level. No per-key or per-level exceptions.
2. **No transition mechanism**: direct cut to the new semantics. The user said it is not needed because the project is still alpha. So: no `graph.pathBase` key, no dual-semantics period. (The exploration had also proposed a startup warning for anchored patterns that no longer match anything; the user's answer "no es necesario" was to the transition question; no warning was requested. Treat the warning as out of scope unless design finds a reason.)
3. **In scope besides the path semantics**:
   - A new command `specd graph why <path>` that explains why a path is excluded, classified, or indexed.
   - Fix for workspace-local negations overriding global exclusions (see below).
4. **Layering for `graph why`** (user correction, explicit): it must delegate to a **use case in code-graph**, not be orchestration in the CLI. Layers: CLI (`packages/cli/src/commands/graph/*.ts`, thin: parse options, `withProvider`, format) -> SDK (`packages/sdk/src/orchestration/run-graph-*.ts`, thin delegation; hosts only import `@specd/sdk` per `default:_global/architecture`) -> code-graph application use case with a composition factory under `packages/code-graph/src/composition/use-cases/` (same pattern as `get-graph-health.ts`, `get-spec-coverage.ts`). The use case must reuse the same evaluation functions as the indexer (`discoverFiles` predicate, `createFileSizeGate`, `classifyFileCategory`), exposing variants that return the winning rule, so the explanation cannot drift from real indexing. `graph-input-visibility.ts` already combines discovery and size gate and may be the base.
5. **Specs registered at creation (user: "hay que meterlo todo al principio")**, seven in total:
   - Existing: `core:config`, `code-graph:indexer`, `code-graph:workspace-integration`, `cli:graph-index`.
   - New (to be created during design): `code-graph:explain-graph-path` (the use case), `sdk:run-graph-why` (thin delegation), `cli:graph-why` (the command). Workspaces: code-graph, sdk, cli respectively.
   - Dependencies registered: `code-graph:explain-graph-path` -> `core:config`, `code-graph:indexer`, `code-graph:workspace-integration`; `sdk:run-graph-why` -> `code-graph:explain-graph-path`, `sdk:host-context`; `cli:graph-why` -> `sdk:run-graph-why`, `cli:entrypoint`, `core:config`.

## Second mismatch: workspace-local negations vs global exclusions (in scope)

`core:config` says workspace-level graph filters "MUST NOT remove or override global exclusions". The implementation concatenates `[...global, ...synthetic, ...workspaceLocal]` into one gitignore-style list where the last matching pattern wins, so a workspace-local `!pattern` could re-include a path excluded by a global rule. This was deduced from reading the code and `ignore` semantics; it was **not tested** with a real configuration. Design must decide how to enforce the requirement (e.g. evaluate global rules as a separate, non-overridable layer before the workspace layer) and add a verify scenario.

## `graph why <path>` outline (to refine in design)

- Input: a project-relative path (consistent with the principle; the CLI help for `specs implementation --file` already says "project-relative file path"). Open: also accept workspace-qualified ids (`ws:path`).
- Resolve the owning workspace: the most specific `codeRoot` that contains the path (nested workspaces exist, e.g. `app` contains `app/webroot`; one physical file can have two workspace identities today, see tangents).
- Evaluate the same chain as the indexer, in order: `.gitignore` (absolute priority), global `excludePaths`, synthetic spec-root exclusions, workspace `excludePaths`, workspace `allowedPaths`, size gate with `largeFilePaths` exemptions, then category (`ignored` / `test` / `source`), then whether an adapter exists (`no-language-adapter` -> document or unsupported).
- Output: project-relative path, owning workspace, verdict, and for each decisive step the matching rule with its origin (global, workspace, `.gitignore` file and line, synthetic spec-root). JSON and TOON formats must be stable and documented like other `graph` commands.
- Today `graph` has `index`, `stats`, `impact`, `search`, `hotspots`; there is no explain command.

## Rejected or deferred alternatives

- Keep codeRoot-relative semantics and only document it (option B in the exploration): rejected because the user wants a single mental model.
- Two keys (`excludePaths` codeRoot-relative plus `projectExcludePaths`): not chosen.
- Evaluate each anchored pattern against both paths: rejected as undefined for negations.
- Transition key `graph.pathBase: project|codeRoot`: explicitly not needed (alpha).
- A startup warning for anchored patterns that no longer match: not requested.
- Doing `graph why` as orchestration inside the CLI: rejected (must be a code-graph use case).
- Splitting `graph why` into a separate change: rejected; everything goes in this change.

## Open questions for design

1. Mechanism: pass a project-relative base (`relative(projectRoot, codeRoot)`) to `discoverFiles` so patterns match `join(base, relPath)`, including directory pruning during the walk; or compute the project-relative path in callers. Must also be applied in `graph-input-visibility.ts` and `get-graph-health.ts` so freshness and health agree with indexing.
2. A `codeRoot` outside the project root: project-relative patterns cannot match (path starts with `../`); the size gate already guards this. Define behaviour and diagnostics.
3. `allowedPaths` is glob syntax (not gitignore syntax) and a different matching function: same project-relative root, different matcher.
4. `.gitignore` is unchanged: its own hierarchical semantics and absolute priority (`respectGitignore`).
5. Built-in defaults (`DEFAULT_EXCLUDE_PATHS`, `DEFAULT_GRAPH_TEST_PATHS`, `DEFAULT_GRAPH_IGNORE_PATHS`) are mostly unanchored (`**/*.spec.*`, `node_modules/`, `.git/`); check each one still behaves identically under project-relative matching, and whether any default is anchored.
6. Fingerprint: the semantics change must force a full reindex (the effective discovery config is in the fingerprint; verify a version or semantic marker is included, since the YAML itself does not change).
7. Nested workspaces: which workspace owns a file for classification and for `graph why`; what to report when two workspaces could own the same path.
8. Whether `graph why` is exposed through MCP as well (the `mcp` package depends on `sdk`); not discussed.
9. Documentation: `default:_global/docs` requires a docs/cli page, index and sidebar entry for every CLI command, docs under `docs/sdk/code-graph` for new SDK surface, and `docs/guide` configuration must match `core:config`. Update the guide section on `graph` configuration and path semantics. New public symbols need full JSDoc.
10. Existing verify scenarios in `core:config` and `code-graph:indexer` that assume codeRoot-relative evaluation must be rewritten; add a nested-workspace scenario (workspace inside another, negation re-inclusion, anchored pattern in a non-root workspace).
