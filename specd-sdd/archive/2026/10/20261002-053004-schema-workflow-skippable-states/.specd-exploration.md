# Exploration Context: Schema Workflow Skippable & Disabled States

Generated: 2026-10-02

## 1. Problem Statement

In SpecD, the workflow lifecycle is currently static and monolithic:

1. `VALID_TRANSITIONS` and `HAPPY_PATH_NEXT` in `packages/core/src/domain/value-objects/change-state.ts` are hardcoded tables. Every change must move through the sequence `drafting -> designing -> ready -> implementing -> verifying -> done -> archivable`.
2. Although `schema.yaml` declares a `workflow: []` section, this array is only a lookup table attaching "extras" (`requires`, `requiresTaskCompletion`, `hooks`, `checks`) to pre-existing states. The docstring of `WorkflowStep` explicitly states: _"It does not define protocol membership or legal hops"_.
3. Use cases requiring workflow agility cannot currently be modeled:
   - **Lightweight / docs-only schemas**: Schemas that don't need tests/verifications (`verifying`), or don't need coding phases (`implementing`), or don't need the ceremonial `ready` phase when approval gates are off.
   - **Dynamic skipping based on change content**: When a change has no code tasks in `tasks.md` (e.g. pure spec delta or 0 tasks), the change cannot bypass `implementing` directly from `ready` to `verifying` or `done`. Today, `TransitionChange` throws `INVALID_TRANSITION` via `protocol.edge`.
   - **User UX & Guidance friction**: `GetStatus` and `resolveLifecycleNextHop` always push `/specd-implement`, even when 0 tasks exist or tasks are 100% complete.

The goal is to allow schemas to define workflow steps as `optional: true` or `disabled: true`, and to support clean, check-governed auto-skipping (such as skipping `implementing` when there are no tasks), while strictly preserving protocol invariants and approval gate security.

## 2. Approach & Solution Architecture

### Core Design Decisions & Architectural Breakthroughs

1. **Reutilización del CheckRegistry con un nuevo Scope (`scope: 'step-skip'` / `step-bypass`)**:
   - _Why rejected alternative_: Initially, tying shortcut edges into `{ scope: 'transition', from: '*', to: 'verifying' }` was considered. The user pointed out that `from: '*'` wildcard would match normal entries to `verifying`, merging two completely different intentions:
     1. "Condition to enter target state `to`" (`scope: 'transition'`).
     2. "Condition to permit skipping an intermediate step `S`" (`scope: 'step-skip'`).
   - _The Solution_: Introduce a new scope in `CheckAttempt` and `CheckApplicability`:
     ```typescript
     export type CheckAttempt =
       | {
           readonly scope: 'transition'
           from: ChangeState
           to: ChangeState
           along: TransitionAlong
         }
       | { readonly scope: 'archive' }
       | { readonly scope: 'operation'; operation: 'verification-start' }
       | { readonly scope: 'step-skip'; step: ChangeState; from: ChangeState; to: ChangeState }
     ```
   - Checks such as `workflow.tasksEmpty` / `workflow.canSkipImplementing` bind to `{ scope: 'step-skip', step: 'implementing' }`.
   - When a transition attempts a hop that bypasses `implementing` (e.g. `ready -> verifying`), the engine evaluates both the transition to `to` AND the skip checks for the bypassed step(s).

2. **`protocol.edge` como árbitro de topología y estados habilitados**:
   - `protocol.edge` receives the active `schema` (and change context).
   - If destination `to` is marked `disabled: true` in the schema: fails with `STEP_DISABLED`.
   - If destination `to` is reached via a bypass of step `S`:
     - Checks if step `S` is allowed to be bypassed in this schema (`optional: true` or `disabled: true`).
     - If allowed, `protocol.edge` passes, authorizing the transition engine to execute the `step-skip` checks for `S`.
     - If not allowed (e.g. `S` is mandatory and not disabled), `protocol.edge` fails with `INVALID_TRANSITION`.

3. **Invariantes de Deshabilitación per State (Qué se puede y qué no se puede deshabilitar)**:
   - `drafting`: Inmutable (creación de changes).
   - `designing`: Inmutable (SpecD is spec-driven; proposal, specs y deltas nacen aquí).
   - `archivable` / `archiving`: Inmutables (persistencia y merge atómico de deltas a specs).
   - `ready`: Condicional. **No se puede deshabilitar si `approvals.spec: true`**. Si `approvals.spec: false` y no tiene checks/hooks exclusivos, un schema ligero puede omitirlo o marcarlo `disabled: true`, avanzando `designing -> implementing`.
   - `done`: Condicional. **No se puede deshabilitar si `approvals.signoff: true`**.
   - `implementing`: Deshabilitable / Opcional per schema.
   - `verifying`: Deshabilitable / Opcional per schema. (Si `verifying` está deshabilitado, `verification.current` no debe bloquear el archive).

4. **Proyección en `GetStatus` y Comandos de Schema (`schema show`)**:
   - `schema show` y `GetStatus`: proyectan el orden completo y efectivo del pipeline de workflow.
   - Ocultan los pasos deshabilitados en vistas estándar.
   - Indican explícitamente qué pasos son opcionales (`[optional]`).
   - `GetStatus` evalúa `step-skip` checks para pasos opcionales activos. Si pasan (ej. no tasks), `canAutoSkip = true` y `nextAction` sugiere directamente el siguiente estado válido (`/specd-verify` o `/specd-archive`).

## 5. Agreements Reached & Design Decisions

1. **Check System Reused**: No secondary ad-hoc engine. The existing `CheckRegistry` is reused completely.
2. **Dedicated Scope `step-skip`**: Avoids wildcard collision in `scope: 'transition'`. Clear semantics: evaluates if bypassing a step is permitted.
3. **`protocol.edge` Evolution**: Becomes the topology authority checking schema step enablement and legal shortcut paths.
4. **Gate Invariant**: `ready` cannot be disabled if `approvals.spec: true`. `done` cannot be disabled if `approvals.signoff: true`.
5. **No-Tasks Auto-Skip**: Evaluated via checks in `scope: 'step-skip'` for step `implementing`.
6. **Status Projection**: Full ordered workflow pipeline in `GetStatus` and `schema show`, with clear `[optional]` annotations.

---

## 6. Open Questions for `/specd-design`

1. **Hook Behavior on Skipped Steps**: Confirm that when an optional step `S` is bypassed (`ready -> verifying`), neither `S.pre` nor `S.post` hooks are executed (since the phase was neither started nor completed).
2. **Multi-Step Bypasses**: Can a single transition bypass multiple consecutive optional steps (e.g. `ready -> done` bypassing both `implementing` and `verifying`)? The engine should evaluate `step-skip` checks for every intermediate bypassed step in order.
3. **Implementation Tracking on Skipped Implementing**: Ensure that if `implementing` is bypassed, any unexpected dirty/modified files in git are caught before entering `done` or `archivable`.

## 8. Revision Decisions after Failed Verification (2026-10-16)

Context: `/specd-verify` full mode (attempt `verification-attempt-11`) failed. Compliance report:
`reports/20261016-125213/specs-compliance-change-schema-workflow-skippable-states-20261016-125213.md`.
User chose "Both" (specs first, then implementation). Decisions agreed with the user:

1. **Pipeline order is always canonical.** `workflow[]` row order carries no meaning; rows only carry per-step
   properties (optional, disabled, checks, skipChecks, hooks). Rows declared out of order are normalized silently
   (no error), consistent with bedrock normalization rule. Remove scenario "Noncanonical delivery order remains
   authoritative within canonical anchors" and its test. This also removes the reorder-skips-approval bug.
2. **Reachability is guaranteed by construction.** Disabling implementing AND verifying together is allowed
   (designing → ready → done). Remove the vacuous `isReachable` guard; replace "Disconnected forward graph throws"
   with a positive connectivity scenario.
3. **Plugin names:** reword spec — external checks are always `@plugin.id` namespaced so they cannot collide with
   built-ins; `InvalidPluginNameError` only covers invalid plugin-name grammar. No reserved prefixes.
4. **Predicate failure error type (documented hybrid, matches code):** `InvalidStateTransitionError` with canonical
   reasons for `protocol.edge`, `workflow.requires`, `workflow.taskCompletion`, `approval.spec`/`approval.signoff`;
   `CheckPredicateFailedError` (with `skippable`) for every other predicate, including step-skip and plugin checks.
   (Initial choice "always InvalidStateTransitionError" was revised after correcting how the CLI actually uses both.)
5. **Schema version advisory is sovereign-only:** remove workspace-default version comparison (change-repository +
   change-manifest "Schema version bumped" scenario). Only the resolver's same-name version drift advisory remains.
6. **`ResolveChangeSchema` returns `{ schema, warnings }`** with typed advisories (code follows spec; update consumers).
7. **edit-change compatibility is sovereign:** remove the old guardrail that uses the global schema for uninitialized specs.
8. **preview-spec:** "always succeeds" applies only to merge/content failures (per-file warnings); schema resolution
   and identity mismatch errors propagate.
9. **CLI transition:** `<name>` required and exactly one of `<step>` or `--next` (spec follows code).
10. **`--skip-hooks` output:** skipped hooks render as skipped (not ✓); the second check pass is shown only when
    hooks could have changed state, or labeled as a re-check.
11. **WorkflowTopology → module functions** (global architecture: stateless services are plain functions), with
    workflow-prefixed names imported by name:
    `orderedPipeline → resolveWorkflowPipeline`, `isStepEnabled → isWorkflowStepEnabled`,
    `legalTransitions → listWorkflowTransitions`, `isLegalTransition → isWorkflowTransitionLegal`,
    `bypassedSteps → listBypassedWorkflowSteps`, `nextForwardStep → nextWorkflowStep`.
12. **Skills:** templates become fully status-driven (targets/hooks from `nextAction` + `availableTransitions`,
    never hooks for disabled/bypassed steps); add a test that parses the real templates and fails on
    unconditional recipes; remove the tautological "simulates…" tests.
