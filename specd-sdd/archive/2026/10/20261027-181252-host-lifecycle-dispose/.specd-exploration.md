## Origin / conversation flow

1. User asked whether this branch let workflow checks use internal use cases. Answer: no. `CheckExecutionContext` (`packages/core/src/domain/services/transition-checks.ts:351`) exposes only `change`, `schema`, `attempt`, `config`, `validity`, `onCheckProgress`, `skipHookPhases`, `effectiveStatusByArtifact`, `approvals`, `passMemo`. `CustomCheckDefinition.execute(ctx)` gets only that. 3. User asked about building the check by hand beforehand sharing config with core. Possible today via `createCompositionResolver(config, options)` + `create*` factories (exported from `@specd/core`), but yields a second composition (divergent state, missing registries, no kernel logging/privacy wrapper) and is host-only.
4. User clarified that check plugins will have config in `specd.yaml` and that `plugin-manager` should be extended. `plugin-manager` today: `PLUGIN_TYPES = ['agent']` (`packages/plugin-manager/src/domain/types/specd-plugin.ts`), manifest `pluginType: z.enum(['agent'])`, loader (`infrastructure/loader/plugin-loader.ts`) calls `create({ config })`. `SpecdPlugin` has `init`/`destroy`, but nothing in `packages/*/src` calls `destroy()`.
5. User decided the interconnection with core is done by **SDK**; SDK will depend on `@specd/plugin-manager` ("no pasa nada"). Chosen over an injected loader port. `AGENTS.md` dependency graph must become `sdk → core, code-graph, plugin-manager` (that belongs to the later change).
6. User said plugin `install`/`uninstall` exist because a check may need to initialize internal things on install; they may be no-ops.
7. User noted there is no `destroy()`/dispose in the host and it must be added to the base. Confirmed by grep: no `dispose|close|destroy|shutdown` in `packages/sdk/src/composition/host-context.ts` or `packages/core/src/composition/kernel.ts`.
8. User wants an automatic close mechanism too (TS explicit resource management), independent of manual close, "por si acaso".

## This change: scope

Base lifecycle only. Independent of check plugins.

- `core:kernel`: `Kernel.dispose()` idempotent; `[Symbol.asyncDispose]` alias; a registry of disposers (`registerDisposer(fn)`), since the kernel itself owns no resources today. Core stays unaware of plugins.
- `sdk:host-context`: `SdkHostContext.dispose()` idempotent + `[Symbol.asyncDispose]`; calls disposers/plugin `destroy()` in reverse load order, then `kernel.dispose()`. Errors from several disposers aggregated (`SuppressedError`/`AggregateError`); one failure must not stop the others. Timeout on a hanging disposer with a warning. If init fails midway, already-initialized resources are destroyed before the error propagates.
- `cli:host-context`: CORRECTED during design (2026-10-27): the CLI has NO signal handlers today (no `process.on` in `packages/cli/src`) and commands call `process.exit()` directly (`handle-error.ts`, `commands/change/archive.ts`); 61 files use `resolveCliContext` and it drops the host object (returns only config, configFilePath, kernel). So cleanup is centralized (registry fed by `resolveCliContext`, run from `index.ts` after `parseAsync`, from `handleError` before exit, and from new SIGINT/SIGTERM handlers) rather than a per-command `finally`. Avoid `process.on('exit')` (sync, cannot await async destroy). `FinalizationRegistry` is not reliable; at most a "host not closed" log warning.
- TS config: add `"ESNext.Disposable"` to `lib` in `tsconfig.base.json` (currently `target: ES2022`, `lib: ["ES2022"]`). TypeScript installed is 5.9.3; Node 25 defines `Symbol.dispose`/`Symbol.asyncDispose`. No `engines` field in package.json; decide a minimum Node if the public API uses `await using`/symbols.
- MCP: `packages/mcp/src/index.ts` is a stub with no specs, so not in scope now.

Spec ids attached: `core:kernel`, `sdk:host-context`, `cli:host-context`. Deps registered: sdk host-context → core kernel; cli host-context → sdk host-context.
Possibly relevant, not attached: `core:kernel-builder`, `core:composition-resolver`, `cli:entrypoint`, `default:_global/testing`, `default:_global/conventions`.

## Open questions for /specd-design

- Exact `dispose()` semantics: second call returns same promise vs no-op; behavior of use of kernel after dispose.
- Timeout value for a hanging disposer and whether it is configurable.
- Error aggregation type given target ES2022 (`SuppressedError` is not in ES2022 lib; `AggregateError` is).
- Whether core references `Symbol.asyncDispose` directly or with a fallback; need for `engines`.
- Whether the SDK host must expose a way to register disposers for later plugin use, shaped so the follow-up change only adds callers.

### 2. `check-plugins-runtime`

- Check plugins configured in `specd.yaml` as `plugins.checks[]` (`name`, `config`); today `plugins` only has `agents` (`packages/core/src/infrastructure/fs/config-loader.ts:656`, `application/ports/config-schema.ts`).
- `plugin-manager`: add `'check'` to `PLUGIN_TYPES`, manifest enum, `validateRuntimePlugin`; new `CheckPlugin extends SpecdPlugin` with `checks(services, pluginConfig)` plus `install`/`uninstall` (may be no-op); new use case `LoadCheckPlugins`; validate plugin config against `configSchema` (today flat `string|boolean|number`, may be too poor for nested config). `PluginContext` should carry the plugin's own config.
- `core`: `registerCheck` accepts a definition or a factory `(services) => definition`, resolved inside `createKernel` after use cases are composed (single composition; avoids chicken-and-egg). `core` must not import `plugin-manager` (cycle: plugin-manager → core).
- `sdk`: orchestrates load → validate → register on builder → build kernel → dispose. Spec `sdk:composition` currently limits runtime deps to core and code-graph and forbids plugin packages; must be relaxed to allow `@specd/plugin-manager` only.
- New spec `core:check-services` (user: "debería tener su propio spec, sí").
- `CheckServices` decisions: frozen typed facade over already composed use cases, built once per kernel. Initial catalog proposal: `getSpecMetadata`, `validateSpecs`, `countTasks`, `getSpec`, `listSpecs`, change read access, `logger`, `projectRoot`. Excluded: use cases that mutate the change under evaluation (`transitionChange`, `archiveChange`, approve, create) because of reentrancy, and `getStatus` because it re-evaluates checks (recursion). Entry criterion: does not re-enter the check engine and does not mutate the change being evaluated.
- Purity discussion outcome: `GetSpecMetadata` (`get-spec-metadata.ts` → `MaterializeSpecMetadata` with `policy: 'if-needed'`) may persist a derived cache under `.specd/metadata/` (gitignored here, path configurable via `specs.fs.metadataPath`). User argued it is effectively read-only (result identical with/without cache) and is the most useful service for spec checks, and that external plugins are trusted code that can do anything anyway. Decision: expose it as is (option A); spec documents "effects limited to derived caches"; the restriction is contract/ergonomics, not security. Rejected: new `policy: 'read'` mode (option B) as over-engineering.
- Host-built alternative (closure over a parallel `createCompositionResolver`) rejected for plugins loaded from config.
