# Exploration: code-graph-package-resolution-hardening

Follow-up of `code-graph-cross-workspace-imports` (second compliance audit, 20261020-230822 and the lite report 231822). Start only after that change is archived; the specs overlap with it and with `code-graph-file-outline`, `code-graph-symbol-contracts`, `go-selectors-python-reexports`.

## Items

1. **TS/Go `prepare` vs `identity`.** `identity` walks up to the nearest `package.json`/`go.mod`, but `prepare` (TS `prepareWorkspaceManifest`) reads only `codeRoot/package.json`. A workspace whose code root is below the manifest gets an identity and then `no-entry-surface`. Decide: prepare walks up too, or identity is bounded to the code root. Go has the same shape.
2. **`resolve-symbol-reference.ts` fallbacks.** When the anchor has no adapter (a Go package surface), the resolver falls back to a generic dotted parser (`~:1117`) although the spec says such text is unresolved. `deriveQualifiedName` (`~:1037`) goes beyond "stored `qualified_name`". Fix the code or relax the spec.
3. **Missing tests.** `prepare` reads each manifest once (TS, Python, Go, PHP), `link` performs no I/O, a `--workspace` subset run (other stored workspaces are hydrated but not mapped or prepared, so their packages count as external), TS side-effect/dynamic/`require` package imports, package re-exports, default import with zero or two default exports, resolver following `import:package` steps for the four real languages with the ordered path, positive anchored-file filter, `graph impact` dependents across workspaces, fingerprint test that edits `exports`.
   3b. **Also from the third audit.** Tests for "capability flags and facets are separate", "a facet does not satisfy a capability flag", "linking performs no I/O" (spy on fs), closure does not re-extract unrelated files; `matchSpecifier`/`entrySurface` failing in Pass 2 skips the file without disabling the adapter; `resolutionManifests()` values not validated at registration; bindings without target ignored in the ambiguity check; Python `matchSpecifier` matching `acme-auth` and `acme_auth` in insertion order.
   3c. **Smaller spec/code mismatches from the audits.**
   - PHP `prepare` reads `composer.json` twice (`buildPsr4Map` and `getPackageIdentity`); read it once, and add a read-count test.
   - Spec text says the `package-unknown` reason is reported, but the indexer counts it only in `externalPackageImports`; align the wording of `code-graph:language-adapter` and the tests.
   - `--workspace` subset runs: other stored workspaces are hydrated but their package identities are not mapped and they are not prepared, so their packages count as external. Decide: map and prepare every configured workspace, or document the limit in `code-graph:indexer`.
   - TS `prepare` keeps the whole parsed `package.json` instead of compact data.
   - TS `dist` mapping also accepts `.jsx` and `.d.ts` targets and maps non-`dist` paths 1:1; the spec only says `dist`.
   - PHP `qualifiedNameEntries` returns one candidate per matching prefix, not a single class file.
   - Python `from pkg import X` finds no submodule dependency when `pkg/__init__.py` is missing; the spec is silent.
   - Go: package directory is computed relative to the workspace code root (wrong if `go.mod` sits above it; same root cause as item 1).
   - The PHP own-PSR-4 fallback (workspace without a Composer `name`) is implemented and tested but not described in `code-graph:php-language-adapter`.
   - `docs/code-graph/language-adapters.md` checklist steps 6 and 7 point to the spec; inline the content for readers without spec access.
     3d. **Fourth audit (20261021-081835).**
   - Identity is first-adapter-wins; the spec is silent (only docs). A workspace with `package.json` and `composer.json` loses the second identity. Decide: spec the rule, or ask every adapter.
   - Excluding test symbols from the global qualified-name map also drops test-to-test-helper bindings; add a test or scope the exclusion to non-test importers.
   - `hydratePersistedFile` never fills the qualified-name map (baseline): incremental PHP/Python/Go name-addressed imports may differ from a clean rebuild. Add incremental tests for those languages and fix.
   - Identity failure also stops TS barrel (relative) re-export linking for the whole run, because the adapter is disabled; the spec only says `packageResolution` is treated as absent. Decide: spec it or keep link independent.
   - `find-manifest-field` walks to the filesystem root when `codeRoot` is outside `repoRoot` (external workspace, symlink, trailing slash); a nearest manifest without a name is skipped silently.
   - PHP `buildPsr4Map` merges `autoload` and `autoload-dev` with a spread, so a shared prefix loses its production directories; PHP own-PSR-4 fallback can return a test file and still tries an absolute id.
   - TS `import type X from` ignores `typeOnly` for the default import; TS namespace member access through published names is not implemented.
   - Go: a quoted `module "x"` line keeps its quotes.
   - Registry validation does not map malformed `languages()`/`extensions()` results to `INVALID_LANGUAGE_ADAPTER`.
   - `scoped-binding-environment` falls through to the same-name search when `findById` misses (practically unreachable); the addition fallback fires on any new file, not only code files.
   - `adaptersWithoutPackageResolution` is deduped by language string.
   - Python `matchSpecifier` normalizes only `_` to `-`.
   - Tests: Python "unknown project is not guessed", "unimported name keeps the workspace lookup", manifest change end to end, workspace added, identity throws with a healthy second workspace/adapter, PHP no-FS after deleting `composer.json` for `entrySurface`/`matchSpecifier`, `.py` + `.pyi` end to end, package re-export dependencies, side-effect/dynamic/`require` package imports, Python `import pkg.mod` and `importlib`, Go blank/dot imports, `package-resolution.spec.ts:425` title contradicts its assertion.
4. **Test titles.** Normalize the casing of test titles added by the previous change.
