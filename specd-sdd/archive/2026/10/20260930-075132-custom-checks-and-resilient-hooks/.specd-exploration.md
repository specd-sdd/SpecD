# Exploration Context: custom-checks-and-resilient-hooks

Generated: 2026-09-30

## Problem Statement

1. **Rigid Hook Execution**: Lifecycle transition hooks (such as `pre` hooks in `ready`, `implementing`, `verifying`, etc.) fail fast upon any non-zero exit code. Teams are forced to resort to shell workarounds like `|| true`, which destroy visibility into real exit codes, stdout, and stderr. There is no first-class mechanism in `HookEntry` to permit a non-fatal failure with warnings.
2. **Closed Transition Checks**: Lifecycle transition checks (`CheckId`) are statically defined as a closed union of 15 literals in `@specd/core`. Third-party plugins, extensions, or customized workflow schemas cannot define, register, or bind custom transition checks.
3. **Conceptual & Operational Ambiguity**: Users and developers lack clear formal guidance distinguishing between **Checks** (in-memory, deterministic state invariants evaluated in `status` and `transition`) and **Hooks** (asynchronous, side-effecting shell/external processes executed during transitions).
4. **Ad-Hoc CLI Flags**: Bypassing checks relies on one-off flags (e.g., `--allow-out-of-scope`), which does not scale to custom checks.

## Approach / Solution Outline

- **Open Check Registry (`CheckRegistry`)**:
  - Replace closed `CheckId` union with dynamic string IDs.
  - Runtime `CheckRegistry` is the single source of truth for check definitions and bindings.
  - Strict namespacing: external checks registered via `register(pluginName, check)` are canonically assigned `@${pluginName}.${check.id}`.
  - Built-in checks (`protocol.edge`, `workflow.requires`, etc.) are constructor-injected and immutable; no `registerBuiltin` is exposed on the public registry interface.
  - Strict predicate-only invariant: custom checks must be `kind: 'predicate'`. Custom `effect` checks are strictly rejected (`InvalidCheckKindError`) because effects belong exclusively to Hooks.
- **Dual-Form Kernel Construction (ADR-0018)**:
  - Form 1: Static `KernelOptions` / `CompositionRegistryInput` accepting `checks?: readonly PluginCheckRegistration[]` in `createKernel(config, options)`.
  - Form 2: Fluent `KernelBuilder` via `createKernelBuilder(config).registerCheck(pluginName, check, defaultBindings?).build()`.
- **Declarative Schema Bindings (`schema.yaml`)**:
  - Extend `WorkflowStep` to declare step-level checks: `checks: [{ id: '@security.code-scan', along: forward, onFailure: abort, skippable: true, options: { ... } }]`.
  - Validation in `buildSchema` ensures check declarations are structurally valid.
- **Resilient Hook Failure Policies**:
  - Extend `HookEntry` with `onFailure?: 'abort' | 'warn'` (default: `'abort'`).
  - In `RunStepHooks`, when a hook with `onFailure: 'warn'` fails, capture its real exit code, stdout, and stderr into `warnings[]` and permit the phase to succeed with `success: true`.
  - `HookEffectCheck` passes if `RunStepHooksResult.success` is true, keeping transitions unblocked while preserving complete failure telemetry.
- **Uniform CLI Interface**:
  - Standard `--skip-checks <id1,id2>` flag on `specd changes transition <name> <step>`.
  - Enforce `skippable: true` declaration; reject non-skippable checks with `CheckNotSkippableError`.
  - Maintain `--allow-out-of-scope` as backward-compatible alias.
  - Render structured Repair Guides for custom check failures via `CheckPredicateFailedError`.
- **User & Developer Documentation**:
  - Comprehensive guide in `@specd/guide` and ADR detailing Checks vs. Hooks.

## Key Design Decisions & Agreements Reached

1. **Check Namespacing & Built-in Protection**:
   - `pluginName` is mandatory, non-empty, and validated against `^[a-zA-Z0-9_-]+$`.
   - The registered check ID is automatically transformed to `@${pluginName}.${check.id}`.
   - Built-in checks have unprefixed IDs (`protocol.edge`, `workflow.requires`) and are immutable.
   - `registerBuiltin()` must NOT be exposed on the public `CheckRegistry` interface.
2. **Predicate-Only Constraint**:
   - Checks are state invariants (in-memory queries). Custom checks of `kind: 'effect'` are explicitly rejected.
   - Any operational action, shell command, or side effect must be modeled as a Hook.
3. **Dual-Form Kernel Registration**:
   - Must support both `createKernel(config, { checks: [...] })` and `createKernelBuilder(config).registerCheck(...).build()`.
4. **Hook Failure Policy**:
   - `onFailure: 'warn'` captures real process telemetry (exitCode, stdout, stderr) in `warnings[]` without aborting transition.
5. **CLI Bypass**:
   - `specd changes transition <name> <step> --skip-checks <ids>` delegates to use case `skipChecks` set.
   - Enforces `skippable: true`.
   - CLI remains a thin adapter delegating strictly to application use cases.
6. **Two-Tier Governance, Binding Coordinates & Options Hierarchy**:
   - **Binding Coordinate Identity**: A binding is uniquely identified by `{ checkId, scope: 'transition', to, along }` (or `{ checkId, scope: 'archive' }`). Duplicates on the exact same coordinate are rejected with `DuplicateCheckBindingError`.
   - **Check-Level Registration** (`PluginCheckRegistration`):
     - `defaultConfig`: Common baseline config applicable across all bindings of this check.
     - `allowConfigOverride`: Global permission for schemas to supply or override config.
     - `allowBindingOverride`: Global embedding lock. If `false`, the check CANNOT be embedded into any workflow steps beyond its declared kernel bindings (`CheckEmbeddingForbiddenError`).
   - **Binding-Level Declaration** (`CheckBindingSpec`):
     - `config`: Overrides/specializes check-level `defaultConfig` for this specific coordinate.
     - `allowBindingOverride`: Policy lock on that specific coordinate. If `false`, locks `onFailure` and `skippable` for that coordinate only (`CheckBindingOverrideForbiddenError`). It does NOT prevent the check from being bound to other steps (governed by the global lock).
     - `allowConfigOverride`: If `false`, locks this specific coordinate's config against schema override (`CheckConfigOverrideForbiddenError`).
   - **Runtime Cascaded Injection**:
     - Effective config computed as `{ ...check.defaultConfig, ...binding.config, ...schema.stepConfig }` and attached to `ctx.config`.
7. **Dual-Source `skip` Semantics**:
   - `outcome: 'skip'` applies symmetrically to built-in and custom checks.
   - Source 1 (Self-Discard): A check (built-in or custom) inspects its `CheckExecutionContext` (`ctx.schema`, step `config`, touched files, workspace settings) and returns `{ outcome: 'skip', message: '...' }` when its internal logic determines it does not apply.
   - Source 2 (Orchestrator Bypass): When a check would run but the user passes `--skip-checks <id>`, the orchestrator validates `skippable: true` and generates `{ outcome: 'skip', details: { bypassedByUser: true } }` without invoking `check.execute()`. Mandatory checks (`skippable: false`) cannot be bypassed and throw `CheckNotSkippableError`.
8. **Check Authoring Contract & Orchestrator Execution Pipeline**:
   - `Check` defines `id`, `label`, `kind: 'predicate'`, and `execute(ctx: CheckExecutionContext): Promise<CheckResult>`.
   - External dependencies/ports are injected via constructor/factory (`createMyCheck(...)`); invocation data (`change`, `schema`, `attempt`, `config`, `validity`) is provided via `ctx`.
   - Execution pipeline in `TransitionChange` and `GetStatus`:
     1. Match active bindings by `attempt` (`from`, `to`, `along`).
     2. Intercept `--skip-checks` (assert `skippable: true` or throw `CheckNotSkippableError`; emit synthetic `skip`).
     3. Inject effective config into `ctx.config`.
     4. Emit `check-start` event.
     5. Execute `await check.execute(ctx)`.
     6. Emit `check-done` event.
     7. Evaluate result: on failure, respect `onFailure` policy (`abort` throws `CheckPredicateFailedError` with repair guide, `collect` accumulates).
     8. `GetStatus` runs matching predicates against `nextAction.targetStep`, projecting failing checks as blockers in `lifecycle.blockers`.

9. **Ergonomic Public Contract Separation (`CustomCheckDefinition` vs internal `Check`)**:
   - Rather than requiring plugin authors to provide engine internals like `kind: 'predicate'`, the public authoring contract is `CustomCheckDefinition` (`id`, `label`, `execute(ctx)`).
   - The engine automatically adapts `CustomCheckDefinition` into the internal `Check` with `kind: 'predicate'` and canonical namespacing `@${pluginName}.${id}` upon registration in `CheckRegistry`.
   - `InvalidCheckKindError` remains as a defensive runtime assertion if an untyped object explicitly supplies `kind !== 'predicate'`.

## Rejected Alternatives

- **Static `CheckId` Union**: Rejected because it prevents extensions and modular plugins.
- **Exposing `registerBuiltin()` on public interface**: Rejected to eliminate the risk of external code tampering with core protocol invariants.
- **Custom Effect Checks**: Rejected because allowing checks to run external commands creates confusion with hooks, breaks `changes status` projection, and invalidates pure DAG invariant queries.
- **Requiring `kind: 'predicate'` in public plugin check type**: Rejected in favor of `CustomCheckDefinition`, which omits internal engine details and stamps `kind: 'predicate'` automatically upon registration.
- **Using `options` for check payloads**: Rejected in favor of `config` to harmonize with `ExternalHookDefinition` (`config: Record<string, unknown>`) and eliminate terminology collision with function call options.
- **Ad-hoc CLI flags per custom check**: Rejected to avoid dynamic Commander flag inflation and option collision.

4. User required mandatory `pluginName` parameter in `register()` composing canonical `@pluginName.id` to prevent collision with built-in checks.
5. User raised concern about `registerBuiltin()` exposure; agreed built-ins must be constructor-injected and immutable.
6. User instructed to create the change.
7. Refined technical proposal:
   - User clarified custom checks must NOT be `effect` kind (checks are strictly predicates; effects are hooks).
   - User pointed out missing kernel build / registration mechanism: must support both existing kernel creation forms (static `createKernel` and fluent `createKernelBuilder`).
8. Proposal updated with dual-form kernel construction and verified against schema.
9. Workflow correction: User reminded agent to adhere strictly to the `/specd-new` workflow protocol before proceeding to `/specd-design`.
10. Two-tier governance and options hierarchy refined (global vs coordinate locks, binding identity coordinate `{ checkId, scope, to, along }`, dual-source skip).
11. Public ergonomic contract separation: user suggested not requiring authors to specify engine internals (`kind`); separated `CustomCheckDefinition` from internal `Check`, keeping `InvalidCheckKindError` as a defensive runtime guard.
12. Harmonized configuration terminology: replaced `options` with `config` (`defaultConfig`, `allowConfigOverride`, `ctx.config`, `CheckConfigOverrideForbiddenError`) to align with `ExternalHookDefinition` and prevent ambiguity with function options.
13. Per-check isolated `ctx.config`: the orchestrator constructs `ctx.config` as the cascaded merge `{ ...check.defaultConfig, ...binding.config, ...schema.stepConfig }` specifically for each check instance prior to calling `check.execute(ctx)`.
14. Retirement of hardcoded check bypasses: eliminated ad-hoc check branches in `GetStatus._mergeBlockers` (`linksInScopeSkippable`, `overlapSkippable`) and purged ad-hoc booleans (`allowOutOfScope`, `allowOverlap`) from `CheckExecutionContext`. `GetStatus` derives `bypassFlag: '--skip-checks ' + check.id` generically for any check with `skippable: true`.
15. Audit and explicit modification matrix for built-in checks: all 15 existing checks audited. `impl.linksInScope` and `spec.overlap` explicitly declare `skippable: true`, while the remaining 11 predicate checks declare `skippable: false`. Backward-compatible CLI aliases (`--allow-out-of-scope`, `--allow-overlap`) map into `--skip-checks`.
16. Unification of Use-Case inputs: Dropped `allowOutOfScope` and `allowOverlap` from `TransitionChangeInput` and `ArchiveChangeInput` in favor of a universal `skipChecks?: readonly string[]` array to deduplicate bypass logic.
17. Error Abstraction Deduplication: Eliminated duplicated bespoke error classes (`ArchiveImplementationStateError`, `ArchiveDependencyMismatchError`, etc.) in `TransitionChange._mapFailedPredicate`. All predicate failures (built-in and custom) are unified under `CheckPredicateFailedError`, radically simplifying the CLI Repair Guide rendering.
18. Boundary Guardrail for `skip-checks` vs `skip-hooks`: Enforced that `--skip-checks` strictly validates `kind: 'predicate'` (rejecting targets like `hook.pre` with `CheckNotSkippableError`), maintaining the explicit operational boundary where effects are only bypassed via `--skip-hooks`.
19. Developer Documentation: Decided to mandate a documentation update including a new `docs/core/custom-checks.md` guide for integrators, along with user-facing updates to `workflow.md`, `configuration.md`, and `cli.md` in `docs/guide/` to document the new `onFailure` hook policy and the `--skip-checks` bypass flag.
20. Skippability Purely on Bindings: Removed `skippable` from `CustomCheckDefinition` and `Check`. In alignment with core architecture (_"Routing lives on CheckBinding, not on the check"_), whether a check can be bypassed is strictly a property of the transition coordinate / workflow binding (`CheckBindingSpec`, `CheckBinding`, `WorkflowStepCheckDeclaration`), not an intrinsic property of the check logic itself.
21. Reusable Core Deep Merge Helper (`deepMergeConfig`): Extracted deep merge logic (currently in `packages/core/src/application/ports/config-schema.ts` as `deepMergeRawConfig`) into a shared domain service helper `packages/core/src/domain/services/deep-merge-config.ts`. Both config cascade and check configuration resolution (`resolveEffectiveCheckConfig`) use this pure helper to support arbitrary nested records of records without shallow-spread key obliteration or hexagonal layer boundary violations.
