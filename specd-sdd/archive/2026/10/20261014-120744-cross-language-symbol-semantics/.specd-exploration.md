# Exploration: cross-language-symbol-semantics

Generated: 2026-10-14

## Problem statement

The user requested a new standalone change to correct cross-language symbol semantics and to make the normative behavior explicit in specs so future language adapters do not repeat the same errors.

The investigation started from the untracked analysis document `SpecD — Análisis de identidad LogicalSymbol, dependencias y casos de uso.md`. Its conclusions were independently checked against the current code graph, canonical specs, source code, focused runtime reproductions, and the complete `@specd/code-graph` test suite.

The central issue is not limited to TypeScript. Some defects are currently easiest to reproduce in TypeScript because its adapter extracts a broader set of local declarations, but the invalid caller-selection algorithm and the logical/physical boundary problems are shared across the supported languages and common graph services.

## User intent and preferences

- Create a new change dedicated to this work.
- Specify the correct behavior normatively before implementation.
- Make the common language-adapter contract strong enough that new languages cannot repeat these mistakes.
- Treat the work as cross-language, covering TypeScript, Python, Go, and PHP.
- Preserve physical evidence while exposing semantic identity consistently.
- The user explicitly authorized ignoring the existence and overlap of the other active changes. This change must be designed on its own merits and must not narrow or defer its scope merely because `code-graph-file-outline` or `code-graph-symbol-semantic-context` also target some of the same specs.

## Required architecture and normative direction

The design should formalize three distinct identity layers:

1. `SymbolNode` / `DeclarationOccurrence`: physical, location-backed source evidence and navigation.
2. `LocalBinding`: lexical identity for parameters, aliases, receivers, and local variables whose meaning belongs to a scope.
3. `LogicalSymbol`: canonical semantic identity for language-defined targets that may have one or more physical declarations.

These layers must not be treated as bijective. A physical symbol may legitimately lack a logical symbol when the language policy classifies it as lexical-only evidence. A logical symbol may own multiple declarations only when the language defines them as one semantic target, such as a TypeScript overload set or declaration merge. Competing declarations must remain distinct.

Physical dependency relations remain the authoritative evidence graph. Semantic search and impact should project or aggregate physical relations by logical identity while retaining every physical edge and location that justifies the semantic result. Physical-only endpoints must remain visible rather than disappearing from semantic results.

## Normative requirements expected during design

### Semantic caller containment

- A `CallFact.callerSymbolId` must identify the semantically valid callable/container whose parser-derived range contains the call site.
- A symbol that merely starts before the call is not an enclosing caller.
- Caller selection must use full source coordinates, including columns for same-line declarations.
- The selected caller kind must be allowed by the language policy, normally a function, method, callable initializer, or another explicitly supported executable container.
- Local variables, properties, types, or unrelated preceding declarations must not usurp the caller role.
- The shared fallback in `scoped-binding-environment.ts` must obey the same rule.
- Adapters must not implement private copies of line-only nearest-preceding selection.
- When no supported containing caller can be proven, the call remains caller-unresolved rather than receiving a speculative source.

### Logical identity and lexical scope

- Every adapter must declare which syntactic categories produce logical symbols, lexical bindings only, physical symbols only, or no graph declaration.
- Logical identity must include a canonical logical owner whenever the language defines an owner.
- Nested functions, closures, callable variables, local types, and block-scoped declarations require an explicit policy per language.
- Same-name declarations in different lexical scopes must not collapse unless the language defines them as one binding.
- Repeated declarations that form one language-defined binding or overload set may share one logical identity.
- Ordinary line or column movement must not change logical identity.
- Physical IDs may remain location-backed.
- Parameters and ordinary local variables should normally be modeled as `LocalBinding` unless a language-specific contract establishes a stable semantic target.
- Classification must not depend only on broad `SymbolKind`; declaration role, scope, visibility, and language semantics matter.

### Overloads and declaration groups

- TypeScript overload signatures and their implementation form one logical method/function target.
- Adding or removing overload signatures must not accidentally change the logical member from `method` to `signature` if it remains the same semantic member.
- Declaration-level signature/implementation form should not be confused with logical-target member semantics.
- Selectors and impact must preserve the complete declaration set for a logical target.

### Selector and resolution boundary

- Resolution results must discriminate logical targets from exact physical declarations.
- Logical resolution must carry all declaration occurrences and resolution evidence.
- File/line/column navigation may select an exact declaration.
- Qualified or canonical logical selectors must not be collapsed to an arbitrary first declaration.
- Ambiguity must be calculated at the semantic layer for semantic selectors and at the declaration layer for physical selectors.
- Existing public compatibility must be assessed explicitly; silent reinterpretation of `symbolId` is not acceptable.

### Impact semantics

- Physical `CALLS`, `CONSTRUCTS`, `USES_TYPE`, `EXTENDS`, `IMPLEMENTS`, and `OVERRIDES` edges remain evidence.
- Impact of a logical target must start from all of its physical declarations.
- A public binding impact must continue to distinguish exact-route impact from canonical-target impact.
- Affected semantic targets should be deduplicated by logical ID while preserving declaration-only results for physical symbols without a logical mapping.
- Counts and risk must define whether they measure physical occurrences, semantic targets, or both; they must not mix the units silently.
- SDK and CLI orchestration must propagate logical resolution instead of reducing it to one `SymbolNode.id`.

### Spec coverage identity

- `COVERS_SYMBOL` has a single normative target identity across indexing, storage, traversal, SDK, and CLI.
- Current canonical indexing writes `COVERS_SYMBOL` against `LogicalSymbol.id`; readers must therefore project physical traversal results to logical IDs before reverse coverage lookup, or the contract must be deliberately redesigned everywhere.
- Tests must not fabricate physical-target coverage relations when production indexing emits logical-target relations.
- Coverage evidence returned to users must retain physical declaration locations where available.
- A physical symbol without a logical identity needs an explicit `not applicable`, `unresolved`, or physical-coverage policy; it must not be silently misclassified.

### Future language adapters

Every new built-in language adapter must pass shared contract tests covering:

- parser-derived declaration ranges and exact containment;
- semantic caller selection, including same-line and multiline declarations;
- nested declarations and declarations following unrelated symbols;
- logical owner creation before member identity creation;
- same-name declarations under different owners/scopes;
- language-defined merged declarations or the explicit absence of them;
- physical symbols without logical identity;
- selector resolution preserving all declarations;
- logical coverage lookup after physical impact traversal;
- incremental indexing equivalence to a clean rebuild for identity-sensitive changes.

Language-specific specs must add their own scenarios for syntax and semantics not expressible in the generic contract.

## Confirmed current-code observations

### Caller selection is line-only in all adapters

The same nearest-preceding algorithm exists in:

- `packages/code-graph/src/infrastructure/tree-sitter/typescript-language-adapter.ts`, `findEnclosingSymbolIdByLine`
- `packages/code-graph/src/infrastructure/tree-sitter/python-language-adapter.ts`, `findEnclosingSymbolIdByLine`
- `packages/code-graph/src/infrastructure/tree-sitter/go-language-adapter.ts`, `findEnclosingSymbolIdByLine`
- `packages/code-graph/src/infrastructure/tree-sitter/php-language-adapter.ts`, `findEnclosingSymbolIdByLine`
- `packages/code-graph/src/domain/services/scoped-binding-environment.ts`, `findEnclosingSymbol`

Each implementation filters by `symbol.line <= call.line` and selects the greatest line/column. None proves range containment.

### TypeScript caller defect reproduced

For:

```ts
function process() {
  const result = Service.run()
}
```

the adapter emitted `process` and `result`, classified `result` as a function, and assigned `Service.run()` a `callerSymbolId` pointing to `result` rather than `process`.

`processVariableDeclarator()` currently classifies every variable initialized by a `call_expression` as `SymbolKind.Function`, even when the returned value is not known to be callable.

Python, Go, and PHP selected the expected enclosing function in simple equivalent reproductions because their current extraction did not emit the intervening local assignment as a symbol. This is accidental protection, not a correct algorithm. Broadening their local-symbol extraction would expose the same defect.

### Logical collisions reproduced

- Two TypeScript local functions named `same` in different nested scopes received the same `LogicalSymbol.id`.
- Two TypeScript block-local callable variables named `result` in alternate branches received the same `LogicalSymbol.id`.
- The current repository index itself groups some different same-name declarations in one file, including variable/property-like occurrences, under one logical ID.

The root ordering problem is that TypeScript builds `referenceFacts` from raw symbols and only returns `symbols: withEnclosingTypeParents(symbols)` afterward. Logical owner construction therefore does not consume the richer physical parent hierarchy. The adapter separately builds a mostly type-member-only owner map.

Python explicitly owner-qualifies nested classes and class members. PHP owner-qualifies type members and uses namespace/file surface. Go uses package surface and receiver ownership. Their currently extracted declaration sets reduce some collision opportunities, but every adapter still relies on the same shared logical-ID constructor and can collapse descriptors with identical semantic components.

### Overload identity instability reproduced

A single TypeScript method receives logical member semantics `{ kind: method, dispatch: instance }`. Adding overload signatures causes the declarations to share an identity with `{ kind: signature }`. The logical ID therefore changes when overload declarations are added or removed even though the semantic method remains the same member.

### Selector-to-impact declaration loss

`resolve-graph-selector.ts` now unifies candidates sharing one logical ID, so the older claim that every overload necessarily appears ambiguous is outdated. However, the unified result still retains one primary physical `symbolId`.

`packages/sdk/src/orchestration/run-graph-impact.ts` resolves the selector, loads that one symbol, and calls provider impact using only its physical ID. `CodeGraphProvider.analyzeImpact()` invokes the domain service without logical resolution. The domain `analyzeImpact()` can traverse all declaration occurrences when supplied with a resolution, but the public orchestration path does not supply it.

### Coverage write/read mismatch

`project-spec-coverage.ts` creates `COVERS_SYMBOL` with `target: resolved.target.id`, which is a logical ID. SQLite validates and persists logical coverage targets.

Impact coverage readers such as `collect-impact-specs.ts` and `analyze-file-impact.ts` query reverse symbol coverage using physical symbol IDs gathered from traversal. Existing impact tests often construct `COVERS_SYMBOL` relations against physical IDs, which does not match production indexing.

This can produce empty `affectedSpecs` or `coveringSpecs` even when logical symbol coverage exists.

### Incremental indexing

- `retainReferenceFactsOutsidePaths()` keeps declarations outside replaced paths, retains logical symbols referenced by those declarations, filters bindings, and removes invalid resolution steps.
- `collectAffectedFileClosure()` expands from physical reverse dependencies and semantic resolution steps/bindings.
- New files conservatively add all existing files as candidates so previously unresolved imports can resolve.
- `replaceReferenceFactsInTransaction()` replaces the semantic snapshot globally.
- `deleteFileLocalState()` removes physical relations incident to deleted/replaced symbols.

If the affected closure misses a consumer, incident relations to the old physical symbol are deleted; the likely failure is a silently lost dependency, not a surviving orphan relation. Incremental tests should compare final semantic state against a clean rebuild.

## Proposed implementation sequence

1. Establish shared contracts and contract-test fixtures before implementation.
2. Replace line-only caller selection with range-based semantic containment in the shared layer and all adapters.
3. Define adapter declaration-classification policy and propagate physical ownership into logical descriptor construction.
4. Stabilize overload-group semantics and prevent competing-scope collisions.
5. Introduce or refine discriminated logical/declaration selector results while planning public compatibility.
6. Propagate complete logical resolution through provider, SDK, and CLI impact flows.
7. Align `COVERS_SYMBOL` generation, persistence, reverse lookup, and evidence projection.
8. Add logical aggregation of impact results without removing physical evidence.
9. Add incremental-versus-full-rebuild equivalence tests for line movement, body changes, overload changes, renames, moves, additions, and deletions.
10. Run complete package and cross-platform verification.

## Rejected or insufficient approaches

- Fixing only TypeScript: rejected because the invalid algorithm is duplicated across every adapter and common services are affected.
- Removing local variables from `SymbolNode` wholesale: rejected as too coarse; some physical declarations are useful evidence, and classification must be language- and role-aware.
- Replacing physical dependency relations with logical relations: rejected because physical relations provide concrete traceability and locations.
- Adding line/column to `LogicalSymbol.id`: rejected because ordinary positional movement must not change semantic identity.
- Treating every physical symbol as requiring a logical symbol: rejected because lexical bindings and ephemeral locals are not necessarily persistent semantic targets.
- Treating every same-name declaration as distinct: rejected because overload sets, declaration merges, and language-defined repeated declarations may form one semantic target.
- Relying only on current passing tests: rejected because direct reproductions demonstrate missing scenarios.
- Deferring or shrinking this change due to active overlapping changes: explicitly rejected by the user for this change.

## Open design questions

- Exact adapter policy table mapping syntax/declaration roles to physical symbol, local binding, and logical symbol.
- Whether local named functions or callable variables deserve logical identity in each language.
- How anonymous/block scopes receive deterministic binding identities without pretending they are stable public semantic targets.
- Final discriminated selector types and compatibility strategy for provider/SDK/CLI consumers.
- Whether semantic dependency projection is computed on demand, exposed as a service, represented by a SQLite view, or materialized.
- Exact counting and risk semantics for physical occurrences versus logical targets.
- Coverage behavior for physical-only declarations.
- Whether logical member semantics need declaration-level occurrence metadata to represent signature versus implementation without destabilizing the target ID.
- How generic adapter contract tests are parameterized so third-party/new adapters can reuse them.
