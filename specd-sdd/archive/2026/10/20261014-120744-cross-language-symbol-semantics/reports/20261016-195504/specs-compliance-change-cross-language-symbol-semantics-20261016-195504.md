## Discrepancies

D1 (MEDIUM, code vs spec) Structural classification from raw lines/text

- Spec: language-adapter "Parser-authoritative structural extraction": "declaration role ... SHALL be derived from typed parser nodes ... Raw-source regular expressions or substring scans MUST NOT independently decide that such a ... fact exists." A regex over text already isolated by a parser node is allowed, but must not escape the node.
- Code: PY `pythonMemberSemantics` reads `lines[symbol.line-2 ...]` upward until a line not starting with `@` (`python-language-adapter.ts:127-146`). PHP `phpMemberSemantics` tests `/\bstatic\s+function\b/i` against the single source line `lines[symbol.line-1]` (`php-language-adapter.ts:335-342`). Both escape the declaration node.
- PROBE (PY): `@staticmethod` followed by a comment line then `def q` => q classified instance (decorator missed); `@staticmethod` above a multi-line `@other(\n 1)` then `def g` => g classified instance.
- PROBE (PHP): `class A { function a(){} static function b(){} }` => both `a` and `b` get `dispatch: static`; `static\n function b(){}` (modifier on previous line) => instance.
- Spec side is clear; code side is a leftover heuristic. Fix direction: read decorators (`decorated_definition` children) / `static_modifier` child.

D2 (HIGH, code violates spec) Name-only CALLS/hierarchy in Pass 2

- Spec: language-adapter "Call resolution": callee resolved "through deterministic local symbols, resolved imports, receiver bindings"; "ambiguous member expressions ... SHALL be silently dropped"; "Detectable dependency boundary": heuristic cases MUST NOT emit relations; "textual proximity MUST NOT be used". Go: "interface dispatch without a proven concrete target ... SHALL not produce guessed relations".
- Code: TS `localSymbolsByName.set(s.name, s.id)` (last wins) then `importMap.get(call.name) ?? localSymbolsByName.get(call.name)` for every free call (`typescript-language-adapter.ts:~1329-1352`); GO same for every call form incl. selector calls (`go-language-adapter.ts:639-660`); PY attribute calls resolved by `resolveLocalCallee` with `s.line <= callLine` nearest-preceding tie-break (`python-language-adapter.ts:947-969`).
- PROBE TS: `class A { helper(){} } function run(){ helper() }` => `CALLS run -> A.helper` (a free call cannot target a method).
- PROBE TS: two same-named nested functions, call `w()` in `b` => resolves to the _last_ `w` in file.
- PROBE PY: `class A: def save..; class B: def save..; def run(x): x.save()` => `CALLS run -> B.save` (unknown receiver; picked by line proximity). With one class it also links.
- PROBE GO: `type A/B` each with `Save`; `func Run(x I){ x.Save() }` => `CALLS Run -> B.Save`.
- Note: the same facts also flow through the shared scoped-binding resolver (`resolvedDependencies`, `index-code-graph.ts:1199`), so these adapter-level edges are redundant and the only source of false positives. PHP buildRelations emits no CALLS of its own (compliant).
- Existing tests that assert this behaviour: TS `typescript-language-adapter.spec.ts:937-966`, GO `:676-725` (asserts CALLS to same-name local function).

D3 (HIGH) Property members lack a declaring-owner logical identity (TS, Go)

- Spec: language-adapter "Logical declaring-owner facts" and TS/Go specs ("Struct fields ... having their declaring struct type as their logical owner"; "property declarations SHALL carry the logical identity of their declaring class or interface").
- Code: TS final fallback descriptor uses `ownerByMemberId.get(symbol.id)` which only contains _method_ ids (`TsTypeDeclarationInfo.memberSymbolIds`), `requiresOwner:false` (`typescript-language-adapter.ts:~960-970`). Go: same pattern (no owner map for fields).
- PROBE TS: `class A { x = 1 }` => logical id `ws|a.ts|x|value|<no owner>` (indistinguishable from top-level `x`); `class A { x = 1 } class B { x = 2 }`, `interface I{p:string} interface J{p:number}`, `enum E{One} enum F{One}` => all those members vanish from logical declarations (ownerless collision then conflict-drop). `class A { run = () => 1 }` (field-method) likewise. Method members are correctly owner-qualified.
- PROBE GO: `type S struct{ X int }` => `X` logical id `ws|.|X|value` ownerless; two structs with field `X` => both dropped.
- Python/PHP properties, class constants, enum cases are owner-qualified (PROBE), so only TS/Go are non-conformant.
- Related: TS/Go publicBindings are built from `!ownerByMemberId.has(symbol.id)`, so fields leak as public exports (Go: D10, TS: PROBE `export class S { Field = 1 } export const Field = 2` yields two `Field` bindings, one with `targetId` undefined).

D4 (MEDIUM) Mutable adapter-instance state and Pass-2 FS I/O in TS

- Spec: "Pass 2 ... MUST NOT perform metadata filesystem I/O or rely on mutable adapter-instance caches shared across sessions"; "MUST NOT perform side effects outside the indexing session".
- Code: `private readonly workspaceCodeRoots = new Map()` (`typescript-language-adapter.ts:452`), written inside `analyzeFile` (`:564`), read in `packageEntryCandidates` (`:2492`) which calls `readFileSync(join(codeRoot,'package.json'))` at `:2496` for each re-export specifier, no session-state caching. Only guard is a test of the PHP path.
- Spec nuance: re-export spec says the adapter "may read package manifests"; but the general requirement wording forbids instance caches; an adapter instance is shared by `registry.register(new TypeScriptLanguageAdapter())` across sessions, so a second session sees the first one's roots.

D5 (MEDIUM) Wrong member semantics

- TS `typeScriptMemberSemantics` (`:~399-427`): `^(modifiers)*get\b` against `node.text()` matches a method _named_ `get`/`set`. PROBE: `class A { get() {} set() {} static() {} }` => `get` and `set` become `property/get` and `property/set`. (`static(){}` is fine.)
- PY: see D1. PHP: see D1.

D6 (HIGH) TS lexical-scope distinctness / overload identity

- Spec (TS): "Same-name functions in different lexical owners do not group"; "Nested named functions or callable variables ... MUST include deterministic lexical ownership"; "Alternate branches ... MUST NOT collapse".
- Code: group key for functions is `function:${filePath}:${symbol.name}` when more than one same-named function exists in the file (`typescript-language-adapter.ts:~954-958`), and the logical id has no lexical owner.
- PROBE: `function a(){ function w(){} } function b(){ function w(){} }` => both `w` share logical id `ws|a.ts|w|value`; `function f(x){ if(x){ const result = () => 1 } else { const result = () => 2 } }` => both `result` share one logical id (two occurrences).
- Existing test `typescript-language-adapter.spec.ts:1518` only covers a non-callable local.

D7 (HIGH) TS overload identity unstable and function overloads dropped

- Spec (TS "overload and declaration-group identity"): "Adding, removing, or reordering overload signatures MUST NOT change the logical target's canonical identity"; logical kind stays `method`; "Function and method overload signatures along with implementation SHALL be united".
- PROBE: `class A { find(a:any){} }` => member semantics `method/instance`; `class A { find(a:string):void; find(a:number):void; find(a:any){} }` => all three occurrences share a logical id whose member kind is `signature` (different id). The normalisation block `if (hasImplementation && sem?.kind === Signature)` (`:~918-935`) does not fire for the implementation in this shape.
- PROBE: `function g(a:string):void; function g(a:number):void; function g(a:any){}` => only one symbol (`g`, col 54) is extracted; signatures (`function_signature`) are not extracted, so a function overload group never forms.
- Existing test `typescript-language-adapter.spec.ts:1483` asserts `logicalIds.size === 1` and occurrence forms but never asserts the id equals the no-overload id or that kind is `method`.

D8 (MEDIUM, scoped-binding fallback) see X6 above: `scoped-binding-environment.ts:487-499`.

D9 (MEDIUM) Python base lookup is name-only after stripping the qualifier

- `normalizePythonTypeName('other.Foo')` => `Foo` then `classesByName.get('Foo')` (`python-language-adapter.ts:~108-119, ~808-812`). PROBE: `import other\nclass Foo: pass\nclass C(other.Foo): pass` => `EXTENDS C -> Foo` (local Foo), though the base is `other.Foo`. Also `classesByName` is keyed by simple name (duplicate class names in one file collapse).

D10 (LOW) Generic code language-name branch and dead code: `in-memory-index-session.ts:221`; PHP `LOADER_RESOLVERS` + `createRegexResolver` (`php-language-adapter.ts:595-870`) are exported but unused in `src` and `test` (dead legacy whole-source regex engine; contradicts "no legacy path" and would violate the lookalike rules if reactivated).

D11 (LOW, spec vs implementation shape) IMPORTS relations ownership

- Spec (language-adapter, TS, Go): `buildRelations()` builds `IMPORTS`; Go verify: "Go buildRelations emits IMPORTS and CALLS relations".
- Code: no adapter except PHP emits `RelationType.Imports` in `buildRelations` (grep: only `php-language-adapter.ts:1406,2464,2866`); TS/PY/GO expose `fileImports` from `resolveImports` and the indexer creates IMPORTS (`index-code-graph.ts:1213-1224`). Result is equivalent for consumers, but the spec text and the Go scenario do not describe it. The existing Go test (`go-language-adapter.spec.ts:676-725`) asserts `importRel` is `undefined`, i.e. it tests the opposite of the scenario title. Either the spec or the adapters should change; neither side is clearly authoritative.

### Discrepancies

- D1 [LOW, spec stale]. `configRelativePath` and `findFilesByConfigRelativePath` in graph-store spec and verify.
  - Spec: "Minimum graph semantics", "Query methods", and scenarios `findFilesByConfigRelativePath ...`.
  - Code: the `FileNode` field is `projectRelativePath` (`src/domain/value-objects/file-node.ts:12`). The store API is `findFilesByProjectRelativePath` (`src/domain/ports/graph-store.ts:511`). Schema v15 drops `config_relative_path` (`schema.ts:8`). The sqlite-graph-store spec and symbol-model spec already say project-relative.
  - Verdict: the code matches the newer specs. The graph-store spec text is stale. The contract suite exercises `findFilesByProjectRelativePath` (`test/domain/ports/graph-store.contract.ts:1748-1800`).
- D2 [HIGH, code contradicts spec]. `COVERS_SYMBOL` accepts a physical declaration as the target, and rejected relations are not reported.
  - Spec, graph-store "Logical-symbol coverage endpoints": "MUST reject a relation whose ... logical-symbol target does not exist". Verify scenario "Missing and occurrence-only targets fail endpoint validation": the occurrence-only relation does not become visible and is not retargeted.
  - Spec, sqlite-graph-store "SQLite logical coverage integrity": "A physical declaration-occurrence symbol row alone MUST NOT satisfy that endpoint". Rejected relations are "reported through the indexing diagnostic contract".
  - Code: `relationEndpointsExist` (`src/infrastructure/sqlite/sqlite-graph-database.ts:4722-4727`) returns `ids.specs.has(source) && (ids.symbols.has(target) || ids.logicalSymbols.has(target))`. The `ids.symbols` branch lets a physical symbol satisfy the endpoint. `insertRelations` (`:3053-3070`) filters invalid relations with `.filter(...)` and returns nothing, so no rejected source or target is reported.
  - Test evidence: the contract test at `test/domain/ports/graph-store.contract.ts:1196-1300` stores a physical-target `COVERS_SYMBOL` through `addRelations` and only asserts that the logical reverse query does not return it. The relation is persisted. It would also be counted in statistics and returned by `getCoveredSymbols`.
  - Mitigation: the indexer only emits logical ids (`src/application/services/project-spec-coverage.ts`). So this is unreachable through normal indexing, but it is reachable through the store API.
- D3 [MEDIUM, spec drift]. "Incompatible derivation rebuild" versus per-workspace fingerprint rebuild. This item is in the indexer section (D-I1), but the store-side spec "Incompatible store handling" depends on it.
- D4 [LOW, spec inconsistency]. Constraint "No dependency on `@specd/core` — error types extend `CodeGraphError`".
  - Code: `SpecdCodeGraphError` extends `SpecdError` from `@specd/core` (`src/domain/errors/specd-code-graph-error.ts`). The symbol-model spec requires exactly that. The graph-store constraint conflicts with it, and `CodeGraphError` does not exist.
- D5 [MEDIUM, untested contract]. Complete logical clear has code but no dedicated tests. See "Missing Tests".
- D6 [LOW]. The abstract class ships non-abstract default implementations for the reference-fact and freshness methods (`src/domain/ports/graph-store.ts:292-460`). They reject with a plain `Error`, not a typed error. The spec says nothing against this.
- D7 [LOW, ambiguity]. Member axes in `findLogicalSymbols`.
  - Spec: "Lookups MUST be equality queries on those structured fields"; "Partial member axes do not match a different member".
  - Code (`:2367-2410`): an unset axis means "any value", via `? IS NULL OR col = ?`. A lookup with `dispatch=instance` and `accessor` unset will return an instance getter. A lookup with every axis unset returns members too. Scenario "Non-member leaves member axes empty" is satisfied because the lookup by name and space returns the row.
  - Gap: no way to ask for "axis must be NULL". Also one SQL statement is run per lookup inside the single RPC, which is acceptable.
- D8 [LOW]. `findLogicalDeclarationsByDeclarationIds` keeps the first row per `symbol_id` with no `ORDER BY` (`sqlite-graph-database.ts:1356-1360`). The PK is `(logical_symbol_id, symbol_id)`, so one declaration could map to two logical ids, and the one returned would be arbitrary. The adapters and the session prevent this (`DuplicateDeclarationMappingError`, `src/application/use-cases/in-memory-index-session.ts:236-244`), so it is theoretical.
- D9 [LOW]. Source-content candidates.
  - `searchSourceCandidates` ignores `rawTerms`/`expandedTerms` shorter than 3 characters when any longer term exists (`:1971`). Short-query fallback uses only `terms[0]`.
  - Candidate query has no category filter and no snippet preference (spec says input carries both).

### Assessment of the known item (RGI:665 `targetDeclarations[0]`)

Code: when the selector came back with a typed `resolved.target`, `sym` is undefined at this point. The block at 664-697 builds a synthetic `SymbolNode` from `targetDeclarations[0]` (name from `logicalSymbol.name` when present, otherwise parsed out of the id via `first.symbolId.split(':').slice(-3)[0]`). `sym` is then used for: the deprecated `symbol` field (returned at ~771), the top-level `projectRelativePath` (738-739 uses `projectedDeclarations[0]` first), and `impact.target` (RGI:742 `target: sym.id`).

Against the scenario "Legacy first-declaration provider fallback is unavailable":

- Scenario text: "it never selects `declarations[0]` or calls physical impact as a compatibility fallback". Strictly, the SDK does select `declarations[0]` (lines 665, 738-739), but only to derive a display/compat summary AFTER the discriminated `analyzeResolvedSymbolImpact` has already run with the complete declaration set. Traversal inputs are not affected. The "impact is physical" reading does not apply to this site: no physical-only provider method is called here. So the known item does not break the traversal guarantee, but it does violate the letter of the requirement ("MUST NOT retain a compatibility branch that selects `declarations[0]`") and the consequence is visible in the output:
  - `impact.target` for a logical target is the first declaration's physical `symbolId` (RGI:742), whereas the domain result's `target` is the logical id (`analyze-impact.ts:~190` `resultTarget`). The same result therefore shows a logical identity in `resolvedTarget` and a physical one in `impact.target`. The spec says compat fields "MUST NOT obscure whether an identifier is logical or physical".
  - `symbol` (typed `SymbolNode`, marked `@deprecated` at RGI:232) for a multi-declaration logical target is an arbitrary declaration; the CLI still prints it (`cli/src/commands/graph/impact.ts:~847`, JSON `symbol: result.symbol` ~930).
  - Name recovery by `symbolId.split(':').slice(-3)[0]` (RGI:~676) is fragile string parsing of a physical id, which conflicts with the "do not parse ids" principle of the resolver spec.
- Spec side: the requirement itself says "Compatibility fields MAY remain during a documented migration" in code-graph:composition, which would allow a derived `symbol` summary, but sdk:run-graph-impact has no such allowance and says "MUST NOT retain a compatibility branch". The two specs disagree; the SDK spec is the stricter and the one that applies here. Verdict: MEDIUM; fix by dropping or documenting `symbol`/`impact.target` as derived, using `logicalSymbol.id` for `impact.target`.

Related fallback at RGI:619-648 (`resolved.target === undefined`): `getSymbol(match.symbolId)` then synthesises a physical `declaration` target. This is the real compat branch and it is the direct cause of X1/D1: an overload set unified by `unifyOverloadSetCandidates` arrives here with one arbitrary `match` and is analysed physically.

### Discrepancies

- D1 (HIGH, inherited). For overloaded/bare-name selectors, the CLI prints "logical impact" only when the SDK got a typed logical target. A bare-name overload set arrives as a declaration-kind, single-declaration result ("declaration impact"), which the spec forbids for a logical selector ("MUST request one canonical logical-target analysis covering every contributing declaration"). The CLI itself is faithful; the root cause is in the selector layer.
- D2 (MEDIUM, spec-side inconsistency). The "Symbol impact analysis" requirement (items 5-6: `analyzeImpact(symbolId, direction)`, "analyzes each one") conflicts with the newer "Logical and declaration symbol-impact presentation" requirement ("MUST NOT call impact separately for one arbitrary declaration or for each overload"). The newer one says it "supersedes legacy behaviour", but the old text was not removed or amended in the merged spec, so the spec as shipped is self-contradictory. The CLI test `reports multiple matching symbols` (940) follows the old text (ambiguous output, `analyzeImpact` not called).
- D3 (MEDIUM). Public export ambiguity: "Ambiguous exports SHALL display deterministic candidates and MUST NOT merge or select them. Text, JSON, and TOON SHALL preserve both impact views and structured provenance." Text prints only `Public export S::N: ambiguous (K routes)` (impact.ts ~537-545), with `candidates` read from the SDK result, which is always `[]` for the binding-ambiguity branch (RGI:880). For resolver-level ambiguity, text prints the status and reason only (no candidate list). JSON/TOON include `resolution` (with candidates), but only for the resolver-level case.
- D4 (LOW). Symbol `ambiguous` presentation prints physical declaration lines (`path:kind:name:line:col`), not "deterministic semantic candidates" (impact.ts ~812-830). Several overload declarations of one logical target may be repeated.
- D5 (LOW). JSON output for logical impact still includes the deprecated `symbol: result.symbol` (impact.ts ~930) and `impact.target` (physical first-declaration id; see sdk D2). The spec requires JSON/TOON to "expose the SDK result without removing" fields; it does not require adding compat ones, but the physical `symbol` beside a logical `resolvedTarget` can mislead.
- D6 (LOW). Text for the logical `Target kind:` line is inserted by `lines.splice(1, 0, ...)` (857), which depends on the `formatImpact` layout. Fragile but functional.
- D7 (LOW). The export JSON `binding`, `target`, `path`, `resolution` are printed without `projectRelativePath` on nested locations (SDK X2). The spec says the CLI must not reconstruct nested path projections, and the SDK is the owner of the fix.
- Architecture: CLI imports only `@specd/sdk` for platform symbols (OK per the requirement "Platform symbols MUST come from `@specd/sdk`"). `process.exit` and `withProvider` handled outside this file.
