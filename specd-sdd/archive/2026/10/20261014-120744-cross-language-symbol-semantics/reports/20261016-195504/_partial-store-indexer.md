# Partial compliance audit: store / sqlite-store / indexer / symbol-model

Change: `cross-language-symbol-semantics`. Read-only audit. Specs were fetched with
`changes spec-preview` (spec merged with deltas). Code root: `packages/code-graph/src`
(abbreviated `src/` below). Tests: `packages/code-graph/test` (abbreviated `test/`).

Method note: the working tree has about 129 uncommitted files. Findings describe the working tree,
not HEAD. Line numbers are from the working tree as read in this audit. Behavioural claims come
from reading the code and tests. I did not run the test suite.

Severity scale: HIGH = code contradicts a MUST/SHALL scenario with observable effect.
MEDIUM = partial implementation or an untested contract. LOW = naming or documentation drift,
or an edge case.

Delta scope of this change for my four specs:

- graph-store: adds "Logical and declaration batch lookup boundary" and "Batched logical coverage lookup".
- sqlite-graph-store: adds "Worker-backed logical declaration mapping" and "SQLite batched logical coverage reads", and rewrites "Reference schema upgrade" (v15, `occurrence_form`).
- indexer: adds "Classification-aware logical identity construction" and "Identity-sensitive incremental equivalence".
- symbol-model: adds "Declaration, binding, and logical identity layers" and "Evidence-preserving semantic projection".

Everything else in the merged specs is pre-existing baseline. I checked it at a lighter depth, mainly through test mapping.

### Discrepancies

- D1 [LOW, spec stale]. `configRelativePath` and `findFilesByConfigRelativePath` in graph-store spec and verify.
  - Spec: "Minimum graph semantics", "Query methods", and scenarios `findFilesByConfigRelativePath ...`.
  - Code: the `FileNode` field is `projectRelativePath` (`src/domain/value-objects/file-node.ts:12`). The store API is `findFilesByProjectRelativePath` (`src/domain/ports/graph-store.ts:511`). Schema v15 drops `config_relative_path` (`schema.ts:8`). The sqlite-graph-store spec and symbol-model spec already say project-relative.
  - Verdict: the code matches the newer specs. The graph-store spec text is stale. The contract suite exercises `findFilesByProjectRelativePath` (`test/domain/ports/graph-store.contract.ts:1748-1800`).
- D2 [HIGH, code contradicts spec]. `COVERS_SYMBOL` accepts a physical declaration as the target, and rejected relations are not reported.
  - Spec, graph-store "Logical-symbol coverage endpoints": "MUST reject a relation whose ... logical-symbol target does not exist". Verify scenario "Missing and occurrence-only targets fail endpoint validation": the occurrence-only relation does not become visible and is not retargeted.
  - Spec, sqlite-graph-store "SQLite logical coverage integrity": "A physical declaration-occurrence symbol row alone MUST NOT satisfy that endpoint". Rejected relations are "reported through the indexing diagnostic contract".
  - Code: `relationEndpointsExist` (`src/infrastructure/sqlite/sqlite-graph-database.ts:4722-4727`) returns `ids.specs.has(source) && (ids.symbols.has(target) || ids.logicalSymbols.has(target))`. The `ids.symbols` branch lets a physical symbol satisfy the endpoint. `insertRelations` (`:3053-3070`) filters invalid relations with `.filter(...)` and returns nothing, so no rejected source or target is reported.
  - Test evidence: the contract test at `test/domain/ports/graph-store.contract.ts:1196-1300` stores a physical-target `COVERS_SYMBOL` through `addRelations` and only asserts that the logical reverse query does not return it. The relation is persisted. It would also be counted in statistics and returned by `getCoveredSymbols`.
  - Mitigation: the indexer only emits logical ids (`src/application/services/project-spec-coverage.ts`). So this is unreachable through normal indexing, but it is reachable through the store API.
- D3 [MEDIUM, spec drift]. "Incompatible derivation rebuild" versus per-workspace fingerprint rebuild. This item is in the indexer section (D-I1), but the store-side spec "Incompatible store handling" depends on it.
- D4 [LOW, spec inconsistency]. Constraint "No dependency on `@specd/core` — error types extend `CodeGraphError`".
  - Code: `SpecdCodeGraphError` extends `SpecdError` from `@specd/core` (`src/domain/errors/specd-code-graph-error.ts`). The symbol-model spec requires exactly that. The graph-store constraint conflicts with it, and `CodeGraphError` does not exist.
- D5 [MEDIUM, untested contract]. Complete logical clear has code but no dedicated tests. See "Missing Tests".
- D6 [LOW]. The abstract class ships non-abstract default implementations for the reference-fact and freshness methods (`src/domain/ports/graph-store.ts:292-460`). They reject with a plain `Error`, not a typed error. The spec says nothing against this.
- D7 [LOW, ambiguity]. Member axes in `findLogicalSymbols`.
  - Spec: "Lookups MUST be equality queries on those structured fields"; "Partial member axes do not match a different member".
  - Code (`:2367-2410`): an unset axis means "any value", via `? IS NULL OR col = ?`. A lookup with `dispatch=instance` and `accessor` unset will return an instance getter. A lookup with every axis unset returns members too. Scenario "Non-member leaves member axes empty" is satisfied because the lookup by name and space returns the row.
  - Gap: no way to ask for "axis must be NULL". Also one SQL statement is run per lookup inside the single RPC, which is acceptable.
- D8 [LOW]. `findLogicalDeclarationsByDeclarationIds` keeps the first row per `symbol_id` with no `ORDER BY` (`sqlite-graph-database.ts:1356-1360`). The PK is `(logical_symbol_id, symbol_id)`, so one declaration could map to two logical ids, and the one returned would be arbitrary. The adapters and the session prevent this (`DuplicateDeclarationMappingError`, `src/application/use-cases/in-memory-index-session.ts:236-244`), so it is theoretical.
- D9 [LOW]. Source-content candidates.
  - `searchSourceCandidates` ignores `rawTerms`/`expandedTerms` shorter than 3 characters when any longer term exists (`:1971`). Short-query fallback uses only `terms[0]`.
  - Candidate query has no category filter and no snippet preference (spec says input carries both).

### Discrepancies

- D10 [MEDIUM, spec vs code]. `occurrence_form` is not on the `symbols` table.
  - Spec (delta), "Reference schema upgrade": "`symbols` SHALL persist `project_relative_path` and the declaration `occurrence_form`". Verify scenario "Version 15 persists occurrence form and project-relative paths": "`symbols` has `project_relative_path` and `occurrence_form`".
  - Code: `schema.ts:25-43` defines `symbols` with no `occurrence_form`. `schema.ts:83-95` puts `occurrence_form TEXT NOT NULL` on `logical_declarations`. The git diff for `schema.ts` shows only this column being added (to `logical_declarations`).
  - The same spec paragraph says `logical_declarations` "MUST keep their current columns", so the spec is internally inconsistent. The code is consistent with the "keep their columns" sentence (it adds the column to the declaration table, not to `symbols`). Test `sqlite-graph-store.spec.ts:778-853` round-trips the form through `logical_declarations`.
  - A physical-only declaration has no `logical_declarations` row, so its occurrence form is not persisted anywhere. Under the spec as written, `symbols.occurrence_form` would cover those. Decide which statement is authoritative.
- D11 [LOW, doc drift]. Verify scenario "Config-relative document path participates in identity ranking" in sqlite verify and the `configRelativePath` mention. The schema now indexes `project_relative_path` in `document_fts` (`schema.ts:189-194`). Same root cause as D1.
- D12 [LOW]. "Destructive recreation" says it must "remove the graph persistence directory including SQLite companion files". The code removes only the three SQLite files and leaves the rest of `graph/` (for example `storage.epoch`, which is rotated, and `index.lock`, which must survive per "Locked recreation preserves the index lease"). The code reconciles the two spec statements sensibly. A `-journal` file is not removed.
- D13 [LOW]. `ensureSchemaVersion` (`:2691-2712`): when the `meta` table exists but has no `schemaVersion` row, the code stamps the current version. A partially migrated v14-shaped database without the row would be accepted.

### Discrepancies

- D-I1 [MEDIUM, spec vs code]. Fingerprint mismatch does not recreate storage or rotate the generation.
  - Spec "Incompatible derivation rebuild": on derivation fingerprint or schema incompatibility, indexing "SHALL perform a visible destructive full rebuild through provider-owned recreation, rotate storage generation, and report the rebuild reason". Verify scenario "Incompatibility triggers visible full rebuild: generation rotates". "Incremental indexing" also says "preferred behavior is to recreate the store".
  - Code: on a fingerprint mismatch the indexer re-processes only paths of mismatched workspaces and states "do NOT recreate the store — other workspaces are unaffected" (`index-code-graph.ts:655-664`). It reports `fullRebuildReason` and `fullRebuild: true`. No generation rotation happens. Recreation exists only for `SCHEMA_INCOMPATIBLE` (and `CORRUPT` with force), driven by the SDK (`packages/sdk/src/orchestration/run-index-project-graph.ts:119-121`).
  - The "Incremental indexing" text allows a non-recreating fallback ("If a backend cannot safely recreate in-place, the caller MAY fail fast"), but it does not describe a workspace-scoped partial rebuild. Resolve this in the spec.
- D-I2 [MEDIUM, code risk against spec text]. A forced or mismatched run on a subset of workspaces clears every workspace.
  - Spec "Incremental indexing": "Only files belonging to workspaces being indexed are considered for deletion ... allows `--workspace <name>` to index a single workspace without destroying data from others."
  - Code: `replaceCodeGraph: fullRebuild` (`index-code-graph.ts:1678`) leads to `clearLogicalGeneration` for the whole store (`sqlite-graph-database.ts:2578-2580`, which deletes all files, symbols, specs, documents, bindings, coverage). For a forced or per-workspace-mismatch run over a subset of `options.workspaces`, other workspaces' data are deleted, yet the merged fingerprint map keeps their old fingerprints (`:631-635`), so the store would report them as indexed. The code comment at `:655` states the opposite intent.
  - Reachability: `graph index` has no `--workspace` option (`packages/cli/src/commands/graph/index-graph.ts` has no workspace flag), so this is reachable only through the library API or a multi-workspace project where some workspace fingerprints mismatch. I did not find a test.
- D-I3 [LOW, spec stale]. ### Discrepancies

- D-S1 [MEDIUM, code gap vs spec]. `LocalBinding` has no source range.
