# Exploration Context: filter-typescript-array-data-symbols

Generated: 2026-10-03

## Problem statement

`TypeScriptLanguageAdapter` currently visits every `pair`/`property_definition` node and
extracts scalar object-literal properties as `SymbolKind.Variable`. Large generated data
catalogs represented as arrays of anonymous objects therefore create tens of thousands of
low-value code symbols. The motivating example was the generated guide catalog, where data
fields such as `topic`, `outline`, `heading`, `lines`, and `startOffset` dominate symbol
extraction and substantially increase parsing and indexing work.

This behavior was originally included in the SQLite variable-limit change
`fix-sqlite-delete-file-variable-limit`. After reviewing the design, the user explicitly
decided that parser semantics and SQLite parameter safety are separate concerns and asked to
move the TypeScript work into this dedicated change before revising the SQLite change.

## Intended behavior

- Preserve named object declarations such as `const Config = { host: '...' }`.
- Preserve dictionary/enum-like declarations wrapped in `as const` or `satisfies`.
- Preserve callable object properties and object methods regardless of whether they occur
  inside an array-backed structure.
- Do not extract non-callable properties from anonymous objects used as array data records.
- Apply the data-record classification through nested objects below an array element, not
  only to a direct `array > object > pair` parent chain.
- Continue indexing the complete source text through the existing file-content search path;
  this change only narrows code-symbol extraction.
- Keep output deterministic and retain valid construct and selection ranges for preserved
  symbols.

## Design direction

Classify a non-callable property from its enclosing object and ancestor path rather than
checking only the immediate parent. The implementation needs to distinguish an object owned
by a named declaration from an anonymous data object and must transparently traverse wrappers
such as `as_expression`, `satisfies_expression`, type assertions, and parentheses. Crossing an
array ancestor before reaching a supported named declaration is evidence that the object is a
data record. Callable values remain symbols even in that case.

Tests should cover at least:

1. Named object scalar properties remain symbols.
2. `as const` and `satisfies` dictionaries remain symbols.
3. Direct anonymous array-record scalar properties are omitted.
4. Scalar properties in objects nested below array records are also omitted.
5. Function, arrow-function, and object-method forms inside array records remain symbols.
6. Preserved symbols retain parser-derived construct and selection ranges.
7. Equivalent analysis remains deterministic.

## Risk and impact

The code graph reports `TypeScriptLanguageAdapter.processPairNode` as CRITICAL risk because
its output feeds indexing, search, resolution, persistence, and numerous integration tests.
The reported blast radius is broad (169 files), although the intended implementation remains
localized to the TypeScript adapter and its tests. Regression coverage must therefore protect
existing named-object and callable-property behavior.

## Decisions and user preferences

- The user approved the name `filter-typescript-array-data-symbols`.
- The user approved attaching only `code-graph:typescript-language-adapter` initially.
- The user wants this change created before the SQLite change is revised.
- Temporary graph exclusions are configuration/implementation details and should not become
  requirements or verification scenarios in the SQLite change.
- Full source-text searchability must remain separate from code-symbol extraction.

## Rejected approaches

- Keeping parser filtering inside `fix-sqlite-delete-file-variable-limit`: rejected because
  it changes symbol semantics and has a different blast radius from SQLite safety.
- Checking only the immediate `array > object > pair` structure: rejected because nested
  data objects would still generate noise and wrappers around named objects would be
  misclassified.
- Dropping every property below an array: rejected because callable properties and object
  methods are meaningful code declarations and must remain discoverable.

## Related SQLite work

The original SQLite change remains responsible for replacing unbounded file-local cleanup
parameter expansion with constant-parameter subqueries and, if retained in its scope, safely
chunking other batch reads. This new change must not be used as a correctness workaround for
SQLite parameter limits; SQLite must remain safe for files with any valid symbol count.

## Current overlap

At creation time SpecD reported that `code-graph:typescript-language-adapter` is also targeted
by `fix-sqlite-delete-file-variable-limit`. This overlap is intentional and temporary. It must
be resolved by removing the TypeScript spec and its deltas from the SQLite change before either
change advances.

## Open questions for design

- Define the exact transparent-wrapper set supported by the Tree-sitter grammar names used in
  this repository.
- Decide whether non-callable properties in arrays nested inside an otherwise named object are
  always data records; the current direction is yes once an array boundary is crossed.
- Establish a lightweight performance regression signal without hard-coding wall-clock timing
  in CI.
