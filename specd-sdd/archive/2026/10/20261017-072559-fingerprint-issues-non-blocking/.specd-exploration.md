# Exploration: fingerprint-issues-non-blocking

Generated: 2026-10-17

Change: `fingerprint-issues-non-blocking` (specs: `core:change`, `core:get-status`, `cli:change-status`).
Created while finishing `schema-workflow-skippable-states`. DO NOT implement before that change is archived.

## Problem statement

`specd changes status <name>` shows a blocker `FINGERPRINT_INPUT_ERROR: Fingerprint inputs could not be read`
on any freshly created change (state `drafting`/`designing`), also with the stock `@specd/schema-std`.
The change has artifact entries with status `missing` whose files do not exist yet, and the fingerprint
service treats a missing file as an unreadable input. The blocker is noise: nothing in the early states
needs a fingerprint, and it appears before any approval/verification could exist.

## Observations (verified in code)

- Computation: `packages/core/src/application/services/validity-fingerprint-service.ts`,
  `ValidityFingerprintService.completeFingerprint()` -> `_collectArtifacts` pushes a failure
  `{scope:'artifact', reason:'missing'}` when `changes.artifact(change, file.filename)` is `null`
  (skips `hasTasks` artifacts and files with status `skipped`). Class docstring says: "Any missing, unreadable,
  or unsafe input makes `fingerprint` null so approval and verification cannot persist a partial baseline."
  So null-on-missing is intentional for the computation; only the blocker is questioned.
- Callers of `completeFingerprint`: `reconcile-change-validity.ts:214` (every status/transition reconcile),
  `start-verification.ts:87`, `complete-verification.ts:70`, `approve-signoff.ts:130`. `approve-spec.ts:119`
  also throws `FingerprintInputError`.
- Blocker emission: `packages/core/src/domain/services/change-validity.ts` `buildBlockers` (~line 507):
  `if (facts.fingerprintFailures.length > 0) blockers.push({code:'FINGERPRINT_INPUT_ERROR', message, details:{failures}})`
  unconditionally (no state check, no stored-evidence check). Union type member at line 36.
- `facts.fingerprintFailures` is ALSO used by `unreadableDifferences` (lines ~317, 323, 363-364, 430) to mark
  stored spec approval / signoff / verification as stale. This MUST be kept.
- All four consuming use cases (ApproveSpec, ApproveSignoff, StartVerification, CompleteVerification) already
  throw `FingerprintInputError` (code `FINGERPRINT_INPUT_ERROR`) when the fingerprint is null. Test:
  `packages/core/test/application/use-cases/start-verification.spec.ts:190`.
- No test asserts the blocker: `change-validity.spec.ts` only has `fingerprintFailures: []`.
- No CLI/SDK/skills code reads the blocker code. Docs mentioning it as a blocker: `docs/core/use-cases.md:495`.
  `docs/core/errors.md` documents the error class (keep).
- `ValidityStatusProjection` (`get-status.ts` `projectValidityStatus`, ~line 84) has no field for fingerprint
  failures; the only way status exposes unreadable inputs today is `blockers[].details.failures`.
- Spec constraint: `specs/core/get-status/spec.md` requirement "Approval, verification, and fingerprint status
  projection" says status exposes "changed, missing, added, removed, renamed, or unlinked fingerprint inputs and
  their causes". Removing the blocker without a replacement would drop the "missing" information.
- `main` (commit 906aa0e1) has no fingerprint/validity code at all; feature introduced in commit
  `3b2a1796e` ("add versioned approval invalidation") on the feature branch. Not caused by
  `schema-workflow-skippable-states`.

## Decision (user chose option 2)

1. Remove the `FINGERPRINT_INPUT_ERROR` blocker from `buildBlockers` (and from `ValidityBlocker['code']`).
2. Keep `completeFingerprint`, `fingerprintFailures` in facts and `unreadableDifferences` (stale approvals and
   verification must still be invalidated).
3. Keep the four consumers throwing `FingerprintInputError`: the check/use case that needs the fingerprint fails;
   the caller of checks should not need to know their details (user's principle).
4. Expose the failures as a NON-blocking diagnostic: new field `validity.fingerprintIssues` in
   `ValidityStatusProjection` (core:get-status), carrying the same `FingerprintInputFailure[]` list.
5. CLI `changes status`: show them as a warning (not under `blockers:`), in text and in json/toon.
   Spec `cli:change-status`.
6. Update `docs/core/use-cases.md` line ~495 (no longer a verdict blocker).
7. Outcome: a fresh `drafting`/`designing` change with not-yet-created artifact files shows no blocker.

## Rejected alternatives

- Option 1: delete the blocker entirely and weaken the `get-status` requirement. Rejected: loses missing-input
  info and requires softening an existing spec requirement.
- Gate the blocker by state (only from `verifying` on). Rejected: consumers already fail; extra state logic in the
  evaluator for something the consumers own.
- Make missing artifacts not count as fingerprint failures. Not chosen: contradicts the documented intent of the
  service (no partial baseline).

## Open questions for /specd-design

- Name/shape of `fingerprintIssues` (reuse `FingerprintInputFailure` as is?) and whether it also appears when the
  state is `drafting` or only once a baseline/approval could exist.
- Whether `ChangeValidityVerdict` should carry the issues, or `GetStatus` should read them from facts another way.
- Whether `core:change` needs a delta at all (it documents validity fingerprints) or only `core:get-status` and
  `cli:change-status`; keep `core:change` only if its text states the blocker.
- Check specs/verify scenarios and tests that might rely on the blocker (none found in tests so far).
- sdk/mcp consumers of the status result type (`ValidityStatusProjection`) need the new optional field.
