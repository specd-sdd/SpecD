# Exploration — archive-schema-checks-and-skip-flag

Generated: 2026-10-20

## Problem statement

`changes archive` is inconsistent with the rest of the check system:

1. A schema cannot declare/disable/configure checks that run when the archive operation executes. Schema workflow-step `checks` (`WorkflowStepCheckDeclaration`: `id`, `from`, `along`, `onFailure`, `skippable`, `disabled`, `config`) only apply to the `transition` scope; `skipChecks` (`WorkflowStepSkipCheckDeclaration`) only to the `step-skip` scope. There is no `archive` scope in the schema grammar (grep for `scope.*archive` / `'archive'` in `build-schema.ts`, `schema-yaml-parser.ts`, `workflow-step.ts` returned 0 matches).
2. `ArchiveChange` (`packages/core/src/application/use-cases/archive-change.ts`) runs the static composition-time `_archiveBindings` (from `ARCHIVE_BINDING_SPECS` in `packages/core/src/domain/services/check-bindings.ts`) directly. It never calls `resolveEffectiveBindings`, so no schema/config overlay, no governance locks (`allowSchemaEmbedding`, `allowBindingOverride`, `allowConfigOverride`, `allowDisable`).
3. `changes archive` only exposes `--allow-overlap` and `--allow-out-of-scope` (`packages/cli/src/commands/change/archive.ts` ~L60). Core maps them to `effectiveSkipChecks` = `spec.overlap` / `impl.linksInScope` (`archive-change.ts` ~L316-322). Meanwhile `changes status` advertises `--skip-checks <id>` (e.g. `spec.overlap`) for archive blockers, which `changes archive` does not accept. The error text at archive.ts ~L151 says "Use --allow-overlap to proceed despite overlap."
4. `changes transition` derives skip validation from resolved bindings (skippability); archive does not.

Archive binding ids today (`ARCHIVE_BINDING_SPECS`): `schema.nameMatch`, `archive.archivable`, `spec.overlap` (skippable), `workspace.readOnly`, `deps.consistent`, `impl.filesResolved`, `impl.linksInScope` (skippable), `workflow.taskCompletion`, `verification.current`, `hook.pre`, `hook.post`. Archive attempt shape: `{ scope: 'archive' }`. A plugin default binding could already be `scope: 'archive'`.

Checks declared on the `archiving` workflow step apply to the transition INTO `archiving`, not to the archive operation.

Origin: user asked "crea un change para arreglar eso de changes archive, porque ahora mismo ¿se pueden poner checks desde schema para archivar?" after I mistakenly suggested `--skip-checks spec.omit` (not a real check; the real one is `spec.overlap`) — surfaced that status hints and archive CLI diverge.

## Approach / solution outline (agreed in discussion)

- Add an `archive` scope to the schema grammar so schemas can declare/disable/configure archive-operation checks.
- `ArchiveChange` resolves its bindings through `resolveEffectiveBindings` (single cascade), under the same governance locks (`allowSchemaEmbedding`, `allowBindingOverride`, `allowConfigOverride`, `allowDisable`).
- Add generic `--skip-checks <id>` (repeatable/comma) to `changes archive`; validate against resolved-binding skippability (same as transition).
- Keep `--allow-overlap` / `--allow-out-of-scope` as aliases mapping to `spec.overlap` / `impl.linksInScope`.
- Align `changes status` hints and CLI error text with what `changes archive` accepts.

User decision: ONE single change (not split into a small bugfix + a feature). Reason: `--skip-checks` only makes sense if skippability comes from resolved bindings, which is what the schema-scope work introduces.
