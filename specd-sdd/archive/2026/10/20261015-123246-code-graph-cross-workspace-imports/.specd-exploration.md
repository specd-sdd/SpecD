## Problem statement

Impact, hotspots, coverage, and (future) contract inference are blind across workspaces in a monorepo. Imports by package specifier
(`import { SymbolNode } from '@specd/code-graph'` in `sdk`) are never resolved into the graph's binding model. Discovered while designing
`code-graph-symbol-contracts`: `graph impact --symbol SymbolNode` reports no `sdk`/`cli` dependents although `sdk/src/orchestration/run-graph-hotspots.ts`
and `run-graph-impact.ts` use `SymbolNode`, and `cli/src/commands/graph/search.ts` declares it in its output schema.

My first explanation ("barrel not resolved") was WRONG — barrels inside a workspace resolve correctly (public bindings chain
`code-graph:src/public.ts` → `src/index.ts` → `domain/index.ts` → `domain/value-objects/symbol-node.ts` to the logical `SymbolNode`).

## Root cause in code (anchors; verify after archive)

- `packages/code-graph/src/infrastructure/tree-sitter/typescript-language-adapter.ts` `resolveImports` (~1081): for non-relative specifiers,
  `resolvePackageFromSpecifier` → `packageToWorkspace.get(pkg)` → `session.findSymbolsByName(imp.originalName, ws + ':')` → takes `candidates[0]`.
  Global same-name match within the workspace, ignores export surface/visibility/tests. Same pattern in `python-language-adapter.ts` (~725) and
  `go-language-adapter.ts` (~549). PHP differs: global qualified names (`qualifiedNames.get`) + PSR-4 from `composer.json` (`psr4Cache`, ~1027/~2356).
- Correct logic exists only for re-exports: `packageEntryCandidates` (~2474) reads `package.json` `exports`/`main` (`publishedTarget`), maps
  `dist/x.js` → `src/x.ts` (`sourceCandidates` ~2615), candidates `ws:rel.ts|.tsx|/index.ts`; used by `resolveReExportSource` (~2445) from
  `linkReExports` (~2324). NOT used for ordinary imports.
- `workspaceCodeRoots` (TS adapter ~451) is filled lazily in `analyzeFile` (~563) only when a file of that workspace is analyzed → may be empty
  in incremental runs (unchanged workspaces are hydrated, not analyzed) → package entry lookup returns []. Code roots must be supplied
  deterministically (context), not as a side effect.
- `packageToWorkspace` built in `index-code-graph.ts` (~838) from `adapter.getPackageIdentity(ws.codeRoot)`; collisions reported.
- `@specd/code-graph` package.json: `exports: { ".": { import: "./dist/public.js", types: "./dist/public.d.ts" }, "./internal": { import: "./dist/index.js" } }`.
- Indexer incremental closure: `collectAffectedFileClosure` (index-code-graph.ts) uses `store.findDirectlyAffectedFiles` + reversed
  `resolution_steps`; import resolution must leave steps/relations so cross-workspace dependents are re-processed.

## Approach outline (to refine in design)

- Per-adapter "package entry" contract: package specifier (+ subpath) → manifest (`package.json` exports/main incl. conditional/subpath exports;
  Python package dirs/`__init__.py`/src layout; Go module path from `go.mod` + package directory; PHP composer PSR-4) → indexed source entry file(s)
  → public bindings of that surface → logical target. Respect visibility/export surface; never test files unless imported surface is a test.
- Code roots and manifest facts provided to adapters deterministically via resolution context.
- Persist import binding targets + resolution steps; emit `IMPORTS` (file) and allow downstream `USES_TYPE`/`CALLS`/... across workspaces.
- Manifest changes (exports, go.mod, composer autoload, package identity) change derivation fingerprint → reindex.
- Verify scenarios: sdk type import of `@specd/code-graph` symbol yields cross-ws `USES_TYPE`; subpath export (`@specd/code-graph/internal`);
  `dist`→`src` mapping; unknown package → no edge; same-name symbol in a test file never chosen; incremental run with unchanged target workspace
  still resolves; Python/Go/PHP equivalents.
