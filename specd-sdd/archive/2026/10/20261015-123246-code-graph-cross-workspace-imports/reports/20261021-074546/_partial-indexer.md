## 4. Discrepancies (new first)

- D1 (NEW, LOW, code vs spec). "One entry per adapter" can be violated. `listDisabledAdapters` (IC:952-955) concatenates adapters lacking `packageResolution` with every member of `disabledPackageResolution`, without deduplication. An adapter that has `reExportLinking` but no `packageResolution` and whose `link` throws is added to the disabled set at IC:1235, so it appears twice (once as absent, once as disabled). It also conflates facets: a failed `reExportLinking.link` disables package resolution for an adapter that never had that facet. Fix: only add to the disabled set when `packageResolution !== undefined`, or dedupe the list. Untested.
- D2 (NEW, LOW-MEDIUM, code/test vs spec). Collision error: spec says "naming both workspaces". The message (IC:906) names the identity and the existing workspace only; the new workspace appears in `filePath`. PI:634 passes because `graph` is a substring of `@fixture/graph`; it never checks `app`. A message-only consumer sees one workspace. Suggest naming both in the message and asserting both distinct names.
- D3 (NEW, MEDIUM for test quality, test vs spec). Scenario "Hydrated workspaces are prepared" is not really verified. PI:645 adds `app/src/extra.ts`; a new code file triggers the addition fallback (IC:808-814), which re-extracts every existing code file, so `graph` is reprocessed, not hydrated. Also `prepare` always receives `options.workspaces`, so the assertion `['app','graph']` would pass regardless. To discriminate, change content of one file with no additions and assert `filesSkipped > 0` for the other workspace, or spy that the other workspace's files were not analyzed.
- D4 (NEW, LOW, code vs spec edge). In `resolveBindingTarget` (SB-src:407-419), if an import-bound name's declaration id is not found by `findById` (or the optional `findById` is absent from a custom `SymbolLookup`), flow falls through to `findTargetCandidates` which searches the importing workspace by name (SB-src:445-446). For the `targetSymbolId` branch the later `candidates.filter(id === targetSymbolId)` prevents a wrong pick; for the `importedTargets` branch (no `targetSymbolId`) it does not, so a same-name local symbol could be chosen. The spec says the environment MUST NOT replace an import-bound name with a same-name symbol of the importing workspace. Practically unreachable in the indexer (hydration populates the session), but `findById` is optional in the `SymbolLookup` interface and nothing tests the unresolvable-id path.
- D5 (verify wording stale, LOW, unchanged). Scenarios "Package identity built from adapter" and "Adapter without getPackageIdentity skips resolution" in the merged verify still name `getPackageIdentity`, which this change replaces by `packageResolution.identity`.
- D6 (code vs spec, MEDIUM edge, unchanged). Subset runs: `packageToWorkspace` and `prepare` use `options.workspaces` only (IC:885, 916). With `--workspace core`, hydrated files of other stored workspaces are in the session but their packages are not mapped or prepared, so an import of such a package is `package-unknown` and counted as external. Spec text "every workspace of the run, including workspaces that were only hydrated" reads as satisfied only when the caller passes all workspaces. Either document "subset runs resolve only against indexed workspaces" or give the indexer the full workspace list. No test.
- D7 (spec precision / design, LOW, informational). "First adapter wins per workspace" plus `break` (IC:912) means a polyglot workspace (for example `package.json` and `go.mod`) maps only the first registered adapter's identity; the other language's packages in that workspace are never mapped. This is what the spec says, so it is not a defect, but it is a limitation worth a sentence in the spec or docs.
- D8 (global spec, LOW, pre-existing). IC imports `node:fs` while `default:_global/architecture` says application uses ports; HEAD already did. No new application-layer I/O was introduced: PR is I/O-free.
