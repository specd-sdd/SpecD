- Evidence: S:application/use-cases/index-code-graph.ts:1209-1237. The loops check only `adapter.packageResolution === undefined` or `adapter.reExportLinking === undefined`. They do not check `disabledPackageResolution.has(adapter)`. The identity loop does (:888).
- Spec: facet model says that after an `identity`, `prepare` or `link` failure the adapter "is treated as if it did not provide `packageResolution` for the rest of the run".
- A (spec right): skip `prepare` for adapters disabled by `identity`, and skip `link` for adapters disabled by `prepare`. Today a broken adapter is called again and may add a second error for the same cause.
- B (code right): the spec could say that the disable applies to import resolution only, and that `prepare` and `link` always run so every error is reported. If so, the sentence "treated as if it did not provide `packageResolution` for the rest of the run" should be narrowed.
- Not tested: every throw test uses one adapter.

### N2 (new, low): a failing `matchSpecifier` or `entrySurface` drops the whole file's relations and does not disable the adapter

- Evidence: the per-file `try/catch` at index-code-graph.ts:1266-1305 pushes an error and skips the file. Later, `resolvedImportsMap.get(prefixedPath)` is undefined (:1323-1324), so `buildRelations` and the file's DEFINES relations are skipped too.
- Spec: "A failure inside per-file resolution is recorded for that file by the indexer's error isolation." This is consistent with the code.
- A: consider isolating helper failures inside `PackageImportResolver` and returning an `unresolved` reason, to avoid losing unrelated relations.
- B: the behaviour matches the spec as written. If so, add a sentence to the spec that the file's other relations are also skipped.

### D1 (editorial, open): spec sentence is garbled

- Evidence: merged language-adapter spec, "Package resolution facet", last paragraph: "It MUST NOT search symbols by name, The shared helper discards entries classified as tests, so a test file is never a package entry whether or not the facet returned it." (comma splice and a second sentence glued to a MUST NOT). The facet interface doc comment (S:domain/value-objects/language-adapter-facets.ts:75-110) never mentions test filtering either. The docs page does (docs/code-graph/language-adapters.md "Rules for `entrySurface`").
- Possibility A: fix the delta text into two sentences. Possibility B: nothing in the code is wrong.

### D3 (new, medium): TS re-export linking does not use the shared entry-surface helper

- Evidence: S:infrastructure/tree-sitter/typescript-language-adapter.ts:2958-2969 `resolveReExportSource` calls the private `packageEntryCandidates` (:2989-2999) and filters by `session.getFileId` only. The `ReExportLinkContext` (language-adapter-facets.ts:155-160) has no `packageEntryFiles`.
- Consequences: (a) a package re-export can target a file classified as `test`; (b) `disabledPackageResolution` is not consulted; (c) the verify scenario "Re-export and ordinary imports share the entry surface" and the spec sentence "using the same entry surface that ordinary package imports use" are satisfied only at the level of the underlying function, not through the helper. The two paths agree today except for test filtering and disabled adapters.
- A (spec right): pass the helper (or a filtered entry list) into `ReExportLinkContext`.
- B (code right): keep the direct call, but say in the spec that re-export linking reads the facet's `entrySurface` directly and applies only the indexed-file filter.
- Related low note: `linkReExports` falls back to a by-name search inside the single source file (typescript-language-adapter.ts:2924-2931) when no public route exists. It requires exactly one match in one file, so it is not a workspace-wide search, but it can bind a declaration that the entry does not export. The relative-import baseline does the same.

### D4 (new, medium): PHP and other `use` imports resolve through the global `qualifiedNames` map, which includes test files

- Evidence: php-language-adapter.ts:~960 `qualifiedNames.get(imp.specifier)` runs before the package path. The map is filled in S:application/use-cases/in-memory-index-session.ts:318-325 from every symbol of every file with a namespace, with last-write-wins and no file-category check. The Go and Python resolveImports also call `qualifiedNames.get(imp.specifier)` first (pre-existing).
- Spec: workspace-integration says "A package-specifier import never resolves through a file classified as a test", and "Qualified names ... resolves to that symbol in any workspace through the exact qualified-name map".
- A (test rule wins): exclude test-category files from `qualifiedNameSymbolMap`, or filter the hit by `getFileCategory`. Also, duplicate FQNs resolve nondeterministically (last indexed file wins).
- B (exact-FQN rule wins): the spec should state that the test-file rule applies to entry-surface resolution only, and that an exact FQN declared in a test file is a valid target.
- Not tested: no PHP or Go test places the FQN in a test file.

### D5 (new, low): bindings without a target are ignored in the ambiguity check

- Evidence: S:application/services/package-import-resolver.ts:105-113 `if (binding.targetId === undefined) continue`. If one entry has a resolved binding and another entry has an unresolved binding for the same name, the result is `resolved`.
- Spec: "resolve a name only when every binding found in every requested space and every entry leads to the same logical target."
- A: treat a target-less binding as `ambiguous` (or unresolved). B: spec says "every resolved binding"; code is right.
- Not tested.

### D6 (editorial, low): spec omits `targetSymbolId` and `step` from the resolved result

- Evidence: language-adapter-facets.ts `PackageExportResolution` (last type) and docs/code-graph/language-adapters.md "Resolving a package import". Spec text lists only target logical id, entry file and public binding id.
- A: add the two fields to the spec (adapters depend on them). B: nothing to fix in code.

### D7 (low): docs refer the reader to the spec

- Evidence: docs/code-graph/language-adapters.md checklist step 6 ("the facet scenarios in the specification's verification") and step 7 ("Write the adapter's specific spec"). Verify scenario "Docs page states the same rules" says "without referring the reader to the spec".
- A: reword steps 6 and 7 to be self-contained. B: the scenario wording is too strict because step 7 is about writing a spec for the new adapter, which is a different subject.
- Also checked: docs omit the line "A new facet is added by a change to the spec; consumers MUST NOT rely on an adapter-specific extension". Minor.

### N5 (low): PHP `resolveToPath` keeps a non-prefixed fallback id

- Evidence: php-language-adapter.ts:2286 `const ids = workspace === undefined ? [absolute] : [`${workspace}:${relative}`, absolute]`. It can return an absolute path as a file id when the session has such a file. A workspace-prefixed id is the only id the rest of the graph uses.
- A: drop the `absolute` fallback. B: keep it for sessions that were not prepared through `preparePackages` (`workspaceByCodeRoot` unset). This is only reachable when `prepareResolutionMetadata` ran without `preparePackages`.

### N6 (low): `resolutionManifests()` values are not validated at registration

- Evidence: adapter-registry.ts only checks that the member is a function. `collectResolutionBasenames` (compute-graph-fingerprint.ts:219-231) silently skips values that contain `/`, `\` or `*`.
- Spec: "Values MUST be exact filenames, not globs or directory paths", but the `INVALID_LANGUAGE_ADAPTER` list does not include it.
- A: validate and reject. B: the spec list is exhaustive on purpose; the silent skip is acceptable.

### N7 (low): TS manifest lookup asymmetry between `identity` and `prepare`

- Evidence: typescript-language-adapter.ts:579-596 `prepareWorkspaceManifest` reads only `<codeRoot>/package.json`. `identity` walks up from `codeRoot` to `repoRoot` (`findManifestField`). If a workspace's `codeRoot` is below its package root (for example `packages/x/src`), the package gets an identity but no entry surface, so every import stays `no-entry-surface`.
- Spec: "`identity` searches at and above `codeRoot`", and `prepare` "prepares the data that matchSpecifier and entrySurface need". Spec says nothing about where `prepare` reads.
- A: have `prepare` use the same walk. B: document that the TS manifest must be at the workspace code root. Current fixtures put the code root at the package root.

### Other low notes

- The TS entry mapping hardcodes `dist/` to `src/` (typescript-language-adapter.ts:sourceCandidates). The scenario "dist path maps to the indexed source" requires it. The spec does not state the rule generally (only the `@specd/code-graph` example). Wildcard `exports` patterns (`./*`) are not supported, and they silently give `no-entry-surface`.
- Stale test titles: `describe('getPackageIdentity')`, `describe('resolvePackageFromSpecifier')`, `describe('resolveRelativeImportPath')`, `describe('resolveQualifiedNameToPath')` in the per-language adapter specs still use the removed method names, while calling the facet methods. Cosmetic.

- PHP `matchQualifiedNameToPackage`: an empty PSR-4 prefix (`"": "src/"`) matches every name, so vendor classes get attributed to that workspace and count as `no-entry-surface` failures instead of external imports. Edge case, not tested.

## 4. Discrepancies (new first)

- D1 (NEW, LOW, code vs spec). "One entry per adapter" can be violated. `listDisabledAdapters` (IC:952-955) concatenates adapters lacking `packageResolution` with every member of `disabledPackageResolution`, without deduplication. An adapter that has `reExportLinking` but no `packageResolution` and whose `link` throws is added to the disabled set at IC:1235, so it appears twice (once as absent, once as disabled). It also conflates facets: a failed `reExportLinking.link` disables package resolution for an adapter that never had that facet. Fix: only add to the disabled set when `packageResolution !== undefined`, or dedupe the list. Untested.
- D2 (NEW, LOW-MEDIUM, code/test vs spec). Collision error: spec says "naming both workspaces". The message (IC:906) names the identity and the existing workspace only; the new workspace appears in `filePath`. PI:634 passes because `graph` is a substring of `@fixture/graph`; it never checks `app`. A message-only consumer sees one workspace. Suggest naming both in the message and asserting both distinct names.
- D3 (NEW, MEDIUM for test quality, test vs spec). Scenario "Hydrated workspaces are prepared" is not really verified. PI:645 adds `app/src/extra.ts`; a new code file triggers the addition fallback (IC:808-814), which re-extracts every existing code file, so `graph` is reprocessed, not hydrated. Also `prepare` always receives `options.workspaces`, so the assertion `['app','graph']` would pass regardless. To discriminate, change content of one file with no additions and assert `filesSkipped > 0` for the other workspace, or spy that the other workspace's files were not analyzed.
- D4 (NEW, LOW, code vs spec edge). In `resolveBindingTarget` (SB-src:407-419), if an import-bound name's declaration id is not found by `findById` (or the optional `findById` is absent from a custom `SymbolLookup`), flow falls through to `findTargetCandidates` which searches the importing workspace by name (SB-src:445-446). For the `targetSymbolId` branch the later `candidates.filter(id === targetSymbolId)` prevents a wrong pick; for the `importedTargets` branch (no `targetSymbolId`) it does not, so a same-name local symbol could be chosen. The spec says the environment MUST NOT replace an import-bound name with a same-name symbol of the importing workspace. Practically unreachable in the indexer (hydration populates the session), but `findById` is optional in the `SymbolLookup` interface and nothing tests the unresolvable-id path.
- D5 (verify wording stale, LOW, unchanged). Scenarios "Package identity built from adapter" and "Adapter without getPackageIdentity skips resolution" in the merged verify still name `getPackageIdentity`, which this change replaces by `packageResolution.identity`.
- D6 (code vs spec, MEDIUM edge, unchanged). Subset runs: `packageToWorkspace` and `prepare` use `options.workspaces` only (IC:885, 916). With `--workspace core`, hydrated files of other stored workspaces are in the session but their packages are not mapped or prepared, so an import of such a package is `package-unknown` and counted as external. Spec text "every workspace of the run, including workspaces that were only hydrated" reads as satisfied only when the caller passes all workspaces. Either document "subset runs resolve only against indexed workspaces" or give the indexer the full workspace list. No test.
- D7 (spec precision / design, LOW, informational). "First adapter wins per workspace" plus `break` (IC:912) means a polyglot workspace (for example `package.json` and `go.mod`) maps only the first registered adapter's identity; the other language's packages in that workspace are never mapped. This is what the spec says, so it is not a defect, but it is a limitation worth a sentence in the spec or docs.
- D8 (global spec, LOW, pre-existing). IC imports `node:fs` while `default:_global/architecture` says application uses ports; HEAD already did. No new application-layer I/O was introduced: PR is I/O-free.
