## 4. Discrepancies (NEW findings only)

For each: A = spec is right and code should change; B = code is right and spec should change.

### D-1 (new, medium): identity is first-adapter-wins; baseline asked every adapter, and the spec is silent

- Evidence: IDX:906-908 `break` after the first adapter that returns an identity; baseline (`git show HEAD:...index-code-graph.ts:873-889`) called `getPackageIdentity` on every adapter for every workspace. Test PI:510 ("the first wins and the second is not asked") enshrines it. Docs language-adapters.md:19 states it ("The first adapter that returns an identity for a workspace wins"); the spec (Package identity extraction, Package resolution facet, Adapter facet model) does not.
- Impact: a polyglot workspace (for example Laravel with `package.json` and `composer.json`, or TypeScript `identity` walking up to a monorepo-root `package.json`) gets only the identity of the earliest registered adapter. The other languages' package imports into that workspace become `package-unknown`, counted as external, with no error. Which language wins depends on registration order.
- A (spec right, "call identity for each workspace's codeRoot"): ask every adapter; key the map by identity so several identities can map to one workspace.
- B (code right): add to the spec "the first adapter, in registration order, that returns an identity claims the workspace", and add a scenario. Consider logging the skipped adapters.

### D-2 (new, low): re-export linking does not consume the shared `entrySurface` helper

- Evidence: S:infrastructure/tree-sitter/typescript-language-adapter.ts:2958-3000 (`resolveReExportSource`, `packageEntryCandidates`, `entryCandidatePaths`). `ReExportLinkContext` (language-adapter-facets.ts:167-172) has no helper. Behavioural differences from ordinary imports: re-exports require exactly one indexed candidate, while ordinary imports accept several (PR:163 returns two alternatives); both filter tests and unindexed files.
- Spec: "using the same entry surface that ordinary package imports use" and the scenario "both use the same `packageResolution.entrySurface` result".
- A: pass `packageEntryFiles` (or a pre-filtered entry list) into `ReExportLinkContext`. B: the spec states "exactly one indexed entry file" for re-exports, so the divergence on multi-entry exports is intended; reword the scenario to "both read the same prepared manifest facts".

### N-2 (new, medium): excluding test symbols from the global qualified-name map also drops test-to-test imports and is not tested

- Evidence: in-memory-index-session.ts:318-325. The map is used by Go (go-language-adapter.ts:724), Python (python-language-adapter.ts:952), PHP (php-language-adapter.ts:967) and TS (typescript-language-adapter.ts:1421) before any other route, for every importer, including importers that are themselves test files and same-workspace imports.
- Effect: a PHP test that does `use Tests\Support\Helper;` (or a Python test importing a helper by dotted module) no longer gets an `importMap` entry, so CALLS/CONSTRUCTS/USES_TYPE from tests to test helpers disappear. The spec rule is literal ("an exact qualified-name lookup used by an import MUST NOT resolve to a symbol declared in a test file"), but its rationale (package entries) applies to cross-workspace package imports.
- A (spec right as written): accept the loss and add a scenario that tests may not import test symbols. B (code or spec narrower): apply the exclusion only when the importer is not a test file, or only across workspaces, and amend the spec sentence accordingly.
- Not tested: no test has a test file importing a test helper by qualified name.

### N-3 (new, low): PHP own-PSR-4 fallback and `resolveToPath` can return a test file; `absolute` id fallback remains

- Evidence: php-language-adapter.ts:977-989 (own-workspace fallback `resolveQualifiedNameFromSession`) and :2286 (`[`${workspace}:${relative}`, absolute]`). Neither checks `getFileCategory`. The shared helper path (`packageEntryFiles`) does filter tests.
- Spec: "A package-specifier import never resolves through a file classified as a test". Same-workspace PSR-4 may or may not be a "package-specifier import".
- A: filter `category === 'test'` in `resolveQualifiedNameFromSession` and drop the `absolute` id. B: spec limited to cross-workspace imports; keep, and state it.

### N-4 (new, low): registry validation raises non-`INVALID_LANGUAGE_ADAPTER` errors for malformed `languages()` / `extensions()` results

- Evidence: adapter-registry.ts `validateAdapter` calls `adapter.languages()` then `languages.length` and `Object.entries(adapter.extensions())` unguarded. A `languages()` that returns `undefined`, or throws, gives a raw `TypeError` or the adapter's own error; entries that are not strings are not checked. The spec's list says "a required core member is missing or is not a function; `languages()` returns no identifier; ..." (only function presence and emptiness).
- A: wrap and map to `INVALID_LANGUAGE_ADAPTER`. B: spec list is exhaustive; third-party misbehaviour beyond it is out of scope. State state is still unchanged because validation runs first.

### N-5 (new, medium, static reading, not executed): hydrated (unchanged) files do not feed the exact qualified-name map, so incremental runs differ from a clean rebuild for name-addressed imports

- Evidence: `hydratePersistedFile` (in-memory-index-session.ts:196-215) fills `symbolsByFile`/`symbolsById`/`symbolsByName` but never `qualifiedNameSymbolMap`; the map is only filled in `registerAnalysis` (:318-325). This was already true in the baseline (`git show HEAD:...:234`), but the change now promises "Incremental run ... equals a clean rebuild" for package imports and covers PHP, Python and Go.
- Effect: when only the importing PHP file changes, `qualifiedNames.get(imp.specifier)` misses the unchanged target; the PHP adapter falls to `packageEntryFiles` and records only a file dependency (PL:204 behaviour), so the `importMap` binding and USES_TYPE/CALLS differ from a clean run.
- A (spec right): hydrate the map from persisted symbols plus namespace data (needs the namespace persisted or derivable from the symbol). B (spec narrower): say that equality with a clean rebuild is required for entry-surface resolution only.
- Not tested: PI:343/PI:600 are TS-only; PL has no incremental case.

## 3. Discrepancies / new findings (beyond deferred list)

N1 (medium, TS): `sourceCandidates` (ts:3213-3225) only ever returns `.ts`, `.tsx`, `/index.ts`, `/index.tsx`. A package whose `exports`/`main` points at JavaScript source (e.g. `./src/index.js` with no TS sources, `.mjs`, `.cjs`, `.jsx`) never maps to an indexed file, although the adapter indexes `.js/.jsx` and the spec says a published `.js/.mjs/.cjs` under `dist` maps to "the indexed TypeScript or JavaScript source". Entry surface is silently empty -> `no-entry-surface`. No test for a JS-only package.

N2 (medium, Python, from code reading, not executed): `entrySurface` (py:386-409) returns every existing candidate of `.py`, `.pyi`, `/__init__.py`, `/__init__.pyi` and of both `src/<top>` and `<top>` roots, with `surface` stripped of extension (py:407). The shared resolver (package-import-resolver.ts:110-124) collects public-binding hits across all entries and returns `ambiguous` when targets differ. A module shipped as `models.py` + `models.pyi` (or `src/pkg` and `pkg` both indexed) therefore makes a name declared in both files `ambiguous`, whereas the relative resolver prefers source over stubs (py:1963). PR:259 locks "both forms in order" but never feeds the result to the resolver. Spec lists the forms as alternatives ("or") and says `.pyi` must not be merged speculatively.

N3 (low-medium, all four via `find-manifest-field.ts:17-40`): the walk stops only on `dir === boundary` (string equality). If `codeRoot` is not a descendant of `repoRoot` (external workspace, symlinked path, trailing-slash mismatch) the loop never hits the boundary and climbs to the filesystem root, reading arbitrary `package.json`/`pyproject.toml`/`go.mod`/`composer.json`; spec: "Filesystem searches MUST stop at the supplied repository root" (TS). Test TS-spec:1104 only covers the descendant case. Also a nearest manifest that has no name (or is unparsable) is skipped and the walk continues upward (PY-spec:680 locks this in); spec says identity comes from "the nearest bounded manifest".

N4 (low, PHP): `buildPsr4Map` (php:2254) merges `autoload['psr-4']` and `autoload-dev['psr-4']` with object spread, so a prefix declared in both keeps only the `autoload-dev` directories (production dirs lost). Dev prefixes also become part of the package's prod entry surface.

N5 (low, TS): a type-only default import (`import type Client from 'pkg'`) goes through the Default branch (ts:1504-1528) which ignores `imp.typeOnly`; it binds the default export declaration without a type-space check. Spec: a type-only name is looked up only in the type space.

N6 (low, Go): identity regex `^module\s+(\S+)` (go:1546) keeps the quotes for `module "example.com/x"` (legal go.mod syntax) so the identity never matches any import path.

N7 (spec/test mismatch, medium wording): Python, Go, PHP scenarios say "nothing is persisted and the reason is `package-unknown`". The pipeline classifies `package-unknown` as an external import and removes it from `byReason`/samples; the tests assert exactly that (PI:211-226 explicit `byReason['package-unknown']` undefined; PL:235-258; PL:331-347). Adapters return the reason as the spec says, but the observable contract is the opposite of the scenario text. One of spec/tests should be adjusted; no adapter-level test asserts the diagnostic reason for Python, Go, or PHP.

N10 (low, PHP): spec says `resolveToPath` "MUST NOT fall back to an absolute-path lookup of an unindexed file". `resolveQualifiedNameFromSession` (php:2292) still tries the absolute path as a second id (and as the only id when the workspace is unknown). It only returns indexed ids and baseline tests (PHP-spec:1770-1855) rely on absolute indexed ids, so no unindexed file is ever targeted, but the literal wording and the code differ. For PSR-4 dirs outside the code root (`../shared/src`) the workspace-prefixed id is `ws:../shared/...` and never matches.

N11 (info, TS): the namespace-import scenario's second clause ("member accesses on `graph` resolve only through names that entry publishes") has no implementation or test: package namespace imports bind nothing and `resolveImportedTypeName` (ts:1565-1591) resolves `ns.Type` only for relative namespace imports. Behaviour is stricter than the spec, never looser.

N12 (info, Python): `matchSpecifier` (py:1979-1988) normalizes only `_`->`-` and is case-sensitive; PEP 503 names also fold `.` and case. Within the spec text, so low.

Not an issue: Go dot/blank imports add package dependencies and never bind (go:709-745); Go `_test.go` exclusion plus resolver-level `category !== 'test'` filter; PHP entry candidates are further filtered to indexed non-test files by the resolver (resolver:83-87); TS `main` only used without `exports`.

## Discrepancies (NEW)

1. MEDIUM - Disabling goes beyond spec and cuts intra-workspace barrel linking. index-code-graph.ts:1229 skips `reExportLinking.link` for any adapter in `disabledPackageResolution`, and :1240 adds to it. Spec says an identity/prepare failure makes the adapter "not provide packageResolution"; it does not say reExportLinking (a separate facet; the TS adapter's link also resolves relative `export * from './x'` barrels) is skipped. Net effect: one bad manifest (identity throw) in any workspace disables TS re-export linking for the whole run, degrading relative barrel/public-binding resolution that has nothing to do with packages. Not tested. Either narrow the skip to prepare failures (link may need prepared data) or document it in the spec.
2. LOW-MEDIUM - Spec gap: prepare failure and link failure disabling the adapter (and the link-only adapter not being listed) are implemented and tested (package-imports.spec.ts:434, 615, 694) but are not stated in spec.md or verify.md; only identity failure is. Add requirement text + scenarios.
3. LOW - Stale baseline verify wording retained in the merged verify: "Package identity built from adapter" (TS adapter "implements getPackageIdentity") and "Adapter without getPackageIdentity skips resolution" (imports "remain unresolved"). The spec now defines `packageResolution.identity` and reports such adapters in `adaptersWithoutPackageResolution`; `getPackageIdentity` no longer exists. Modify those two scenarios (baseline wording contradicts new requirement).
4. LOW - Scoped env fallback: scoped-binding-environment.ts:411-420. In the `targetSymbolId === undefined` branch, if `importedTargets` yields an id but `localSymbolsById`/`findById` find nothing, control falls through to `findTargetCandidates`, i.e. the same-name workspace search the spec forbids ("MUST NOT replace it with a same-name symbol of the importing workspace"). Practically unreachable (ids come from resolved declarations in the same session) but a hydrated/stale id would hit it. Return undefined when an import-bound id is not found.
5. LOW - Over-broad addition fallback: index-code-graph.ts:808-810 triggers on `newFiles.length > 0`, and newFiles includes non-code inputs (docs/specs coverage paths), so adding a markdown file re-extracts every existing code file. Spec says "adds new code files". Conservative, correctness-safe, but costly and not what the requirement text says.
6. INFO - Manifest walk bounds differ: identity() is bounded by `projectRoot` (spec-mandated) while the fingerprint manifest discovery uses `vcsRoot` (index-code-graph.ts:636-637, compute-graph-fingerprint). Fingerprint may be sensitive to manifests identity never reads (over-invalidation only; no correctness issue).
7. INFO - `adaptersWithoutPackageResolution` is deduped by joined language string (index-code-graph.ts:952-956); spec says one entry per adapter. Two adapters with identical language lists would collapse. Unlikely.
