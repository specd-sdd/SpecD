## 3. Discrepancies / new findings (beyond deferred list)

N1 (medium, TS): `sourceCandidates` (ts:3213-3225) only ever returns `.ts`, `.tsx`, `/index.ts`, `/index.tsx`. A package whose `exports`/`main` points at JavaScript source (e.g. `./src/index.js` with no TS sources, `.mjs`, `.cjs`, `.jsx`) never maps to an indexed file, although the adapter indexes `.js/.jsx` and the spec says a published `.js/.mjs/.cjs` under `dist` maps to "the indexed TypeScript or JavaScript source". Entry surface is silently empty -> `no-entry-surface`. No test for a JS-only package.

N2 (medium, Python, from code reading, not executed): `entrySurface` (py:386-409) returns every existing candidate of `.py`, `.pyi`, `/__init__.py`, `/__init__.pyi` and of both `src/<top>` and `<top>` roots, with `surface` stripped of extension (py:407). The shared resolver (package-import-resolver.ts:110-124) collects public-binding hits across all entries and returns `ambiguous` when targets differ. A module shipped as `models.py` + `models.pyi` (or `src/pkg` and `pkg` both indexed) therefore makes a name declared in both files `ambiguous`, whereas the relative resolver prefers source over stubs (py:1963). PR:259 locks "both forms in order" but never feeds the result to the resolver. Spec lists the forms as alternatives ("or") and says `.pyi` must not be merged speculatively.

N3 (low-medium, all four via `find-manifest-field.ts:17-40`): the walk stops only on `dir === boundary` (string equality). If `codeRoot` is not a descendant of `repoRoot` (external workspace, symlinked path, trailing-slash mismatch) the loop never hits the boundary and climbs to the filesystem root, reading arbitrary `package.json`/`pyproject.toml`/`go.mod`/`composer.json`; spec: "Filesystem searches MUST stop at the supplied repository root" (TS). Test TS-spec:1104 only covers the descendant case. Also a nearest manifest that has no name (or is unparsable) is skipped and the walk continues upward (PY-spec:680 locks this in); spec says identity comes from "the nearest bounded manifest".

N4 (low, PHP): `buildPsr4Map` (php:2254) merges `autoload['psr-4']` and `autoload-dev['psr-4']` with object spread, so a prefix declared in both keeps only the `autoload-dev` directories (production dirs lost). Dev prefixes also become part of the package's prod entry surface.

N5 (low, TS): a type-only default import (`import type Client from 'pkg'`) goes through the Default branch (ts:1504-1528) which ignores `imp.typeOnly`; it binds the default export declaration without a type-space check. Spec: a type-only name is looked up only in the type space.

N6 (low, Go): identity regex `^module\s+(\S+)` (go:1546) keeps the quotes for `module "example.com/x"` (legal go.mod syntax) so the identity never matches any import path.

N7 (spec/test mismatch, medium wording): Python, Go, PHP scenarios say "nothing is persisted and the reason is `package-unknown`". The pipeline classifies `package-unknown` as an external import and removes it from `byReason`/samples; the tests assert exactly that (PI:211-226 explicit `byReason['package-unknown']` undefined; PL:235-258; PL:331-347). Adapters return the reason as the spec says, but the observable contract is the opposite of the scenario text. One of spec/tests should be adjusted; no adapter-level test asserts the diagnostic reason for Python, Go, or PHP.

N10 (low, PHP): spec says `resolveToPath` "MUST NOT fall back to an absolute-path lookup of an unindexed file". `resolveQualifiedNameFromSession` (php:2292) still tries the absolute path as a second id (and as the only id when the workspace is unknown). It only returns indexed ids and baseline tests (PHP-spec:1770-1855) rely on absolute indexed ids, so no unindexed file is ever targeted, but the literal wording and the code differ. For PSR-4 dirs outside the code root (`../shared/src`) the workspace-prefixed id is `ws:../shared/...` and never matches.

N11 (info, TS): the namespace-import scenario's second clause ("member accesses on `graph` resolve only through names that entry publishes") has no implementation or test: package namespace imports bind nothing and `resolveImportedTypeName` (ts:1565-1591) resolves `ns.Type` only for relative namespace imports. Behaviour is stricter than the spec, never looser.

N12 (info, Python): `matchSpecifier` (py:1979-1988) normalizes only `_`->`-` and is case-sensitive; PEP 503 names also fold `.` and case. Within the spec text, so low.

Not an issue: Go dot/blank imports add package dependencies and never bind (go:709-745); Go `_test.go` exclusion plus resolver-level `category !== 'test'` filter; PHP entry candidates are further filtered to indexed non-test files by the resolver (resolver:83-87); TS `main` only used without `exports`.
