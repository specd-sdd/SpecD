## 4. Discrepancies (NEW findings only)

For each: A = spec is right and code should change; B = code is right and spec should change.

### D-1 (new, medium): identity is first-adapter-wins; baseline asked every adapter, and the spec is silent

- Evidence: IDX:906-908 `break` after the first adapter that returns an identity; baseline (`git show HEAD:...index-code-graph.ts:873-889`) called `getPackageIdentity` on every adapter for every workspace. Test PI:510 ("the first wins and the second is not asked") enshrines it. Docs language-adapters.md:19 states it ("The first adapter that returns an identity for a workspace wins"); the spec (Package identity extraction, Package resolution facet, Adapter facet model) does not.
- Impact: a polyglot workspace (for example Laravel with `package.json` and `composer.json`, or TypeScript `identity` walking up to a monorepo-root `package.json`) gets only the identity of the earliest registered adapter. The other languages' package imports into that workspace become `package-unknown`, counted as external, with no error. Which language wins depends on registration order.
- A (spec right, "call identity for each workspace's codeRoot"): ask every adapter; key the map by identity so several identities can map to one workspace.
- B (code right): add to the spec "the first adapter, in registration order, that returns an identity claims the workspace", and add a scenario. Consider logging the skipped adapters.

### D-2 (new, low): re-export linking does not consume the shared `entrySurface` helper

- Evidence: S:infrastructure/tree-sitter/typescript-language-adapter.ts:2958-3000 (`resolveReExportSource`, `packageEntryCandidates`, `entryCandidatePaths`). `ReExportLinkContext` (language-adapter-facets.ts:167-172) has no helper. Behavioural differences from ordinary imports: re-exports require exactly one indexed candidate, while ordinary imports accept several (PR:163 returns two alternatives); both filter tests and unindexed files.
- Spec: "using the same entry surface that ordinary package imports use" and the scenario "both use the same `packageResolution.entrySurface` result".
- A: pass `packageEntryFiles` (or a pre-filtered entry list) into `ReExportLinkContext`. B: the spec states "exactly one indexed entry file" for re-exports, so the divergence on multi-entry exports is intended; reword the scenario to "both read the same prepared manifest facts".

### N-2 (new, medium): excluding test symbols from the global qualified-name map also drops test-to-test imports and is not tested

- Evidence: in-memory-index-session.ts:318-325. The map is used by Go (go-language-adapter.ts:724), Python (python-language-adapter.ts:952), PHP (php-language-adapter.ts:967) and TS (typescript-language-adapter.ts:1421) before any other route, for every importer, including importers that are themselves test files and same-workspace imports.
- Effect: a PHP test that does `use Tests\Support\Helper;` (or a Python test importing a helper by dotted module) no longer gets an `importMap` entry, so CALLS/CONSTRUCTS/USES_TYPE from tests to test helpers disappear. The spec rule is literal ("an exact qualified-name lookup used by an import MUST NOT resolve to a symbol declared in a test file"), but its rationale (package entries) applies to cross-workspace package imports.
- A (spec right as written): accept the loss and add a scenario that tests may not import test symbols. B (code or spec narrower): apply the exclusion only when the importer is not a test file, or only across workspaces, and amend the spec sentence accordingly.
- Not tested: no test has a test file importing a test helper by qualified name.

### N-3 (new, low): PHP own-PSR-4 fallback and `resolveToPath` can return a test file; `absolute` id fallback remains

- Evidence: php-language-adapter.ts:977-989 (own-workspace fallback `resolveQualifiedNameFromSession`) and :2286 (`[`${workspace}:${relative}`, absolute]`). Neither checks `getFileCategory`. The shared helper path (`packageEntryFiles`) does filter tests.
- Spec: "A package-specifier import never resolves through a file classified as a test". Same-workspace PSR-4 may or may not be a "package-specifier import".
- A: filter `category === 'test'` in `resolveQualifiedNameFromSession` and drop the `absolute` id. B: spec limited to cross-workspace imports; keep, and state it.

### N-4 (new, low): registry validation raises non-`INVALID_LANGUAGE_ADAPTER` errors for malformed `languages()` / `extensions()` results

- Evidence: adapter-registry.ts `validateAdapter` calls `adapter.languages()` then `languages.length` and `Object.entries(adapter.extensions())` unguarded. A `languages()` that returns `undefined`, or throws, gives a raw `TypeError` or the adapter's own error; entries that are not strings are not checked. The spec's list says "a required core member is missing or is not a function; `languages()` returns no identifier; ..." (only function presence and emptiness).
- A: wrap and map to `INVALID_LANGUAGE_ADAPTER`. B: spec list is exhaustive; third-party misbehaviour beyond it is out of scope. State state is still unchanged because validation runs first.

### N-5 (new, medium, static reading, not executed): hydrated (unchanged) files do not feed the exact qualified-name map, so incremental runs differ from a clean rebuild for name-addressed imports

- Evidence: `hydratePersistedFile` (in-memory-index-session.ts:196-215) fills `symbolsByFile`/`symbolsById`/`symbolsByName` but never `qualifiedNameSymbolMap`; the map is only filled in `registerAnalysis` (:318-325). This was already true in the baseline (`git show HEAD:...:234`), but the change now promises "Incremental run ... equals a clean rebuild" for package imports and covers PHP, Python and Go.
- Effect: when only the importing PHP file changes, `qualifiedNames.get(imp.specifier)` misses the unchanged target; the PHP adapter falls to `packageEntryFiles` and records only a file dependency (PL:204 behaviour), so the `importMap` binding and USES_TYPE/CALLS differ from a clean run.
- A (spec right): hydrate the map from persisted symbols plus namespace data (needs the namespace persisted or derivable from the symbol). B (spec narrower): say that equality with a clean rebuild is required for entry-surface resolution only.
- Not tested: PI:343/PI:600 are TS-only; PL has no incremental case.

### D-4 (low, carried): target-less public bindings are ignored in the ambiguity check

package-import-resolver.ts:105-113. Spec: "every binding found ... leads to the same logical target". A: treat a target-less binding as ambiguous. B: reword to "every resolved binding".

### D-5 (low, editorial, carried): resolved result carries `targetSymbolId` and `step`; spec lists only logical id, entry file, public binding id.

### D-6 (low, carried): docs/code-graph/language-adapters.md:276-277 step 6 ("the facet scenarios in the specification's verification") and step 7 ("Write the adapter's specific spec") refer the reader to the spec, while the scenario "Docs page states the same rules" says "without referring the reader to the spec". A: reword. B: the scenario is too strict for step 7.

### D-7 (low, new, docs): the docs omit the exact-qualified-name test rule

- Evidence: docs/code-graph/language-adapters.md:69 states the entry-surface test rule only. Nothing says that `session.getQualifiedNames()` excludes test-file symbols, which adapters that use the map need to know. The docs spec test (T:docs/language-adapters-docs.spec.ts) would not catch it.
- A: add one sentence to the "Resolving a package import" or qualified-name section. B: spec sentence moves to the indexer/session spec instead.
