### 1.2 Discrepancies

**D1. PHP `qualifiedNameResolution.resolveToPath` reads composer.json on every call (candidate a: CONFIRMED).**

- Description: `resolveToPath(qualifiedName, codeRoot, repoRoot?)` -> `resolveQualifiedNameToPath` -> `buildPsr4Map(codeRoot, repoRoot)` -> `findManifestField` (`existsSync` + `readFileSync`) each call (`php-language-adapter.ts:2322-2328`, `:2232-2258`). The spec requires "using metadata already prepared in the run-scoped session. It MUST NOT probe the filesystem per call" (Qualified-name resolution facet). Scenario "Resolve to path uses prepared metadata" (no filesystem access on repeated calls) is therefore false for the PHP adapter.
- Evidence the code is wrong: the spec text is explicit; the design (design.md "New constructs", `QualifiedNameResolutionFacet` comment) says "Reads prepared metadata only; no filesystem probing"; the same adapter already has the correct session-based method `resolveQualifiedNameFromSession` (`:2267`), and `prepare` already stores the PSR-4 map (`:2133-2152`).
- Evidence the spec is wrong or unimplementable as written: the facet signature has no `session` parameter, so a conforming implementation cannot reach run-scoped state from `resolveToPath`; it would need adapter-instance state, which the Full-file analysis requirement also forbids ("MUST NOT rely on mutable adapter-instance caches shared across sessions"). The Constraints section still says only "SHOULD read parsed autoloader/manifest metadata prepared per codeRoot or session", which contradicts the requirement's MUST NOT. The facet method is dead code in the engine (grep: no caller outside registry validation and tests); Pass 2 never invokes it, so the "no I/O in Pass 2" rule holds. Existing tests (`php-language-adapter.spec.ts:679-732`) write a real composer.json and call `resolveToPath` with no prepare, which only works because it reads disk; the test titled "caches PSR-4 map across calls" does not cache.
- Severity: medium. Public facet contract violated and a spec scenario is false, but no runtime Pass 2 impact. Fix options: add a session parameter to the facet (spec + code), or drop `resolveToPath` from the facet and keep session resolution internal.

**D2. `symbolReferenceSyntax.render` signature differs between spec and code.**

- Spec: `render(member: LogicalSymbol, options?: RenderSymbolReferenceOptions): RenderedSymbolReference`. Code, docs and design.md (design line ~271): `render(symbol, ownerPath)` returning `{ generic, native? }`.
- Code is wrong? No evidence: HEAD already had `renderSymbolReference(symbol, ownerPath)` (git show HEAD, language-adapter.ts:192); design.md, tasks.md 5.3 and docs all use `ownerPath`; `RenderSymbolReferenceOptions` and `RenderedSymbolReference` exist only in the delta file (grep over specs, docs, src).
- Spec is wrong: invented type names not present in any code or design; `ownerPath` is required because the facet "does not query a store".
- Severity: medium (spec wording blocks an adapter author who follows the spec; docs say the opposite of the spec). Fix the spec.

**D3. `prepare` does not read manifests uniformly (candidate c: PARTIALLY CONFIRMED, spec text is not violated, design/tasks claims are).**

- Code: TS reads each `<codeRoot>/package.json` once (`prepareWorkspaceManifest`, guarded by `manifests.has`); Python `prepare: () => undefined` with comment "nothing to read per workspace"; Go `prepare` calls `goPackageFiles(context.session, '', '')` to build the directory index; PHP `preparePackages` calls `buildPsr4Map` and `getPackageIdentity` (two more reads of the same composer.json per workspace, in addition to the earlier indexer `identity` call and the per-codeRoot read in `prepareResolutionMetadata` during `analyzeFile`).
- Spec: "reads, with I/O allowed, the manifest facts the adapter needs for every workspace and stores them". It does not say "once per file" or "exactly once per run per manifest". Python and Go need no facts beyond the identity map, so a no-op or index-building `prepare` satisfies it. The verify scenario "Prepare runs once" checks the number of `prepare` calls (satisfied), not the number of reads.
- design.md and tasks.md claim otherwise: tasks 15.1 "stores `{ projectName, codeRoot }` per workspace under `'py:packages'`", 16.1 "stores `{ modulePath, codeRoot }` under `'go:packages'`", 11.1/17.1 "read each file once per run"; design.md line 562 and lines 642-645 ("`prepare` once"). Those are ticked `[x]` but not implemented that way.
- Verdict: spec OK, code OK against the spec, design/tasks stale. Severity low. PHP's repeated reads are an efficiency issue, not a correctness one.

**D4. A throwing `packageResolution.identity` stops the run.**

- Spec: "A facet that is present but throws while being used SHALL be handled by the indexer's per-file error isolation. It MUST NOT stop the run." Verify: "Facet that throws does not stop the run".
- Code: `index-code-graph.ts:884-902` calls `adapter.packageResolution.identity(...)` with no try/catch, inside the run-level try/finally (`:491`, `:1938`), so the exception propagates out of `execute`. design.md "Error handling" says identity/prepare/link are "caught per adapter ... treated as having no facet", and `docs/code-graph/language-adapters.md:49` says the same. `prepare` and `link` are handled; `identity` is not.
- Spec might be wrong: `identity` is per workspace, not per file, so "per-file isolation" does not literally cover it; the spec should say what happens.
- Severity: medium (unhandled third-party adapter failure aborts a whole index run and the docs promise otherwise).

**D5. TypeScript `prepare`/entry surface only works when the workspace code root is the package root.**

- `identity` walks up from `codeRoot` (verify scenario "Manifest found above codeRoot"), but `prepareWorkspaceManifest` reads only `join(codeRoot, 'package.json')` and `sourceCandidates(workspace, published)` maps `./dist/x.js` to `workspace:src/x.ts`. For a workspace with `codeRoot` below the manifest directory, the package gets an identity in `packageToWorkspace` but `entrySurface` returns `[]`, so every import ends as `no-entry-surface`. design.md line 122 said "find the nearest bounded `package.json`".
- All workspaces in this repo have code roots equal to the package root (specd.yaml), so this is not visible here.
- Spec: silent on the walk-up for `entrySurface`. Severity: low to medium (latent; spec and test gap, no scenario covers it).

**D6. Test-file exclusion is in the resolver, not in the facet, and ignores the "explicitly addressed" exception.**

- Spec (Package resolution facet): the facet "MUST NOT return files classified as tests unless the specifier addresses one explicitly"; workspace-integration says the same for the import result. Code: TS, Python and PHP `entrySurface` do not look at the file category; `package-import-resolver.ts:80-84` drops `getFileCategory === 'test'` entries unconditionally. Go filters `_test.go` by name in `goPackageFiles`.
- Behaviour is safe (no test file is ever selected), stricter than the spec. design.md says the exception is "practically never" used. Severity: low. Either the facet text should assign the filtering to the indexer or the resolver should keep the exception.

**D7. Registration error details.**

- Spec: message names "the offending adapter language, the failed rule, and the missing or invalid member". `languages() returned no language` and `extension ".rs" maps to undeclared language` messages do not name a member (`adapter-registry.ts:101-111`). Also `register` throws plain `Error` for declaration-policy violations (`:56-65`) which are not in the spec's list and contradict `default:_global/error-handling-conventions` ("MUST NOT use generic Error for validation errors"). These two checks pre-date the change but the change rewrote `register`.
- Severity: low.

**D8. TS re-export fallback binds an unexported same-name declaration in the entry file.**

- `typescript-language-adapter.ts:2916-2926`: when no public binding of the entry exists for the imported name but the entry file declares exactly one symbol of that name, a binding is emitted. Verify scenario "Missing exported name emits no binding" is covered by a test whose entry does not declare the name (`typescript-language-adapter.spec.ts` "emits no binding for two entry candidates, a missing name, or an unknown package"), so the unexported-but-declared case is untested. File-scoped, so the rule "MUST NOT choose the first symbol of that name anywhere in the target workspace" is not broken. Severity: low.

**D9. PHP exposes `relativeImportResolution`.**

- Spec: "An adapter whose language has no relative imports MUST NOT provide this facet"; the import table says PHP `use` imports are never relative. PHP's facet resolves `require`/`include` paths. No spec statement defines PHP include paths as relative imports. Severity: low (spec clarification).

**D10. Verify scenario "Adapter is a required core plus declared facets" is wrong for TypeScript, and the loose-method claim is only compile-time (candidate b).**

- (i) The scenario says the TS adapter exposes `qualifiedNameResolution`. The TS adapter has no such facet (grep: 0 matches in `typescript-language-adapter.ts`); this is intended: tasks.md 5.2 "Expose `qualifiedNameResolution` only if real", and the spec itself says an adapter without qualified-name addressing MUST NOT provide it. Spec (verify) is wrong; code is right.
- (ii) "exposes no loose `getPackageIdentity`, `resolvePackageFromSpecifier`, `resolveRelativeImportPath`, `buildQualifiedName`, `resolveQualifiedNameToPath`, `parseSymbolReference`, `renderSymbolReference`, `linkReExports` method": in the four adapters these exist as TypeScript-`private` methods (TS: `:736,746,2826,3038,3081,3103`; PHP: `:552,574,584,2098,2116,2322,2782`; Python and Go analogous). `LanguageAdapter` (the public interface) no longer declares them and the facet objects delegate to them, which is what design.md line 121 intends ("become private"). At runtime they are still own-prototype methods and callable, so a literal "no method present" check (`'getPackageIdentity' in adapter`) would FAIL. No test checks either way. Verdict: the intent (removed from the contract, not reachable through the typed API, consumers cannot depend on them) is met; the literal wording is not. Either soften the scenario to "not declared on `LanguageAdapter`" or rename/inline the private methods. Severity: low.

## 4. Docs vs spec differences (`docs/code-graph/language-adapters.md` vs merged language-adapter spec)

Docs state the required core, five facets, members, unresolved reasons, registration errors and replacement semantics. Differences, each with the side that looks wrong:

1. `render` signature: docs `render(symbol, ownerPath)` (line 108) vs spec `render(member, options?)`: spec wrong (D2).
2. Step order: docs list "Package map" (identity) as step 2, after Pass 1; spec says `identity` "is called once per workspace before Pass 1 completes", and the code calls it before Pass 1 (`index-code-graph.ts:884`, before the analyze loop). Docs order is inaccurate; spec and code agree. Low.
3. `prepare`: docs "called once per adapter with every workspace, including unchanged ones" vs spec "once per run, after all workspaces have been analyzed". Equivalent in effect; docs add "per adapter". Low.
4. Facet throws: docs line 49 "If `identity`, `prepare`, or `link` throws, the adapter behaves as if it did not provide that facet for the rest of the run". Spec says only "handled by per-file error isolation". Code does this for `prepare` only (D4); `link` is recorded but nothing is disabled; `identity` aborts the run. Docs overpromise; code or docs must change.
5. Test files: docs "The indexer also discards files classified as tests and files that are not indexed" vs spec "MUST NOT return files classified as tests unless the specifier addresses one explicitly" (facet duty). Docs describe actual behaviour; spec exception not documented (D6).
6. Docs omit: that facets are part of the public contract and a new facet needs a spec change; the Python identity rules (`[project].name` only, quote styles, continue the walk) beyond the table cell; the `repoRoot` source (VCS adapter) and the filesystem-root fallback when `repoRoot` is absent; "`identity` is called once per workspace before Pass 1 completes"; `matchSpecifier` "has no side effects"; the "ambiguous" definition is present but the spec's "resolve a name only when every binding in every requested space and every entry leads to the same target" is paraphrased only. The spec says the page must state "the same required core, facets, members, invariants, and steps": the first four omissions are invariants missing from the page.
7. Docs add rules not in spec: "Return every alternative the manifest offers" (entrySurface), the 20-sample cap and `importDiagnostics` structure (`total`, `byReason`, `samples`, `externalPackageImports`), `PackageExportRequest` fields (`fromFile`, `localBindingId`), `targetSymbolId`, `step` usage. The spec defines none of them (spec gap: `PackageExportRequest`/`PackageExportResolution`/`PackageEntryResolution` field lists are not in the spec).
8. Checklist step 6: docs "Add tests: structural-text boundary fixtures, unresolved imports producing no relation, Pass 2 performing no filesystem reads after preparation, and incremental indexing producing the same graph as a clean rebuild" vs spec "Pass the cross-language semantic conformance suite and the facet scenarios in this spec's verification". The docs drop the "add to the list" duty and make the spec conditional while the spec makes the specific spec unconditional.
