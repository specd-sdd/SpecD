## Findings that need a decision, by kind

### Code does not do what the spec, design, or docs say

1. **A throwing `packageResolution.identity` aborts the whole run.** The package-map loop has no try/catch (`index-code-graph.ts` ~884-902). Spec, design, and `docs/code-graph/language-adapters.md` say a facet failure must not stop the run. Severity: medium-high.
2. **PHP `qualifiedNameResolution.resolveToPath` reads the filesystem on every call** (`php-language-adapter.ts` ~2322). The spec forbids per-call filesystem access, but the facet signature has no session, so the rule cannot be met as written. Nothing in the engine calls it. Fix needs a signature change or removing the member.
3. **The `facet-absent` startup notice is counted in `importDiagnostics.total` and `byReason`**, inflating the failure total (`index-code-graph.ts` ~935-943).
4. **The shared binding environment keys `importedTargets` by name only.** A nested-scope shadow without a target id could resolve to the import. Same-workspace results are unchanged today.
5. **"First adapter wins" for package identity is not enforced** in the package-map loop.
6. **TypeScript `prepare` reads only `<codeRoot>/package.json` while `identity` walks up.** A workspace whose code root is below its package root gets an identity but no entries. Latent: every workspace in this repository has the code root equal to the package root. Go has the same shape with `go.mod`.
7. **Python: a submodule import adds the file dependency but creates no namespace binding**, which the spec and its scenario require.
8. **TypeScript default and namespace package imports skip `resolvePackageExport`**, so they produce no step and take the first entry.
9. **TypeScript uses `main` as a fallback when `exports` exists but has no usable target.** The spec says only when `exports` is absent.
10. **PHP legacy fallback in `resolveImports` can return an absolute path without checking it is indexed**, and the indexer turns it into an `IMPORTS` relation. Pre-existing code, now redundant with the facet.
11. **`register` still throws a plain `Error` for declaration-policy violations**, and two registration messages do not name a member.

### Spec, design, tasks, or docs do not match the code

12. **`prepare` wording.** The spec, design.md (`py:packages`, `go:packages`, `php:packages` state), and the ticked tasks 11.1, 15.1, 16.1, 17.1 say `prepare` reads and stores manifest data per workspace. Python's is a no-op, Go's only builds a directory index, and PHP reads `composer.json` three times per workspace. The scenarios "Prepare reads each pyproject.toml once" and "Prepare reads composer.json once per workspace" cannot hold literally.
13. **`symbolReferenceSyntax.render` signature.** Code, docs, and design: `render(symbol, ownerPath)`. Spec: `render(member, options?)` returning `RenderedSymbolReference`, a type that exists nowhere else.
14. **Test entries.** The spec allows them when the specifier addresses the file; the resolver always drops them, and the ADR and docs say "never".
15. **Phase wording.** The spec says the package map is built between the passes; the code builds it before Pass 1. The docs list the steps in the wrong order.
16. **"Closure does not scan every file."** The pre-existing `additionCandidates` seeding re-extracts every existing file whenever any file is new, which contradicts the scenario. It is also the only mechanism that covers "newly resolvable import".
17. **The loose-methods scenario.** The eight old methods remain TypeScript-`private` methods, still callable at runtime. The scenario also lists `qualifiedNameResolution` as a TypeScript facet, which the TypeScript adapter correctly omits.
18. **Smaller:** ADR-0030 uses `### Confirmation` and a nested `### Consequences` instead of `## Decision Outcome Confirmation` and a top-level section; the CLI does not print `importDiagnostics`; in incremental runs the diagnostics cover only reprocessed files; fourteen wording differences between the docs page and the spec are listed in the contract report.

### Missing or weak tests

19. **Uncovered scenarios (19):** prepare receives every workspace in an incremental run; identity collision; newly resolvable import; closure does not scan every file; unimported name keeps the workspace lookup; TypeScript type-only restricts to the type space; TypeScript package namespace import; Python absolute submodule import; PHP `resolveToPath` without filesystem access; and the loose-methods scenario.
20. **Weak assertions:** resolver tests check only status and target id (no provenance path, no same-name decoy, no steps from the four languages); the bounded-diagnostics test asserts `>= 25` rather than the exact count; the documentation test only checks that names appear.

### Global specs (low)

Test titles mix "Given" and "given" and some new test files do not mirror a `src` file; facet backing fields lack the private-field prefix of the conventions; `index-code-graph.ts` is 2086 lines and the new diagnostics bookkeeping could move to a service. No violations of the architecture or eslint specs, and no contradictions with `code-graph:workspace-integration` or `code-graph:symbol-model`.

### 1.2 Discrepancies

**D1. PHP `qualifiedNameResolution.resolveToPath` reads composer.json on every call (candidate a: CONFIRMED).**

- Description: `resolveToPath(qualifiedName, codeRoot, repoRoot?)` -> `resolveQualifiedNameToPath` -> `buildPsr4Map(codeRoot, repoRoot)` -> `findManifestField` (`existsSync` + `readFileSync`) each call (`php-language-adapter.ts:2322-2328`, `:2232-2258`). The spec requires "using metadata already prepared in the run-scoped session. It MUST NOT probe the filesystem per call" (Qualified-name resolution facet). Scenario "Resolve to path uses prepared metadata" (no filesystem access on repeated calls) is therefore false for the PHP adapter.
- Evidence the code is wrong: the spec text is explicit; the design (design.md "New constructs", `QualifiedNameResolutionFacet` comment) says "Reads prepared metadata only; no filesystem probing"; the same adapter already has the correct session-based method `resolveQualifiedNameFromSession` (`:2267`), and `prepare` already stores the PSR-4 map (`:2133-2152`).
- Evidence the spec is wrong or unimplementable as written: the facet signature has no `session` parameter, so a conforming implementation cannot reach run-scoped state from `resolveToPath`; it would need adapter-instance state, which the Full-file analysis requirement also forbids ("MUST NOT rely on mutable adapter-instance caches shared across sessions"). The Constraints section still says only "SHOULD read parsed autoloader/manifest metadata prepared per codeRoot or session", which contradicts the requirement's MUST NOT. The facet method is dead code in the engine (grep: no caller outside registry validation and tests); Pass 2 never invokes it, so the "no I/O in Pass 2" rule holds. Existing tests (`php-language-adapter.spec.ts:679-732`) write a real composer.json and call `resolveToPath` with no prepare, which only works because it reads disk; the test titled "caches PSR-4 map across calls" does not cache.
- Severity: medium. Public facet contract violated and a spec scenario is false, but no runtime Pass 2 impact. Fix options: add a session parameter to the facet (spec + code), or drop `resolveToPath` from the facet and keep session resolution internal.

**D2. `symbolReferenceSyntax.render` signature differs between spec and code.**

- Spec: `render(member: LogicalSymbol, options?: RenderSymbolReferenceOptions): RenderedSymbolReference`. Code, docs and design.md (design line ~271): `render(symbol, ownerPath)` returning `{ generic, native? }`.
- Code is wrong? No evidence: HEAD already had `renderSymbolReference(symbol, ownerPath)` (git show HEAD, language-adapter.ts:192); design.md, tasks.md 5.3 and docs all use `ownerPath`; `RenderSymbolReferenceOptions` and `RenderedSymbolReference` exist only in the delta file (grep over specs, docs, src).
- Spec is wrong: invented type names not present in any code or design; `ownerPath` is required because the facet "does not query a store".
- Severity: medium (spec wording blocks an adapter author who follows the spec; docs say the opposite of the spec). Fix the spec.

**D3. `prepare` does not read manifests uniformly (candidate c: PARTIALLY CONFIRMED, spec text is not violated, design/tasks claims are).**

- Code: TS reads each `<codeRoot>/package.json` once (`prepareWorkspaceManifest`, guarded by `manifests.has`); Python `prepare: () => undefined` with comment "nothing to read per workspace"; Go `prepare` calls `goPackageFiles(context.session, '', '')` to build the directory index; PHP `preparePackages` calls `buildPsr4Map` and `getPackageIdentity` (two more reads of the same composer.json per workspace, in addition to the earlier indexer `identity` call and the per-codeRoot read in `prepareResolutionMetadata` during `analyzeFile`).
- Spec: "reads, with I/O allowed, the manifest facts the adapter needs for every workspace and stores them". It does not say "once per file" or "exactly once per run per manifest". Python and Go need no facts beyond the identity map, so a no-op or index-building `prepare` satisfies it. The verify scenario "Prepare runs once" checks the number of `prepare` calls (satisfied), not the number of reads.
- design.md and tasks.md claim otherwise: tasks 15.1 "stores `{ projectName, codeRoot }` per workspace under `'py:packages'`", 16.1 "stores `{ modulePath, codeRoot }` under `'go:packages'`", 11.1/17.1 "read each file once per run"; design.md line 562 and lines 642-645 ("`prepare` once"). Those are ticked `[x]` but not implemented that way.
- Verdict: spec OK, code OK against the spec, design/tasks stale. Severity low. PHP's repeated reads are an efficiency issue, not a correctness one.

**D4. A throwing `packageResolution.identity` stops the run.**

- Spec: "A facet that is present but throws while being used SHALL be handled by the indexer's per-file error isolation. It MUST NOT stop the run." Verify: "Facet that throws does not stop the run".
- Code: `index-code-graph.ts:884-902` calls `adapter.packageResolution.identity(...)` with no try/catch, inside the run-level try/finally (`:491`, `:1938`), so the exception propagates out of `execute`. design.md "Error handling" says identity/prepare/link are "caught per adapter ... treated as having no facet", and `docs/code-graph/language-adapters.md:49` says the same. `prepare` and `link` are handled; `identity` is not.
- Spec might be wrong: `identity` is per workspace, not per file, so "per-file isolation" does not literally cover it; the spec should say what happens.
- Severity: medium (unhandled third-party adapter failure aborts a whole index run and the docs promise otherwise).

**D5. TypeScript `prepare`/entry surface only works when the workspace code root is the package root.**

- `identity` walks up from `codeRoot` (verify scenario "Manifest found above codeRoot"), but `prepareWorkspaceManifest` reads only `join(codeRoot, 'package.json')` and `sourceCandidates(workspace, published)` maps `./dist/x.js` to `workspace:src/x.ts`. For a workspace with `codeRoot` below the manifest directory, the package gets an identity in `packageToWorkspace` but `entrySurface` returns `[]`, so every import ends as `no-entry-surface`. design.md line 122 said "find the nearest bounded `package.json`".
- All workspaces in this repo have code roots equal to the package root (specd.yaml), so this is not visible here.
- Spec: silent on the walk-up for `entrySurface`. Severity: low to medium (latent; spec and test gap, no scenario covers it).

**D6. Test-file exclusion is in the resolver, not in the facet, and ignores the "explicitly addressed" exception.**

- Spec (Package resolution facet): the facet "MUST NOT return files classified as tests unless the specifier addresses one explicitly"; workspace-integration says the same for the import result. Code: TS, Python and PHP `entrySurface` do not look at the file category; `package-import-resolver.ts:80-84` drops `getFileCategory === 'test'` entries unconditionally. Go filters `_test.go` by name in `goPackageFiles`.
- Behaviour is safe (no test file is ever selected), stricter than the spec. design.md says the exception is "practically never" used. Severity: low. Either the facet text should assign the filtering to the indexer or the resolver should keep the exception.

**D7. Registration error details.**

- Spec: message names "the offending adapter language, the failed rule, and the missing or invalid member". `languages() returned no language` and `extension ".rs" maps to undeclared language` messages do not name a member (`adapter-registry.ts:101-111`). Also `register` throws plain `Error` for declaration-policy violations (`:56-65`) which are not in the spec's list and contradict `default:_global/error-handling-conventions` ("MUST NOT use generic Error for validation errors"). These two checks pre-date the change but the change rewrote `register`.
- Severity: low.

**D8. TS re-export fallback binds an unexported same-name declaration in the entry file.**

- `typescript-language-adapter.ts:2916-2926`: when no public binding of the entry exists for the imported name but the entry file declares exactly one symbol of that name, a binding is emitted. Verify scenario "Missing exported name emits no binding" is covered by a test whose entry does not declare the name (`typescript-language-adapter.spec.ts` "emits no binding for two entry candidates, a missing name, or an unknown package"), so the unexported-but-declared case is untested. File-scoped, so the rule "MUST NOT choose the first symbol of that name anywhere in the target workspace" is not broken. Severity: low.

**D9. PHP exposes `relativeImportResolution`.**

- Spec: "An adapter whose language has no relative imports MUST NOT provide this facet"; the import table says PHP `use` imports are never relative. PHP's facet resolves `require`/`include` paths. No spec statement defines PHP include paths as relative imports. Severity: low (spec clarification).

**D10. Verify scenario "Adapter is a required core plus declared facets" is wrong for TypeScript, and the loose-method claim is only compile-time (candidate b).**

- (i) The scenario says the TS adapter exposes `qualifiedNameResolution`. The TS adapter has no such facet (grep: 0 matches in `typescript-language-adapter.ts`); this is intended: tasks.md 5.2 "Expose `qualifiedNameResolution` only if real", and the spec itself says an adapter without qualified-name addressing MUST NOT provide it. Spec (verify) is wrong; code is right.
- (ii) "exposes no loose `getPackageIdentity`, `resolvePackageFromSpecifier`, `resolveRelativeImportPath`, `buildQualifiedName`, `resolveQualifiedNameToPath`, `parseSymbolReference`, `renderSymbolReference`, `linkReExports` method": in the four adapters these exist as TypeScript-`private` methods (TS: `:736,746,2826,3038,3081,3103`; PHP: `:552,574,584,2098,2116,2322,2782`; Python and Go analogous). `LanguageAdapter` (the public interface) no longer declares them and the facet objects delegate to them, which is what design.md line 121 intends ("become private"). At runtime they are still own-prototype methods and callable, so a literal "no method present" check (`'getPackageIdentity' in adapter`) would FAIL. No test checks either way. Verdict: the intent (removed from the contract, not reachable through the typed API, consumers cannot depend on them) is met; the literal wording is not. Either soften the scenario to "not declared on `LanguageAdapter`" or rename/inline the private methods. Severity: low.

## Candidate findings (a) to (d)

### (a) Python and Go `prepare` do not read or store what the spec says

Confirmed. `PY:377` is `prepare: () => undefined`. `GO:272-275` only builds the directory index by calling `goPackageFiles(session, '', '')`. The spec text ("SHALL read each workspace's pyproject.toml once per run and store its project name and code root", same for `go.mod`) is not implemented literally.
Verdict: the code is right and the spec text is wrong or redundant.

- Code right: the facet needs only the package map (built by the indexer from `identity`) and the indexed file set. `PackageEntryRequest` already carries `packageName` and `workspace`, and the workspace-relative paths need no code root. A real read in `prepare` would be a second read of the same manifest that `identity` just read. `language-adapter` "Package resolution facet" says `prepare` reads "the manifest facts the adapter needs"; Python and Go need none. Total reads of `pyproject.toml` / `go.mod` per run are still exactly one per workspace (the `identity` call, `IDX:887`).
- Spec right: `design.md` lines 135 and 143 say `prepare` stores `py:packages` / `go:packages` (and the Go directory index is built there). The task list and the verify scenario "Prepare reads each pyproject.toml once" assume a `prepare` read. Removing the claim silently would hide a design deviation.
- Severity: medium (spec-code mismatch on a SHALL, no behavioural bug). Resolution: reword the two spec sentences ("`prepare` reads no manifest; the package map from `identity` and the indexed files are the only inputs; Go `prepare` builds the per-run directory index") and reword or drop the Python verify scenario.
- Side note (Go): the `goPackageFiles(session, '', '')` call is used for its side effect of building the index. That is correct but obscure; a named `prepareGoDirectories(session)` would be clearer (low).

### (b) PHP composer.json is read more than once per workspace

Confirmed. Reads of `composer.json` per workspace in one run:

1. Indexer `identity` loop (`IDX:887`, via `PHP:getPackageIdentity`), one read walk.
2. `analyzeFile` -> `prepareResolutionMetadata` -> `buildPsr4Map` (`PHP:2212-2222`), on the first PHP file of that workspace.
3. `prepare` -> `getPackageIdentity` again (`PHP:2142`) for every workspace.
4. `prepare` -> `buildPsr4Map` (`PHP:2139-2141`) only when step 2 did not run for that code root (workspaces without PHP files in this run, hydrated workspaces).
   So 3 reads for a workspace analyzed in this run and 3 for a hydrated one (identity, prepare PSR-4, prepare identity). The verify scenario "Prepare reads composer.json once per workspace" cannot hold literally, and `prepare` alone reads twice for a non-analyzed workspace.
   Pass 2 does no filesystem read for resolution: `matchQualifiedNameToPackage` and `qualifiedNameEntries` use only session state, `resolveQualifiedNameFromSession` too. One exception: the facet member `qualifiedNameResolution.resolveToPath` (`PHP:493`, `PHP:2322-2328`) calls `buildPsr4Map` and reads the filesystem on every call. It has no callers in `src` (only the facet wiring), so it is dead at runtime, but it violates `language-adapter` "Qualified-name resolution facet" ("MUST NOT probe the filesystem per call").

- Spec right: one read of the manifest in `prepare` is cheap to achieve (parse once, derive name and PSR-4 together, drop the duplicate in `analyzeFile`).
- Code right: the double read costs little, `identity` must stay independent of `prepare` (it runs earlier, before the package map exists), and the spec's "once per run" is about not re-reading in Pass 2, which holds. The facet signature `resolveToPath(qualifiedName, codeRoot, repoRoot?)` has no session argument, so a compliant implementation is impossible with the contract as written; that contradiction is in the `language-adapter` spec text and should be fixed there (add a session parameter or drop the member).
- Severity: medium for the `resolveToPath` contract violation and the unmet scenario; low for the redundant reads.

### (c) Python entry surface id equals the surface of the adapter's public bindings

Confirmed. `PY:763` builds public-binding surfaces with `filePath.replace(/(?:\/__init__)?\.pyi?$/, '')` and `PY:401` builds the entry `surface` with the identical regular expression. For `ws:src/pkg/mod.py`, `ws:src/pkg/mod.pyi` and `ws:src/pkg/__init__.py` both produce `ws:src/pkg/mod` and `ws:src/pkg` respectively. The end-to-end test (languages spec, Python) proves the lookup works. Facet-level test: package-resolution spec "Given a module and a package, when asked, then the surface is the path without extension or **init**".
Nits: (1) the regular expression is duplicated in two places; a shared helper (for example `pythonModuleSurface(filePath)`) removes the drift risk (low). (2) `mod.py`, `mod.pyi` and `mod/__init__.py` all share one surface, so competing definitions merge into one slot and can report `ambiguous`; this is deliberate but not stated in the spec (low). (3) A workspace-root `ws:__init__.py` yields `ws:__init__` on both sides, consistent but odd (low).

### (d) TypeScript `entryCandidatePaths` returns nothing when `prepare` was not called

Refuted for production. `IDX:1193-1210` calls `packageResolution.prepare` unconditionally for every adapter before Pass 2, on every run (full or incremental), with `packageWorkspaces` built from `options.workspaces` (all configured workspaces, `IDX:900-903`). A fresh `InMemoryIndexSession` is created per run (`IDX:861`), so there is no stale state. If `prepare` throws, the adapter is added to `disabledPackageResolution` and behaves as facet-absent (test: package-imports spec "prepare throws"). Also `analyzeFile` registers the code root and manifest for analyzed workspaces (`TS:787-792`), a harmless duplicate that is cached by code root.
Residual risks (different from the suspected one):

- Inconsistency between `identity` and `prepare` in TS: `identity` walks up to the nearest bounded `package.json` (`TS:3100-3112`), but `prepareWorkspaceManifest` reads only `join(codeRoot, 'package.json')` (`TS:579-592`). If a workspace `codeRoot` is a subdirectory of the package (for example `pkg/src`), the package is registered by name, `entrySurface` returns `[]`, and every import fails with `no-entry-surface`. `design.md:122` says `prepare` should find "the nearest bounded package.json", and the spec says "`prepare` SHALL read the `package.json` of every workspace". Severity low-medium. Even with the nearest manifest, `exports` paths are relative to the manifest directory, not to `codeRoot`, so a correct fix needs an offset.
- Go has the same shape: module prefix stripped from the import path is looked up relative to the workspace root, but `identity` uses the nearest `go.mod` walking up (`GO:1538-1549`). A workspace nested below its module root resolves wrong directories (low-medium).
- `prepare` no longer passes `repoRoot` to anything in TS, so the "searches stop at the repository root" rule is satisfied only trivially.

### Discrepancies

4. `sourceCandidates` handles only `dist/`. Severity: low. Spec right: "a build directory". Code right: only `dist` is exemplified and tested. Clarify the spec or add `build/`, `lib/`, `out/`.
