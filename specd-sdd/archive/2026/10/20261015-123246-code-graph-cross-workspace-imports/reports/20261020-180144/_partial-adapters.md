## Candidate findings (a) to (d)

### (a) Python and Go `prepare` do not read or store what the spec says

Confirmed. `PY:377` is `prepare: () => undefined`. `GO:272-275` only builds the directory index by calling `goPackageFiles(session, '', '')`. The spec text ("SHALL read each workspace's pyproject.toml once per run and store its project name and code root", same for `go.mod`) is not implemented literally.
Verdict: the code is right and the spec text is wrong or redundant.

- Code right: the facet needs only the package map (built by the indexer from `identity`) and the indexed file set. `PackageEntryRequest` already carries `packageName` and `workspace`, and the workspace-relative paths need no code root. A real read in `prepare` would be a second read of the same manifest that `identity` just read. `language-adapter` "Package resolution facet" says `prepare` reads "the manifest facts the adapter needs"; Python and Go need none. Total reads of `pyproject.toml` / `go.mod` per run are still exactly one per workspace (the `identity` call, `IDX:887`).
- Spec right: `design.md` lines 135 and 143 say `prepare` stores `py:packages` / `go:packages` (and the Go directory index is built there). The task list and the verify scenario "Prepare reads each pyproject.toml once" assume a `prepare` read. Removing the claim silently would hide a design deviation.
- Severity: medium (spec-code mismatch on a SHALL, no behavioural bug). Resolution: reword the two spec sentences ("`prepare` reads no manifest; the package map from `identity` and the indexed files are the only inputs; Go `prepare` builds the per-run directory index") and reword or drop the Python verify scenario.
- Side note (Go): the `goPackageFiles(session, '', '')` call is used for its side effect of building the index. That is correct but obscure; a named `prepareGoDirectories(session)` would be clearer (low).

### (b) PHP composer.json is read more than once per workspace

Confirmed. Reads of `composer.json` per workspace in one run:

1. Indexer `identity` loop (`IDX:887`, via `PHP:getPackageIdentity`), one read walk.
2. `analyzeFile` -> `prepareResolutionMetadata` -> `buildPsr4Map` (`PHP:2212-2222`), on the first PHP file of that workspace.
3. `prepare` -> `getPackageIdentity` again (`PHP:2142`) for every workspace.
4. `prepare` -> `buildPsr4Map` (`PHP:2139-2141`) only when step 2 did not run for that code root (workspaces without PHP files in this run, hydrated workspaces).
   So 3 reads for a workspace analyzed in this run and 3 for a hydrated one (identity, prepare PSR-4, prepare identity). The verify scenario "Prepare reads composer.json once per workspace" cannot hold literally, and `prepare` alone reads twice for a non-analyzed workspace.
   Pass 2 does no filesystem read for resolution: `matchQualifiedNameToPackage` and `qualifiedNameEntries` use only session state, `resolveQualifiedNameFromSession` too. One exception: the facet member `qualifiedNameResolution.resolveToPath` (`PHP:493`, `PHP:2322-2328`) calls `buildPsr4Map` and reads the filesystem on every call. It has no callers in `src` (only the facet wiring), so it is dead at runtime, but it violates `language-adapter` "Qualified-name resolution facet" ("MUST NOT probe the filesystem per call").

- Spec right: one read of the manifest in `prepare` is cheap to achieve (parse once, derive name and PSR-4 together, drop the duplicate in `analyzeFile`).
- Code right: the double read costs little, `identity` must stay independent of `prepare` (it runs earlier, before the package map exists), and the spec's "once per run" is about not re-reading in Pass 2, which holds. The facet signature `resolveToPath(qualifiedName, codeRoot, repoRoot?)` has no session argument, so a compliant implementation is impossible with the contract as written; that contradiction is in the `language-adapter` spec text and should be fixed there (add a session parameter or drop the member).
- Severity: medium for the `resolveToPath` contract violation and the unmet scenario; low for the redundant reads.

### (c) Python entry surface id equals the surface of the adapter's public bindings

Confirmed. `PY:763` builds public-binding surfaces with `filePath.replace(/(?:\/__init__)?\.pyi?$/, '')` and `PY:401` builds the entry `surface` with the identical regular expression. For `ws:src/pkg/mod.py`, `ws:src/pkg/mod.pyi` and `ws:src/pkg/__init__.py` both produce `ws:src/pkg/mod` and `ws:src/pkg` respectively. The end-to-end test (languages spec, Python) proves the lookup works. Facet-level test: package-resolution spec "Given a module and a package, when asked, then the surface is the path without extension or **init**".
Nits: (1) the regular expression is duplicated in two places; a shared helper (for example `pythonModuleSurface(filePath)`) removes the drift risk (low). (2) `mod.py`, `mod.pyi` and `mod/__init__.py` all share one surface, so competing definitions merge into one slot and can report `ambiguous`; this is deliberate but not stated in the spec (low). (3) A workspace-root `ws:__init__.py` yields `ws:__init__` on both sides, consistent but odd (low).

### (d) TypeScript `entryCandidatePaths` returns nothing when `prepare` was not called

Refuted for production. `IDX:1193-1210` calls `packageResolution.prepare` unconditionally for every adapter before Pass 2, on every run (full or incremental), with `packageWorkspaces` built from `options.workspaces` (all configured workspaces, `IDX:900-903`). A fresh `InMemoryIndexSession` is created per run (`IDX:861`), so there is no stale state. If `prepare` throws, the adapter is added to `disabledPackageResolution` and behaves as facet-absent (test: package-imports spec "prepare throws"). Also `analyzeFile` registers the code root and manifest for analyzed workspaces (`TS:787-792`), a harmless duplicate that is cached by code root.
Residual risks (different from the suspected one):

- Inconsistency between `identity` and `prepare` in TS: `identity` walks up to the nearest bounded `package.json` (`TS:3100-3112`), but `prepareWorkspaceManifest` reads only `join(codeRoot, 'package.json')` (`TS:579-592`). If a workspace `codeRoot` is a subdirectory of the package (for example `pkg/src`), the package is registered by name, `entrySurface` returns `[]`, and every import fails with `no-entry-surface`. `design.md:122` says `prepare` should find "the nearest bounded package.json", and the spec says "`prepare` SHALL read the `package.json` of every workspace". Severity low-medium. Even with the nearest manifest, `exports` paths are relative to the manifest directory, not to `codeRoot`, so a correct fix needs an offset.
- Go has the same shape: module prefix stripped from the import path is looked up relative to the workspace root, but `identity` uses the nearest `go.mod` walking up (`GO:1538-1549`). A workspace nested below its module root resolves wrong directories (low-medium).
- `prepare` no longer passes `repoRoot` to anything in TS, so the "searches stop at the repository root" rule is satisfied only trivially.

### Discrepancies

1. `prepare` reads only `codeRoot/package.json`, `identity` reads the nearest one (see (d)). Spec right: "`prepare` SHALL read the package.json of every workspace" plus design says nearest bounded. Code right: relative-to-codeRoot paths make the root manifest the only one whose `exports` paths map to workspace-relative ids. Severity: low-medium. Fix either way: make `prepare` and `identity` use the same lookup, or state "the `package.json` at the workspace code root" in the spec.
2. `main` fallback also applies when `exports` exists but has no usable target for `.`. Spec right: fallback only when `exports` is absent (a package with `exports` that only has `require` would then resolve via `main` against the Node rules). Code right: tests "Given only platform conditions, when asked, then nothing is published" use a manifest with no `main`, so the doc comment is the only evidence; a manifest with `exports` and `main` is common, and Node itself ignores `main` when `exports` is defined. In that sense the code is looser than Node. Severity: low. Recommend aligning code with the spec (return nothing when `exports` is defined).
3. Default/namespace package imports bypass `resolvePackageExport` (no step, first entry wins). Spec right: "resolve to the entry file's namespace or default public binding", "Resolved package imports SHALL return an `import:package` step". Code right: namespace imports have no public binding to link; the spec text for namespaces is satisfied by "depends on the entry file". Severity: low-medium for default imports (no step, silent first-wins on multiple entries).
4. `sourceCandidates` handles only `dist/`. Severity: low. Spec right: "a build directory". Code right: only `dist` is exemplified and tested. Clarify the spec or add `build/`, `lib/`, `out/`.
5. `prepare` does not store `name`. Severity: low; the spec lists `name` but nothing needs it (the package map has it). Code right; reword the spec.
6. `analyzeFile` also reads `package.json` (`TS:787-792`). Not forbidden, and cached, but it makes the "prepare is the reader" statement in the spec and in the language-adapter spec ("only `identity` and `prepare` may perform I/O") untrue for TS Pass 1. The hydrate-only incremental case is covered by `prepare`. Severity: low. Code right (analysis-time reads are Pass 1, not resolution); spec right if strict. Suggest removing the eager read from `analyzeFile` or noting it.
