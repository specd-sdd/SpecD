## 3. Discrepancies (both possibilities stated)

**D-A. Facet failure in `identity` (and `link`) does not disable the facet as the spec now requires.**

- Spec (language-adapter, Adapter facet model, plus verify "Facet that throws in identity, prepare, or link ..."): failure in `identity`, `prepare`, or `link` is recorded as an indexing error and "the adapter is treated as if it did not provide the facet for the rest of the run".
- Code: `identity` -> `index-code-graph.ts:886-897` pushes an error and `continue`s; the adapter is not added to `disabledPackageResolution`, so for the rest of the run its `prepare` still runs (`:1206`), `matchSpecifier`/`entrySurface` still serve other workspaces, and it is not listed in `adaptersWithoutPackageResolution` (`listDisabledAdapters`, `:949-952`). `link` -> `:1224-1233` adds the adapter to `disabledPackageResolution`, which switches off its `packageResolution` (imports then resolve as `facet-absent`) although it was `reExportLinking` that failed; no `reExportLinking` set exists but `link` is only invoked once per run, so "for the rest of the run" is vacuous for it. `prepare` -> correct. Test for `identity` (`package-imports.spec.ts:496`) asserts only "error recorded, run completes".
- Code wrong: a failed `identity` leaves the adapter half-active (identity absent for the failing workspace, matching still active for others). If an adapter throws for one workspace and succeeds for another, it is neither "absent" nor consistent. Disabling on identity failure would match the spec and docs line 49 of `language-adapters.md`.
- Spec wrong or ambiguous: "the facet" for `identity`/`link` is under-specified (disable `packageResolution` only, or disable per facet?). Per-workspace isolation (continue with other workspaces) could be a legitimate reading; if so, the spec and docs should say that only `prepare` failure disables the facet.
- Severity: low to medium (observable only with faulty third-party adapters).

**D-B. Test files are excluded by the indexer, not by the facet (spec says the facet MUST NOT return them).**

- Spec: Package resolution facet: "It MUST NOT return files classified as tests. The indexer also discards test files, so a test file is never a package entry." Verify scenario "Test files are not entries" calls `entrySurface`.
- Code: TS/Python/PHP `entrySurface` ignore categories; Go filters by `_test.go`; the resolver filters `category === 'test'` (`package-import-resolver.ts:80-85`).
- Behaviour is safe (no test is ever selected). Spec wrong if the intent is defence in depth only (then the MUST NOT on the facet should be relaxed, or rewritten as "the facet SHOULD NOT"). Code wrong if the facet-level obligation is intended: adapters would filter with `session.getFileCategory`, and a facet-level test with `category: 'test'` is needed.
- Docs (`language-adapters.md`, entry surface rules) say "Do not return test files. The indexer discards..." which matches the spec's duty but not the code.
- Severity: low.

**D-C. `Tipo.miembro` fallthrough: "other human text with no proven adapter MUST resolve as unresolved".**

- Spec (Structured reference input): "When none of those identifies an adapter, that other text MUST resolve as unresolved."
- Code: `resolve-symbol-reference.ts:1052-1055` returns unresolved only when there is neither `anchored` (file/surface) nor `language`. If `anchored` is present but `registry.getAdapterForFile(anchored)` finds nothing (for example a public surface that is a package or directory, as the Go surface is), `parseAnchoredReference` returns `parseDottedMemberReference(request.requested)` (`:1117`), a language-neutral dotted parser. The text is then resolved with an invented default syntax.
- Code wrong: it picks "a default language" by another name, which the spec forbids for the unanchored lookup and requires to be unresolved for other text. Spec possibly too strict: the spec step "indexed public-surface metadata" implies the resolver should look up the language stored for the surface, which the code does not do (it only maps file extension). Either implement the surface-metadata lookup or drop the dotted fallback.
- Related: line 1037 falls back to a derived qualified name when `target.qualifiedName` is missing; spec says equality "on stored `qualified_name`". If every logical symbol persists a name, the fallback is dead code; if not, it makes results depend on derivation rules.
- Severity: low to medium.

**D-D. TS default package import binds without an `import:package` step; value is found by scanning the entry file.**

- Spec (Cross-workspace import resolution): a package import that names a symbol and resolves produces binding target, resolution step and `IMPORTS`; a name resolves "only through the target package's published entry surface and the public bindings of those entry files".
- Code: `typescript-language-adapter.ts:1492-1520` for `Default`/`Namespace` imports: file-level `IMPORTS` to every entry, and for default imports a binding target found by `findDefaultExportDeclaration(session, entry.filePath)` (declaration scan, if exactly one). No step is emitted, so the binding has no provenance and the incremental closure follows only the `IMPORTS` edge. Test: `package-imports.spec.ts:529` asserts the binding and the dependency, not the step.
- Spec wrong or silent: the spec has no case for default and namespace imports, and `resolvePackageExport` takes an exported name (`default` is stored as a public binding name by the TS adapter, see `typescript-language-adapter.spec.ts:1531`). Code wrong if the rule is that every bound import must have a step: use `resolvePackageExport({ exportedName: 'default', ... })`.
- Severity: low.

**D-E. TS `prepare` ignores a manifest above `codeRoot` that `identity` finds (prior D5, still open).** See section 0.

**D-F. Docs vs spec wording (carried over, re-checked).**

- `docs/code-graph/language-adapters.md` lines 17-23: step 1 "Package map" is described as happening before Pass 1; correct and now consistent with the spec ("once per workspace before Pass 1 completes").
- Line 49 (facet throws): "If `identity`, `prepare`, or `link` throws, the adapter behaves as if it did not provide that facet for the rest of the run" is consistent with the spec but not with the code for `identity` and `link` (D-A).
- Checklist step 6 and 7 are shorter than spec steps 6 and 7 ("facet scenarios in this spec's verification"; "add it to the list of built-in adapter specs"): the docs drop the "add to the list" duty and the conformance suite reference is replaced by "useful extra tests". Spec says "The spec and the page MUST state the same rules." Docs wrong (low).
- Example code in the docs pushes `result.step` even when `localBindingId` is `''`; the TS adapter pushes the step only when a local binding exists (`typescript-language-adapter.ts:1546`). Docs example could emit a step with an empty `fromId`. Docs wrong (low).
- `docs/code-graph/index.md` "Package imports across workspaces" and ADR-0030 agree with the code. ADR-0030 lists `Spec: code-graph:indexer`, which is not in this batch (not audited here).

**D-G. Registration details (prior D7, open).** Plain `Error` for declaration-policy violations (`adapter-registry.ts:49-59`) versus `default:_global/error-handling-conventions`; messages for no-language and undeclared-extension rules carry no `member`. Spec requires the message to name "the missing or invalid member" (applies where a member is the problem). Low.

**D-H. Over-inclusive fingerprint (prior W2).** Whole-manifest hash; spec lists specific inputs. Spec does not forbid it. Low, informational.

## 3. Discrepancies (spec vs code; either may be wrong)

1. PHP `resolveToPath` returns unindexed target (HIGH-ish, only open prior item). Spec: "MUST NOT fall back to an absolute-path lookup of an unindexed file" and scenario "an unindexed file is never targeted". Code PHP:2283-2285 returns the single candidate regardless of index; tests php-language-adapter.spec.ts:706-719 and :772-785 enshrine it; `resolveFileImport` PHP:1020 pushes it into `fileImports` without `getFileId` (and as an absolute path rather than a workspace-prefixed file id). Possibility A: code wrong (add `getFileId` check, update tests). Possibility B: spec wording is about FS fallback only and `resolveToPath` is a pure mapping (then reword the scenario; note `resolveToPath` has no other consumers in src, only adapter-registry facet listing).
2. PHP `prepare` reads composer.json twice per workspace (`buildPsr4Map` + `getPackageIdentity`, PHP:2144-2150) vs spec "read once (identity reads separately)". Also `analyzeFile` may have pre-read it (PHP ~2213). Wording vs code; no read-count test.
3. TS `matchSpecifier`: spec "longest known package prefix"; code exact first-1/2-segment match (TS:3070-ish `resolvePackageFromSpecifier`). Behaviorally fine; spec wording stricter.
4. TS build-dir mapping: spec generic "a build directory"; code maps only `dist/`. `lib/`, `build/`, `out/` published targets will not map to `src/`. Either broaden code or narrow spec to `dist`.
5. TS `exports` wildcard patterns (`./*`) and nested conditions beyond `import/default/types`: not handled; spec silent on `./*`, consistent with "other conditional resolution unsupported" but a subpath like `pkg/foo` against `"./*"` yields no entry (silent).
6. Python submodule fallback is attempted on any unresolved result (including shared-resolver `ambiguous`), not only "not published by the entry file". Low risk.
7. Go/Python/TS (and PHP) still consult `qualifiedNames.get(imp.specifier)` before package resolution (TS:1420, PY:~949, GO:724). Only PHP supplies a qualified-name facet, so for TS/Py/Go the map is normally empty; spec does not describe this branch. Dead/undocumented path.
8. Go entry assumes package dir = specifier minus module prefix relative to workspace root; if `go.mod` is found above `codeRoot` (bounded walk-up) the directory would be offset. Spec says "under the module's code root"; edge case.
9. TS test naming: PR:424 title "another workspace file is not returned" but asserts a file in the `shared` workspace is returned (title misleading, no defect).

## 4. Discrepancies

- D1 (spec vs spec, MEDIUM). Indexer delta: after an `identity` failure the adapter "SHALL be treated as not providing the facet for that workspace". Language-adapter delta (spec line 54): a failure in `identity`, `prepare`, or `link` makes the adapter "treated as if it did not provide the facet for the rest of the run". Code does the indexer reading (IC:888-896 `continue`; the adapter keeps running `prepare`/`matchSpecifier`/`entrySurface`) but run-wide disabling for `prepare`/`link` (IC:1218, 1232). If the spec is truth: align the language-adapter text to "for that workspace" for identity (and say prepare/link disable the adapter for the run). If the code is truth: add the adapter to `disabledPackageResolution` on identity failure. Either way one spec is wrong today.
- D2 (code vs spec, MEDIUM, edge). `packageToWorkspace` and `prepare` use `options.workspaces` only (IC:884, 912). In a subset run (`--workspace core`, the "Deleted file removal remains scoped" case), files of other stored workspaces are hydrated (IC:864-880) but their package identities are not in the map and they are not prepared, so an import of a package living in a non-indexed workspace is reported `package-unknown` (counted as external) and not resolved. Spec text "every workspace, including workspaces that were only hydrated" can be read as requiring all configured workspaces. If spec is truth, the CLI/SDK must pass the full list or the indexer needs an input for non-indexed workspaces. If code is truth, the spec should say "every workspace of the run" and document that subset runs resolve only against indexed workspaces. No test either way.
- D3 (code vs spec, LOW). `adaptersWithoutPackageResolution` also contains adapters disabled at runtime after `prepare` or `link` threw (IC:949-952). `link` belongs to the `reExportLinking` facet; disabling `packageResolution` because `link` failed conflates two facets, and the spec defines the list only as adapters that "do not provide the facet". Tested for `prepare` only (PI:434).
- D4 (verify.md stale wording, LOW). Scenarios "Package identity built from adapter" and "Adapter without getPackageIdentity skips resolution" still name `getPackageIdentity`, which the change replaces with `packageResolution.identity` (the language-adapter delta states the loose methods are removed). Code and tests use the facet.
- D5 (code vs spec, LOW). On identity collision the second workspace is not mapped and processing continues (IC:898-905). Spec only requires the error naming both workspaces. Error `filePath` is `<ws>:<manifest>`; the first workspace appears in `message`. Fine, but the "names both" check is untested.
- D6 (global-spec consistency, LOW, pre-existing). IC imports `node:fs` (IC:1) although `default:_global/architecture` says application depends on ports. HEAD already imported it (not introduced by this change); the indexer spec bans it only for the fingerprint module. Change adds no new application-layer I/O: `package-import-resolver.ts` is I/O-free, uses `type` imports only, kebab-case file, named exports, JSDoc present (conventions/eslint satisfied in the files read). Docs: `docs/code-graph/index.md` and `language-adapters.md` document `importDiagnostics` and `adaptersWithoutPackageResolution` (docs rule satisfied for this requirement).
- D7 (spec precision, LOW). Spec says unresolved reason is reported "in the indexing output"; `facet-absent` and `package-unknown` are intentionally not in `byReason`/`samples`. Consistent, but "facet-absent" never appears in output beyond the adapter list. Spec wording could say so (it does in the Facet-driven requirement).
