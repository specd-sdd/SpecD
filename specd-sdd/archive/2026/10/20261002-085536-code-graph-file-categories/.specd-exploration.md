# Exploration Context: code-graph-file-categories

Generated: 2026-10-02

## Problem Statement

In `specd`'s codebase intelligence engine (`code-graph`), all discovered files that are not explicitly excluded via `excludePaths` are indexed as uniform `FileNode` instances.

This causes critical distortions across operations:

1. **Artificial blast-radius inflation in `specd graph impact`:**
   Test files (`*.spec.ts`, `test/**`, etc.) import many production modules for setup, fixtures, and mocks. When querying the upstream dependents of a core function or class, every unit test that imports it is treated as a dependent. This falsely inflates `riskLevel` to `HIGH` or `CRITICAL` even when the production blast radius is trivial (e.g. 1 production caller vs 50 test callers).
2. **Transitive bridge contamination:**
   In bidirectional or transitive graph traversals, test files import multiple disparate modules (e.g. testing integration between module A and module B), acting as artificial bridges that cause the traversal to link unrelated production symbols.
3. **Hotspot distortion in `specd graph hotspots`:**
   Hotspot scoring weights caller count: `(sameWsCallers * 3) + (crossWsCallers * 5) + fileImporters`. Heavily tested methods get disproportionately high scores, and test helpers or test files themselves can end up in top hotspot positions.
4. **Search pollution in `specd graph search`:**
   Searching for symbols or documents returns mocks, stubs, test suites (`describe`/`it`), and test variables, burying production domain definitions.
5. **Why `excludePaths` is insufficient:**
   If test files are excluded via `excludePaths`, they are never indexed in SQLite. We lose test-to-code traceability, test coverage links (`COVERS_FILE`, `COVERS_SYMBOL`), and the ability to query test dependencies when specifically requested.

## Approach & Solution Outline

Introduce three distinct semantic categories for indexed files, rather than treating tests as generic ignored files:

- **`source`** (default): Production code. Only `source` files contribute to production blast radius, risk level calculations, and default hotspot rankings.
- **`test`**: Test and verification files. Fully parsed and indexed in SQLite (AST, symbols, relations), but excluded from default calculations and default outputs.
- **`ignored`**: Truly auxiliary files (fixtures, static mocks, dev/scratch scripts, benchmark helpers). Fully indexed in SQLite, but excluded from default calculations and default outputs.
- _(In addition to **`excluded`** via `excludePaths`, which are never read or stored)._

### Key Capabilities

1. **Language-agnostic classification:**
   No hardcoding of language extensions (e.g., no hardcoded `.ts`). Instead, classification uses configurable glob patterns (`testPaths`, `ignorePaths`) in `specd.yaml` at both project and workspace levels, with smart language-neutral default conventions (`**/*.spec.*`, `**/*.test.*`, `**/test/**`, `**/tests/**`, `*_test.*`).
2. **Default exclusion with visibility notices:**
   By default, `test` and `ignored` files are excluded from calculations and output in `impact`, `hotspots`, and `search`.
   **Critical requirement:** The CLI and structured output (`text`, `toon`, `json`) MUST explicitly indicate when items have been omitted from results (e.g., `ℹ 14 test files and 2 ignored files excluded from results. Use --include-tests, --include-ignored, or --all to include them.`).
3. **Inclusion and Category Restriction Flags:**
   - Inclusion: `--include-tests`, `--include-ignored`, `--all`.
   - Category restriction: `--category <source|test|ignored>` (or shorthand flags like `--only-tests` / `--only-ignored`) allowing users or agents to inspect _only_ tests or _only_ ignored files.

## Design Decisions & Agreements

1. **Explicit category distinction:**
   `test` and `ignored` are NOT merged into a single "ignored" flag. They are separate categories (`source`, `test`, `ignored`) because test code has distinct verification semantics, while ignored code represents auxiliary non-test assets.
2. **Language neutrality:**
   Do not hardcode TypeScript or any specific language extension in domain rules. Match using glob patterns configurable in `specd.yaml`.
3. **Default exclusion from calculations:**
   Tests and ignored files must not contribute to `riskLevel` or default `affectedFiles` in `graph impact`, nor caller weights in `graph hotspots`, nor default results in `graph search`.
4. **Notice of omitted results:**
   Whenever results are excluded by default, commands MUST output a visible notice informing the user/agent about the exclusion and the flags to reveal them.
5. **Single-category filtering:**
   Provide `--category <source|test|ignored>` (or equivalent dedicated flags) so that users can restrict queries strictly to tests or strictly to ignored files when diagnosing test impact or fixtures.
