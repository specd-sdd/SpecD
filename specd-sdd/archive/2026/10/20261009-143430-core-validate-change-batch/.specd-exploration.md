# Exploration: core-validate-change-batch

Generated: 2026-10-09

## Problem Statement

Currently in `packages/cli/src/commands/change/validate.ts`, the `executeBatch()` function orchestrates batch validation (`specd change validate --all`). This private CLI helper:

1. Loads the change and checks for `specIds`.
2. Resolves the active schema of the project (`kernel.specs.getActiveSchema.execute()`).
3. Iterates over the topological order of the schema's artifact DAG.
4. For each artifact in topological order:
   - If `scope: change`, invokes `ValidateArtifacts` once without `specPath`.
   - If `scope: spec`, invokes `ValidateArtifacts` once per `specId` in `change.specIds`.
5. Aggregates results step by step (`spec`, `artifact`, `passed`, `failures`, `warnings`, `files`) without aborting on failure.

Because this logic is private to the CLI, external hosts (such as SpecD Studio HTTP API, Desktop IPC, LSP, and alternative CLI frontends) cannot reuse it without duplicating the DAG walk and batch aggregation logic. Furthermore, the CLI was previously fetching the project's active schema directly without validating compatibility with the change's recorded schema name (`change.schemaName`).

## Approach & Solution Outline

Extract this batch orchestration into a canonical use case in `@specd/core`: `ValidateChangeBatch`.
The CLI's `executeBatch()` will be refactored into a thin adapter delegating directly to `kernel.changes.validateBatch.execute()`.

### Use Case: `ValidateChangeBatch`

- **Location**: `packages/core/src/application/use-cases/validate-change-batch.ts`
- **Dependencies**: `ChangeRepository`, `SchemaProvider`, `ValidateArtifacts`
- **Input**: `{ name: string, artifactId?: string }`
- **Behavior**:
  1. Load change from `ChangeRepository.get(input.name)`. If not found, throw `ChangeNotFoundError(input.name)`.
  2. Resolve schema via `SchemaProvider.get()`.
  3. Validate schema compatibility: ensure `schema.name() === change.schemaName`. If not, throw `SchemaMismatchError(change.name, change.schemaName, schema.name())`.
  4. Empty scope check: If `change.specIds.length === 0`, return `{ passed: true, total: 0, results: [] }` immediately without calling `ValidateArtifacts`.
  5. DAG traversal: Retrieve `schema.artifactDag().topologicalOrder()`.
     - If `input.artifactId` is specified, filter only steps matching `artifactId`.
     - For each artifact in topological order:
       - If `artifactType.scope === 'change'`, call `ValidateArtifacts.execute({ name: input.name, artifactId })` with no `specPath`.
       - If `artifactType.scope === 'spec'`, call `ValidateArtifacts.execute({ name: input.name, specPath, artifactId })` for each `specId` in `change.specIds`.
  6. Failure handling: Run all scheduled steps without early termination, accumulating step results.
  7. Output: Return `{ passed: boolean, total: number, results: readonly ValidateChangeBatchStepResult[] }`.

### Wiring & Composition

- Factory: `packages/core/src/composition/use-cases/validate-change-batch.ts` with explicit `createValidateChangeBatch(deps)` and config overload `createValidateChangeBatch(config, options?)`.
- Composition resolver: update `CompositionResolver` and `Kernel` in `packages/core/src/composition/kernel.ts` to expose `kernel.changes.validateBatch`.
- Re-export in `@specd/core` and `@specd/sdk`.
- CLI refactor: `packages/cli/src/commands/change/validate.ts` delegates `executeBatch` to `kernel.changes.validateBatch.execute()`.

## Design Decisions & Agreements Reached

1. **Schema Resolution Decision**:
   - Discussion around whether to dynamically resolve `change.schemaName` vs checking `schema.name() === change.schemaName`.
   - Agreement with user: stick to the canonical pattern in `@specd/core` where `SchemaProvider` provides the resolved schema, and `ValidateChangeBatch` explicitly checks `if (schema.name() !== change.schemaName) throw new SchemaMismatchError(...)`, matching `ValidateArtifacts` and preventing silent cross-schema runs.
2. **Empty Scope Handling**:
   - If `change.specIds` is empty, return `{ passed: true, total: 0, results: [] }` without calling `ValidateArtifacts`.
3. **Artifact Filter**:
   - When `artifactId` is provided, only steps for that specific artifact ID are executed, retaining topological ordering.
4. **Resilience / No Early Abort**:
   - All scheduled DAG steps execute even if one or more fail.
5. **Types**:
   - Step results expose `spec: string | null`, `artifact: string`, `passed: boolean`, `failures`, `warnings`, `files`.
   - `warnings` maps directly from `ValidationWarning[]` (or notes).

## Key Codebase Observations

- `packages/cli/src/commands/change/validate.ts`:
  - `executeBatch` currently contains the manual loop.
  - Text formatting relies on step results (`fileLines`, `noteLines`, `passedSteps / results.length`).
  - JSON formatting outputs `{ passed, total, results }`.
- `packages/core/src/composition/kernel.ts`:
  - `kernel.changes` holds all change-related use cases (`validate: ValidateArtifacts`, etc.).
  - `validateBatch` will be added to `Kernel['changes']`.
