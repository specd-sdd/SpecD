# Proposal: bound-indexer-ast-resource-lifecycle

## Motivation

Indexing an existing large project (3234 files) consumes several GB of native memory, stalls for minutes with no diagnostic, and gives the user no way to bound the cost of individual files. The indexer retains every parsed native AST root until the whole run succeeds, which contradicts the existing `Bounded analysis memory` requirement, and the isolated worker hides everything it does behind coarse progress and discarded stdio.

## Current behaviour

- Each Tree-sitter adapter (TypeScript, Python, Go, PHP) pushes its parsed `SgRoot` into a run-scoped `unknown[]` under the magic adapter-state key `napi-keepalive` (`typescript-language-adapter.ts:983`, `python-language-adapter.ts:672`, `go-language-adapter.ts:584`, `php-language-adapter.ts:799`). The array is only cleared on the success path (`index-code-graph.ts:2031`, no `finally`), so a failed SDK-hosted run keeps it reachable for as long as the session lives.
- The workaround exists to avoid a V8 finalizer running during event-loop yields, attributed in code comments to a native double-free in `@ast-grep/napi`. The retention is run-wide, so memory grows with the whole input set.
- There is no per-file size limit. Vendored and minified bundles are analysed like any source file.
- `supervisor.ts:285` forks the worker with `stdio: ['ignore', 'ignore', 'ignore', 'ipc']`; progress is reported every 50 analysed files (`index-code-graph.ts:1065`) and files skipped before analysis (binary or unsupported) never reach that counter. A stall therefore looks like an unexplained freeze.

### Evidence gathered in a spike (throwaway worktree, not part of this change)

- `@ast-grep/napi` 0.42.3 (installed) and 0.51.0 (latest) behave identically; the typings expose no explicit dispose, release depends on the GC. No segfault was reproduced in any variant (drop with forced GC, concurrent `parseAsync`, live `SgNode` after dropping the root, GC during traversal). A live `SgNode` keeps its root alive.
- Retaining roots grows RSS linearly (about 3.4 GB after 2500 parses of a 100 KB file); dropping them with a forced GC plateaus near 500 MB; dropping without a GC does not bound memory.
- Full indexing of that existing project with roots released at chunk, 50-file and per-file boundaries completed without a crash and produced a graph identical to the baseline (896 files, 55911 symbols, same relation counts). Wall time dropped from about 386-449 s to about 203-346 s.
- Peak RSS did not improve (about 7.5-8.1 GB in every mode). V8 heap stayed at 50-200 MB, so the cost is native and per file: `analyzeFile` on a 492 KB minified vendored bundle adds about 1.4 GB and 4.5 s versus 29 MB for parsing and 186 MB for a full tree walk, roughly 3 KB of RSS per source byte. A 50 KB file adds about 170 MB.
- Multi-minute stalls on tiny files (for example a 7 KB file taking 174 s inside the run versus 39 ms in isolation) coincided with large RSS drops and high system time, i.e. memory-pressure stalls on macOS, not adapter behaviour.
- The heaviest files in that project are duplicated vendored and minified JavaScript bundles (each present in two directories) and third-party charting export sources, all tracked in git.

## Proposed solution

1. **Central, library-neutral ownership of parser resources.** Replace the adapter-local `napi-keepalive` pushes (an undocumented magic key) with an explicit parser-resource scope exposed by the indexing session. An adapter that parses with a library holding native or WASM memory registers what it parsed, optionally with a disposal function when its library requires explicit release. The indexer knows nothing about the parsing library: it closes the scope's current epoch at a synchronous boundary (after each analysed file, once compact facts exist) inside `try/finally`, so every exit path (success, parse failure, cancellation, persistence failure, thrown error) releases the resources. Closing runs the registered disposals, drops the references and then requests a garbage collection when one is available, because the spike showed that dropping references alone does not bound memory. Adapters without such resources register nothing and do not change.
2. **Per-file size limit.** A file larger than the effective limit is not read, hashed, analysed or stored, whether it would be indexed as source code or as a document (files without a language adapter are stored whole as documents, so they are subject to the same limit), and is recorded in coverage as `unsupported` with the reason `file-too-large`; its size and the applied limit are reported by the run result and by a typed event. Default `262144` bytes (256 KB).
3. **Configuration.** `graph.maxFileBytes` at project level with an optional per-workspace override (`0` disables the limit), and `graph.largeFilePaths` (gitignore syntax, relative to the project root at project level and to `codeRoot` at workspace level, workspace entries are added to the project ones) listing files exempt from the size limit regardless of size. The exemption applies only to the size limit; discovery rules (`excludePaths`, `allowedPaths`, gitignore) still apply.
4. **Observability.** The worker child announces the file it is about to analyse (rate bounded without losing the expensive ones, see the technical decisions) and the supervisor, which stays responsive while the child is busy in synchronous analysis, tracks the time since the last message and warns naming the active file when a single file has been in flight for too long. Worker stderr/stdout tails are captured and returned with failures, and failure diagnostics distinguish slow analysis, cancellation, native crash, and resource-limit termination. The final summary reports files skipped for size and size-exempt files that were analysed, with their sizes.
5. **Safety fallback.** If a native crash is ever reproduced, recycling the worker process per resource budget is the escape hatch; it is not implemented unless the spike evidence changes.

## Technical context

- Alternatives evaluated and ruled out:
  - Deleting `napi-keepalive` outright: the original crash is documented in code comments, and releasing without a GC does not bound memory.
  - Upgrading `@ast-grep/napi` (0.42.3 to 0.51.0): no behavioural or memory difference, no crash fix or release API in the release notes, and breaking changes to the rule API; left out of this change.
  - Splitting oversized files into coherent AST nodes for piecewise analysis: parsing is cheap (29 MB for a 492 KB bundle), the cost is the adapter analysis, so splitting would only lower the per-piece peak, while scope, binding, call and re-export resolution, merged declarations, source positions and deterministic identities all need whole-file context. Deferred as a possible opt-in future improvement.
  - Recycling worker processes by budget as the primary mechanism: heavier, because compact pass-1 facts would have to cross process boundaries; kept only as a fallback.
  - Making file analysis asynchronous, or moving it to worker threads, to keep a host responsive: it would turn the four synchronous `analyzeFile` implementations into asynchronous ones against the synchronous, deterministic adapter contract, and yielding the event loop with parser resources alive is exactly what the original native crash is attributed to. Process isolation already keeps any host responsive, including a future long-lived HTTP host, so the analysis stays synchronous inside the isolated child.
  - Asserting on absolute RSS or wall time in tests: platform dependent (macOS compresses and pages under pressure). Verification targets retained-root count, cleanup on every exit path, skip/exemption behaviour and graph equivalence.
- **Technical decisions recorded so far** (to be carried into specs, verify, design and tasks; none of them may be dropped silently):
  1. The resource scope is parser-library neutral: the indexer and session API speak of parser-owned resources, never of `SgRoot`, `@ast-grep/napi` or Tree-sitter specifics. A resource is registered with an optional disposal function; libraries that need explicit release (for example WASM trees) provide it, libraries that rely on the garbage collector provide none. Library names appear only as spike evidence.
  2. The scope replaces the `napi-keepalive` adapter-state key in all four built-in adapters; no adapter keeps parser objects in private state. Registration is the only change required in an adapter, and adding a language still requires no change to the indexer, session, resolver or stores.
  3. The epoch is closed after every analysed file, including files that exit early (binary, unsupported, parse failure), and closing is done in `try/finally` around the per-file work, so none of the early `continue` paths can skip it. Closing runs the registered disposals, then drops the references, then requests a garbage collection. The existing clear at the end of a successful run (`index-code-graph.ts:2031`) is removed in favour of the scope.
  4. The garbage-collection request is best-effort: it is a no-op when the host did not expose it. The isolated worker child must be started with it available (preferably a fork execution argument rather than toggling flags at runtime, to be confirmed in design); SDK-hosted in-process runs get the bounded retention but not necessarily the collection.
  5. Roots are not needed after the file's compact facts exist: pass 2 and persistence consume the session's compact facts only. The spike produced identical graphs with per-file release, and verification keeps a graph-equivalence check.
  6. Heartbeat design constraint found in the spike: analysis is synchronous, so a timer inside the child cannot fire while a file is being analysed. The indexer therefore announces every file with its size, the task forwards those announcements to the supervisor with a rate bound of four per second that never withholds an announcement marked mandatory (files of at least 32 KiB), so the file being processed during a stall is not the one whose announcement was dropped, and the supervisor owns the timer that detects silence and produces the warning, the stderr/stdout tail capture and the failure classification.
  7. Files skipped before analysis for any reason (binary, unsupported, over the size limit) still pass through the same per-file bookkeeping, so progress counters and the active-file announcement are not blind to them (the original progress event only counted analysed files).
  8. Size-limit decision order: discovery rules first (`excludePaths`, `allowedPaths`, gitignore), then the size check using the file's stat size before reading its content, then `largeFilePaths` as the only exemption. A skipped file is recorded in coverage with status `unsupported` and reason `file-too-large` (the persisted coverage has no size or limit column and no schema change is made, so size and limit travel in the result and the event); an exempt file is analysed normally and listed with its size in the summary.
  9. `maxFileBytes` and `largeFilePaths` (resolved per workspace) are part of the derivation fingerprint, so changing either rebuilds the affected files.
  10. Tests assert retained-resource count, cleanup on every exit path (success, parse failure, cancellation, persistence failure, thrown error), disposal being called when an adapter provides one and not required when it does not, skip and exemption behaviour, fingerprint sensitivity and graph equivalence against the previous behaviour. They never assert absolute RSS or wall time.
  11. Progress, warning and failure information produced by an indexing run is presentation-neutral typed data with stable identifiers, not sentences, so any host can render it (the CLI today, an HTTP host with a streaming response in the future). The existing `(percent, phase)` callback, where `phase` mixes a phase name with a human detail such as `Analyzing files — 50/3234`, keeps working unchanged for current consumers; the new information is delivered through an additional optional typed event channel next to it, derived from the same source, and no existing public signature is changed. The runner port already carries generic JSON progress values, so no new port is needed.
  12. The worker IPC protocol is strict (exact key sets, tagged messages, versioned identifier `specd.graph-index.v1`). Supervisor-level needs that cannot ride inside an opaque task progress value (active file for the silence watchdog, stderr/stdout tail, failure classification) require a new tagged message type and therefore a protocol version bump, with parent and child shipping together. The supervisor never inspects task progress payloads.
  13. Failure classification is a closed, typed set that extends the current protocol categories (`task-contract`, `task-execution`, `protocol`) with supervisor-observed causes: slow or silent analysis, cancellation, abnormal child exit or signal (native crash), and resource-limit termination. Each failure carries the captured stderr/stdout tail and the last known active file.
  14. Documentation is part of the definition of done for this change, per the project documentation rules: every new configuration field, public type and CLI-visible behaviour is documented in the pages listed under Impact, and examples in the guide include the new fields. `tasks` must contain explicit documentation tasks and `verify` must cover the documented defaults.
  15. The configuration fields are added at every link of the chain (zod schemas, config types, loader and cascade, graph config builders including the no-config bootstrap, fingerprint, discovery) in one coherent step, because the zod schemas are strict and a partial rollout would either reject valid configuration or silently ignore it. Validation rejects negative or non-integer `maxFileBytes`, and a missing value resolves to the 256 KB default in the single place that builds the effective graph config, never in scattered call sites. No per-run command-line or SDK override of `maxFileBytes` is planned in this change.
  16. The size decision happens before any content is read. The indexer currently reads and hashes every discovered file in full during its change-detection phase (`index-code-graph.ts:762`, before analysis), so applying the limit only at analysis time would still load every oversized file into memory. Size comes from the file's `stat` size in bytes on disk (not decoded characters), is evaluated once per file and reused by the change-detection and analysis phases, and an oversized file is neither read nor hashed.
  17. Incremental runs: a file already in the graph that now exceeds the limit (it grew) has its previously indexed symbols, documents and relations removed and is recorded as skipped for size, exactly as if it had been excluded; a file that shrinks below the limit, or is newly exempted, is indexed on the next run. A change of the limit itself is covered by the fingerprint (decision 9); growth of a single file is covered by the normal per-file change detection plus the size check.
  18. Imports and references that resolve to a file skipped for size stay unresolved exactly as for any unindexed file; no new import diagnostic reason is introduced (the unresolved-import diagnostics cover package imports only and their reason vocabulary belongs to a spec outside this change). The user can tell a configuration limit from a real missing file because the skipped file has a coverage entry with reason `file-too-large` and appears in the size-skip summary.
  19. Coverage must stay honest about absence claims: a file skipped for size must not let the graph claim that a symbol is absent or unreferenced. The coverage status and reason used for it reuse the existing `IndexCoverageStatus` vocabulary with a new stable reason (`file-too-large`) so that the persisted coverage and the `byStatus` result shape do not gain a new enum member; the status is `unsupported` with reason `file-too-large` (agreed), because the file cannot be analysed; `excluded` is reserved for exclusions chosen by rules. Absence claims that could depend on a skipped file are unproven rather than absent: a lookup addressed to the file reports it as not indexed and graph health reports the coverage as complete with warnings (decision 28).
  20. The size limit applies independently of file category (source, test, ignored) and of the language; it is a resource guard, not a classification.
  21. The indexing result and the SDK result type gain additive fields for the summary (count of files skipped for size, list of the largest skipped files with size and applied limit, list of size-exempt files analysed with size). No existing field is removed or renamed. No new command is added; the data is available through the existing result and coverage reporting.
  22. Behaviour change for existing users: with a 256 KB default, files above it that were indexed before are no longer indexed after upgrading, the fingerprint change forces a rebuild, and the graph shrinks. This is intentional but user-visible, so it is stated in the changeset (minor bump for the affected packages), in the documentation pages listed under Impact and in the first run's summary, and `maxFileBytes: 0` or `largeFilePaths` restore the previous behaviour for a project.
  23. Tests also include a regression test that runs the real built-in adapters and the real native binding over a generated corpus of many files, closing the parser-resource scope with a forced garbage collection at every file boundary and asserting no crash, bounded retained resources and the same facts as the previous behaviour. Fixtures are generated in the test, never copied from a real project, and the test must run on all CI platforms.
  24. Measurable success criteria: at most one file's parser resources are retained at any moment; no parser resource remains reachable from the session after a run, whether it succeeded, failed or was cancelled; the graph produced for a project without files above the limit is identical to the one produced before this change; a hang or very slow file is reported with its path within the watchdog threshold.
  25. The CLI helps the user resolve size skips. In text output of `graph index`, when files were skipped for size, the summary lists the largest ones (capped at 10, with a "and N more" line and the total always shown) with their size, then a copy-pasteable `graph.largeFilePaths` snippet using project-root-relative paths (valid for any workspace, escaped where gitignore syntax requires it), mentions raising `graph.maxFileBytes` (`0` disables it) and warns that large files cost roughly 3 KB of memory per source byte while analysed. Size-exempt files that were analysed are listed separately with their size. Structured formats (`json`, `toon`) carry the data (path, size, applied limit, reason) and no hint text, so other hosts build their own presentation. The slow-file warning also suggests `excludePaths` or a lower limit when the file is not of interest. The CLI never edits `specd.yaml` on its own. The exact wording is fixed in `cli:graph-index`.
  26. The size limit applies to documents as well as to source files (agreed): any file the indexer would read in full to index is subject to `maxFileBytes`, and `largeFilePaths` exempts either kind. Documents skipped for size are recorded with the same coverage status and reason, so they do not enter the graph or its search index.
  27. The per-language adapter specs are modified too, not only the shared `code-graph:language-adapter` spec: the shared spec defines the contract, and each adapter spec states that its adapter implements it and where (`analyzeFile`, immediately after parsing, before any traversal, so a failure during traversal still releases the resource). The statements that allowed "run-scoped keepalive state" (TypeScript, Python, PHP) are replaced, and the PHP statement that Pass 2 visits "the retained AST" is replaced by consuming immutable parser-derived facts, which is also how the code behaves (verified by indexing with per-file release and obtaining an identical graph).
  28. Intermediate coverage completeness (agreed after verification). The existing `code-graph:get-graph-health` rule says that `unsupported` and `excluded` outcomes do not by themselves make aggregate coverage incomplete, so the boolean `coverageComplete` stays `true` with size skips. To avoid hiding the gap, graph health additionally exposes `coverageCompleteness` (`complete`, `complete-with-warnings`, `incomplete`, `unknown`) and `coverageWarnings` (`{ code: 'file-too-large', count }`). Only gaps caused by the configured size limit raise a warning; files without an adapter and rule exclusions do not. `graph stats` renders `coverage: complete with warnings (...)` with a hint in text mode and exposes the fields unchanged in structured modes. This replaces the earlier wording that absence claims about a skipped file are "unknown".
  29. Event scope corrections (agreed after verification). `file-activity` is emitted for files that enter per-file processing, including those the analysis then skips (no adapter, undecodable content); files skipped for size or excluded by discovery never enter processing and size skips are reported by `file-skipped`. The `onEvent` receiver of `runIndexProjectGraph` carries only indexer events; isolated-worker events (`activity`, `worker-silent`, `stale-lock-recovered`) are delivered by `runIsolatedGraphIndex` through its own receiver, and the SDK exports the types of both families. Captured worker output appears only in failure diagnostics, never in events. The task entrypoint documents its third `announce` argument. `graphConfig` forwarded to the indexer carries the limit and exemption lists as declared; the indexer resolves them.
- Agreed direction: default limit 256 KB; `maxFileBytes` configurable with `0` meaning no limit; `largeFilePaths` exempt files from the limit only, not from discovery; workspace `largeFilePaths` add to the project ones while a workspace `maxFileBytes` replaces the project value; the summary distinguishes size-skipped from size-exempt files.
- A 256 KB file costs about 770 MB of transient native memory at the measured ratio, which is why the default is not higher; real source files of that size are rare compared with generated or vendored ones.
- Out of scope: adapter traversal optimisations (separate change, already merged), per-project `specd.yaml` exclusion cleanup, graph store performance, persisted schema changes.

## Open questions

None. The questions raised during the proposal conversation were resolved as follows:

- **Fingerprint (agreed).** `maxFileBytes` and `largeFilePaths` (resolved per workspace) are part of the derivation fingerprint, so changing either triggers a rebuild of the affected files instead of leaving stale skip decisions.
- **Release policy (agreed).** The owner's epoch is closed after every analysed file that registered a native root, and a garbage collection is requested at that boundary. This is the simplest deterministic policy and the one the spike exercised end to end (per-file release with GC: 346 s versus 386 s baseline, no crash, identical graph). Moving to a coarser interval or to a retained-bytes budget is only reconsidered in `design` if a measured cost appears.
- **Progress and duration thresholds (agreed).** These are fixed constants, not configuration: the existing per-50-files progress event stays, and a warning naming the active file is emitted when no message has arrived for more than 10 seconds. They become configurable only if production evidence requires it. The watchdog runs in the supervisor because the child cannot run timers while it is blocked in synchronous analysis (see the technical decisions).
