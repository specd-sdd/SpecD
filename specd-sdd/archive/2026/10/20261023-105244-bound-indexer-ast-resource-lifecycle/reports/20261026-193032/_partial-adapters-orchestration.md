### Discrepancies

- D-IPG-1 (LOW, spec wording wrong): Spec "Executes project indexing" says `graphConfig` includes "the resolved per-file size limit and size-exempt patterns of every workspace".
  - Evidence spec-wrong: the code deliberately forwards the raw config and resolves in exactly one place (`resolve-effective-graph-config.ts`), which is what the new "Effective size limit resolution" requirement demands ("no other call site SHALL apply the default"). Resolving before `provider.index()` would create a second resolution site. `build-project-graph-config.ts:35-70` forwards only declared values.
  - Evidence code-wrong: none; the design (design.md "Effective size limit resolution") places resolution inside the indexer.
  - Severity: LOW. Recommendation: reword to "`graphConfig`, carrying the declared per-file size limit and size-exempt patterns of the project and every workspace; they are resolved by Requirement: Effective size limit resolution".
- D-IPG-2 (LOW, code side, redundant fallback): `file-size-gate.ts:118-120` and `compute-graph-fingerprint.ts:79,158` apply `?? effective.rootMaxFileBytes` when a workspace is missing from the effective map. Severity LOW; recommendation: leave, or assert the workspace exists.
- D-IPG-3 (LOW, spec wording): The requirement says "one effective set of `largeFilePaths` (the project patterns together with the workspace patterns, each kept with its base directory)" while the code keeps two arrays (`projectLargeFilePaths`, `workspaceLargeFilePaths`) and the base directory is implicit in which array it is in. Semantically equal; recommendation: say "kept apart by level so that each resolves against its base directory".

### Discrepancies

- D-SDK-1 (MEDIUM, spec wrong): "Typed event passthrough" says the orchestration forwards worker events (`activity`, `worker-silent`, `stale-lock-recovered`) "when the run is executed through the isolated worker", and scenario "Worker events are forwarded too" requires `worker-silent` to reach the receiver.
  - Evidence spec-wrong: `runIndexProjectGraph` never starts a worker; it runs inside the child (CLI task `cli/src/graph-index-task.ts:100` calls it). Worker events are produced by the supervisor and delivered through a different surface, `runIsolatedGraphIndex({ onEvent?: (e: GraphIndexWorkerEvent) => void })` (`code-graph/src/application/ports/isolated-graph-index-runner.ts:45`; CLI consumes it at `cli/src/commands/graph/index-graph.ts:183-184`). design.md:614 states this explicitly: "The typed worker events are produced by the isolated runner ... the SDK function runs inside the child ... where only the indexer events exist."
  - Evidence code-wrong: type of the SDK `onEvent` is `IndexEventReceiver` (indexer events only; `run-index-project-graph.ts:26`), so the code cannot carry worker events; contradicts the literal spec and scenario.
  - Severity: MEDIUM (requirement text and a scenario cannot be satisfied or verified; hosts could believe worker events arrive through the SDK function).
  - Recommendation: fix the spec/verify (code and design agree): restrict "Typed event passthrough" to the three indexing event kinds, and state that worker events (`activity`, `worker-silent`, `stale-lock-recovered`) are delivered by the isolated runner's own `onEvent`, with the types exported from the SDK. Replace scenario "Worker events are forwarded too" by "Worker event types are exported". Alternatively, if hosts must get worker events through the SDK orchestration, add an SDK function that wraps `runIsolatedGraphIndex` (new scope).
- D-SDK-2 (LOW, code side, test/design deviation): design.md:819 promises a type-level test importing the event types from `@specd/sdk`, and "order" assertions; neither exists. Scenario "Event types are exported" has no test. Recommendation: add `expectTypeOf`/type import test in `packages/sdk/test`, plus an ordering test where the mocked `indexExecute` invokes `onEvent` with several events.
- D-SDK-3 (LOW, code side, documentation): requirement says types exported "with complete documentation". In `code-graph/src/domain/value-objects/index-event.ts` the interface headers have JSDoc but most members do not (`FileSkippedEvent.*`, `ResourceDisposalFailedEvent.*`, `SizeSkippedFile.*`, `SizeExemptFile.*`; `FileActivityEvent` members are documented). In `graph-index-worker-types.ts` `GraphIndexFailureCause` members, `GraphIndexWorkerDiagnostics.cause` and the three `GraphIndexWorkerEvent` union members are undocumented. `GraphIndexWorkerError` export in SDK/code-graph has no check here (not read). Severity LOW. Recommendation: add member-level JSDoc (including semantics of `kind` identifiers and units: ms, bytes) so hosts can render without reading internals.
- D-SDK-4 (LOW, spec/progress text): "Progress callback passthrough" modified text now says "forward progress events ... without transformation" and the scenario says the callback receives "the same `(percent, phase)` calls as before this change". Implementation is unchanged, but the scenario cannot be verified without a baseline; the current test does not compare calls. Recommendation: assert the exact sequence produced by a mocked indexer.

## Consistency with global specs (item 6)

- `default:_global/architecture`, conventions: new domain types (`parser-resource-scope.ts`, `index-event.ts`) are pure interfaces in `domain/value-objects`; the scope implementation sits in `application/use-cases/in-memory-parser-resource-scope.ts` and is wired from `InMemoryIndexSession` (consistent with layering: adapters in infrastructure depend only on the domain interface through `IndexSession`). SDK imports from `@specd/code-graph` public entry only. Named exports only, explicit return types observed in the new service files read.
- Public entry: `public.ts` exports `AdapterAnalyzeContext` (whose `session` is an `IndexSession`) but exports neither `IndexSession` (pre-existing) nor, new in this change, `ParserResourceScope` and its helper types (D-ADP-3 below).
- Docs: `docs/code-graph/language-adapters.md:44,290`, `docs/code-graph/index.md:272-273`, `docs/code-graph/use-cases.md:95-96`, `docs/sdk/index.md:293,339,344,464` document the new contract, consistent with the specs. `language-adapters.md:44` example uses `register(resource, () => resource.delete())`, which is illustrative for WASM trees; the built-in adapters register `SgRoot` without a disposer (consistent with spec "together with a disposal function when its library requires explicit release").

### Additional findings

- D-ADP-3 (LOW, code side): the new `ParserResourceScope`, `ParserResourceDisposer`, `ParserResourceCloseResult`, `ParserResourceDisposalFailure` types are exported from `packages/code-graph/src/index.ts:191-194` but not from `public.ts` or `packages/sdk/src/index.ts`. The language-adapter spec says third-party adapters must satisfy the contract "without a change to the indexer"; an adapter author consuming only the public entry can name `LanguageAdapter` and `AdapterAnalyzeContext` but not the scope type. Recommendation: export them (with `IndexSession`) from `public.ts`, or state that the scope is internal-only.
- Docs/spec mismatch in worker events (see D-SDK-1): `docs/sdk/index.md:293` shows `onEvent: (event: GraphIndexWorkerEvent)` under `runIsolatedGraphIndex`, which matches the code and contradicts the SDK spec sentence, supporting the "spec wrong" verdict.

## Overall

All four adapters comply: registration directly after `parse()` and before any traversal, no retained nodes, single production call site with per-file `finally` epoch close, keepalive key fully removed from source. Default limit is resolved in a single place and feeds the fingerprint; `onEvent` is forwarded through `IndexProjectGraph` and the SDK. Real issues: 1 MEDIUM (SDK spec promises worker-event passthrough that the orchestration layer cannot and, per design, should not provide) and a handful of LOW items (spec wording on `graphConfig`/`largeFilePaths`, incomplete member-level JSDoc on exported event types, `ParserResourceScope` not in `public.ts`/SDK, weaker-than-promised tests for the draft-is-plain-data and event-type-export scenarios).
