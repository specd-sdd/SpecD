### Discrepancies

**D1. Size-skipped files are never announced via `file-activity`, never counted in progress counters, and the epoch is never "closed" for them (spec scenarios vs code and design)** — Severity MEDIUM

- Spec text: scenario "Skipped files are announced too" (GIVEN binary, unsupported, oversized file; THEN each produces a `file-activity` event AND each is counted in the progress counters); requirement text "Files skipped before analysis for any reason SHALL be counted in the progress counters"; Parser resource lifecycle: "close ... after every file it begins to analyse, including ... over the size limit"; scenario "Files that exit early also close the epoch" lists an over-the-limit file.
- Code: oversized files are removed from `allDiscoveredPaths`/`absolutePaths` at discovery (index-code-graph.ts:577-596, 645-664) and so never appear in `filesToProcess`, `processed`, `totalToProcess`, nor in the per-file loop. They only produce one `file-skipped` event at discovery. Test `index-code-graph.events.spec.ts` "emits file-activity and file-skipped events..." asserts 2 `file-activity` events for 3 files, i.e. it pins the contradicting behaviour.
- Evidence code is wrong: three scenarios and two requirement sentences explicitly include the oversized case; a consumer building a per-file display from `file-activity` will not see these files, and the progress `total` excludes them.
- Evidence spec is wrong: design.md section A.3 deliberately removes skipped files from the working set ("do NOT push into allDiscoveredPaths"); the stall rationale of `file-activity` does not apply because a size skip costs one `stat`, never a read; no parser resource can be registered for a file that is never opened, so "close the epoch for it" is vacuous; `file-skipped` already carries path and size. The design never states that skipped files get `file-activity`.
- Recommendation: fix the spec (more likely). Reword Typed indexing events and the two scenarios so that `file-activity` covers files that reach per-file processing (binary/undecodable, document, unsupported) and `file-skipped` is the announcement for size skips, and remove "over the size limit" from the "begins to analyse" list of the lifecycle requirement. Update the test title accordingly. If the spec is kept, emit `file-activity` (with `index/total` including skipped files) for size-skipped files.

**D2. "Absence claims about a skipped file are unknown" is only honoured for requests addressed to the skipped file** — Severity MEDIUM

- Spec: Per-file size limit, "Coverage consumers MUST treat absence claims about such a file as unknown"; scenario "A symbol whose only possible declaration is in a file skipped for size ... THEN the result is unknown rather than absent".
- Code: `resolve-symbol-reference.ts:729-735` yields `unresolved` (reason `file-too-large`) only when `filePath`/`publicSurface` equals the skipped file. For logicalId lookups the code returns `status: 'missing'`, `LOGICAL_TARGET_NOT_FOUND` (line ~712) when `graphReason === null`, and `get-graph-health.ts:274-285` sets `complete` from `ParseFailed`/`Partial` only, so a graph with `file-too-large` (status `unsupported`) rows is "complete". Name-only requests return `REFERENCE_UNPROVEN` (unresolved), which is safe.
- Evidence code is wrong: the scenario literally describes a symbol (not a file-addressed claim); any supported-language file skipped for size is a real coverage gap, unlike a `no-language-adapter` document which `unsupported` was designed for.
- Evidence spec is wrong/ambiguous: requirement says "absence claims about such a file", which can be read as file-addressed claims only; `unsupported` semantic was already "unknown for that resource" and design.md says nothing about changing health or resolver (no resolver/health task); `IndexCoverageStatus.Unsupported` excluded from `complete` is pre-existing behaviour.
- Recommendation: decide the intent. Either narrow the scenario to "a lookup addressed to the skipped file" (spec fix, matches code), or make `complete` false when any coverage row has reason `file-too-large` (code fix). In both cases add a resolver test using `file-too-large`.

**D3. `file-activity` is not guaranteed to precede the first read of a file in incremental runs** — Severity LOW

- Spec: "a `file-activity` event ... is delivered before the file is read".
- Code: in the non-forced branch every kept file is `readFileSync` + hashed in "Checking files" (index-code-graph.ts ~856-885) without any event; `file-activity` is only emitted at Pass 1. A stall while hashing a just-under-limit file is unattributed.
- Evidence code is wrong: stall diagnosis was the stated purpose of unthrottled `file-activity`.
- Evidence spec is wrong: scenario says "when the indexer starts that file"; hashing happens only for files whose stamp mismatches (stamp reuse skips reads) and the 2-5% "Checking files" phase has a progress detail; design A.9 emits it only in the Pass-1 loop.
- Recommendation: clarify spec to "before Pass-1 processing of the file", or emit `file-activity` (or reuse the child announcer) in the hashing loop.

**D4. Previously indexed file that grows past the limit is not removed on forced / fingerprint-mismatch runs for workspaces not being rebuilt (generalised pre-existing limitation)** — Severity LOW

- Spec: "When a file that is already in the graph now exceeds the limit ... the indexer SHALL remove its previously indexed nodes ..."
- Code: removal is implemented in the incremental `else` branch only (904-916). In the mismatch branch (`fingerprintMismatch`) only workspaces whose fingerprint differs are invalidated (lines ~810-818), so if workspace A mismatches while workspace B has a file that grew, B's now-oversized file keeps its nodes (same already true for deleted files). With `force` it is covered (all invalidated or store replaced).
- Evidence code is wrong: requirement is unconditional; stale nodes of a no-longer-indexable file remain visible.
- Evidence spec is wrong: not realistic to expect, since the same branch already misses deletions; not a regression.
- Recommendation: low priority; compute `deletedFiles` for non-invalidated workspaces in the mismatch branch (benefits deletions too), or note the limitation in the spec.

**D5. Disposal failures at run-level close are dropped silently** — Severity LOW

- Spec: "A disposal failure SHALL be reported as a typed diagnostic". Run-level `finally` calls `closeParserResourceEpoch(activeSession.parserResources)` without `onDisposalFailure` (index-code-graph.ts:2206) and no file path is available.
- Evidence code is wrong: reachable only if a resource is registered outside a per-file epoch or the run aborts mid-file (callbacks run outside the per-file try, so normally the scope is already empty); the safety net is therefore almost never non-empty.
- Evidence spec is wrong: design A.13 itself specifies the safety net without callback.
- Recommendation: pass a callback emitting `resource-disposal-failed` (use a sentinel `filePath` or the last processed path) or state in the spec that only per-file closes report.

**D6. "Evaluated once per file ... reused by every phase" vs repeated stat** — Severity LOW

- Code: gate stat at discovery; `statSync` again in the hashing loop (~862, for mtime/size stamp comparison) and again when building observations (~1990). `fileSizes` is reused only for chunking and event size. Scenario text only requires a single request "for the size decision", which holds.
- Evidence spec is wrong: mtime is needed by the stamp comparison, so a second stat is unavoidable without a larger refactor; the requirement sentence over-promises.
- Evidence code is wrong: size (`lastObservedSize`) could be taken from `fileSizes`.
- Recommendation: reword to "the size used for the size decision is obtained once"; optionally reuse the cached size for the stamp comparison.

**D7. `sizeExemptAnalysed` also lists exempt files that were not analysed in this run** — Severity LOW

- Spec: "the files that exceeded the effective size limit but were analysed because they are exempt". Code (`sizeExempt` filled at discovery for every `exempt` decision, 589-599; JSDoc in `index-result.ts` says unchanged exempt files are included). In an incremental run an unchanged exempt file is hash-skipped and not analysed but is listed.
- Evidence code is wrong: literal reading of "analysed". Evidence spec is wrong: design says "every exempt file that exceeded its limit and was analysed" yet also builds the list at discovery; reporting every exempt file is arguably more useful and stable across runs.
- Recommendation: align wording: "are in the indexed set because they are exempt".

**D8. Tie-break by `localeCompare` is locale dependent** — Severity LOW

- Spec: "descending size order and then by path". Code: `a.filePath.localeCompare(b.filePath)` (index-code-graph.ts ~2166, 2169). Output could differ between hosts (e.g. case ordering), contradicting deterministic output norms of the graph.
- Recommendation: code fix, use codepoint comparison (`a < b ? -1 : a > b ? 1 : 0`) like the rest of the graph; add a test with mixed-case paths.

**D9. Spec text of "Incremental indexing" not aligned with new deletion rule** — Severity LOW

- "Deleted — file exists in the store but not on disk" is unchanged, while code now also removes files that exist but are oversized (covered only by the new Size skip requirement). Not contradictory; merged spec reads inconsistently. Recommendation: add a clause in the Deleted bullet referencing Requirement: Size skip in incremental runs and dependents.

**D10. `filesRemoved` can over-count for coverage-only rows** — Severity LOW

- Code treats any `existingArtifactHashes.has(path)` as "has nodes", but `existingArtifactHashes` is also filled from coverage rows with a `contentHash` (index-code-graph.ts:711-713), e.g. a previously binary/undecodable file (`non-text-content`, hash set) that now becomes oversized is pushed to `deletedFiles` and counted in `filesRemoved` and triggers `semanticRefreshRequired`, though no nodes existed. ### Discrepancies

**D1. Duplicate-terminal / mismatch tests do not test what they claim (test-only, LOW).**

- Spec: Scenarios "Duplicate terminal message cannot settle twice" and "A protocol version mismatch is a protocol failure".
- Code-wrong evidence: supervisor.spec.ts:175-176 emits `{ protocol: 'specd.graph-index.v1', type: 'result' }` twice; both fail `isChildMessage` (PROTO:96), so the test exercises "invalid message" twice, not "valid result then valid duplicate" (SUP:278-281 branch). The branch "message after terminal" and the "version mismatch" branch are therefore never covered by a supervisor-level test (the v1 literal is a leftover from before the bump to v2).
- Spec-wrong evidence: none.
- Recommendation: use `GRAPH_INDEX_PROTOCOL` for the duplicate test and add an explicit v1-mismatch supervisor test asserting `GRAPH_INDEX_WORKER_PROTOCOL`, `diagnostics.cause==='protocol'`, no result.

**D2. stdout/stderr tail and IPC result are read at `exit`, not `close` (MEDIUM, robustness).**

- Code evidence: SUP:413 listens to `'exit'`; `onExit` settles and `attach` snapshots `stderrTail.toString()` synchronously (SUP:196,204-206), then finalize detaches the `data` listeners (SUP:227-228,245). Node documents that `'exit'` can fire before the child's stdio streams are fully flushed (`'close'` is the event emitted after stdio ends). The OOM fatal report is written immediately before abort, so the exact evidence the `resource-limit` rule needs (CLS:70-72) can be in the pipe but not yet delivered when `exit` is emitted, degrading to `native-crash` (SIGABRT/134) or `exited`. The same race theoretically applies to a final `message` (result) that is queued but unread when `exit` fires (pre-existing).
- Spec evidence: "classification SHALL use the exit code, the signal, and the captured output tails" and "capture ... instead of discarding" imply the tails are complete for the run; the spec does not name `exit` vs `close`. Design (design.md line ~577/715) is silent on drain.
- Recommendation: classify/settle on `close` (or after `exit` wait for stdout/stderr `end`/`close` with a short bounded grace, still guaranteeing settlement for fakes that never emit close, as the existing no-exit tests demand); at minimum, on `exit` defer the snapshot by one `setImmediate` tick. Add a test emitting stderr data after `exit` but before `close`. Spec could add a sentence "tails are complete up to stream end".

**D3. Events do not carry output tails although spec says they may/do (LOW-MEDIUM, spec/code mismatch).**

- Spec: Child output capture: "It SHALL appear only in the diagnostics of a failure and in the payload of the events defined by Requirement: Activity and silence watchdog"; scenario "captured tails are available only through failure diagnostics and the worker events".
- Code: `GraphIndexWorkerEvent` `worker-silent` is `{kind,item,silentForMs}` (TYPES:36; SUP:426-430); `activity` is `{kind,item}`. No tails anywhere in events.
- Spec-wrong evidence: Typed worker events requirement defines the event fields exhaustively (activity = item; worker-silent = item + duration) with no tails, and the watchdog requirement says "naming the last announced item and the silent duration". The two requirements contradict each other.
- Recommendation: decide one way. Cheapest: edit the capture requirement/scenario to say tails appear only in failure diagnostics (and remove the "worker events" mention). If tails are wanted on `worker-silent` (useful to explain a stall), add optional `stdoutTail`/`stderrTail` fields to the event, spec and type.

**D4. `SIGBREAK` handler releases the lease before the child has terminated (MEDIUM on Windows, pre-existing but now in the audited spec).**

- Code: SUP:389-392 `onSigbreak` does `lease.release()` then `forwardSignal('SIGBREAK')`. The lock is removed while the child (the actual indexing writer) may still run for an unbounded time, so a second indexer could start. Contradicts Signal forwarding: "wait for child termination, release the lock" and Encapsulated lock ownership: "own the lock for the complete child lifetime". Also `GraphIndexWorkerSignalError` signal type includes SIGBREAK but spec text of Signal forwarding names only SIGINT/SIGTERM.
- Spec evidence: Index lease release on exit: "On Windows it MUST also release the lease on SIGBREAK" (written for the lease holder; for a supervisor this conflicts with the forwarding requirement). Note the lease helper itself (index-lock.ts:262-264) never registers SIGBREAK; only the supervisor does, in all platforms (registering on POSIX is harmless).
- Recommendation: for the supervisor, treat SIGBREAK like SIGINT/SIGTERM (forward, wait, release in finalize) and only release synchronously in the `exit` handler; clarify the spec so the SIGBREAK sentence applies to a process that holds the lease directly (direct-provider mode) and add SIGBREAK to Signal forwarding. Update the supervisor.spec test "releases the lease on SIGBREAK" accordingly.

**D5. Watchdog and `onEvent` failure edge cases (LOW).**

- SUP:419-443: the silence interval is not `unref()`ed (it is cleared in finalize, so no leak on every settle path found; but if `finalize` were never reached the host would be held open) and keeps ticking after a terminal `result` has been received while the child does cleanup, so `worker-silent` events can be delivered after the result (spec: silence = no message of any kind; terminal counts as message, so arguably it should stop). SUP:432-439 overwrites an already recorded `terminal` (including a received `result` or an earlier failure) with `GraphIndexProgressHandlerError`, unlike `protocolFailure` which preserves the first failure. Throwing `onEvent` from `activity` (SUP:288-295) is guarded by `terminal !== undefined` earlier, fine. The error is reused class `GraphIndexProgressHandlerError` with `cause: 'protocol'` (CLS:63-65) although a throwing host handler is not a protocol fault.
- Spec evidence: spec silent on handler failures and on post-terminal silence; design only says "onEvent throwing yields GraphIndexProgressHandlerError".
- Recommendation: stop the watchdog on terminal message; do not overwrite an existing terminal in the interval catch; consider an own cause (or document `protocol`); `unref()` the interval defensively (injected timers return `unknown`, so guard).

**D6. `resource-limit` regex false positives / order (LOW).**

- CLS:11-12 matches `Allocation failed`/`heap out of memory`/`Reached heap limit` anywhere in the 16 KiB stderr tail, including output printed by the task for unrelated reasons, and wins over native-crash and any exit code (CLS:70-72). Spec: "fatal out-of-memory report in the captured error output or an OS kill after that evidence". Code is looser (no check that exit was abnormal; a task-printed line plus plain `exit 1` becomes resource-limit). Also the SIGKILL "OS kill" without evidence correctly stays `exited` (matches design line 715).
- Recommendation: require abnormal exit (signal or non-zero code) for the regex rule (already always true when classification is reached, because typed task/protocol errors return earlier), and anchor on `FATAL ERROR:` / `Ineffective mark-compacts` lines; add a negative test.

**D7. Precedence of `cancelled` over crash evidence (LOW, design choice).**

- SUP:335-343 settles with `GraphIndexWorkerSignalError` whenever a signal was forwarded, even if the child had already crashed (native signal, OOM) or had delivered a valid result and exited 0 before the signal; diagnostics then say `cancelled` (CLS:67-69, before resource-limit/native-crash). Spec: "cancelled (termination caused by a signal the supervisor forwarded)". If the child died of SIGSEGV/OOM independently, the cause is mis-attributed.
- Recommendation: only classify `cancelled` when child exit signal equals the forwarded signal, or exit code is the conventional 128+n/130/143, or evidence of crash absent; otherwise prefer crash causes. Add a test (forwarded SIGINT but child exits SIGSEGV).

**D8. Windows/other exit-code details (LOW).**

- CLS:23 includes 134 and 3221225477 only. Node on Windows reports abort as 3 (or 0xC0000409 = 3221226505 stack-buffer-overrun/fast-fail used by `abort()` in MSVC CRT) and V8 OOM on Windows frequently exits via 0xC0000409/exit 134 variants; negative signed forms (-1073741819) are not matched. Design only lists access violation. Recommendation: add 3221226505 (and 3) or document the closed list in the spec ("an abort exit").

**D9. execArgv handling (LOW).**

- SUP:398-400 dedups only the exact string `--expose-gc`; `--expose_gc` (underscore form) or `--expose-gc=...` already supplied by host would be duplicated (harmless). `NODE_OPTIONS` is inherited through `env` spread (SUP:407) untouched. Inspector flags (`--inspect`) from the host are inherited into the child (Node's own default fork behaviour handles port increment). Meets spec ("MUST NOT remove arguments supplied by the host"). No action required beyond optionally normalising underscores.

**D10. Rate limiting semantics (LOW, spec clarity).**

- ANN:42-47: a mandatory announcement resets the 250 ms window, so ordinary items right after a mandatory one are dropped, and the last announced item at a stall can be an ordinary withheld one when it follows another ordinary within 250 ms. Spec accepts that only mandatory ones are guaranteed. No code bug; the "last announced item" in diagnostics can therefore lag the true active item by up to one ordinary announcement. Spec could say "last forwarded item".

**Race / lifecycle checks with no defect found.** `exitCode` and `signal` are assigned before `settle` -> `attach` (SUP:333-334); `attach` runs before `finalize` clears `child` (SUP:215-216); `finalize` is memoised (SUP:231-233) and `lease.release` is idempotent (index-lock.ts:240-243), so exit+message ordering and terminal+exit succession release once; interval cleared, process listeners (SIGINT/SIGTERM/SIGBREAK/exit) removed by reference, child listeners and data listeners removed, tails disposed, IPC disconnected (SUP:238-249); fork throwing or no-IPC settle with the lease released (SUP:445-458, 482-492). Residual: `finalize` does not destroy `stdout`/`stderr` pipe streams or unref them; after the data listener is removed the stream stays flowing and is discarded, closing on EOF, so a grandchild process keeping the pipe open could keep the stream (and an event-loop handle) alive; consider `child.stdout?.destroy()`/`unref` on finalize (LOW). The send-failure case does best-effort `terminate` with SIGTERM only (no SIGKILL escalation) and settles regardless, matching "bounded" (spec OK).

### Discrepancies

- D-IPG-1 (LOW, spec wording wrong): Spec "Executes project indexing" says `graphConfig` includes "the resolved per-file size limit and size-exempt patterns of every workspace".
  - Evidence spec-wrong: the code deliberately forwards the raw config and resolves in exactly one place (`resolve-effective-graph-config.ts`), which is what the new "Effective size limit resolution" requirement demands ("no other call site SHALL apply the default"). Resolving before `provider.index()` would create a second resolution site. `build-project-graph-config.ts:35-70` forwards only declared values.
  - Evidence code-wrong: none; the design (design.md "Effective size limit resolution") places resolution inside the indexer.
  - Severity: LOW. Recommendation: reword to "`graphConfig`, carrying the declared per-file size limit and size-exempt patterns of the project and every workspace; they are resolved by Requirement: Effective size limit resolution".
- D-IPG-2 (LOW, code side, redundant fallback): `file-size-gate.ts:118-120` and `compute-graph-fingerprint.ts:79,158` apply `?? effective.rootMaxFileBytes` when a workspace is missing from the effective map. It is not the built-in default, so the rule "no other call site applies the default" holds, but a workspace missing from the map silently inherits the root limit instead of failing. Severity LOW; recommendation: leave, or assert the workspace exists.
- D-IPG-3 (LOW, spec wording): The requirement says "one effective set of `largeFilePaths` (the project patterns together with the workspace patterns, each kept with its base directory)" while the code keeps two arrays (`projectLargeFilePaths`, `workspaceLargeFilePaths`) and the base directory is implicit in which array it is in. Semantically equal; recommendation: say "kept apart by level so that each resolves against its base directory".

**D1. Snippet pattern for a root-level file is not anchored (MEDIUM)**

- Description: Spec says the escaped pattern must match "only that file". A skipped file directly under the project root, e.g. `big.ts`, is emitted as `- big.ts`. In gitignore syntax a pattern without a slash matches at any depth, so it would also exempt `sub/big.ts`, `packages/x/big.ts`, etc. Files with a slash in the path are anchored and fine.
- Evidence spec-wrong: scenario "Special characters are escaped ... pattern matches only that file" speaks of escaping only; the design lists a closed escape set without anchoring. So the spec/design are silent on anchoring.
- Evidence code-wrong: `escapeGitignorePattern` never prefixes `/`; `formatTextIndexResult` uses it directly.

**D2. Snippet is not YAML-safe for some paths (LOW)**
