### Discrepancies

**D1. Duplicate-terminal / mismatch tests do not test what they claim (test-only, LOW).**

- Spec: Scenarios "Duplicate terminal message cannot settle twice" and "A protocol version mismatch is a protocol failure".
- Code-wrong evidence: supervisor.spec.ts:175-176 emits `{ protocol: 'specd.graph-index.v1', type: 'result' }` twice; both fail `isChildMessage` (PROTO:96), so the test exercises "invalid message" twice, not "valid result then valid duplicate" (SUP:278-281 branch). The branch "message after terminal" and the "version mismatch" branch are therefore never covered by a supervisor-level test (the v1 literal is a leftover from before the bump to v2).
- Spec-wrong evidence: none.
- Recommendation: use `GRAPH_INDEX_PROTOCOL` for the duplicate test and add an explicit v1-mismatch supervisor test asserting `GRAPH_INDEX_WORKER_PROTOCOL`, `diagnostics.cause==='protocol'`, no result.

**D2. stdout/stderr tail and IPC result are read at `exit`, not `close` (MEDIUM, robustness).**

- Code evidence: SUP:413 listens to `'exit'`; `onExit` settles and `attach` snapshots `stderrTail.toString()` synchronously (SUP:196,204-206), then finalize detaches the `data` listeners (SUP:227-228,245). Node documents that `'exit'` can fire before the child's stdio streams are fully flushed (`'close'` is the event emitted after stdio ends). The OOM fatal report is written immediately before abort, so the exact evidence the `resource-limit` rule needs (CLS:70-72) can be in the pipe but not yet delivered when `exit` is emitted, degrading to `native-crash` (SIGABRT/134) or `exited`. The same race theoretically applies to a final `message` (result) that is queued but unread when `exit` fires (pre-existing).
- Spec evidence: "classification SHALL use the exit code, the signal, and the captured output tails" and "capture ... instead of discarding" imply the tails are complete for the run; the spec does not name `exit` vs `close`. Design (design.md line ~577/715) is silent on drain.
- Recommendation: classify/settle on `close` (or after `exit` wait for stdout/stderr `end`/`close` with a short bounded grace, still guaranteeing settlement for fakes that never emit close, as the existing no-exit tests demand); at minimum, on `exit` defer the snapshot by one `setImmediate` tick. Add a test emitting stderr data after `exit` but before `close`. Spec could add a sentence "tails are complete up to stream end".

**D3. Events do not carry output tails although spec says they may/do (LOW-MEDIUM, spec/code mismatch).**

- Spec: Child output capture: "It SHALL appear only in the diagnostics of a failure and in the payload of the events defined by Requirement: Activity and silence watchdog"; scenario "captured tails are available only through failure diagnostics and the worker events".
- Code: `GraphIndexWorkerEvent` `worker-silent` is `{kind,item,silentForMs}` (TYPES:36; SUP:426-430); `activity` is `{kind,item}`. No tails anywhere in events.
- Spec-wrong evidence: Typed worker events requirement defines the event fields exhaustively (activity = item; worker-silent = item + duration) with no tails, and the watchdog requirement says "naming the last announced item and the silent duration". The two requirements contradict each other.
- Recommendation: decide one way. Cheapest: edit the capture requirement/scenario to say tails appear only in failure diagnostics (and remove the "worker events" mention). If tails are wanted on `worker-silent` (useful to explain a stall), add optional `stdoutTail`/`stderrTail` fields to the event, spec and type.

**D4. `SIGBREAK` handler releases the lease before the child has terminated (MEDIUM on Windows, pre-existing but now in the audited spec).**

- Code: SUP:389-392 `onSigbreak` does `lease.release()` then `forwardSignal('SIGBREAK')`. The lock is removed while the child (the actual indexing writer) may still run for an unbounded time, so a second indexer could start. Contradicts Signal forwarding: "wait for child termination, release the lock" and Encapsulated lock ownership: "own the lock for the complete child lifetime". Also `GraphIndexWorkerSignalError` signal type includes SIGBREAK but spec text of Signal forwarding names only SIGINT/SIGTERM.
- Spec evidence: Index lease release on exit: "On Windows it MUST also release the lease on SIGBREAK" (written for the lease holder; for a supervisor this conflicts with the forwarding requirement). Note the lease helper itself (index-lock.ts:262-264) never registers SIGBREAK; only the supervisor does, in all platforms (registering on POSIX is harmless).
- Recommendation: for the supervisor, treat SIGBREAK like SIGINT/SIGTERM (forward, wait, release in finalize) and only release synchronously in the `exit` handler; clarify the spec so the SIGBREAK sentence applies to a process that holds the lease directly (direct-provider mode) and add SIGBREAK to Signal forwarding. Update the supervisor.spec test "releases the lease on SIGBREAK" accordingly.

**D5. Watchdog and `onEvent` failure edge cases (LOW).**

- SUP:419-443: the silence interval is not `unref()`ed (it is cleared in finalize, so no leak on every settle path found; but if `finalize` were never reached the host would be held open) and keeps ticking after a terminal `result` has been received while the child does cleanup, so `worker-silent` events can be delivered after the result (spec: silence = no message of any kind; terminal counts as message, so arguably it should stop). SUP:432-439 overwrites an already recorded `terminal` (including a received `result` or an earlier failure) with `GraphIndexProgressHandlerError`, unlike `protocolFailure` which preserves the first failure. Throwing `onEvent` from `activity` (SUP:288-295) is guarded by `terminal !== undefined` earlier, fine. The error is reused class `GraphIndexProgressHandlerError` with `cause: 'protocol'` (CLS:63-65) although a throwing host handler is not a protocol fault.
- Spec evidence: spec silent on handler failures and on post-terminal silence; design only says "onEvent throwing yields GraphIndexProgressHandlerError".
- Recommendation: stop the watchdog on terminal message; do not overwrite an existing terminal in the interval catch; consider an own cause (or document `protocol`); `unref()` the interval defensively (injected timers return `unknown`, so guard).

**D6. `resource-limit` regex false positives / order (LOW).**

- CLS:11-12 matches `Allocation failed`/`heap out of memory`/`Reached heap limit` anywhere in the 16 KiB stderr tail, including output printed by the task for unrelated reasons, and wins over native-crash and any exit code (CLS:70-72). Spec: "fatal out-of-memory report in the captured error output or an OS kill after that evidence". Code is looser (no check that exit was abnormal; a task-printed line plus plain `exit 1` becomes resource-limit). Also the SIGKILL "OS kill" without evidence correctly stays `exited` (matches design line 715).
- Recommendation: require abnormal exit (signal or non-zero code) for the regex rule (already always true when classification is reached, because typed task/protocol errors return earlier), and anchor on `FATAL ERROR:` / `Ineffective mark-compacts` lines; add a negative test.

**D7. Precedence of `cancelled` over crash evidence (LOW, design choice).**

- SUP:335-343 settles with `GraphIndexWorkerSignalError` whenever a signal was forwarded, even if the child had already crashed (native signal, OOM) or had delivered a valid result and exited 0 before the signal; diagnostics then say `cancelled` (CLS:67-69, before resource-limit/native-crash). Spec: "cancelled (termination caused by a signal the supervisor forwarded)". If the child died of SIGSEGV/OOM independently, the cause is mis-attributed.
- Recommendation: only classify `cancelled` when child exit signal equals the forwarded signal, or exit code is the conventional 128+n/130/143, or evidence of crash absent; otherwise prefer crash causes. Add a test (forwarded SIGINT but child exits SIGSEGV).

**D8. Windows/other exit-code details (LOW).**

- CLS:23 includes 134 and 3221225477 only. Node on Windows reports abort as 3 (or 0xC0000409 = 3221226505 stack-buffer-overrun/fast-fail used by `abort()` in MSVC CRT) and V8 OOM on Windows frequently exits via 0xC0000409/exit 134 variants; negative signed forms (-1073741819) are not matched. Design only lists access violation. Recommendation: add 3221226505 (and 3) or document the closed list in the spec ("an abort exit").

**D9. execArgv handling (LOW).**

- SUP:398-400 dedups only the exact string `--expose-gc`; `--expose_gc` (underscore form) or `--expose-gc=...` already supplied by host would be duplicated (harmless). `NODE_OPTIONS` is inherited through `env` spread (SUP:407) untouched. Inspector flags (`--inspect`) from the host are inherited into the child (Node's own default fork behaviour handles port increment). Meets spec ("MUST NOT remove arguments supplied by the host"). No action required beyond optionally normalising underscores.

**D10. Rate limiting semantics (LOW, spec clarity).**

- ANN:42-47: a mandatory announcement resets the 250 ms window, so ordinary items right after a mandatory one are dropped, and the last announced item at a stall can be an ordinary withheld one when it follows another ordinary within 250 ms. Spec accepts that only mandatory ones are guaranteed. No code bug; the "last announced item" in diagnostics can therefore lag the true active item by up to one ordinary announcement. Spec could say "last forwarded item".

**Race / lifecycle checks with no defect found.** `exitCode` and `signal` are assigned before `settle` -> `attach` (SUP:333-334); `attach` runs before `finalize` clears `child` (SUP:215-216); `finalize` is memoised (SUP:231-233) and `lease.release` is idempotent (index-lock.ts:240-243), so exit+message ordering and terminal+exit succession release once; interval cleared, process listeners (SIGINT/SIGTERM/SIGBREAK/exit) removed by reference, child listeners and data listeners removed, tails disposed, IPC disconnected (SUP:238-249); fork throwing or no-IPC settle with the lease released (SUP:445-458, 482-492). Residual: `finalize` does not destroy `stdout`/`stderr` pipe streams or unref them; after the data listener is removed the stream stays flowing and is discarded, closing on EOF, so a grandchild process keeping the pipe open could keep the stream (and an event-loop handle) alive; consider `child.stdout?.destroy()`/`unref` on finalize (LOW). The send-failure case does best-effort `terminate` with SIGTERM only (no SIGKILL escalation) and settles regardless, matching "bounded" (spec OK).

### Spec text consistency with global specs

- Spec uses `GraphIndexWorkerDiagnostics`/`cause` vocabulary consistent with error-handling-conventions (typed errors, stable upper-snake codes). The `cause` values are lower-kebab strings, distinct from error `code`s; acceptable, but note `GraphIndexWorkerError.cause` getter on Start/ProgressHandler errors (ERR:44-46,167-169) is the original Error cause, while diagnostics `cause` is the classification: two different "cause" concepts on the same object, possible reader confusion (suggest naming `diagnostics.cause` -> `failureCause` or documenting it).
- "Requirement: Child runtime options" and "Child output capture" use a bound of 16 KiB consistently with TAIL:2.
- Constraints still say "MUST NOT implement ... stale-lock detection" while Typed worker events defines `stale-lock-recovered` consumption: consistent (supervisor only consumes outcome).
- Spec Dependencies list only `sqlite-graph-store`; the spec now depends on `code-graph:staleness-detection` (lock helper, Constraints) and on the indexer-task contract (`announce` third argument, `GraphIndexTaskAnnouncer`) of the CLI/SDK task; add them to Spec Dependencies. The Trusted injected task module requirement still describes the entrypoint as receiving only input and a progress emitter (spec lines "The task entrypoint SHALL receive: input; a progress emitter") while code passes a third `announce` argument (CH:179, PORT:`GraphIndexTask`): spec-stale, MEDIUM-LOW; update that requirement (the Activity requirement says "task contract SHALL allow the task to announce" but the contract list was not amended).
- Index lease release on exit says "On Windows ... SIGBREAK" but implementation only does so in the supervisor (see D4).

### Test Coverage gaps

1. No supervisor-level test for protocol version mismatch (D1) and genuine duplicate/late terminal (D1).
2. No end-to-end/supervisor test of `cause==='cancelled'` for forwarded SIGINT, `native-crash` for SIGSEGV exit, nor diagnostics on onError, send failure, no-IPC, protocol-failure and signal-error paths (only one diagnostics test).
3. No test that host stdout/stderr receive nothing from child output, nor of 1 MiB stderr bound at the supervisor level (only OutputTail unit), nor invalid UTF-8 through the supervisor.
4. No test that the watchdog does not terminate the child, runs while the child is blocked synchronously (real child), or stops after settle (timer cleared: only indirectly).
5. No test of `onEvent` throwing inside the silence interval; no test of activity `agoMs`.
6. No test for stdout/stderr data arriving after `exit` (D2) or for `close` handling.
7. `Atomics`/blocking-task fixture for "works while child blocked" absent from dist.spec.
8. Child (CH) wiring of `announce` through real IPC (activity reaching a real supervisor) not covered end-to-end; child.activity.spec tests the announcer in isolation only.
