# Exploration Context: bound-indexer-ast-resource-lifecycle

Generated: 2026-10-23

## Problem statement

Indexing an existing large project with its current `specd.yaml` used to complete but now appears to freeze. The immediate trigger is a superlinear PHP adapter traversal covered by the separate `optimize-language-adapter-ast-traversals` change, but independent reproduction showed that process memory still grows to multiple gigabytes after excluding the problematic PHP file or even all PHP files.

Every built-in Tree-sitter adapter appends its parsed `SgRoot` to the run-scoped `IndexSession` state under `napi-keepalive`. The collection is retained until the indexing operation completes successfully. This workaround prevents V8 garbage collection from running a native Rust finalizer during event-loop yields because `@ast-grep/napi` has exhibited a concurrency/double-free `SIGSEGV`. It also violates the existing `code-graph:indexer` requirement that heavyweight parser objects must not be retained across the complete run.

The user explicitly requested a separate change so this native-resource lifecycle issue is not forgotten. This change is independent of the adapter traversal design and should be implementable in parallel with it.

## Observed behaviour and evidence

### Real project reproduction

- The original run stopped reporting progress after `550/3234` files and saturated a CPU core.
- Native sampling of the blocked process showed hot frames in `ast_grep_napi::SgNode.kind` / `children` plus V8 garbage-collection pressure.
- Physical memory approached 4.9-5.0 GB in the failing run.
- Excluding `articles_importers_controller.php` removed the exact PHP trigger but the run still approached approximately 3 GB quickly.
- Excluding all PHP still allowed RSS to approach approximately 4 GB while processing thousands of files. Per-file logging showed forward progress rather than a second identical hang, demonstrating cumulative run-scoped retention.
- An in-process SDK reproduction reached roughly 1.8 GB around file 1,500 before it was stopped to avoid exhaustion.

### Current lifecycle anchors

Each adapter performs the same operation near the start of `analyzeFile`:

- `packages/code-graph/src/infrastructure/tree-sitter/typescript-language-adapter.ts`, around lines 824-832
- `packages/code-graph/src/infrastructure/tree-sitter/python-language-adapter.ts`, around lines 533-541
- `packages/code-graph/src/infrastructure/tree-sitter/go-language-adapter.ts`, around lines 447-455
- `packages/code-graph/src/infrastructure/tree-sitter/php-language-adapter.ts`, around lines 693-701

They call `context.session.getAdapterState<unknown[]>('napi-keepalive')`, create one shared array when absent, and push each `SgRoot` into it.

`packages/code-graph/src/application/use-cases/index-code-graph.ts`, around line 2031, clears that state only on the successful return path. The clear is not in a `finally`, so SDK-hosted failures may leave the state reachable for as long as the session remains reachable. In the isolated CLI path the child process eventually exits, but not before the full run has accumulated every root.

`packages/code-graph/src/infrastructure/isolated-index-worker/supervisor.ts`, around line 285, launches the child with stdout and stderr ignored. Progress from `IndexCodeGraph` is emitted only every 50 analyzed files around `index-code-graph.ts:1065`, which hides the current file and makes memory thrashing look like an unexplained freeze.

### Existing specification conflict

`code-graph:indexer` already contains `Requirement: Bounded analysis memory`, including the explicit rule that the indexer must not retain parser ASTs, parse trees, or equivalent heavyweight parser objects across the full run. The current `napi-keepalive` implementation is therefore an implementation/spec compliance defect, not merely an optional optimization.

## Desired outcomes

1. Bound the lifetime and maximum number/bytes of native AST roots retained at once.
2. Preserve the safety property that motivated `napi-keepalive`: no native finalizer double-free, concurrent disposal, or process crash.
3. Centralize ownership and cleanup instead of relying on four adapter-local pushes into an untyped magic state key.
4. Guarantee cleanup on success, parse failure, cancellation, persistence failure, and other thrown errors.
5. Allow the isolated worker to make forward progress on very large projects without monotonically accumulating parser roots for the entire run.
6. Surface actionable diagnostics before or when a memory/resource guard activates.
7. Improve progress granularity enough to identify the active file or batch when a run stalls, without flooding normal output.
8. Preserve graph semantics, incremental/full-rebuild semantics, and atomic commit guarantees.

## Solution directions to evaluate during design

The change is intentionally investigative about the exact disposal mechanism because native safety must be demonstrated rather than assumed.

### Preferred direction: centrally owned bounded epochs

- Introduce a typed native-parser resource owner associated with an analysis batch or epoch.
- Adapters register roots with that owner instead of a session-wide `unknown[]` state entry.
- Complete all synchronous use of the roots and convert outputs to compact normalized facts before closing an epoch.
- Dispose or make the epoch unreachable only at a proven-safe boundary.
- Use `try/finally` so every exit path closes the current epoch.

### Worker/process isolation fallback

If the installed `@ast-grep/napi` version cannot safely release roots inside a long-lived process, process lifetime is the hard safety boundary:

- Analyze bounded groups in short-lived worker children.
- Return only serializable compact facts to the coordinator.
- Restart workers after a configurable file/byte/resource budget.
- Preserve cancellation and deterministic ordering across restarts.

This is heavier than in-process epochs but safer than relying on finalizer timing when the native binding is defective.

### Dependency investigation

- Reproduce the original finalizer crash with a minimal native-binding test.
- Determine whether a newer `@ast-grep/napi` release fixes the underlying double-free/concurrency defect.
- Review whether the binding exposes an explicit deterministic disposal API.
- Do not remove the keepalive workaround solely because ordinary tests happen to pass.

### Guardrails and telemetry

- Consider a configurable soft resource budget based primarily on analyzed source bytes/root count; RSS may be diagnostic because it is noisy and platform-dependent.
- Emit structured batch/file progress over the existing worker IPC protocol.
- Report why a worker was recycled or why indexing failed due to a resource guard.
- Avoid strict cross-platform assertions on absolute RSS or wall-clock time; verify bounded retained-root count, cleanup paths, restart behaviour, and semantic equivalence deterministically.

## Decisions and agreements

- This is a new change rather than an extension of `optimize-language-adapter-ast-traversals`.
- There is no formal dependency between the two changes. Adapter traversal optimization reduces per-file work; this change bounds cross-file native-resource lifetime.
- Both changes may be implemented in parallel, but this change should concentrate lifecycle policy in the indexer/session/worker rather than independently rewriting each adapter's semantic analysis.
- The current workaround must not simply be deleted. Any replacement must prove native safety under garbage collection, cancellation, exceptions, and multiple files.
- Existing `code-graph:indexer` bounded-memory requirements should be treated as authoritative. Design may add scenarios or clarify lifecycle guarantees rather than inventing a conflicting contract.
- Operational visibility belongs here when it is directly tied to detecting active batches, recycling, or memory/resource failure.

## Out of scope

- PHP/Python/TypeScript/Go superlinear AST traversals, repeated symbol lookups, scope caches, and removal of unused PHP `parserState.scopes`; these belong to `optimize-language-adapter-ast-traversals`.
- Per-project `specd.yaml` exclusion corrections. Shallow or workspace-mismatched patterns greatly increase the input set, but configuration cleanup belongs in that project rather than this repository change.
- General graph-store performance unrelated to staging compact analysis results or preserving atomic commits.
- Changing persisted graph schemas or graph identity semantics.

## Rejected or unsafe alternatives

- **Delete `napi-keepalive` immediately:** rejected because comments and prior failures identify a native double-free/segmentation-fault risk.
- **Keep every root until full-run success:** current behaviour; rejected because memory grows with the complete input set and violates the bounded-memory spec.
- **Rely only on V8/RSS timing tests:** rejected as nondeterministic and platform-sensitive.
- **Make this change depend on adapter traversal optimization:** rejected because the memory-lifetime defect persists even when individual analyses become faster.

## Open questions for design

1. Can the current or an upgraded `@ast-grep/napi` safely release roots at an in-process batch boundary, including under forced GC?
2. What is the smallest safe lifetime unit: individual file, source-size chunk, adapter epoch, or child process?
3. Should the resource budget be internal and fixed initially, exposed through existing graph configuration, or configurable only after production evidence?
4. Which worker IPC events and result diagnostics are needed to distinguish slow analysis, worker recycling, cancellation, native crash, and resource-limit termination?
5. Can the existing chunking mechanism become the lifecycle boundary without retaining raw roots for Pass 2, given that the indexer already requires compact facts between passes?

## Tangential findings retained for context

- That project currently discovers many vendored/generated files, including bundled JavaScript libraries, Java build output, JARs, backups, deployment files, and third-party dependencies. This magnifies memory pressure but is not the root lifecycle defect.
- The isolated worker discards standard output/error, and progress is reported at coarse fixed intervals. These choices made the original PHP trigger appear to be a generic freeze.
- `articles_importers_controller.php` remains the strongest regression fixture shape for end-to-end stress testing, but proprietary project content should be represented with generated fixtures rather than copied into this repository.
