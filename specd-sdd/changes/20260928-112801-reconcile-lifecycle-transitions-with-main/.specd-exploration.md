## Problem statement

Merge `main` into `feat/lifecycle-transitions-ux`, understand the divergent work since the branches split, and semantically reconcile the feature with the repository shape and contracts now present on `main`. The merge touches source, tests, docs, canonical specs, generated spec metadata, the lockfile, and an already-active change manifest. An automatic conflict resolution is insufficient because both sides changed lifecycle-related specs and behavior.

The user explicitly wants the merge to happen before designing the adaptation. This ensures the change is written against the integrated canonical specs from `main`, rather than designing against stale pre-merge specs and later trying to retrofit them.

## Approach and sequence agreed with the user

1. Inspect branch divergence and the prospective merge.
2. Preserve pre-existing dirty spec-lock refreshes recoverably in a stash.
3. Merge `main` into the feature branch.
4. Create a new adaptation change on the integrated, conflict-bearing tree.
5. Resolve conflicts semantically under that change, including specs rather than treating generated locks as an ordinary text merge.
6. Adapt code, tests, documentation, package structure, and metadata to the post-merge canonical format.
7. Re-index the graph once conflict markers no longer make inputs ambiguous.
8. Validate the merged specs and implementation and drive the change to `ready` when authorized by the lifecycle skills.

The first attempt, `adapt-lifecycle-transitions-to-main`, was deliberately discarded because it was created before merging `main`. Its proposal was therefore based on the wrong canonical baseline. Discard reason: `Recreate after merging main so design uses the integrated canonical specs`.

## Resolution principles

- Preserve the feature branch's lifecycle semantics unless a newer canonical spec on `main` intentionally supersedes them.
- Layer `main`'s portability fixes into the preserved lifecycle behavior.
- Treat `packages/cli/src/index.ts` as a structural port, not an ours/theirs selection: `main` extracted program construction and removed roughly 273 lines while the feature added lifecycle registrations.
- Adopt `main`'s new guide/docs layout. Content from feature-side files deleted by `main` must be relocated or rewritten where still semantically required, not automatically resurrected at obsolete paths.
- Resolve canonical spec content before regenerating or refreshing `spec-lock.json`; generated metadata should reflect the final spec, not textual conflict-marker surgery.
- Union independent manifest histories chronologically where both branches added valid invalidation events.
- Re-run graph indexing after conflict resolution because the integrated worktree invalidates the pre-merge graph fingerprint.
- Specs are requirements and source of truth; every implementation adjustment must be covered by an existing or newly scoped spec. No source-only reconciliation.

## Initial scope decision

The change intentionally starts with no attached specs. The integrated tree contains unresolved spec and spec-lock conflicts, so attaching guessed IDs at creation time would encode an unreliable scope and could create misleading overlap warnings. During design, first identify canonical requirements from the resolved or inspectable spec sources, then add every affected owned spec before writing its delta.

An earlier pre-merge change proposed roughly 11 specs and produced an acknowledged overlap around `core:change` with the active `implementation-snapshot` change. That scope is evidence for investigation, not an authoritative scope for this new change. If `core:change` or any other candidate overlaps active changes when added, surface the exact overlap and ask the user before continuing, per the workflow rules.
