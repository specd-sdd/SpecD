## Problem statement

Workflow checks (transition and archive) cannot use internal use cases, and there is no way to ship checks as plugins configured in `specd.yaml`. User opened with: "no sé si llegamos a solucionar en esta rama que los checks del workflow puedan usar use cases internos". Answer found: not solved on this branch.

## Key codebase observations (verify before trusting; anchors given)

- `CheckExecutionContext` (`packages/core/src/domain/services/transition-checks.ts:351`) exposes only `change`, `schema`, `attempt`, `config`, `validity`, `onCheckProgress`, `skipHookPhases`, `effectiveStatusByArtifact`, `approvals`, `passMemo`. No use cases, no kernel.
- `CustomCheckDefinition` (same file, ~385): `id`, `label`, optional `command`, `execute(ctx)`.
- `Check` has a mandatory `kind` and `label` (gerund); custom definitions omit `kind` and `skippable` (engine internals / routing policy).
- Built-in checks DO use use cases (`countTasks`, `runStepHooks`, overlap detector) but receive them as deps in `createWorkflowCheckRegistry` (`packages/core/src/application/checks/workflow-check-registry.ts`), wired by `resolveWorkflowCheckRegistry` (`packages/core/src/composition/use-cases/workflow-check-registry.ts`). Custom bindings with ids starting with `@` come from `resolver.registry.checks.bindings()`.
- `registerCheck(pluginName, check, defaultBindings?, options?)` exists only on `KernelBuilder` (`packages/core/src/composition/kernel-builder.ts:180`, impl ~402), pushes into `options.checks`. No package other than core calls it.
- Schema side: workflow step `checks`, `skipChecks`, `archiveChecks` only reference a check by `id` with `skippable`/`disabled`/`config`/`onFailure` (`packages/core/src/infrastructure/schema-yaml-parser.ts` ~253-311, `WorkflowStepArchiveCheckZodSchema` is `.strict()`). A schema cannot define check logic.
- Hooks have a typed `external` entry (`external: { type, config }`) dispatched to runners registered with `registerExternalHookRunner` — precedent for typed extension points.
- `createCompositionResolver(config, options)` and `create*` use case factories (`createCountTasks`, `createValidateSpecs`, `createGetStatus`, ...) are exported from `@specd/core` (`packages/core/src/composition/index.ts`, `use-cases/index.ts`). A host could build use cases by hand and close over them in a check, but that creates a second composition (divergent registries, state, logging/privacy wrapper) and only works for TS hosts.
- `plugin-manager` (`packages/plugin-manager/src`): `PLUGIN_TYPES = ['agent']` (`domain/types/specd-plugin.ts`), manifest `pluginType: z.enum(['agent'])` and `validateRuntimePlugin` hardcode agent (`infrastructure/loader/plugin-loader.ts`). Loader resolves package from project root then CLI runtime, reads `specd-plugin.json`, imports entry and calls `create({ config })`. `SpecdPlugin` = `name`, `type`, `version`, `configSchema` (flat `Record<string, {type: 'string'|'boolean'|'number', description, default?, required?}>`), `init(context)`, `destroy()`. `PluginContext` only has `config: SpecdConfig`. `AgentPlugin` adds `install`/`uninstall`. `plugin-manager` depends on `@specd/core` and `zod`.
- `specd.yaml` `plugins:` only has `agents:` (`packages/core/src/infrastructure/fs/config-loader.ts:656`, `application/ports/config-schema.ts`, `config-writer.ts`, `config-cascade.ts`). `cli plugins install/list/show/uninstall/update` specs exist and are agent-oriented.
- `sdk:composition` currently limits runtime deps to `@specd/core` and `@specd/code-graph` and forbids `@specd/cli`, `@specd/mcp` and plugin packages. `sdk:host-context`: `SdkHostContext = { kernel, createGraphProvider }`; `createSdkContext(config, options)` awaits `createKernel(config, options?.kernel)`; `openSpecdHost` loads config then calls `createSdkContext`.
- `cli:host-context`: CLI only depends directly on `@specd/sdk` among platform packages.
- `@specd/mcp` is a stub (`packages/mcp/src/index.ts`, 14 bytes), no specs.
- Metadata: `GetSpecMetadata` → `MaterializeSpecMetadata` with `policy: 'if-needed'` may persist a derived cache at `.specd/metadata/<ws>/<spec>/metadata.json` (gitignored here; path configurable via `specs.fs.metadataPath`).

## Conversation flow and decisions

1. Investigated the gap (above). Listed options: A) services in the check context; B) factory with kernel; C) declarative checks in the schema (`usecase:` like `external:` in hooks); D) export `create*` check factories.
2. User asked whether a check could be built beforehand by hand sharing config with core → possible today but second composition (see above). Variant preferred: `registerCheck` accepts `definition | (services) => definition`, resolved inside `createKernel` after use cases are composed (single composition, no chicken-and-egg).
3. User stated check plugins will have their config in `specd.yaml` → host-closure pattern rejected for plugins loaded from config; a loader is needed.
4. User: "tenemos el pluginmanager, que habría que ampliar para estas cosas" → extend `plugin-manager`: add plugin type `'check'`, `CheckPlugin extends SpecdPlugin` with `checks(services, pluginConfig)`, use case to load check plugins, `PluginContext` carrying the plugin's own config, validation of plugin config against `configSchema`. Dependency direction: `core` must not import `plugin-manager` (plugin-manager → core).
5. User: "la interconexión con el core debe hacerla sdk" and "SDK pasaría a depender de plugin-manager sí, no pasa nada" → relax `sdk:composition` to allow `@specd/plugin-manager` only; AGENTS.md dependency graph becomes `sdk → core, code-graph, plugin-manager`. Injected-loader-port alternative rejected.
6. User: install/uninstall exist on plugins in case a check needs to do something at install ("puede no ser nada, o puede ser que necesiten instalar o inicializar cosas para ellos internas") → `CheckPlugin` keeps `install`/`uninstall` (may be no-ops).
7. User noted there is no destroy/dispose in the host and it must be added to the base → separate change `host-lifecycle-dispose`.
8. Later refinement (user): "y si plugin manager recibiera un kernelBuilder antes de inicializar?" and "plugin manager es el que sabe cómo funcionan los plugins" → FINAL SHAPE: `plugin-manager` receives the `KernelBuilder` before `build()`, loads and `init`s plugins, calls `builder.registerCheck(...)` for their checks and `builder.registerDisposer(...)` with ONE disposer (its plugin session's `destroyAll`, reverse order, error isolation). SDK only wires: create builder → call plugin-manager registration → `build()` → `host.dispose()` delegates to `kernel.dispose()`. Plugins themselves never touch builder or kernel. Core's disposer list is generic (provided by `host-lifecycle-dispose`).
9. Services: need a spec `core:check-services` (user: "debería tener su propio spec, sí").

## CheckServices (new spec `core:check-services`)

- Frozen, typed facade over already-composed use cases, built once per kernel, injected into check factories by `createKernel`.
- Plugin shape: `checks(services, pluginConfig)` returns `{ definition, defaultBindings, options }[]`; evaluation-specific data still arrives per call in `ctx`; `services` and `pluginConfig` are captured once.
- Initial catalog proposal: `getSpecMetadata`, `validateSpecs`, `countTasks`, `getSpec`, `listSpecs`, read access to changes, `logger`, `projectRoot`. Re-check each use case for hidden writes/reentrancy during design.
- Excluded on purpose: use cases that mutate the change under evaluation (`transitionChange`, `archiveChange`, approve, create, ...) because of reentrancy, and `getStatus` because it re-evaluates checks (recursion; could be guarded via `passMemo`, left out of v1).
- Entry criterion (agreed): the service does not re-enter the check engine and does not mutate the change being evaluated.
- Purity discussion outcome (user): `GetSpecMetadata` is "practically the one with the most possibilities in a check of specs"; without cache it would be read-only; and an external plugin can do anything anyway ("no vamos a poder comprobarlo siempre"). Decision: expose it as is; spec documents "effects limited to derived caches"; restrictions are API contract and ergonomics, NOT a security boundary. Rejected: a new `policy: 'read'` mode in `MaterializeSpecMetadata` (over-engineering). Plugins are trusted in-process code (same trust model as `plugins.agents`); say so explicitly in the spec.
- Spec should state that adding a service is compatible, removing one or changing a signature is breaking; services must be the same instances the kernel uses (no second composition); a service that throws becomes a `fail` result, not a crashed evaluation.

## Planned shape per package

- `core`: `registerCheck` accepts a definition or a factory `(services) => CustomCheckDefinition`; factories resolved in `createKernel`; `CheckServices` type (+ spec `core:check-services`); `plugins.checks[]` in config schema/loader/writer/cascade (entries `{ name, config }`); `core:check-registry` references services.
- `plugin-manager`: add `'check'` to `PLUGIN_TYPES`, manifest enum and `validateRuntimePlugin`; new spec `plugin-manager:check-plugin-type` (`CheckPlugin`, guard `isCheckPlugin`); new spec `plugin-manager:load-check-plugins-use-case` (loads all configured check plugins, validates each plugin's config against `configSchema`, registers on the builder, owns the session/`destroyAll`, cleans up already-initialized plugins if a later `init` fails); `PluginContext` carries plugin config. `configSchema` is flat (string/boolean/number) — may be too poor for nested config; open question.
- `sdk`: depends on `@specd/plugin-manager`; `openSpecdHost`/`createSdkContext` create the builder, call plugin-manager registration, build, expose `dispose()` (from the base change).
- `cli`: `plugins install/list/show/uninstall/update` are agent-oriented today; decide whether check plugins appear there (install/uninstall hooks of check plugins).
- `docs`: AGENTS.md / package dependency graph update; docs pointer.

Example config shape discussed:

```yaml
plugins:
  checks:
    - name: '@acme/specd-check-security'
      config: { severity: high }
```

Two config levels: plugin-level config (`plugins.checks[].config`, validated against the plugin's `configSchema`) and per-binding config in schema.yaml (`checks[].config`, arrives as `ctx.config`, already supported). Config cascade already exists in `config-cascade.ts`.

## Rejected alternatives (with reasons)

- Check plugins loaded by the host with closures over use cases: second composition, duplicated wiring per host, no help for config-loaded plugins.
- `registerCheck` taking the whole `Kernel`: exposes mutating use cases and too much surface.
- SDK owning plugin lifecycle (list of plugins, destroy order, errors): reimplements what `plugin-manager` knows.
- Injected `CheckPluginLoader` port in the SDK: returns wiring to CLI/MCP.
- New `policy: 'read'` for metadata: over-engineered because plugins are trusted.
- `process.on('exit')` / `FinalizationRegistry` for plugin cleanup: see `host-lifecycle-dispose`.

## Open questions for /specd-design

- Final `CheckServices` catalog after a use-case-by-use-case review of writes and reentrancy; whether `getStatus` can ever be allowed (guard via `passMemo`).
- How a plugin declares its config schema (flat `configSchema` vs zod/JSON schema) and how errors surface.
- Whether the plugin registration is generic ("runtime plugins": checks first, hook runners/parsers later) or check-specific now.
- Whether `plugins.checks` entries need ordering, enable/disable flags, or per-plugin skippable overrides.
- Check plugin install/uninstall semantics and whether `cli plugins *` commands cover them.
- Where the `specd-plugin.json` manifest declares `pluginType: check` and `minCoreVersion` handling.
- Namespacing: custom check ids are `@plugin.id`; confirm how a plugin name maps to the `pluginName` namespace (`^[a-zA-Z0-9_-]+$`, scoped npm names contain `@` and `/`).
- Security note to write: plugins are imported from config as trusted in-process code.

## Added after review of host-lifecycle-dispose (2026-10-27)

- Registration point in the SDK is `createSdkContext` (`packages/sdk/src/composition/host-context.ts`), NOT `openSpecdHost`: `openSpecdHost` loads config and delegates to `createSdkContext`, and `with-provider.ts`, `graph-index-task.ts` and `helpers/sdk-host.ts` call `createSdkContext` directly. `createSdkContext` switches from `createKernel(config, options?.kernel)` to `createKernelBuilder(config, options?.kernel)` + plugin-manager registration + `builder.build()`. `createKernelBuilder` already supports base registration state (`core:kernel-builder`, "Builder accepts base registration state"); verify that `KernelOptions` passed by `resolveCliContext` (`buildCliKernelOptions`) enters as that base state without duplicating registrations.
- Not every host path should load plugins: the worker `graph-index-task.ts` only indexes the graph and does not evaluate checks. Add an SDK option such as `options.plugins: false` (name open).
- `host-lifecycle-dispose` provides `KernelBuilder.registerDisposer(name, fn)` (named), `Kernel.dispose()` (idempotent, reverse order, `AggregateError`, fixed timeout), `SdkHostContext.dispose()` / `[Symbol.asyncDispose]`, and `engines.node: ">=22"`. This change only adds callers (plugin-manager registers ONE named disposer for its plugin session).
