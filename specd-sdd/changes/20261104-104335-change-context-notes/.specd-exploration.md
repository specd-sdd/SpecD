## Candidate design from prior agent — NOT all confirmed

Suggested shape (names and exact types still design choices):

```typescript
interface ChangeNote {
  id: string
  by: ActorIdentity
  text: string
  at: Date
  persist: 'until-transition' | 'sticky'
  code?: string
}
```

- `statusNotes`, `contextNotes`, `advisories`, or `notes` are candidates. User mentioned an existing notes concept elsewhere; previous agent checked only change.ts and get-status.ts and claimed no collision there. Investigate actual existing notes before selecting a name.
- Suggested transition operation: append `transitioned` with existing `by` and optional `reason`; remove expiring notes; add the reason as a fresh expiring note with actor and time. Perform these aggregate mutations and persistence atomically.
- Separate `addNote` for internal issues detected while already in the recovery state. Sticky notes require removal/resolution semantics; `resolveNote(id)` or `clearNotes(code)` were suggestions, not finalized API requirements.
- Suggested normalization: trim, single line, approximately 500 chars; blank reason could be treated as absent. Earlier discussion both said reject blank and treat as absent: resolve explicitly.
- Suggested deduplication evolved from consecutive `(actor, reason)` to existing `(actor, code, text)` matches, optionally refreshing timestamp. Suggested caps evolved from 10 reason entries to 20 notes, evicting old expiring entries first and preserving sticky notes. None of these limits or policies is confirmed.
- Optional `code` for stable machine-readable causes, e.g. artifact-drift, spec-overlap-conflict, stale-signoff, revoked-signoff. Reuse actual supported vocabulary after inspection; these are examples from discussion, not verified call-site inventory.
- CLI sticky flag was tentatively excluded from v1; API/internal use only was suggested. User has not finalized this boundary.
- Old manifests should default missing notes to []; old events permit absent reason. No backfill from historical events was suggested because user explicitly opposes extra event derivation. Do not cross-validate notes against last event as competing current-state truth.
- Atomic recovery persistence matters: when reconciliation recovery commits but the requested transition subsequently fails, its context must stay committed with recovery.
- Normal transitions without reason still expire relevant old notes; sticky notes survive. Same-state observations must not clear notes by accident.
- Consider repeated status calls: no unbounded duplicate drift notes. Define which findings deserve notes, when resolved findings disappear, and whether notes are append-only versus resolvable current context.
