# Exploration: report-overlap-dependency-changes

Generated: 2026-08-20

## Problem statement

When an archive is allowed despite spec overlap, `ArchiveChange` invalidates every other active change targeting the same specs. The invalidated change is returned to `designing`, its affected artifacts require review, and `change status` explains that the reason is `spec-overlap-conflict`.

The invalidation currently reports only the archived change name and overlapping spec IDs. It does not report whether the successful archive changed the canonical dependencies of those specs. This omission matters because the invalidated change may retain a `specDependsOn` snapshot captured before the archive. That snapshot has priority during context compilation and can hide newly published canonical dependencies until someone manually reconciles it.

## Desired outcome

Record and surface dependency deltas when an overlapping archive invalidates another active change. A user inspecting the invalidated change must be able to see not only that an overlap occurred, but also which direct dependencies were added or removed for each overlapping spec.

Illustrative human-readable output discussed during discovery:

```text
Invalidated because change 'new-change' was archived with overlapping specs: core:auth/oauth.
Dependency changes:
- core:auth/oauth: added core:identity/session; removed core:legacy/oauth-client
```

The exact presentation can be refined during design, but the underlying information should be structured data rather than text that consumers must parse.

## Current behavior observed

- `ArchiveChange` detects overlap after the archivable guard. Without `allowOverlap`, it throws `SpecOverlapError`. With `allowOverlap`, it invalidates each overlapping active change.
- The invalidation call uses cause `spec-overlap-conflict`, actor `system`, a message containing the archived change name and overlapping specs, and affected artifact/file entries.
- `Change.invalidate()` appends an `invalidated` history event, returns the change to `designing` when necessary, and reopens artifacts according to the invalidation policy. It does not alter `specDependsOn`.
- `specDependsOn` is explicitly advisory and is not subject to approval invalidation.
- `CompileContext` gives a change's declared `specDependsOn` higher priority than freshly materialized canonical metadata for dependency traversal. An old snapshot can therefore shadow new canonical dependencies.
- `LifecycleEngine` currently reconstructs overlap details by parsing the invalidation message with regular expressions. `GetStatus` projects this as `review.reason = 'spec-overlap-conflict'` and `review.overlapDetail`.
- CLI text status renders the overlap reason, archived change name, overlapping spec IDs, and affected files. Structured output includes `review.overlapDetail`.
- Dependency resolution for the change being archived is performed during archive preflight and persisted to canonical `spec-lock.json`; invalidated peer changes are not reconciled or refreshed.
- The current overlap invalidation occurs before full archive-plan preparation. Reliable dependency deltas are only available after comparing pre-archive canonical dependencies with the fully resolved publication plan.

## Approach / solution outline

1. During archive preflight, derive the final direct dependency set for every spec that will be published.
2. Compare that final set with the pre-archive canonical persisted dependency set.
3. For each overlapping change and overlapping spec, retain only meaningful dependency changes, separated into `added` and `removed` IDs.
4. Attach those changes as structured data to the `spec-overlap-conflict` invalidation event. Preserve the human-readable message for diagnostics, but do not make downstream behavior depend on parsing it.
5. Project the structured dependency changes through `LifecycleEngine` and `GetStatus` alongside existing overlap details.
6. Render them in `change status` text output and include them in JSON/TOON output.
7. Add domain, application, persistence, lifecycle, and CLI verification for overlap with unchanged dependencies, added dependencies, removed dependencies, and multiple overlapping specs/changes.

## Ordering and atomicity concern

The existing invalidation happens before archive preflight and permanent publication. To report real dependency differences, design must decide where invalidation belongs relative to preflight and commit.

Preferred direction from discovery: complete enough preflight to know the validated final dependency sets before invalidating peers. The design must also prevent a failed archive from leaving peer changes invalidated based on dependency changes that were never published. This needs to respect the existing full-batch preflight and rollback guarantees in `core:archive-change`.

## Decisions and agreements

- Dependency changes should be visible because they explain the semantic consequence of the overlap, not merely the fact that two changes touched the same spec.
- Store dependency changes structurally on the invalidation event; appending more free text alone is not sufficient.
- Report direct per-spec additions and removals. Transitive graph differences were not requested and should not be inferred into scope without a later decision.
- Preserve the existing `spec-overlap-conflict` reason and existing archived-change/spec detail.
- The user explicitly approved creation with the proposed five-spec scope.
- Creation emitted an overlap warning because `core:change` is also targeted by active change `implementation-snapshot` in `designing`. The user explicitly chose to keep `core:change` in this change and continue.

## Rejected or discouraged alternatives

- Only append dependency information to the existing free-form message. This is fragile because current lifecycle status already parses that message with regular expressions.
- Automatically overwrite the invalidated change's `specDependsOn` without an explicit design. The conversation established the visibility gap, but automatic reconciliation has broader semantics and was not approved as the solution.
- Remove `core:change` merely to avoid overlap with `implementation-snapshot`. The structured invalidation event belongs to the `Change` domain model, so omitting it would make the scope misleading.

## Open questions for design

- Should `core:change-manifest` be added to the formal change scope because the serialized `invalidated` event gains structured dependency-change fields? Current evidence suggests yes, but this was not added autonomously after the initial scope confirmation.
- Should dependency changes be optional fields on the generic `InvalidatedEvent`, or a discriminated payload available only for `cause: 'spec-overlap-conflict'`?
- What backward-compatible fallback should status use for old overlap events that only contain the parseable message?
- At exactly which archive boundary should peer invalidation occur so failed preflight/commit attempts never leave false dependency-change notifications?
- Should archive command success output also include dependency deltas, or only the invalidated change's later status? The user asked specifically about the invalidation message and status; archive success output was not agreed as required scope.
- Should the system only inform the user, or also offer/perform a deliberate refresh of stale `specDependsOn` snapshots? Automatic mutation was not agreed and should remain separate unless design establishes safe semantics.
