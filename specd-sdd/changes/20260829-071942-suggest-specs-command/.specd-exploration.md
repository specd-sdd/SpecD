## 1. Problem Statement & Motivation
- **Context**: In previous iterations, SpecD gained two crucial discovery use cases:
  1. `SuggestImplementationLinks` (correlating existing specs with AST source files and symbols).
  2. `SuggestSpecDependencies` (deducing canonical `dependsOn` relationships between specs from code imports).
- **The Gap**: In **brownfield projects** (projects without specs or partially specced projects like `../iccms`), developers and agents currently have no automated, deterministic way to discover candidate specifications, identify unspecced structural areas (*gap analysis*), and bootstrap a clean Spec-Driven Development architecture.
- **Goal**: Introduce a unified `specd specs suggest` command backed by a reusable `SuggestSpecs` use case in `@specd/sdk` that:
  1. Operates in pure **brownfield mode** (discovering candidate specifications across the whole codebase when `--ignore-current-specs` is passed or when no specs exist).
  2. Operates in **gap analysis mode** (by default, taking into account existing specs, checking their implementation links, enriching incomplete ones using shared AST correlation, identifying unspecced capability gaps, and deducing inter-spec dependencies with transitive reduction).

## 2. Key Architecture & Design Decisions

### A. Triad of Codebase Intelligence
The system unites three complementary use cases under `@specd/sdk`:
1. `SuggestImplementationLinks` (`sdk:suggest-implementation-links`): AST symbol / requirement correlation.
2. `SuggestSpecDependencies` (`sdk:suggest-spec-dependencies`): Graph-based inter-spec dependency inference with transitive reduction.
3. `SuggestSpecs` (`sdk:suggest-specs`): High-level capability clustering, brownfield discovery, and gap analysis diffing.

### B. Shared Core Components in `@specd/sdk`
To avoid code duplication (DRY) and guarantee mathematical consistency:
- **`TransitiveReductionEngine`**: Pure DAG optimization algorithm that prunes redundant transitive dependency edges ($A \rightarrow B \rightarrow C \implies$ prune $C$ from $A$).
- **`DependencyInferenceFromCallGraph`**: Translates file-level SQLite call/import graph edges into spec-level `dependsOn` edges using a dynamic `fileToSpecMap`.
- **`CapabilityClusteringEngine`**: Categorizes AST files into Clean Architecture / DDD structural layers:
  - `APPLICATION_USE_CASE`: `use-cases/`, `workflows/`, `interactors/`, `*-use-case.*`
  - `CORE_DOMAIN_ENTITY`: `entities/`, `models/`, `domain/`, `aggregates/`
  - `PORT_OR_CONTRACT`: `ports/`, `contracts/`, `repositories/`, `*-repository.*`, `*-port.*`
  - `INFRASTRUCTURE_SUBSYSTEM`: `infrastructure/`, `adapters/`, `storage/`, `database/`, `vcs/`
  - `PUBLIC_INTERFACE_API`: `commands/`, `controllers/`, `routes/`, `api/`, `index.*`, `public.*`
  - `DOMAIN_SERVICE`: `services/`, `*-service.*`, `*-detector.*`, `*-resolver.*`
- **`ConfidenceAndEvidenceScorer`**: Deterministic 5-factor scoring model ($0-100\%$):
  1. Caller & Hotspot Centrality ($0-25$ pts)
  2. Architectural Clarity & Invariants ($0-25$ pts)
  3. Graph Coupling & Cohesion ($0-20$ pts)
  4. Public Surface & Exports ($0-15$ pts)
  5. Test Alignment Evidence ($0-15$ pts)
- **`WorkspaceFileResolver`**: Reads authoritative workspaces dynamically via `host.kernel.project.listWorkspaces.execute()`, resolving file ownership by `codeRoot`.

### C. CLI Interface Contract (`specd specs suggest`)
- Command signature: `node packages/cli/dist/index.js specs suggest [options]`
- Options:
  - `--ignore-current-specs`: Ignore existing specs and perform 100% brownfield discovery.
  - `--workspace <name>`: Filter discovery/gap analysis to a single workspace.
  - `--min-confidence <0.0-1.0>`: Filter candidate suggestions by minimum confidence score.
  - `--limit <n>`: Limit number of displayed suggestions.
  - `--json` / `--format toon`: Structured machine-readable output for agent consumption.
  - `--cwd <path>` / `--project-root <path>`: Target external repositories (e.g. `../iccms`).

### D. Mandatory Invariant: 100% Repository Agnosticism & Zero Hardcoding
- **NO hardcoded workspace names**: Workspaces must never be assumed (`core`, `cli`, `sdk`, etc.). They must be queried dynamically from `host.kernel.project.listWorkspaces.execute()`, `host.config.workspaces`, or inferred from generic monorepo patterns / project root fallback.
- **NO hardcoded domain terms or symbol names**: No specific business words (e.g., `change`, `spec`, `article`, etc.) may be hardcoded. The use case relies exclusively on generic architectural layer patterns (`use-cases/`, `entities/`, `ports/`, `repositories/`, `services/`, `controllers/`, etc.), AST Tree-Sitter extractions, and SQLite caller graphs.
- **Polyglot & Multi-language Support via `AdapterRegistry`**: For language-specific specifics (supported file extensions, language identifiers, import/export semantics), leverage `@specd/code-graph`'s `AdapterRegistryPort` / `LanguageAdapter` (`ts`, `js`, `php`, `py`, `go`, etc.) to dynamically inspect supported languages without hardcoded file extension tables.
- **Works on Any Brownfield Project**: Must run seamlessly on external repos like `../iccms` or any other foreign codebase without configuration prerequisites.
