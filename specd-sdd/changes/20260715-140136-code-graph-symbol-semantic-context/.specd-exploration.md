# Problem Statement

The change explores how to support semantic purpose extraction and, later, semantic search for `@specd/code-graph` without bloating the persisted graph store with duplicated text artifacts.

The core problem identified is that the current graph model is good at identity, file placement, and some limited ownership (`method -> class`), but not yet rich enough to support hierarchical semantic extraction for arbitrary symbols.

The main target use case is generating a useful `purpose` for symbols, especially leaf symbols such as properties, variables, or parameters, by using structural context from their containing function/method and class.

# Approach / Solution Outline

The preferred approach is to prioritize deterministic structural context over storing derived text in the database.

Key direction discussed:

- Add minimal structural data to the graph so a symbol can be understood in context.
- Reuse `FileNode.content` to reconstruct declaration/body text at runtime rather than persisting duplicated signature/body text.
- Support hierarchical context assembly:
  - leaf symbol
  - containing function or method
  - containing class
  - file
- Use pregenerated `purpose` values for ancestors (class/method) to help generate the `purpose` for leaf symbols later.

The semantic extraction pipeline discussed is:

1. Build deterministic structural context from the graph and file content.
2. Reconstruct exact symbol text and owner text on demand.
3. Generate `purpose` hierarchically, with larger structural symbols first and leaf symbols later.

# Key Codebase Observations

## Current persisted symbol information

Current `SymbolNode` includes:

- `id`
- `name`
- `kind`
- `filePath`
- `line`
- `column`
- `parentId`
- `comment`

But it does not include:

- exact end range
- generic owner chain
- signature
- declaration text
- structural summary

## File content availability

`FileNode` already persists `content` and also contains an unused/deferred `embedding` field.

This strongly influenced the design direction:

- avoid storing signature/body/purpose text directly in the main graph tables when the source text can be reconstructed from `FileNode.content`

## Ownership today

The graph already persists enough to support:

- `method -> class/interface` ownership via `parentId`
- querying children by `parentSymbolId` through `findSymbols`

But this is limited:

- ownership is not general for arbitrary symbols
- there is no general persisted `ownerSymbolId` for variables/properties/nested functions/etc.
- there is no general persisted owner chain

## Deterministic context already available during parsing

During parsing/adapters, there is richer information than what is persisted:

- AST node ranges
- declaration boundaries
- class/method containment
- call facts
- binding facts
- parser-state-derived structural data

This means some context already exists transiently but is lost or only partially materialized in the graph.

## Adapter-specific structural extraction already exists partially

TypeScript adapter already extracts:

- methods
- comments
- imports
- binding facts
- call facts
- `extends` / `implements`
- a type declaration helper with `methodsByName`

This confirms there is already a base for structural extraction, but not yet a shared persisted model suitable for semantic context assembly.

# Design Decisions

## Preferred storage strategy

Do not bloat the database with duplicated text when it can be reconstructed from `FileNode.content`.

Preferred persisted additions are minimal structural fields, not semantic text fields.

## Preferred graph expansion

The graph should be expanded toward structural ownership and exact ranges, not immediately toward:

- stored signatures
- stored code blocks
- stored generated `purpose`
- stored semantic prompt text

## Proposed minimal persisted additions

The minimum useful expansion discussed was:

- `endLine`
- `endColumn`
- `ownerSymbolId`

This would allow:

- exact text reconstruction for a symbol
- lookup of immediate owner
- owner-chain reconstruction in runtime

## Hierarchical semantic generation

Agreed direction:

- class purpose can be generated from class declaration and structure
- method/function purpose can be generated from method block plus class summary
- leaf symbol purpose can be generated from the leaf plus containing method/function plus containing class summary

This hierarchical model was considered much better than trying to infer a leaf symbol purpose in isolation.

## DB size preference

Explicit preference from the user:

- avoid inflating the DB if equivalent information can be derived from existing `FileNode.content`

This is a strong design constraint.

# Agreements Reached

- The value for semantic work is mostly in structural context, not isolated symbol records.
- For code, embeddings over full source files are probably not a good first step.
- Full-file embeddings may make sense more for non-code documents and chunked document search.
- For code, symbols or structural units are the right level.
- To generate useful semantic context, it matters much more to know ownership and container hierarchy than just file/line position.
- `purpose` for a leaf symbol should likely use pregenerated purpose/context from its ancestors.
- The extractor itself must remain deterministic; interpretation belongs later.

# Steps / Plan Defined

The conversation implicitly converged on this staged plan:

1. Expand graph structure minimally.
2. Make ownership/range deterministic and reconstructable from graph + file content.
3. Build deterministic context extraction for symbols using owner hierarchy.
4. Generate ancestor purposes first.
5. Generate leaf symbol purposes using hierarchical context.
6. Use this as a basis for semantic retrieval/search later.

Potential future semantic search sequence discussed:

1. semantic retrieval
2. lexical retrieval
3. hybrid merge
4. graph expansion from seed symbols/specs

But the current change should focus first on structural foundations, not full semantic search delivery.

# Rejected Alternatives

## Add embeddings directly to every graph node now

Rejected as the immediate first move because it couples too much too early and does not solve the real context problem for leaf symbols.

## Store full code blocks/signatures/purpose text directly in the main graph tables

Rejected because:

- it duplicates content already available in `FileNode.content`
- it risks bloating the DB
- the user explicitly preferred avoiding that if reconstruction is possible

## Generate purposes from isolated symbols only

Rejected because leaf-symbol meaning depends heavily on owner and ancestor context.

## Treat full code files as the main semantic retrieval unit

Rejected as a likely poor first step for code because it is too coarse and loses precision compared to symbols and structural units.

# Why These Decisions Were Made

- Structural ownership is more reusable and less expensive than storing semantic text.
- `FileNode.content` already gives a source of truth for reconstructing code snippets.
- Leaf symbols derive meaning from their parents and ancestors more than from isolated declarations.
- Deterministic extraction should avoid semantic interpretation and instead focus on stable structural selection.
