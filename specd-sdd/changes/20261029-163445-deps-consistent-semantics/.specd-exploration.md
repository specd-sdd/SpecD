# Exploration: deps-consistent-semantics

Generated: 2026-10-29

Branch: `feat/lifecycle-transitions-ux` (nothing released; breaking changes acceptable). Origin: noticed while designing `check-plugins-runtime`, where `changes status` showed `DEPS_INCONSISTENT` right after registering dependencies at proposal time. Analysed with the user, who judged two aspects to be faults. Nothing here is implemented or decided beyond what is marked agreed.

## Verified facts (anchors; re-verify before trusting)

- Check `deps.consistent`: domain `packages/core/src/domain/checks/deps-consistent.ts` (`runDepsConsistent`, `arraysEqual`), application `application/checks/deps-consistent.ts`, facts from `application/services/ready-predicate-facts.ts` (`loadReadyPredicateFacts`, `extractDependsOnForSpec`, `loadExtractArtifacts`).
- Bindings (`domain/services/check-bindings.ts`): transition `* -> ready` (any), plus archive with the archive locks (`allowBindingOverride/allowConfigOverride/allowDisable: false`, `skippable: false`).
- `arraysEqual` compares by position. Observed: `core:kernel-builder` persisted `[kernel, composition, default:_global/architecture, composition-resolver, materialize-spec-metadata]` vs extracted `[kernel, composition, composition-resolver, materialize-spec-metadata, default:_global/architecture]`: same set, different order, reported as a mismatch.
- `extractDependsOnForSpec`: for each spec-scoped artifact, loads the change delta (merged over the live spec) and, when the change has no file for it, falls back to the LIVE spec artifact content (`specRepo.artifact`). If no artifact content at all, returns `undefined` and the spec is skipped. So before the `specs` artifact is written, "extracted" is the live spec's deps, which says nothing about what the change will leave.
- Persisted side is `change.specDependsOn`: dependency seeds from `CreateChange` plus `changes deps`. The proposal artifact's rulesPost tells the agent to register deps at proposal time ("do not defer this to the specs artifact"), so any proposal that adds a dependency produces `DEPS_INCONSISTENT` by construction until `specs` is validated.
- `core:get-status` scenario "Enter-ready deps check omits ready when extract mismatches": in `designing`, a mismatch fails the check and omits `ready` from `availableTransitions`; failed predicates of candidate hops MUST appear as `blockers` (so surfacing in `designing` is specified).
- `core:validate-artifacts` ("In-change dependsOn persistence"): validating a spec-scoped artifact calls `change.setSpecDependsOn(specId, extracted)`. So the mismatch self-heals once `specs` is validated, and the order difference too.
- Same blocker also visible in `implementation-snapshot` (designing), an unrelated change.
- Also while `specs` is missing, `INCOMPLETE_ARTIFACT` already blocks, so `DEPS_INCONSISTENT` adds noise.

## Agreed with the user

1. Order-sensitive comparison is a fault.
2. If spec-scoped artifacts are not created, the outcome should be something other than `DEPS_INCONSISTENT`.

## Proposed (not yet agreed)

- Compare as sets, only after verifying that `dependsOn` order carries no meaning (look at `CompileContext`, `core:change-deps`/`cli:change-deps` "highest-priority source for dependsOn resolution", `core:update-spec-deps`, `setSpecDependsOn`). If order is meaningful, normalize order when persisting instead.
- While the spec-scoped artifacts needed to extract a spec are not complete, `deps.consistent` is not evaluable for that spec: prefer `skip` (the gate is already held by `INCOMPLETE_ARTIFACT`) over a new failure code.
- Distinguish "artifact not yet written" from "spec intentionally without delta" (`op: no-op` or unmodified specs, for which live content is the final content).

## Specs likely involved

`core:transition-checks` (deps.consistent contract and scenarios), `core:get-status` (enter-ready scenario), `core:check-registry` (archive locks unchanged), possibly `core:validate-artifacts`, `core:change`.

## Open

- Does `dependsOn` order matter anywhere?
- `skip` vs a dedicated "not evaluable" outcome/code; how the archive row behaves (same logic, plus its sealed-deps variant `loadArchiveSealedDependsOnBySpecId`).
- Whether the proposal rulesPost instruction (register deps at proposal time) should change, or stays as is once the check no longer fires spuriously.
- Whether `INCOMPLETE_ARTIFACT` plus `DEPS_INCONSISTENT` duplication is solved by this or needs a status-level grouping decision.
