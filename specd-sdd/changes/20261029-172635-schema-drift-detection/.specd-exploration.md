# Exploration: schema-drift-detection

Generated: 2026-10-29

Branch: `feat/lifecycle-transitions-ux` (nothing released; breaking changes acceptable). Origin: questions raised while designing `check-plugins-runtime` about how project schema layers interact with sovereign change schemas. An earlier change `schema-layers-scope` was created and discarded; its exploration contained a wrong claim (see "Corrected"). Nothing here is decided beyond what is marked agreed.

## Problem

A change records only `schema: { name, version }`. The merged schema (base + `extends` chain + `schemaPlugins` + `schemaOverrides`, with templates) is recomputed in memory from the CURRENT config on every resolution and never persisted. So changing the schema or its layers in the middle of a change is neither recorded nor detected.

## Verified facts (re-verify before trusting)

- `manifest.json` of a change has keys `manifestVersion, name, createdAt, updatedAt, description, schema, specIds, specDependsOn, invalidation, artifacts, history`; `schema` is `{ name, version }` only (`packages/core/src/infrastructure/fs/manifest.ts`, schema fields `schemaName`/`schemaVersion`).
- `CreateChange` takes the name and version from `GetActiveSchema` (or an explicit pair) and persists only those.
- `ResolveChangeSchema` (`core:resolve-change-schema`) calls `SchemaProvider.get(schemaName)`, never the workspace default first; a same-name version difference is a non-blocking advisory. A name that does not resolve and does not match the default's name throws `SchemaNotFoundError` (no silent switch to the new default).
- `LazySchemaProvider.get(ref)` (`composition/lazy-schema-provider.ts`) -> `_resolveNamed(ref)` -> `ResolveSchema.execute(ref)`; on `SchemaNotFoundError` it falls back to the default only when the default carries that name.
- `ResolveSchema` is built from config (`createResolveSchemaForConfig` in `composition/schema-resolution.ts`) with `config.schemaPlugins` and `config.schemaOverrides` as constructor state; `execute(targetRef)` (`application/use-cases/resolve-schema.ts`) applies them to ANY reference: base -> extends cascade -> plugin layers -> override layer -> merge (`mergeSchemaLayers`) -> `buildSchema`. The merged ref is named `"<ref> (resolved)"` only in memory.
- Therefore every change-bound operation gets the project's current layers, whatever schema the change records. The raw/ref/file mode of `GetActiveSchema` (used by `schema show`/`schema validate`) builds without `ResolveSchema` and skips layers; no change operation uses it.
- Existing `computeSchemaFingerprintFromSchema` (`application/use-cases/_shared/validate-specs-cache-fingerprints.ts`) is PARTIAL: name, version, spec-scoped artifact validations, spec-scoped cross rules and whether dependsOn extraction is declared. Built for the `ValidateSpecs` cache. Not a whole-schema fingerprint.
- Validity fingerprints of a change (`ValidityFingerprintService`) cover artifact hashes and implementation files, not the schema.
- `schema-std` is about 64 KB (`schema.yaml` 40 KB plus `templates/`). 213 archived changes at that size would be about 14 MB if copied per change.
- Invalidation policy already exists per change: `invalidation: { artifacts: none|surgical|downstream|global, workflow: preserve|redesign }`, used for artifact drift.

## Consequences (observed)

1. Edits to `schemaPlugins`/`schemaOverrides`, or to a parent schema in `extends`, change the semantics of in-flight changes with no signal. The only comparison is the leaf schema's declared version.
2. If the config points to a different schema while a change keeps the old name: error `SchemaNotFoundError` when the name no longer resolves; if the new default keeps the same name, the change silently runs on the new schema with the current layers; removing a layer from the config removes it from every change.
3. The schema a change was archived with cannot be reproduced; only name and version remain.
4. Which layers existed at creation is not recorded.
5. Applying the same layers to a schema they were not written for may fail or misbehave when ops target hooks/artifacts/steps the schema lacks. Not verified whether `mergeSchemaLayers` fails or ignores a missing target.

## Corrected

The discarded `schema-layers-scope` exploration said layers apply only when the default schema is resolved and that a change with a different schema name gets none. That is wrong: they apply to any resolved reference (see above).

## Options (nothing chosen)

- **A. Detect only**: persist a fingerprint of the EFFECTIVE schema (after layers, templates included) as an input of change validity, like artifacts. A change triggers the existing `invalidation` policy (review or redesign). No storage. Cannot say what changed, and a change always runs on the current schema.
- **A+. Detect plus references**: A, plus record in the manifest the references of the merge (which `schemaPlugins` and overrides, with their versions), a few lines, so the diagnosis can say which layer varied.
- **B. Pin by content-addressed store**: store the resolved schema once per fingerprint (shared, deduplicated across changes, tracked in git for reproducibility), manifest records `{ name, version, fingerprint }`, the change evaluates the pinned snapshot, upgrading is explicit. Cost: store, garbage collection, snapshot format versioning.
- **C. Copy per change**: rejected by the user (excessive).

Leaning (not agreed): A or A+, B only if finishing a change on an old schema becomes a requirement.

## Open

- What the fingerprint covers and how templates are obtained from the `Schema` entity; determinism.
- Existing changes have no fingerprint: take it as baseline at first reconciliation.
- Does a schema change force `designing` or just mark review (depends on `workflow: preserve|redesign`)?
- Behaviour of `mergeSchemaLayers` with ops that target things the schema does not have.
- Whether a bare schema name (e.g. `schema-std`) resolves directly in the registry or only through the default fallback.
- Vocabulary: "plugin" currently means both `schemaPlugins` (workflow-schema layers) and the `specd-plugin.json` plugins; consider clarifying in specs (relation with `plugin-architecture`).
