# Exploration: check-plugins-example

Generated: 2026-10-27

Branch: `feat/lifecycle-transitions-ux` (nothing from this branch has been released; breaking changes are acceptable, per the user).

Sibling changes (same conversation): `host-lifecycle-dispose` (base: dispose, engines), `check-plugins-runtime` (check plugin loading, `CheckServices`). This change DEPENDS on both and should be designed and implemented last; it is the proof that the design is usable.

## Problem statement

User: "al final, lo suyo es la creación de una carpeta examples o similar, con algún 'host' con un check por plugin o similar que se vea cómo funciona". There is no `examples/` folder today. A runnable example validates the design of check plugins (config in `specd.yaml`, `CheckServices`, lifecycle) and doubles as documentation.

## Proposed structure (agreed in principle, details open)

```
examples/
  check-plugins/
    host/                        # small TS script: openSpecdHost + `await using`
    plugins/
      specd-check-todo-scan/     # simple CheckPlugin: only config + change, no services
      specd-check-spec-lint/     # CheckPlugin using CheckServices (getSpecMetadata/validateSpecs)
    project/                     # specd.yaml with plugins.checks[].config + minimal schema with archiveChecks
    README.md
```

What each piece demonstrates:

- `todo-scan`: configured from `specd.yaml`, made skippable and bypassed with `--skip-checks`.
- `spec-lint`: calls an internal use case through `CheckServices` — the case that motivated the whole effort.
- `host`: opens the host with `await using`, runs a transition or archive, shows a check failing and being skipped, and shows `destroy()` / dispose being executed (full lifecycle).
- `project`: `specd.yaml` with `plugins.checks[]` and schema `archiveChecks` bindings.

## Decisions and recommendations from the conversation

- Location: `examples/` at the repo root (documentation for users), not `dev/` (internal tooling: `dev/ai-agents`, `dev/scripts`, `dev/skills`). Recommendation, not yet confirmed explicitly by the user.
- pnpm workspace: add `examples/*` (or `examples/**`) to `pnpm-workspace.yaml` (currently `apps/*`, `packages/*`) so `workspace:*` resolves and turbo builds it; `private: true`. Reason: otherwise it rots silently.
- Automated test: start the example host and assert that the check fails and that `--skip-checks` bypasses it; the example must not rot. Part of this change, not an extra.
- Docs: a guide pointing to the example under `docs/` (candidate `docs/sdk/` or `docs/config/`); governed by `default:_global/docs`.
- Process issue: `examples/` is not a specd workspace (`specd.yaml` has 16: default, core, schema-std, cli, code-graph, sdk, skills, guide, plugin-manager, plugin-agent-{claude,copilot,codex,opencode,standard}, specd-metapackage, public-web). Recommended: add an `examples` workspace in `specd.yaml` with a short spec describing the example contract, rather than code with no spec ("no code without spec"). The change was created with no specs on purpose; workspace and spec are added during design.

## Dependencies on the other changes

- Needs from `host-lifecycle-dispose`: `dispose()`, `[Symbol.asyncDispose]`, `engines` value (decided direction: `>=22`, one common value; `await using` in the example).
- Needs from `check-plugins-runtime`: `CheckPlugin` contract (`checks(services, pluginConfig)`, `install`/`uninstall`, `destroy`), `plugins.checks[]` config, `CheckServices` catalog, SDK wiring through `plugin-manager`, manifest `specd-plugin.json` with `pluginType: check`.
- Because the plugins live inside the repo, the plugin loader resolution (project root first, then CLI runtime; `plugin-loader.ts`) must be able to resolve workspace packages from the example project: check this during design.

## Open questions for /specd-design

- Whether the example plugins are real workspace packages (`@specd/example-check-*`) or plain folders resolved by path; how the loader resolves them.
- Whether `examples/` joins `turbo.json` pipelines, lint, typecheck and CI (cross-platform CI: macOS, Linux, Windows per `default:_global/continuous-integration`).
- Shape of the host script and what its output should look like (it is also documentation).
- Whether to include a third illustrative case (a check that fails on purpose, a skippable one) or keep two plugins.
- Whether the example project ships its own `specd.yaml` and schema or reuses `@specd/schema-std` with `archiveChecks` overrides.
- Changeset/publish: example packages are private and excluded from publishing.

- The branch has `EXPLORATION_*.md` files at the repo root; those are unrelated exploration notes for other efforts.
