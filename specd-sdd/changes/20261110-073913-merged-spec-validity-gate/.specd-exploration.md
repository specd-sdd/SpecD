# Exploration: merged-spec-validity-gate

Generated: 2026-11-10

## Problem statement

Before entering `ready` (typically `designing → ready`), SpecD should verify that
**generated specs or merged deltas** produce **structurally valid specs** from which
**metadata can be extracted** — the same bar as `specd specs validate` /
`ValidateSpecs` (artifact rules + `GetSpecMetadata` materialization).

The same check must also run **before archive**, so invalid merged specs cannot be
published into the workspace.

## Approach / solution outline

Add a **transition/archive predicate check** (check-registry / transition-checks
binding model) that:

1. For each spec in the change scope, build the **effective merged content**
   (create artifacts or base + deltas — same idea as `preview-spec` / archive merge).
2. Run **ValidateSpecs-equivalent** validation on that effective content:
   - schema `scope:spec` artifact rules
   - metadata materialization via `GetSpecMetadata` path (or equivalent that proves
     metadata is extractable from the merged result)
3. Fail the transition/archive with actionable blockers (repair command pointing at
   validate / fix deltas) when any scoped spec fails.

Applicability agreed with user:

- Gate on path into **`ready`** (at least `* → ready`, along forward/design flow)
- Gate on **archive** operation (same check, not a fake transition)

Scope: **change-scoped specs only**, not whole-project validation.

## Design decisions

- **New change**, not extending `change-context-notes` (user corrected after initial
  suggestion to continue that change).
- **Do not block on overlap** with `change-context-notes` on
  `core:transition-checks` / `core:archive-change` (user explicit).

  extractable — not merely artifact file presence.
- Applies to **both** ready entry **and** archive.
- Change-scoped only (merged/created specs in the change).

## Open questions for `/specd-design`

1. Check id naming: e.g. `specs.valid` / `specs.mergedValid` / `specs.metadataReady`?
2. Should the check be **skippable** via `--skip-checks`? (Default lean: no, unless
   parity with other structural gates suggests yes.)
3. Validate against **in-memory merged content** only, or also require that
   materialization could persist? (User said “extract metadata”; likely
   materialize-from-merged without requiring workspace write before ready.)
4. Interaction with existing `changes validate` (structural artifact complete): is
   this check redundant with completed `specs`/`verify` artifacts, or a stricter
   post-merge metadata gate beyond schema artifact validation?
5. Whether `core:check-registry` / `core:transition-change` / `core:get-status`
   need to be added to the change during design.
6. How to reconcile concurrent edits with `change-context-notes` on shared specs
   at archive time (user waived worry; still a design note).

## Key codebase observations

- Existing ready predicates: `deps.consistent`, `workspace.readOnly` (`* → ready`).
- `ValidateSpecs` already: per-spec artifact validate → `GetSpecMetadata.execute`;
  materialization impossible → failure; dependsOn extraction mismatch → failure.
- Archive is an **operation**, never a fake transition (`core:transition-checks`).
- Schema must not list check IDs; bindings are code-owned.
- Project health already showed a metadata materialization failure example:
  `core:config` dependsOn curated-overwrite conflict — proves metadata gate surfaces
  real failures today at project level; change gate should catch analogous merged
  failures earlier.
